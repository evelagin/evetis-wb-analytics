# EVETIS BI Consumption

## Цель

BI — consumption и decision layer, а не второй analytics engine.

Dashboard должен помогать принять решение на основе уже определённых и валидированных метрик. Не переносить в BI бизнес-логику, которая должна жить в SQL-модели, MART/view или другом authoritative upstream layer.

Metabase является текущим BI-инструментом проекта, но правила этого skill относятся к consumption layer в целом и не должны зависеть от конкретного продукта без необходимости.

## Перед изменением

1. Определи пользователя dashboard и решение, которое он должен принять.
2. Найди authoritative upstream source для каждой метрики.
3. Проверь grain, dimensions, период и freshness.
4. Проверь, существует ли метрика уже в MART/view.
5. Определи необходимые filters, drill-down и comparison periods.
6. Только после этого меняй BI-представление.

Если для dashboard требуется новая бизнес-метрика, сначала определить её upstream-контракт. Не создавать альтернативную формулу непосредственно в BI.

## Source contract

Для каждого KPI должно быть понятно:

- что измеряется;
- из какого объекта приходит значение;
- на каком grain оно рассчитано;
- какой период используется;
- полный ли период;
- какие dimensions допустимы;
- как трактуются NULL и отсутствие данных;
- какой contract/source-of-truth определяет показатель.

Не использовать удобную таблицу только потому, что она уже подключена к dashboard.

## Metric governance

Одна бизнес-метрика должна иметь одно определение в рамках соответствующего контракта.

Не дублируй формулы revenue, costs, advertising, contribution, profit, margin, orders, sales, returns или других критичных KPI в нескольких BI-объектах.

Если две визуализации показывают показатели с одинаковым названием, но разной семантикой, различие должно быть явным для пользователя.

Не скрывай partial period, неполные данные или ограничения источника визуальным оформлением.

## Dashboard design

Строй dashboard от решений к деталям:

1. ключевые KPI и состояние;
2. изменение относительно релевантного периода или baseline;
3. основные drivers;
4. разрез по SKU/marketplace/другим нужным dimensions;
5. drill-down к диагностике.

Не добавляй график только потому, что данные доступны.

Каждый элемент должен отвечать на конкретный вопрос пользователя.

Визуальное представление не должно искажать смысл данных: проверяй axes/scales, units, signs, baselines и другие presentation choices, если они способны изменить интерпретацию показателя.

## Filters

Фильтры должны соответствовать grain и контракту источника.

Проверяй:

- period/date semantics;
- marketplace;
- SKU/product identity;
- campaign/promotion identity;
- warehouse/geography, если применимо;
- совместимость фильтра со всеми затронутыми карточками.

Не создавай фильтр, который визуально применяется к dashboard, но семантически неприменим к части показателей без явного обозначения.

## Time

Явно различай:

- complete и partial periods;
- event date и recognition/accounting date;
- snapshot date;
- rolling windows;
- calendar periods.

Не сравнивай неполный текущий период с полным предыдущим как эквивалентные периоды без явной нормализации или предупреждения.

## Performance

Сначала исправляй модель данных, grain или запрос upstream, если проблема производительности возникает из-за архитектуры данных.

Не компенсируй тяжёлый BI-запрос копированием бизнес-логики в dashboard.

Не создавай BI-layer join/blend с недоказанной cardinality или риском many-to-many row multiplication. Если такой JOIN нужен для бизнес-логики, предпочитай доказать и реализовать его upstream.

Для frequently-used consumption paths предпочитай стабильные подготовленные views/MART, если это соответствует архитектуре проекта.

## Metabase

При работе с текущим Metabase:

- сначала устанавливай источник и семантику метрики;
- сохраняй бизнес-логику upstream;
- используй BI для presentation, filtering и exploration;
- проверяй, что dashboard не создаёт вторую версию финансовой или marketplace-логики;
- не считать существующую карточку authoritative только потому, что она уже опубликована.

Изменение shared dashboard или другого общего BI-объекта является внешним изменением и должно быть явной частью задачи.

## Validation

Перед завершением изменения проверь:

- соответствие KPI upstream-контракту;
- отсутствие дублирующей бизнес-логики;
- корректность filters;
- корректность периода;
- поведение NULL/empty;
- consistency между summary и drill-down;
- отсутствие необъяснимого расхождения с authoritative source.

Если изменение затрагивает код или data objects проекта, используй существующую систему Definition of Done и определяемые проектом quality gates. Не заменяй их визуальной проверкой dashboard.

## Запрещено

- рассчитывать критичную бизнес-логику только внутри BI;
- использовать dashboard как источник истины вместо upstream contract;
- копировать формулу в несколько карточек вместо общей модели;
- скрывать partial/incomplete data;
- смешивать разные grain без явной агрегации;
- добавлять KPI без определённой семантики;
- считать визуальное совпадение доказательством корректности данных;
- зашивать в skill текущие dashboard IDs, контрольные значения или другую быстро меняющуюся конфигурацию.
