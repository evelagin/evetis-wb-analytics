# sql/current — канонический слой текущего SQL

**Назначение.** `sql/current/**` — авторитетное Git-определение того, какими объекты BigQuery
являются **сейчас**. Один файл = один объект production. Это не миграция, не откат и не
история развёртываний; временные проверки сюда не кладутся.

**Исторические миграции** (`sql/ozon/stage*`, `sql/*/pr_*` и т. п.) остаются доказательством того,
как система пришла к текущему состоянию. Их не удаляют и не переписывают, но текущее определение
объекта из них больше не выводят: если историческая миграция и канонический файл расходятся,
текущим считается канонический файл.

## Правила

1. **Один объект — один файл:** `sql/current/<dataset>/<OBJECT>.sql`. Имя файла = имя объекта в
   `CREATE` = `object_name` в манифесте.
2. **В файле ровно один оператор:** `CREATE OR REPLACE VIEW` с текущими `OPTIONS(description)`.
   Перед ним допустим комментарий-заголовок (происхождение, пояснения). Никаких `DROP`, `DELETE`,
   `TRUNCATE`, `UPDATE`, `INSERT`, `MERGE`, `ALTER`, `CREATE OR REPLACE TABLE`, `ASSERT`, логики
   развёртывания.
3. **Тело не переформатируется.** Для объектов, снятых с production, тело после `AS` — дословно
   `INFORMATION_SCHEMA.VIEWS.view_definition`. Исторические комментарии переносятся в заголовок,
   а не в тело.
4. **`MANIFEST.json`** на датасет перечисляет каждый объект: тип, путь, внутренние зависимости
   (`dependencies`), внешние (`external_dependencies`: `ozon_raw.*`, `evetis_ref.*`), уровень в
   графе, состояние синхронизации, хеши и схемы. Каждому файлу соответствует ровно одна запись и
   наоборот. Контракт — версия 2, см. ниже.
5. **Порядок пересборки** — только по графу зависимостей из самих канонических тел: уровень 0 —
   объекты без внутренних зависимостей, уровень N — после всех своих зависимостей. Номера стадий
   (4c / 4d2 / 4d3) порядок не задают. Граф обязан быть ацикличным.

## canonical_hash_v1

- **Тело (VIEW):** текст после верхнеуровневого `AS` оператора `CREATE OR REPLACE VIEW` (комментарии,
  строки и скобки учитываются при поиске `AS`, заголовок в тело не входит) → обрезать пробельные
  символы по краям → убрать ровно одну завершающую `;`, если она есть → SHA-256 от байт UTF-8.
  Внутренние пробелы, комментарии, регистр, кавычки и квалификация имён **не нормализуются**.
  Живое тело хешируется так же: `view_definition` → те же шаги.
- **Схема:** упорядоченный список колонок как JSON-массив объектов с ключами
  `column_name`, `data_type`, `is_nullable`, `ordinal_position` (типы в стандартной нотации
  BigQuery: `INT64`, `FLOAT64`, `BOOL`, …; `is_nullable` = `YES`/`NO`), сериализация
  `json.dumps(cols, ensure_ascii=False, sort_keys=True, separators=(',', ':'))` → SHA-256 UTF-8.
- **Описание:** SHA-256 от точного текста описания (без внешних кавычек) в UTF-8.
- Все хеши — полные 64 символа.

`live_body_sha256_at_capture` и `canonical_body_sha256` — разные величины: первое снято с production,
второе пересчитывается из файла. Их равенство проверяется, а не предполагается. Совпадение тела
после настоящего развёртывания (round trip BigQuery) этим не доказано — только dry-run.

Алгоритм `canonical_hash_v1` не «улучшается»: любое изменение нормализации — это новый
версионированный контракт (`canonical_hash_v2`), а не правка v1.

## Манифест v2

Верхний уровень: `manifest_version` (= 2), `dataset`, `project`, `hash_contract`,
`allowed_external_datasets`, `rebuild_order`, `objects`. Неизвестные и отсутствующие поля,
повторяющиеся ключи JSON и неполные хеши — ошибка.

- **`allowed_external_datasets`** — внешние датасеты, которые объекты этого датасета читают. Это
  **подмножество** жёсткой политики валидатора (`EXTERNAL_DATASET_POLICY` в
  `tools/validate_current_sql.py`; для `ozon_mart` — только `ozon_raw` и `evetis_ref`). Манифест
  не может разрешить себе больше: ссылка на `wb_*` или любой другой датасет вне политики падает,
  даже если её вписать в манифест. Расширить политику можно только отдельным ревью валидатора.

Поля объекта:

| Группа | Поля | Смысл |
|---|---|---|
| Идентичность | `dataset`, `object_name`, `object_type` (`VIEW`), `canonical_path` | путь ровно `sql/current/<dataset>/<object_name>.sql` |
| Граф | `dependencies`, `external_dependencies`, `dependency_level` | ровно те ссылки, что есть в SQL |
| Состояние | `sync_state` | `captured_live` или `pending_deploy` |
| Снимок production (история) | `capture_main_sha`, `captured_at`, `live_body_sha256_at_capture`, `live_schema_sha256_at_capture`, `live_description_sha256_at_capture`, `live_schema_at_capture` | что было в production при последнем read-only снятии |
| Канон Git | `canonical_body_sha256`, `canonical_description_sha256`, `canonical_schema`, `canonical_schema_sha256`, `canonical_column_count`, `canonical_schema_verification` | что утверждает текущий файл |
| Происхождение | `provenance` | источник, историческая миграция, паритет preflight |

### sync_state

- **`captured_live`** — канонический файл сверен read-only с production. CI требует: тело, схема и
  описание канона по хешам равны снимку production (`canonical_* == live_*_at_capture`),
  `canonical_schema == live_schema_at_capture`, `canonical_schema_verification = bigquery_verified`.
  Все 11 объектов `ozon_mart` — в этом состоянии (R2A доказал точный паритет).
- **`pending_deploy`** — Git-first изменение, намеренно опережающее production. Канонические тело,
  схема и описание могут отличаться от снимка. Поля `live_*_at_capture` — историческое
  доказательство последнего снятия: их **нельзя** переписывать, делая вид, что production уже
  совпадает. `canonical_schema_verification = unverified`.

**Схема не бывает «неизвестной».** `canonical_schema` обязателен в обоих состояниях: автор PR
явно пишет ожидаемую выходную схему (имя, тип в стандартной нотации BigQuery, `YES`/`NO`,
порядок). CI проверяет её целостность и хеш, а если внешний `SELECT` без `*` — ещё и совпадение
имён и порядка колонок с SQL. Типы офлайн не выводятся, поэтому такая схема помечается
`unverified`: это заявление автора, а не факт BigQuery.

**Как `unverified` становится `bigquery_verified`.** Только так: изменение развёрнуто в production
→ read-only снятие `INFORMATION_SCHEMA` (тело, `COLUMNS`, описание) → отдельным PR поля
`live_*_at_capture`, `capture_main_sha`, `captured_at` заменяются новым снимком, `sync_state` →
`captured_live`, `canonical_schema_verification` → `bigquery_verified`. CI пропустит такой PR,
только если новый снимок совпал с каноном по всем трём хешам. Инструмент снятия и сверки — R2C.

Новый объект, которого в production ещё нет: `pending_deploy`, все поля снимка = `null`
(все сразу, частично — ошибка).

Что CI **не может** доказать офлайн: что `live_*_at_capture` действительно сняты с production и
не переписаны. Ловится только очевидный случай — `pending_deploy`, у которого снимок равен канону
по всем трём хешам (нечего развёртывать). Подмена снимка в остальных случаях видна только на ревью
диффа и сверкой с production (R2C).

## Исторические определения (C17)

`historical_definitions.json` — список файлов **вне** `sql/current/`, которые делают
`CREATE [OR REPLACE] VIEW|TABLE` канонического объекта, с точным числом определений на объект.
Сейчас это три исторические миграции Ozon (4c, 4d2, 4d3 — 14 определений). CI сканирует токенами
все `.sql` вне `sql/current/`: новый файл или лишний `CREATE` канонического объекта — ошибка, пока
не проверен и не внесён в список. Комментарии и строки не считаются. Это не проверка корректности
исторического SQL: он не обязан совпадать с каноном и даже разбираться парсером. Не видит SQL,
собранный в коде `.py`/`.gs`/`.ts`.

## CI (R2B)

`.github/workflows/sql-current.yml`, проверка `sql-current`: на каждый PR и после слияния в `main`.
Без облачных креденшелов и секретов, `contents: read`. Шаги: тесты валидатора, затем
`python tools/validate_current_sql.py` по репозиторию. Локально:

```bash
pip install --only-binary=:all: --require-hashes -r tools/requirements-sql-ci.txt
python -m pytest -q tools/tests && python tools/validate_current_sql.py
```

Проверки C1–C18: раскладка каталогов, строгий JSON, 1:1 файл ↔ запись, безопасный путь,
идентичность имени, один оператор, только `CREATE OR REPLACE VIEW`, нет DDL/DML/`CALL`/
`EXECUTE IMMEDIATE`/`ASSERT`/нераспознанного SQL (`Command`), хеши тела/схемы/описания, точные
зависимости, полная квалификация ссылок, изоляция маркетплейсов, ацикличный граф, уровни и
`rebuild_order`, нет дублей, исторические определения, `sync_state`.

**Что R2B доказывает:** целостность канонического контракта в Git, структурную безопасность SQL,
манифест, граф, изоляцию маркетплейсов, хеши на стороне Git. **Что не доказывает:** текущий
паритет с production, хранение тела BigQuery после развёртывания, живую выходную схему,
потребителей в Metabase, живые метаданные — это R2C.

Без платного тарифа GitHub проверку нельзя сделать обязательной: сейчас она рекомендательная, а
запуск на `push` в `main` ловит нарушение уже после слияния.

## Изменения

- **Git-first (штатно):** сначала меняется канонический файл и манифест (PR, проверки), затем
  изменение применяется в production, затем снимаются и сверяются хеши.
- **После одобренного изменения, сделанного в production:** снять определение read-only, заменить
  тело дословно, пересчитать хеши и манифест, отдельным PR.
- **Сверка с production (drift) — только чтение.** Детектор никогда не исправляет production сам;
  расхождение разбирает владелец.

## Сверка с production (R2C, фаза 1)

`tools/verify_current_sql_live.py` — ручная сверка **только чтением**: каждый объект из манифестов
`sql/current/**` против того, что сейчас хранит BigQuery. Ничего не создаёт, не меняет и не удаляет в
BigQuery, не правит манифест, не выравнивает production — только отчёт.

**Что читает.** Только метаданные: REST `tables.list` и `tables.get` для датасетов с манифестом.
Никаких query jobs, `INFORMATION_SCHEMA`, dry-run и чтения данных таблиц. Разрешены только HTTPS GET на
`www.googleapis.com` (или `bigquery.googleapis.com`) и только по путям управляемых объектов; любой
другой метод, хост или путь — отказ до отправки запроса. Проект задаётся явно (`--project`) и обязан
совпасть с манифестом; сначала проходит проверка контракта R2B, иначе ошибка без сетевых запросов.

**Доступ.** Токен задаётся явно: переменная окружения `BQ_VERIFY_ACCESS_TOKEN` (имя меняется
`--token-env`) или команда оператора `--token-command "gcloud auth print-access-token"` (выполняется без
shell). Сам инструмент никакой команды за токеном не запускает. Токен не попадает ни в отчёт, ни в
сообщения об ошибках. Достаточно роли `roles/bigquery.metadataViewer` на датасете (на ограниченной
учётной записи ещё не проверено).

```bash
python tools/verify_current_sql_live.py --project project-fa311fc0-4d87-4781-986 \
  --token-command "gcloud auth print-access-token" --output /path/outside/git/report.json
```

**Сравнение.** Тело — `canonical_hash_v1` из кода R2B (`validate_current_sql.view_body`, второй
реализации нет); BigQuery при хранении обрезает края и одну `;`, хеш к этому нечувствителен. Схема
из API приводится к записи манифеста: `INTEGER→INT64`, `FLOAT→FLOAT64`, `BOOLEAN→BOOL`, `STRING`,
`NUMERIC`, `DATE`, `TIMESTAMP` без изменений, `REQUIRED→NO`, иначе `YES`. Любая другая форма
(`RECORD`/`STRUCT`, `REPEATED`, параметры типа, прочие типы) — `METADATA_UNPROVEN`, без догадок.
Описание — сырой текст из `tables.get`. Каждый объект перечитывается в конце: если изменились `etag`
или `lastModifiedTime`, объект `METADATA_UNPROVEN`, не `MATCH`.

**Статусы объекта** (по убыванию тяжести): `MISSING_LIVE`, `OBJECT_TYPE_DRIFT` (не VIEW или legacy
SQL), `BODY_DRIFT`, `SCHEMA_DRIFT`, `DESCRIPTION_DRIFT`, `METADATA_UNPROVEN`,
`PENDING_DEPLOYED_MATCH`, `PENDING_NOT_DEPLOYED`, `MATCH`. Все найденные расхождения — в
`drift_kinds`. На уровне датасета — `UNEXPECTED_LIVE`: живой объект без записи в манифесте (таблица,
вью — любой); его никто не удаляет.

Для `pending_deploy`: production равен прежнему снимку — `PENDING_NOT_DEPLOYED`; равен новому канону по
телу, схеме и описанию — `PENDING_DEPLOYED_MATCH`; ни то ни другое — обычный drift, решение за владельцем.

**Итог и код выхода:** `MATCH` (0) — всё совпало; `PENDING` (0) — нет drift и сомнений, но есть
pending-объекты; `DRIFT` (1); `UNPROVEN` (2) — drift не найден, но хоть один факт не доказан;
`ERROR` (3) — сравнение не состоялось (контракт, доступ, конфигурация). `UNPROVEN` никогда не
превращается в `MATCH`.

**Отчёт** — JSON: хеши, статусы, различия схемы на уровне колонок (имя, тип, nullable). Без текста
SQL, описаний, токенов, учётных записей и тел ответов API (ошибки — только код).

**`canonical_git_sha` — это чистый коммит Git, чей `sql/current/**` сравнивался с production во время
этой сверки. Это НЕ доказательство того, какой коммит был развёрнут.** Провенанс подтверждён, только
если рабочее дерево чистое и коммит достижим из `origin/main` (сверка сама не делает `fetch`).

**Перевод `pending_deploy` → `captured_live`.** Для объекта в `PENDING_DEPLOYED_MATCH` при
подтверждённом провенансе отчёт содержит `proposed_capture`: только наблюдённые значения и метаданные
снятия (`capture_main_sha` = `canonical_git_sha`, `captured_at` = начало сверки). Манифест инструмент не
меняет: отчёт → ревью владельца → отдельный PR → проверка R2B.

**Не входит в фазу 1:** dry-run (фактическая выходная схема, транзитивные базовые таблицы — только
явный ручной режим, фаза 2), расписание и оповещения, отдельная сервисная учётная запись, архив
доказательств, WB-датасеты. Сохранение комментариев внутри тела при хранении в BigQuery не доказано.
