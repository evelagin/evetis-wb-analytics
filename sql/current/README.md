# sql/current — канонический слой текущего SQL

**Назначение.** `sql/current/**` — авторитетное Git-определение того, какими объекты BigQuery
являются **сейчас**. Один файл = один объект production. Это не миграция, не откат и не
история развёртываний; временные проверки сюда не кладутся.

**Исторические миграции** (`sql/ozon/stage*`, `sql/*/pr_*` и т. п.) остаются доказательством того,
как система пришла к текущему состоянию. Их не удаляют и не переписывают, но текущее определение
объекта из них больше не выводят: если историческая миграция и канонический файл расходятся,
текущим считается канонический файл.

## Правила

1. **Один объект — один файл:** `sql/current/<dataset>/<OBJECT>.sql`. Имя файла = имя объекта в
   `CREATE` = `object_name` в манифесте.
2. **В файле ровно один оператор:** `CREATE OR REPLACE VIEW` с текущими `OPTIONS(description)`.
   Перед ним допустим комментарий-заголовок (происхождение, пояснения). Никаких `DROP`, `DELETE`,
   `TRUNCATE`, `UPDATE`, `INSERT`, `MERGE`, `ALTER`, `CREATE OR REPLACE TABLE`, `ASSERT`, логики
   развёртывания.
3. **Тело не переформатируется.** Для объектов, снятых с production, тело после `AS` — дословно
   `INFORMATION_SCHEMA.VIEWS.view_definition`. Исторические комментарии переносятся в заголовок,
   а не в тело.
4. **`MANIFEST.json`** на датасет перечисляет каждый объект: тип, путь, внутренние зависимости
   (`dependencies`), внешние (`external_dependencies`: `ozon_raw.*`, `evetis_ref.*`), уровень в
   графе, хеши и схему на момент снятия. Каждому файлу соответствует ровно одна запись и наоборот.
5. **Порядок пересборки** — только по графу зависимостей из самих канонических тел: уровень 0 —
   объекты без внутренних зависимостей, уровень N — после всех своих зависимостей. Номера стадий
   (4c / 4d2 / 4d3) порядок не задают. Граф обязан быть ацикличным.

## canonical_hash_v1

- **Тело (VIEW):** текст после верхнеуровневого `AS` оператора `CREATE OR REPLACE VIEW` (комментарии,
  строки и скобки учитываются при поиске `AS`, заголовок в тело не входит) → обрезать пробельные
  символы по краям → убрать ровно одну завершающую `;`, если она есть → SHA-256 от байт UTF-8.
  Внутренние пробелы, комментарии, регистр, кавычки и квалификация имён **не нормализуются**.
  Живое тело хешируется так же: `view_definition` → те же шаги.
- **Схема:** упорядоченный список колонок как JSON-массив объектов с ключами
  `column_name`, `data_type`, `is_nullable`, `ordinal_position` (типы в стандартной нотации
  BigQuery: `INT64`, `FLOAT64`, `BOOL`, …; `is_nullable` = `YES`/`NO`), сериализация
  `json.dumps(cols, ensure_ascii=False, sort_keys=True, separators=(',', ':'))` → SHA-256 UTF-8.
- **Описание:** SHA-256 от точного текста описания (без внешних кавычек) в UTF-8.
- Все хеши — полные 64 символа.

`live_body_sha256_at_capture` и `canonical_body_sha256` — разные величины: первое снято с production,
второе пересчитывается из файла. Их равенство проверяется, а не предполагается. Совпадение тела
после настоящего развёртывания (round trip BigQuery) этим не доказано — только dry-run.

## Изменения

- **Git-first (штатно):** сначала меняется канонический файл и манифест (PR, проверки), затем
  изменение применяется в production, затем снимаются и сверяются хеши.
- **После одобренного изменения, сделанного в production:** снять определение read-only, заменить
  тело дословно, пересчитать хеши и манифест, отдельным PR.
- **Сверка с production (drift) — только чтение.** Детектор никогда не исправляет production сам;
  расхождение разбирает владелец.
