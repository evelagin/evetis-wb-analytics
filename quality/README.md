# quality — ворота качества данных

Набор проверок — это исполнимая форма уже согласованного бизнес-правила. Здесь не пишут новые
пороги: сюда переносят те, что владелец утвердил при приёмке этапа, вместе со ссылкой на
документ приёмки.

## Как устроено

- `suites.json` — реестр: какие наборы есть, что они покрывают, какие из них ворота (`gate`),
  и список файлов, ещё не переведённых на исполнимый контракт (`backlog`).
- Сами проверки живут рядом с SQL этапа (`sql/**/*_validation.sql`) — их не переносят в этот
  каталог, чтобы проверка оставалась рядом с определением объекта.
- Исполнитель — `tools/run_data_checks.py`, только чтение.

## Контракт файла проверок

```sql
-- @check V01_SOME_INVARIANT
-- Комментарий: что именно доказывается и откуда взят порог.
SELECT <измеримые величины>,
       IF(<условие>, 'PASS', 'FAIL') AS status
FROM `project….dataset.OBJECT`;
```

Правила:

1. блок начинается строкой `-- @check <ID>` (A–Z, 0–9, подчёркивание), ID уникален в наборе;
2. в блоке **ровно один** оператор, завершённый `;`;
3. оператор — `SELECT` или `WITH`; всё остальное отклоняется до отправки в BigQuery;
4. в результате обязана быть колонка `status` со значением `PASS` или `FAIL` в каждой строке;
   любое другое значение — ошибка, а не «предупреждение»;
5. **пустой результат — не успех.** Он означает `EMPTY`: проверка ничего не доказала. Если
   пустота и есть ожидаемый успех, блок помечается строкой `-- @expect empty_ok`.

Проверка может возвращать много строк (например, по месяцам): набор красный, если не PASS
хотя бы одна.

## Запуск

```bash
# разобрать без обращения к BigQuery
python tools/run_data_checks.py --suite ozon_unit --list

# прогнать против production
python tools/run_data_checks.py --suite ozon_unit \
  --project project-fa311fc0-4d87-4781-986 \
  --token-command "gcloud auth print-access-token" \
  --output ~/checks/ozon_unit.json
```

Отчёт пишется по явному пути **вне Git**: он содержит значения бизнес-данных, а репозиторий
хранит решения и код (`docs/architecture/REPOSITORY_DATA_POLICY.md`).

## Добавить набор

1. Перевести файл проверок на контракт `-- @check`, не меняя ни одного порога.
2. Если в приёмочном документе порога нет — не придумывать: вынести как нерешённое
   бизнес-правило владельцу.
3. Добавить запись в `suites.json` (`scope`, `dimensions`, `provenance` со ссылкой на документ
   приёмки), убрать файл из `backlog`.
4. `pytest -q tools/tests` — тесты проверяют, что реестр не врёт: файлы существуют, разбираются
   и не числятся одновременно в воротах и в долге.
5. Прогнать набор против production и приложить вердикт.
