# Security audit events — contract `wbcomm.security.v1` (D-19b / F-18)

Why. `evetis-wb-communications` is publicly invocable (`allUsers` → `run.invoker`) because
Telegram must reach the webhook. Cloud Run IAM therefore cannot say who caused a write. These
events let the trusted audit (`tools/autonomy/ingress_attribution.py`, F-18 semantics) prove, per
request, that every external mutation happened only after the service's own authentication.

Producer: `app/utils/audit_events.py`. One JSON line on stdout per event (Cloud Logging
`run.googleapis.com/stdout`), independent of the `logging` level and handlers; a failed write never
changes the response (a missing event makes the audit fail closed).

## Correlation chain

```
run.googleapis.com/requests   trace = projects/P/traces/T   (written by Cloud Run; T may be client-chosen)
  request_start               trace_id = T (alt_trace_id = T'), correlation_id = C, seq = 1
  auth_ok | auth_denied       T, C, auth_mechanism, principal_class
  authz_ok | authz_denied     T, C  (Telegram allow-list, allowlist_configured)
  mutation_attempt            T, C, mutation_id = M, auth_event_id → the auth_ok, authz_event_id → the authz_ok
  mutation_success | mutation_failure   T, C, M, result
  request_done                T, C, status_code, result = ok|denied|none, mutation_attempts = n, seq = last
```

`seq` is a per-request counter: the order of events is proven by it, never by timestamps (Cloud
Logging stamps stdout lines at ingestion). "Preceded by" is proven causally: the attempt carries the
`event_id` of the `auth_ok` (and `authz_ok`) that the request recorded before it.

**Trace headers are client-controlled.** The Google front end accepts an incoming
`X-Cloud-Trace-Context`, so any internet client can choose `T`, repeat headers, or send a conflicting
`traceparent`. The service never guesses which one the platform logged: the first valid trace
(`X-Cloud-Trace-Context` before `traceparent`, in header order) is `trace_id`, a second different one is
`alt_trace_id`, more than two distinct → no trace (the request is then unattributable and the audit
fails closed). `C` is generated by the service per request (uuid4 hex).

## Fields (closed set)

| field | values |
|---|---|
| `security_schema` | `wbcomm.security.v1` |
| `event_type` | `request_start`, `request_done`, `auth_ok`, `auth_denied`, `authz_ok`, `authz_denied`, `mutation_attempt`, `mutation_success`, `mutation_failure` |
| `event_id`, `correlation_id`, `mutation_id` | 32 hex; `correlation_id` = `none` outside a request |
| `trace_id` / `alt_trace_id` / `span_id` | 32 hex / 32 hex / 16 hex, or null |
| `seq` | integer ≥ 1 per request; 0 outside a request |
| `ts` | RFC 3339 UTC, microseconds |
| `service`, `revision` | `K_SERVICE`, `K_REVISION` |
| `route` | one of `/poll`, `/telegram-webhook`, `/health`, `/admin/test-*`, else `other`; `none` outside a request |
| `method` | HTTP method or `other` |
| `auth_mechanism` → `principal_class` | `scheduler_secret` → `cloud_scheduler`; `telegram_webhook_secret` → `telegram_bot_api`; `admin_token` → `admin_operator`; `telegram_allowlist` → `telegram_user` |
| `result` | auth: `ok`/`denied`; mutation: `attempt`, `success`, `rejected`, `error`, `outcome_unknown`; request_done: `ok`/`denied`/`none` |
| `reason` | `missing`, `mismatch`, `not_configured` (auth_denied only) |
| `mutation_class` | `wb_feedback_answer`, `wb_question_answer`, `tg_send_message`, `tg_edit_message`, `tg_answer_callback`, `tg_set_webhook`, `tg_other` |
| `target_system` / `target_ref` | `wb` → `wb:<WB id>` (public object id; anything unusual is hashed); `telegram` → `tg_chat:configured` / `tg_chat:other` (the class only — chat ids are low-entropy, a hash would be reversible), `tg_callback:<sha256[:16]>`, `tg:bot` |
| `auth_event_id` / `authz_event_id` | `event_id` of the request's `auth_ok` / last `authz_ok` of a CONFIGURED allow-list (a later denial clears it), or null |
| `error_class` | exception class name, `HTTP<status>`, `NoStatus`, `TelegramNotOk`, `NonJsonResponse` |
| `status_code`, `mutation_attempts`, `duration_ms` | integers |
| `allowlist_configured` | true only if BOTH chat and user allow-lists are non-empty |

Never emitted: request/response headers, secrets or tokens, message or answer text, buyer data,
raw chat/user/callback ids. Every string value must match `^[A-Za-z0-9_.:/@+=-]{0,160}$`
after redaction; otherwise it is replaced by `<invalid>`, which the audit treats as a failure.

## Outcome classification (audit meaning; business behaviour unchanged)

| write | success | rejected | error (provably not sent) | outcome_unknown |
|---|---|---|---|---|
| WB feedback / question answer | response 2xx (for questions: without in-band `error: true`) | 4xx, in-band `error: true` | 429 after retries | 5xx, read timeout / transport after send, **a non-2xx status the business logic accepts (e.g. unfollowed 3xx)**, anything unexpected |
| Telegram Bot API | `ok: true` (a retried send may have been delivered twice) | `ok: false` | only if EVERY attempt failed with `ConnectError`/`ConnectTimeout` | any attempt that may have been sent (e.g. `ReadTimeout` then `ConnectError`), non-JSON response |

## What the audit derives (not the service)

For each platform request log of the service in the audit window: exactly one `request_start` (first
by `seq`) and one `request_done` (last) with one `correlation_id`; every `mutation_attempt` referencing an
earlier `auth_ok` whose mechanism matches the route; WB writes from `/telegram-webhook` also referencing an
earlier `authz_ok` with `allowlist_configured=true`; exactly one later known outcome per attempt;
`request_done.mutation_attempts` equal to the attempts seen; no security event in the window outside an
attributed request; a trace shared by several platform requests only if none of them mutated. Anything
else is BLOCKED, never PASS.
