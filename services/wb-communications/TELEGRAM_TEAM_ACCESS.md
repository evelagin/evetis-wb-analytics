# Доступ команды через Telegram (R2.4A)

Статус: код в `main` после слияния; **включается отдельным ACK владельца** (`TELEGRAM_DYNAMIC_ACCESS_ENABLED`,
по умолчанию `false`). Без флага всё работает как в R2.3: доступ только по спискам из окружения.

## Архитектура

Один источник прав — `app/services/team_access.py`:

    доступ = bootstrap-пользователи из окружения  ∪  ACTIVE-участники Firestore этого чата модерации

- **Bootstrap** — `TELEGRAM_ALLOWED_USER_IDS` ∪ `V31_OWNER_OVERRIDE_USER_IDS`. Всегда OWNER, работают без
  Firestore, командой не отзываются. Это аварийный (break-glass) доступ; списки не трогаем.
- **Участники команды** — Firestore, ключ `(chat_id, telegram_user_id)`, только для настроенного
  `TELEGRAM_CHAT_ID`. Доступ в другом чате не даёт ничего.
- Идентичность — только Telegram `from.id`. Имя, фамилия и `@username` — лишь подписи, права от них не зависят.
- Права перечитываются при каждом нажатии: отзыв действует со следующего callback, без перезапуска.

| Роль | Модерация (все кнопки, включая «Опубликовать как есть» и двухшаговое решение) | Управление командой |
|---|---|---|
| OWNER (bootstrap) | да | да |
| OPERATOR | да | нет |

Коллекции Firestore (тот же проект и база): `telegram_team_members`, `telegram_team_requests`,
`telegram_team_audit` (только добавление), `telegram_team_profiles` (подписи для `/team`).

## Как сотрудник получает доступ

1. Сотрудника добавляют в группу модерации EVETIS.
2. Он пишет `/apply` → бот: «✅ Запрос доступа отправлен владельцам EVETIS.» и карточка в группе:

       👤 Запрос доступа EVETIS
       Имя: Мария Иванова
       Telegram: @maria
       Telegram ID: 123456789
       Запрашивает доступ к модерации отзывов и вопросов.
       [✅ Добавить оператора]  [❌ Отклонить]

3. Владелец нажимает «✅ Добавить оператора» → одна транзакция: запрос APPROVED, участник ACTIVE OPERATOR,
   запись аудита. Бот: «✅ Мария: доступ активирован…». Кнопки нажимать может только OWNER; остальные
   получают отказ без изменений.

Повторный `/apply` не создаёт дубль («⏳ Запрос доступа уже ожидает подтверждения»); после отказа можно
подать снова (`attempt_count` растёт).

## Команды

| Команда | Кто | Что делает |
|---|---|---|
| `/apply` | любой участник группы | запрос доступа |
| `/me` | любой | мой статус: ACTIVE (роль, источник), PENDING или «доступа нет» |
| `/help` | любой | справка по роли |
| `/team` | OWNER | команда (по 8 на странице), карточка участника, отзыв доступа |
| `/requests` | OWNER | ожидающие запросы с кнопками ✅ / ❌ |

Отзыв: `/team` → участник → «🚫 Отозвать доступ» → «⚠️ Да, отозвать» → ACTIVE → REVOKED (`revoked_by`,
`revoked_at`, аудит). Bootstrap-владельца отозвать нельзя.

**Режим приватности бота не меняется.** Бот видит только команды, нажатия кнопок и ответы на свои сообщения
(правка ответа) — этого достаточно; менять настройки в BotFather не нужно.

## Аудит и идентичность модератора

- `telegram_team_audit`: `ACCESS_REQUESTED / APPROVED / REJECTED / REVOKED` — `event_id`, чат, кто, кому,
  статус до/после, роль, время. Повторное нажатие новых записей не создаёт.
- Каждое событие модерации (публикация, «как есть», двухшаговое решение, начало и завершение правки,
  «Другой вариант», безопасная альтернатива, пропуск) несёт `telegram_user_id` и `payload_json.actor`
  (`user_id`, роль, источник, действие); журнал публикации — `publish_trace.actor`. Вместе с
  `answer_versions` это даёт цепочку «черновик ИИ → действия людей → опубликованный ответ → кто» для R2.4B.

## Если Firestore недоступен

Bootstrap-пользователи продолжают работать как обычно. Все остальные получают отказ (fail closed); `/apply`
отвечает «Сервис доступа временно недоступен». Сбой никогда не открывает доступ.

## Включение и откат

Включение (аддитивно, без `--env-vars-file`): `TELEGRAM_DYNAMIC_ACCESS_ENABLED=true`. Текущих двух людей
переносить не нужно — они bootstrap. Откат: новая ревизия с `TELEGRAM_DYNAMIC_ACCESS_ENABLED=false` (или трафик
на предыдущую ревизию) — доступ снова только по спискам окружения; данные команды в Firestore сохраняются.
