# Проект RAW-слоя поставок WB

Дата: 17.08.2026
Статус: **проект на ревю.** Код не написан, DML не выполнялся.
Основание — `docs/wb_incomes_api_retirement.md`, разделы 9–13.

---

## 1. Задача

Получить таблицу «сколько каждого товара завезено на WB с сентября 2024 года» и
детальный слой под неё, из которого потом собирается материальный баланс.

Прямая формулировка владельца: историческим потоком «передано в поставку WB»
служит `supplies/{supplyID}/goods.quantity` на грейне поставка × SKU.
`acceptedQuantity` остаётся диагностическим полем и **в расчёт исторического
ввоза не входит** — обоснование в разделе 13 исходного документа.

### 3.2 `RAW_WB_SUPPLIES_GOODS` — состав поставки

Грейн: **поставка × позиция × снимок**. Позиция идентифицируется `barcode`.

⚠️ Уникальность `barcode` внутри одной поставки — **предположение, а не
проверенный факт**. После §5.2 позиции читаются JOIN'ом по `(entity_key,
run_id)` без выбора по `barcode`, поэтому дубль штрихкода внутри одного прогона
уже не «теряет» строку — он даёт **обе**, и `SUM(quantity)` удваивается по этой
позиции. Отказ сменился с тихой потери на тихое завышение, то есть остался
тихим. Страхует инвариант И10 (§6).

| Колонка | Тип | Источник |
|---|---|---|
| `snapshot_ts`, `run_id`, `entity_key`, `supply_id` | | как выше |
| `barcode` | STRING | `barcode` |
| `vendor_code` | STRING | `vendorCode` |
| `nm_id` | INT64 | `nmID` |
| `tech_size` | STRING | `techSize` |
| `color` | STRING | `color` |

| `need_kiz` | BOOL | `needKiz` |

| `ready_for_sale_quantity` | INT64 | `readyForSaleQuantity` |
| `unloading_quantity` | INT64 | `unloadingQuantity` |
| `accepted_quantity_zero` | BOOL | `accepted_quantity = 0 AND quantity > 0` |

| `raw_json`, `row_hash` | | как выше |

🔴 **Имя флага намеренно нейтральное.** Первая редакция называла его
`accepted_not_identified` — и это было бы распространением интерпретации двух
документально проверенных поставок на все сорок нулей. Документы WB доказывают
механизм «принято как неопознанное» для `36836448` и `37022425`; для нулей
2024 — августа 2025 причина не установлена и может быть иной, например
legacy-незаполненность поля. Флаг фиксирует **наблюдение** — значение равно
нулю при положительном `quantity`.

`acceptance_resolution` — место для документально подтверждённой причины, и
только для неё. Допустимые значения:

| Значение | Когда ставится |
|---|---|
| `NULL` | по умолчанию: причина не установлена |
| `NOT_IDENTIFIED_CONFIRMED` | есть акт приёмки WB, подтверждающий приёмку как «неопознанный товар» |

Заполняется **не загрузчиком из API**, а отдельным справочником документальных
корректировок, если мы решим их вносить. Пока таких записей две, и вносить их не
обязательно: на расчёт ввоза они не влияют.

## 4. Ключ: `entity_key`

Проблема установлена в §12.5: пропуски у двух идентификаторов лежат на разных
концах истории. 16 записей без `supply_id` — свежие заявки; 14 без
`preorder_id` — старые служебные записи.

```
entity_key = IF(preorder_id IS NOT NULL, 'P:' || preorder_id, 'S:' || supply_id)
```

Почему `preorder_id` первым, а не `supply_id`:

- на текущем снимке завершённые объекты содержат **оба** идентификатора, а
  незавершённые — только `preorder_id`. Ключ на `supply_id` расщепил бы объект
  на две записи при переходе заявки в оформленную поставку;
- 14 записей без `preorder_id` уже терминальны и получают ключ `S:`.

🔴 Префикс обязателен. Голый `COALESCE(supply_id, preorder_id)` небезопасен:
`supply_id = 123` одной записи и `preorder_id = 123` другой дали бы коллизию.
Уникальность доказана внутри каждой колонки, но не между ними.

⚠️ **Статус контракта.** `entity_key` — **рабочий** lifecycle-ключ, основанный
на структуре одного снимка от 17.08.2026. Мы **не наблюдали** один и тот же
объект во времени до и после присвоения `supply_id`, значит неизменность
`preorder_id` при переходе строго не доказана — только не опровергнута.
Стабильность подтверждается повторными снимками и **тремя** инвариантами
ключа — И7, И8 и И9 (§6). Они закрывают три разные мутации: ветвление
`preorder → supply`, ветвление `supply → preorder` и появление `preorder_id`
задним числом у объекта, который раньше его не имел. Последний сценарий меняет
`entity_key` с `S:` на `P:` и расщепляет объект надвое — именно он опаснее
всего, потому что И7 его пропускает.

## 5. Канонические вью

### 5.1 `V_WB_SUPPLIES_CURRENT` — она же выбор committed-прогона

```sql
CREATE VIEW V_WB_SUPPLIES_CURRENT AS
SELECT * EXCEPT(rn)
FROM (
  SELECT *,
    ROW_NUMBER() OVER (
      PARTITION BY entity_key
      ORDER BY snapshot_ts DESC, run_id DESC
    ) AS rn
  FROM `RAW_WB_SUPPLIES`
)
WHERE rn = 1;
```

🔑 Эта вью решает не только «какое последнее состояние шапки», но и **из какого
прогона читать позиции**. См. §5.2.

### 5.2 `V_WB_SUPPLIES_GOODS_CURRENT` — позиции того же прогона

🔴 **Независимый выбор последней строки по `(entity_key, barcode)` использовать
нельзя.** Он ломается двумя способами, и второй тихий.

**Отказ записи.** `LOAD header` прошёл, `LOAD goods` упал: новая шапка уже
текущая, а позиции остались от прошлого прогона. Канонический объект собран из
двух разных снимков.

**🔴 Исчезнувшая позиция — без всякой аварии.** WB убрал `barcode Y` из состава:

```
run A:  X, Y
run B:  X
```

Независимая вью даст `X` из B и `Y` из **A** — новой строки `Y`, которая могла
бы «перебить» старую, просто не существует. Удалённая позиция **никогда не
исчезнет** из текущего слоя, и `V_WB_SUPPLIES_INTAKE_BY_SKU` завысит
`SUM(quantity)`. Это прямой удар по задаче «сколько товара привезено».

Поэтому позиции читаются **только того прогона, который выбран шапкой**:

```sql
CREATE VIEW V_WB_SUPPLIES_GOODS_CURRENT AS
SELECT g.*
FROM `RAW_WB_SUPPLIES_GOODS` g
JOIN `V_WB_SUPPLIES_CURRENT` s
  ON  g.entity_key = s.entity_key
 AND  g.run_id     = s.run_id;
```

Один объект всегда читается из одного `run_id` целиком. Связующим механизмом
между таблицами становится `run_id + entity_key`, а не `snapshot_ts` — то есть
ровно тот ключ, на котором уже построена идемпотентность записи (§7.2).

Объекты без `supply_id`, у которых состав не запрашивается, дают шапку с нулём
позиций — это нормальный снимок, а не потеря данных.

### 5.3 `V_WB_SUPPLIES_INTAKE_BY_SKU` — то, ради чего всё делалось

```sql
SELECT
  g.nm_id,
  ANY_VALUE(g.vendor_code)            AS vendor_code,
  COUNT(DISTINCT g.barcode)           AS barcodes_cnt,      -- контроль, не значение
  MIN(s.fact_dt)                      AS first_supply_dt,
  MAX(s.fact_dt)                      AS last_supply_dt,
  COUNT(DISTINCT s.entity_key)        AS supplies_cnt,
  SUM(g.quantity)                     AS qty_sent,          -- 🔑 привезено на WB
  SUM(g.accepted_quantity)            AS qty_accepted_diag, -- контроль, НЕ истина
  SUM(g.quantity - g.accepted_quantity) AS qty_delta_diag
FROM `V_WB_SUPPLIES_GOODS_CURRENT` g
JOIN `V_WB_SUPPLIES_CURRENT`       s USING (entity_key)
WHERE s.is_completed                                        -- 🔴 только состоявшиеся
GROUP BY g.nm_id
ORDER BY qty_sent DESC
```

🔴 `barcode` из этой витрины **убран**. При `GROUP BY nm_id` конструкция
`ANY_VALUE(barcode)` выдала бы случайный исторический штрихкод, если у товара он
когда-либо менялся, и он выглядел бы как канонический. Вместо значения — счётчик
`barcodes_cnt`: при значении больше единицы это сигнал разобраться, а не молча
подставленное число. Сам `barcode` живёт в детальном слое §5.5.

Канонический грейн этой витрины — **`nm_id`**, потому что бизнес-вопрос звучит
как «сколько каждого товара привезено на WB».

🔴 Правило, которое нельзя терять: в историческое «привезено на WB» входят
**только** `status_id = 5` с непустым `fact_dt`. Те 23 заявки и несостоявшиеся
объекта не попадают.

### 5.4 Контракт дедупликации: что делает `row_hash`, а что нет

Формулировка первой редакции — «дубли снимков снимает `row_hash` во вью» — была
неверна: в `V_WB_SUPPLIES_CURRENT` и `V_WB_SUPPLIES_GOODS_CURRENT` `row_hash`
не участвует вообще. Честный контракт:

- **RAW append-only между committed `run_id`.** Формулировка уточнена
  намеренно: внутри незавершённого прогона проект сознательно использует
  `DELETE` для идемпотентного перезаписывания объекта (§7.2). Повторная запись
  одного и того же состояния допустима **между разными `run_id`** — это обычные
  снимки. Дубль внутри одного `run_id` контрактом запрещён.
- **Current-вью устроены несимметрично, и это принципиально.**
  `V_WB_SUPPLIES_CURRENT` выбирает последнюю committed-шапку по `entity_key`.
  `V_WB_SUPPLIES_GOODS_CURRENT` собственного выбора **ни по времени, ни по
  `barcode` не делает**: она читает строки `(entity_key, run_id)` того прогона,
  который выбрала шапка (§5.2). Именно это не даёт исчезнувшей позиции
  протечь из старого снимка. Повторный снимок при этом не мешает — он либо
  оказывается выбранным, либо не выбирается вовсе. Исторически дубль в RAW
  **остаётся**, и это нормально для append-only слоя.
- **`row_hash` — поле детекции изменений и аудита**, а не механизм дедупа.
  Он отвечает на вопрос «изменилось ли состояние объекта между прогонами» и
  используется инкрементом и разбором инцидентов. Текущие вью дубли им не
  чистят.
- Логическая единица идемпотентности — `run_id + entity_key` для шапки и
  `run_id + entity_key + barcode` для позиций: внутри одного прогона объект
  пишется ровно один раз.

Если когда-нибудь понадобится историческая лента без повторов одного состояния —
это отдельная вью с `PARTITION BY entity_key, row_hash`, а не изменение
current-слоя.

### 5.5 Детальный слой для баланса

`V_WB_SUPPLIES_DETAIL`: `entity_key × supply_id × fact_dt × warehouse_name ×
transit_warehouse_name × nm_id × vendor_code × quantity` по состоявшимся. Из
него одним запросом получается и итог по товару, и история по складам.

## 6. Инварианты

| № | Инвариант | Реакция при нарушении |
|---|---|---|
| И1 | `entity_key` уникален внутри каждого `run_id` в `RAW_WB_SUPPLIES` | загрузка не выполняется, разбор |
| И2 | В `_GOODS` нет строк с `(run_id, entity_key)`, которого нет в `RAW_WB_SUPPLIES` **для завершённых прогонов** | предупреждение: осиротевшие позиции от прерванного прогона ожидаемы и вьюхами не читаются, см. §7.2 |
| И3 | `is_completed` ⇒ `fact_dt IS NOT NULL` | то же |
| И4 | `SUM(quantity)` по позициям = `card_quantity` | предупреждение, строка помечается |
| И5 | `SUM(accepted_quantity)` = `card_accepted_quantity` | ⚠️ известны 2 нарушения из 108, §12.2 — предупреждение, не ошибка |
| И6 | `actual_warehouse_id` равен транзиту или назначению | предупреждение: правило проверено на 115 карточках |
| И7 | 🔴 один `preorder_id` связан не более чем с одним `supply_id` **за всю историю RAW** | ошибка: связь ветвится, ключ пересматривается |
| И8 | 🔴 один `supply_id` связан не более чем с одним непустым `preorder_id` за всю историю RAW | ошибка: то же с другой стороны |
| И9 | 🔴 один `supply_id` не встречается **и** с `preorder_id IS NULL`, **и** с непустым `preorder_id` | ошибка: `entity_key` этого объекта сменился с `S:` на `P:`, объект расщепился надвое |
| И10 | `barcode` уникален внутри `(run_id, entity_key)` | ошибка: грейн позиции шире, чем `barcode`. При JOIN-модели обе строки попадут в current-слой и могут **завысить** `SUM(quantity)`. До загрузки витрины грейн позиции пересматривается |

### 6.1 Почему одного И7 мало

И7 ловит только одно направление — ветвление `preorder → supply`. Но при
текущей формуле ключа опасна и обратная мутация:

```
снимок 1:  supply_id = 123, preorder_id = NULL   → entity_key = S:123
снимок 2:  supply_id = 123, preorder_id = 456    → entity_key = P:456
```

И7 при этом проходит идеально: `preorder 456` связан ровно с одним `supply 123`.
А объект уже расщеплён на два `entity_key`, и `V_WB_SUPPLIES_CURRENT` покажет
**две** поставки вместо одной.

🔴 Сценарий не гипотетический: у нас **14 завершённых объектов без
`preorder_id`**, и мы нигде не доказали, что WB не проставит им `preorder_id`
задним числом. Именно эту дыру закрывает И9.

### 6.2 SQL инвариантов ключа

```sql
-- И7: ветвление preorder → supply
SELECT preorder_id, COUNT(DISTINCT supply_id) AS supply_ids
FROM `RAW_WB_SUPPLIES`
WHERE preorder_id IS NOT NULL AND supply_id IS NOT NULL
GROUP BY preorder_id
HAVING supply_ids > 1;

-- И8: ветвление supply → preorder
SELECT supply_id, COUNT(DISTINCT preorder_id) AS preorder_ids
FROM `RAW_WB_SUPPLIES`
WHERE supply_id IS NOT NULL AND preorder_id IS NOT NULL
GROUP BY supply_id
HAVING preorder_ids > 1;

-- И9: смена entity_key с S: на P: у одного и того же supply_id
SELECT supply_id
FROM `RAW_WB_SUPPLIES`
WHERE supply_id IS NOT NULL
GROUP BY supply_id
HAVING COUNTIF(preorder_id IS NULL)     > 0
   AND COUNTIF(preorder_id IS NOT NULL) > 0;

-- И10: грейн позиции — действительно ли barcode уникален внутри поставки
SELECT run_id, entity_key, barcode, COUNT(*) AS cnt
FROM `RAW_WB_SUPPLIES_GOODS`
GROUP BY run_id, entity_key, barcode
HAVING cnt > 1;
```

И10 отрабатывает уже на первом бэкфилле: либо подтверждает предположение о
грейне, либо сразу показывает, что позицию надо ключевать шире, чем одним
штрихкодом. Дешёвая страховка — один запрос после прогона.

### 6.3 Реакция на нарушение И9

Не предупреждение. Два допустимых выхода, выбирается по факту:

1. **Пересмотр ключа** — если случай единичный и понятный.
2. **Alias resolution в каноническом слое** — вью получает crosswalk
   `S:<supply_id> → P:<preorder_id>` и склеивает обе версии объекта в одну до
   выбора последнего снимка. Тогда `entity_key` перестаёт быть «сырым»
   вычислением и становится разрешаемым через справочник соответствий.

Второй путь надёжнее, но стоит усложнения канонического слоя, поэтому вводится
только когда И9 действительно сработает.

И4/И5 — это `MISMATCH`-детектор пробы, перенесённый в загрузчик. Он уже нашёл
два дефекта источника, снимать его нельзя.

## 7. План загрузки

### 7.1 Бэкфилл: объём вызовов

🔴 Первая редакция считала «131 шапка + 115 составов» — и это занижение. Список
даёт только часть полей шапки; склады, коэффициенты и агрегаты карточки живут в
`/supplies/{ID}`. Значит на объект нужно **два** запроса:

```
1 запрос списка
+ до 115 GET /supplies/{ID}          (карточка)
+ до 115 GET /supplies/{ID}/goods    (состав)
≈ 231 вызов
```

При паузе 900 мс это порядка четырёх минут чистого ожидания плюс повторы на
`429` — за пределы шести минут Apps Script с учётом накладных расходов.

### 7.2 Бэкфилл: курсор и атомарность

Загрузчик работает порциями. Состояние в свойствах скрипта:

| Свойство | Смысл |
|---|---|
| `WB_SUPPLIES_BACKFILL_RUN_ID` | идентификатор текущего бэкфилла |
| `WB_SUPPLIES_BACKFILL_NEXT_INDEX` | индекс следующего объекта в отсортированном списке |
| `WB_SUPPLIES_BACKFILL_STARTED_AT` | когда бэкфилл начат |

🔴 **Атомарная единица — один объект целиком:**

```
строка списка → карточка → состав → запись шапки и позиций → сдвиг курсора
```

Курсор двигается **только после** успешной записи обеих частей. Авария между
карточкой и составом не оставляет наполовину загруженную сущность с уже
продвинутым индексом: следующий запуск переделает этот объект с начала.

#### Протокол записи одного объекта

🔴 **Атомарность здесь логическая, а не транзакционная.** Запись в две разные
таблицы BigQuery одной транзакцией не является, и Apps Script может умереть
между ними — или после успешной записи, но до обновления курсора. Без
дополнительной защиты повтор объекта внутри того же бэкфилла даст такое:

```
run_id = BF_001, entity = P:123
1. header записан
2. запись goods упала
3. курсор не сдвинут — верно
4. повторный запуск того же BF_001 переделывает объект
5. header пишется ВТОРОЙ раз с тем же run_id + entity_key
```

Инвариант И1 упал бы не из-за WB, а из-за нашей же retry-механики. Поэтому
запись объекта обязана быть **идемпотентной по ключу прогона**:

| Таблица | Ключ идемпотентности |
|---|---|
| `RAW_WB_SUPPLIES` | `run_id + entity_key` |
| `RAW_WB_SUPPLIES_GOODS` | `run_id + entity_key + barcode` |

Реализация: перед записью объекта — `DELETE` его строк по этому ключу, затем
загрузка. Наш штатный помощник `bqLoadRows_()` пишет load-job'ом, а не
стримингом, поэтому DML над свежими строками разрешён.

🔴 **Порядок записи: шапка идёт ПОСЛЕДНЕЙ и работает как commit-marker.**

`RAW_WB_SUPPLIES` — не просто заголовок, а отметка «этот объект в этом прогоне
записан целиком». Канонический слой читает позиции только того `run_id`, который
выбран шапкой (§5.2), поэтому пока шапки нет, позиций для вью тоже как бы нет.

```
DELETE header+goods по (run_id, entity_key)
  ↓ упал → курсор не сдвинут, объект будет переделан. Безопасно.
LOAD goods
  ↓ упал → позиции есть частично, ШАПКИ ЭТОГО ПРОГОНА НЕТ;
           вью продолжают читать предыдущий committed run_id целиком.
           Курсор не сдвинут, следующий проход всё удалит и перепишет. Безопасно.
LOAD header   ← COMMIT объекта
  ↓ упал → то же, что выше: объект остаётся на предыдущем снимке. Безопасно.
СДВИГ КУРСОРА
  ↓ упал → объект записан полностью и уже виден в вью;
           следующий проход переделает его идемпотентно. Безопасно.
```

Ни один отказ не оставляет ни дубля внутри `run_id`, ни объекта, собранного из
двух разных снимков. Осиротевшие позиции прерванного прогона в RAW остаются —
это ожидаемый мусор, канонический слой их не видит, а следующий проход того же
объекта их удалит.

**Итоговый контракт:**

- повтор одинакового состояния **между разными `run_id`** допустим — это
  обычные снимки append-only слоя;
- дубль одной сущности **внутри одного `run_id`** недопустим и предотвращается
  write-path, а не только обнаруживается инвариантом после загрузки.

⚠️ `DELETE` — это DML. По правилам проекта production-DML выполняется только
после явного «выполняй» от владельца; на бэкфилле это учитывается один раз, при
первом запуске.

Порядок — по `createDate`, от старых к новым, как в пробе. Прогон завершается
статусом `PARTIAL` при упоре в бюджет времени и `COMPLETE` на последнем объекте,
после чего курсор сбрасывается.

### 7.3 Суточный инкремент

Список читается всегда — это один запрос. Перечитываются карточка и состав у:

1. всех объектов с `status_id != 5` — они ещё меняются;
2. объектов, у которых `updatedDate` в списке новее сохранённого в RAW;
3. 🔴 **всех завершённых с `fact_dt` за последние 14 дней** — скользящее
   перекрытие.

Третий пункт добавлен намеренно. Мы **не проверяли как контракт**, что любое
изменение карточки или состава обязательно двигает `updatedDate` в списке. Мы
видели, что состояние `accepted / ready / unloading` бывает сложным и что
карточка иногда расходится с позициями (§12.2) — этого достаточно, чтобы не
полагаться на один watermark. Перекрытие стоит единицы запросов и страхует от
отложенной правки на стороне WB.

Если наблюдения покажут, что `updatedDate` действительно двигается всегда,
окно можно будет сузить — но не раньше.

### 7.4 Гарантии

- RAW append-only **между committed `run_id`**; внутри незавершённого прогона
  используется `DELETE`-repair по `(run_id, entity_key)` — §7.2. Каноничность
  даёт вью, как в остальных наших потоках;
- ошибка **до** записи → RAW и курсор не тронуты;
- ошибка **до commit-шапки** → канонический слой остаётся на предыдущем
  committed-прогоне целиком; осиротевшие позиции в RAW вьюхами не читаются;
- ошибка **после commit-шапки, но до сдвига курсора** → объект уже виден в вью,
  а следующий запуск идемпотентно перепишет тот же `(run_id, entity_key)`;
- 🔴 непрочитанная карточка не превращается в нули: `card_read_ok = FALSE`,
  количества из позиций остаются;
- при `429` — до трёх попыток с ростом задержки, как в пробе №4.
