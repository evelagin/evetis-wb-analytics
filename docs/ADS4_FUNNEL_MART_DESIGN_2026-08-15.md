## 0. Рамка — что это и чем это НЕ является

**Ads-4 v1 — диагностическая витрина рекламной воронки.** Она отвечает на вопрос
«где именно ломается путь от показа до заказа и на чём уходят деньги», опираясь
только на то, что можно утверждать при фактическом объёме трафика.

**Ads-4 v1 НЕ является оптимизатором ставок.** Не предлагает значений ставок,
не ранжирует запросы по «выгодности» без доказанной выборки, не содержит
автоматических действий. Никаких write-вызовов в WB не появляется.

Решения владельца, зафиксированные до проектирования: факт суточный · 28d оперативно /
90d устойчивые паттерны · решение = SKU, диагноз = запрос · ставка Ads-3 контекстом
только с 14.08, история не достраивается · экономика `pre_cogs` · только VIEW + SQL
в репозитории, job витрины и heartbeat не трогаем.

## 1. Почему решение — SKU, а диагноз — запрос

Окно 28d (17.07–13.08, 31 229,75 ₽), порог 40 кликов (вывод в §6.2):

```
единица                 всего   ≥40 кликов   доля расхода в проходящих
пара (SKU × запрос)      480         4              5,8%
запрос (все SKU)         409         6              9,3%
SKU (все запросы)         16        11             97,9%
```

На 90d лучше, но не принципиально: 22 пары из 1 432 = 22,8% расхода.
Статистически обоснованное суждение о паре невозможно для 94% расхода 28-дневного окна.
На уровне SKU — возможно почти для всего, но там мы и так всё видим в `MART_SKU_DAILY`.

**Запрос объясняет, SKU решает.**

## 2. Grain и ключи

### 2.1 Слой факта — суточный, чужой

Ads-4 **не создаёт нового факта** и не копирует строки. Суточный грейн живёт в Ads-2:

```
(period_from, advert_id, nm_id, norm_query) — ключ внутри канонического среза
```

🔴 Читать `V_ADV_QUERY_STATS`, а не `RAW_WB_ADV_QUERY_STATS`: канонический слой публикует
ровно одну retrieval-версию периода, чтение RAW склеило бы разные версии выдачи
в набор, которого не существовало.

### 2.2 🔴 Грейн витрины: `advert_id` выведен из ключа

В ред. 1 ключ витрины включал `advert_id`. Это ошибка проектирования, обнаруженная
при пересчёте: **кампания — способ доставки показа, а не измерение диагноза.** Вопрос
«работает ли этот запрос для этого товара» не зависит от того, какая кампания его
обслужила, а включение кампании в ключ дробит и без того скудную доказательность.

Замер (окно 90d, один и тот же набор данных, отличается только ключ):

```
ключ                              строк   ACTIONABLE   доля расхода ACTIONABLE
(advert_id, nm_id, norm_query)    1 837       17              15,1%
(nm_id, norm_query)               1 432       22              22,8%
```

Одна пара обслуживалась **до 7 кампаний** на 90d и до 3 на 28d. Дробление по кампаниям
уводит пять пар из ACTIONABLE в OBSERVATIONAL и теряет 7,7 п.п. объяснённого расхода
ни за что.

**Решение:** грейн витрины — `(nm_id, norm_query)`. Кампании переносятся справочно:

```sql
advert_ids     ARRAY<INT64>   -- какие кампании обслуживали пару в окне
advert_count   INT64
```

Если позже понадобится разрез по кампаниям — это отдельная вью поверх того же факта,
а не усложнение диагностического ключа.

### 2.3 Объекты

| объект | грейн | ключ |
|---|---|---|
| `V_ADS_FUNNEL_QUERY_DAILY` | сутки × запрос × SKU | `(day, nm_id, norm_query)` |
| `V_ADS_FUNNEL_QUERY_28D` | окно × запрос × SKU | `(as_of_date, window_days, nm_id, norm_query)` |
| `V_ADS_FUNNEL_QUERY_90D` | то же, окно 90 | то же |
| `V_ADS_FUNNEL_SKU_28D` | окно × SKU | `(as_of_date, window_days, nm_id)` |
| `V_ADS_FUNNEL_SIGNALS` | окно × запрос × SKU × сигнал | `(as_of_date, window_days, nm_id, norm_query, signal_code)` |

`as_of_date` = `MAX(period_from)` по `V_ADV_QUERY_STATS`, а не `CURRENT_DATE()`.
Витрина обязана быть детерминированной относительно данных, а не относительно момента
запроса.

🔴 `window_days` — колонка, а не подразумеваемое имя вью: две строки про одну пару
с разными окнами обязаны различаться ключом, иначе при любом `UNION` окна склеятся.

## 3. Источники и join semantics

### 3.1 Источники

| источник | что даёт | глубина на якоре |
|---|---|---|
| `wb_raw.V_ADV_QUERY_STATS` | воронка запроса | 13.04–13.08, 123 суток, 39 177 строк |
| `wb_raw.V_ADV_QUERY_STATS_COVERAGE` | какие сутки опубликованы | 124 суток универсума, 123 опубликовано |
| `wb_raw.V_ADV_QUERY_BIDS` (Ads-3) | ставка — снимок | снимки 14.08 и 15.08, оба `OK`, по 101 строке |
| `wb_mart.MART_SKU_DAILY` | экономика SKU, `pre_cogs` | вся история витрины |
| `wb_raw.V_ADV_COSTS` | расход по балансу — знаменатель покрытия | вся история |

### 3.2 🔴 Join Ads-2 ↔ Ads-3: ставка — текущий контекст, а не ставка окна

Ошибка ред. 1: ставка бралась при `snapshot_date <= as_of_date`. При `as_of_date = 13.08`
и снимках 14–15.08 это условие не пропускает ни одной строки, то есть заявленное
покрытие 14,6% было арифметически невозможным. Замечание принято целиком.

**Новая семантика.** Ставка — не историческая величина окна, а **последнее известное
состояние**. Ads-3 по своему контракту фиксирует, что история ставок начинается с первого
снимка и назад не восстанавливается, поэтому «ставки, действовавшей в мае», у нас нет
и не будет.

```
берётся последний канонический снимок ВООБЩЕ:
  MAX(snapshot_date) среди snapshot_status = 'OK'
без всякой привязки к as_of_date статистического окна
```

Обязательные колонки рядом со ставкой — не опция, а часть контракта:

```sql
bid_min, bid_max                 -- ставка; диапазон, см. ниже
bid_kopecks_min, bid_kopecks_max
bid_is_uniform          BOOL     -- одна ли ставка на всю пару
bid_campaign_count      INT64
payment_type            STRING   -- 🔴 cpc и cpm — разные экономические единицы ставки
bid_type                STRING
campaign_status         STRING   -- агрегируется в список: пара живёт в нескольких кампаниях
bid_snapshot_date       DATE
bid_snapshot_ts         TIMESTAMP
bid_snapshot_status     STRING   -- 🔴 канонический слой Ads-3 может опубликовать PARTIAL
bid_snapshot_offset_days INT64   -- DATE_DIFF(bid_snapshot_date, as_of_date, DAY)
bid_is_after_stats_as_of BOOL    -- снимок позже конца окна
```

🔴 В описании витрины и в любом её представлении обязана стоять фраза:
**«эта ставка не обязательно действовала в анализируемом окне».** На якоре
`bid_snapshot_offset_days = +2` и `bid_is_after_stats_as_of = TRUE` для всех строк —
то есть сейчас ставка описывает состояние *после* конца обоих окон.

**Почему диапазон, а не одно значение.** Грейн витрины `(nm_id, norm_query)`,
а ставка задаётся на `(advert_id, nm_id, norm_query)`. Замер по снимку 15.08:
96 ключей витрины, из них **4 обслуживаются несколькими кампаниями, и у всех четырёх
ставки различаются — разброс до 3,51×**. Схлопывать это в среднее означало бы
придумать ставку, которой нет ни в одной кампании.

**Fan-out структурно невозможен**, потому что ставки агрегируются до грейна витрины
ДО соединения:

```sql
bids_at_grain AS (
  SELECT nm_id, norm_query,
         MIN(bid) AS bid_min, MAX(bid) AS bid_max,
         COUNT(DISTINCT advert_id) AS bid_campaign_count,
         COUNT(DISTINCT bid) = 1 AS bid_is_uniform, ...
  FROM `wb_raw.V_ADV_QUERY_BIDS`
  WHERE snapshot_date = (SELECT MAX(snapshot_date) FROM `wb_raw.V_ADV_QUERY_BIDS`
                         WHERE snapshot_status = 'OK')
    AND snapshot_status = 'OK'
  GROUP BY nm_id, norm_query          -- 🔴 ровно одна строка на ключ витрины
)
... LEFT JOIN bids_at_grain USING (nm_id, norm_query)
```

**Покрытие ставкой на якоре** (последний OK-снимок 15.08):

```
окно   ключей витрины   со ставкой   % ключей   % расхода окна
28d          480             87        18,1%       51,2%
90d        1 432             95         6,6%       29,2%
```

Покрытие по деньгам втрое выше покрытия по ключам — ставки есть именно у тех запросов,
куда идут деньги. Обе цифры выводятся, потому что «18% ключей» и «51% расхода» отвечают
на разные вопросы.

Ставка **не участвует ни в одном сигнале v1**: два снимка не дают ни истории, ни
возможности связать изменение ставки с изменением результата.

### 3.3 Join с экономикой SKU

`MART_SKU_DAILY` соединяется только в SKU-вью, по `(day, nm_id)`, только для окна.
Query-level строки с экономикой SKU **не соединяются**: разложить выручку SKU по
запросам нечем, любая такая аллокация была бы выдумкой.

## 4. Формулы derived metrics

Все метрики называются по знаменателю. Все деления — `SAFE_DIVIDE`.

### 4.1 Базовые агрегаты окна

```sql
views_sum        = SUM(views)                              -- NULL игнорируются, §9
clicks_sum       = SUM(clicks)
clicks_on_imp    = SUM(IF(views IS NOT NULL, clicks, 0))   -- 🔴 числитель CTR
atbs_sum         = SUM(atbs)
orders_sum       = SUM(orders)
shks_sum         = SUM(shks)
spend_sum        = SUM(spend)
spend_on_imp     = SUM(IF(views IS NOT NULL, spend, 0))
days_with_data   = COUNT(DISTINCT day)
days_with_spend  = COUNT(DISTINCT IF(spend > 0, day, NULL))
advert_count     = COUNT(DISTINCT advert_id)
```

### 4.2 Ставки конверсии

```sql
ctr              = SAFE_DIVIDE(clicks_on_imp, views_sum)      -- 🔴 §9.1
cart_cr_clicks   = SAFE_DIVIDE(atbs_sum,   clicks_sum)
order_cr_carts   = SAFE_DIVIDE(orders_sum, atbs_sum)
order_cr_clicks  = SAFE_DIVIDE(orders_sum, clicks_sum)
buyout_ratio_shk = SAFE_DIVIDE(shks_sum,   orders_sum)
```

🔴 `ctr` считается только по строкам с показами: числитель `clicks_on_imp`, не `clicks_sum`.
Иначе клики CPC-размещений попадут в числитель при отсутствующем знаменателе и CTR
будет завышен в 2,3 раза (§9.1 — там эта ошибка показана на наших данных).

### 4.3 Деньги

```sql
cpc_calc   = SAFE_DIVIDE(spend_sum,    clicks_sum)
cpo_ads    = SAFE_DIVIDE(spend_sum,    orders_sum)      -- NULL при orders_sum = 0
cpm_calc   = SAFE_DIVIDE(spend_on_imp, views_sum) * 1000
spend_share_window = SAFE_DIVIDE(spend_sum, SUM(spend_sum) OVER ())
```

`cpo_ads` при нуле заказов — **NULL, а не 0**. «Стоимость заказа не определена»
и «стоимость заказа равна нулю» — разные утверждения, второе ложно.

### 4.4 Позиция

```sql
avg_pos_w_views  = SAFE_DIVIDE(SUM(avg_pos * views),  SUM(views))   -- строки с показами
avg_pos_w_clicks = SAFE_DIVIDE(SUM(avg_pos * clicks), SUM(clicks))  -- все строки
```

Две колонки, а не одна: у CPC-строк показов нет. Простое `AVG(avg_pos)` запрещено —
оно уравнивает сутки с одним показом и сутки с тысячей.

### 4.5 Экономика SKU (только в SKU-вью)

Берётся из `MART_SKU_DAILY` как есть, с сохранением имён и суффикса `pre_cogs`.
Ads-4 не пересчитывает экономику и не вводит своих формул прибыли.

## 5. Окна 28d и 90d

| окно | назначение | почему такое |
|---|---|---|
| **28d** | оперативная картина: что происходит сейчас, куда идут деньги | кратно неделе → гасит недельную сезонность WB; горизонт, на котором владелец реально меняет кампании |
| **90d** | устойчивые паттерны, кандидаты на разбор | единственное окно, где заметная часть пар проходит evidence gate: 22 пары против 4 |

Оба окна скользящие, привязаны к `as_of_date`, присутствуют одновременно, различаются
колонкой `window_days`. Календарный месяц в v1 не вводится: сверка с балансом уже живёт
в контуре Ads-2/costs и query-level разреза не требует.

Дополнительно `prev_window_*` и `delta_*` по предыдущему непересекающемуся окну.
🔴 Дельта считается, только если **оба** окна проходят evidence gate; иначе NULL.
Сравнение шума с шумом даёт шум, но выглядит как вывод.

## 6. Evidence model

### 6.1 Принцип

Строка не делится на «годную» и «негодную» — делится **право на утверждение**. Одна
и та же строка может быть достаточной для суждения о CPC и недостаточной для суждения
о конверсии. Поэтому:

* `evidence_status` — грубый ярлык для человека, три уровня;
* `can_*` — булевы флаги по классам утверждений; **именно ими гейтятся сигналы в SQL.**

### 6.2 Вывод порогов из данных якоря

Базовые линии всего массива (16.05–13.08):

```
CTR (только строки с показами)   2,563%      cart CR (от кликов)   25,41%
order CR (от корзин)            28,77%      order CR (от кликов)   7,31%
CPC                             20,19 ₽      CPO                  276 ₽
```

**Заказы — 40 кликов.** `P(0 | n) = (1 − 0,0731)ⁿ`: n=30 → 10,3%; n=40 → **4,8%**;
n=50 → 2,2%. 40 — минимальное n, при котором «ноль заказов» перестаёт быть рядовой
случайностью на уровне 5%.

**CTR — 1000 показов.** При p = 2,563% `SE = sqrt(p(1−p)/n)`: n=300 → 0,91 п.п.,
n=1000 → 0,50 п.п. Разрыв «вдвое ниже baseline» ≈ 1,28 п.п. даёт при n=300 лишь 1,4σ,
при n=1000 — 2,6σ. Порог 300 не даёт ничего.

**Корзина — 60 кликов.** p = 25,41%: SE(40) = 6,9 п.п. → 1,8σ; SE(60) = 5,6 п.п. → 2,3σ.

**Корзина→заказ — 40 корзин.** p = 28,77%: SE(40) = 7,2 п.п. → 2,0σ.

**🔴 CPC — 20 кликов, порог пересмотрен.** В ред. 1 стояло 10 кликов с обоснованием
«устойчивая оценка», которого не было: CPC — не биномиальная доля, и её разброс зависит
от распределения цены клика, а не выводится из формулы для долей. Измерена изменчивость
суточного CPC внутри пары (окно 90d, пары с ≥3 сутками активности):

```
корзина          пар    медианный CV суточного CPC   средних суток
клики ≥ 40        22             0,575                   30,1
клики 10–39      137             0,565                   12,3
клики < 10       287             0,476                    4,4
```

При CV ≈ 0,57 стандартная ошибка средней ≈ `CV/√n`: при 10 кликах это ≈ 18% средней,
и порог отклонения 1,3× (30%) даёт лишь ~1,7σ — ниже 2σ, принятых для остальных гейтов.
При 20 кликах SE ≈ 12,7% → ~2,4σ. Порог поднят до **20**.

Это оценка «на глаз по CV», а не строгий тест: суточный CV смешивает внутридневной
разброс цены клика и межсуточное движение аукциона. Формулировка в контракте —
**«эмпирически подобранный минимум, проверенный по наблюдаемому CV; при накоплении
данных подлежит пересмотру»**, а не «доказанный доверительный порог».

### 6.3 Определения

```sql
can_compare_ctr       = (views_sum  >= 1000)
can_judge_cart_cr     = (clicks_sum >= 60)
can_judge_order_cr    = (clicks_sum >= 40)
can_judge_order_carts = (atbs_sum   >= 40)
can_compare_cpc       = (clicks_sum >= 20)

evidence_status =
  CASE WHEN clicks_sum >= 40                        THEN 'ACTIONABLE'
       WHEN clicks_sum >= 10 OR views_sum >= 1000   THEN 'OBSERVATIONAL'
       ELSE 'INSUFFICIENT' END

evidence_reason   -- 'clicks=47;views=2310' — какой порог сработал
```

| статус | что разрешено | что запрещено |
|---|---|---|
| `INSUFFICIENT` | попадать в суммы расхода, быть видимым, накапливаться | любое сравнение качества, любой вывод «плохо/хорошо» |
| `OBSERVATIONAL` | сравнения CPC и позиции, наблюдение динамики, вход в агрегат «расход без заказов» | сильные утверждения о конверсии, вывод «отключить», рекомендация по ставке |
| `ACTIONABLE` | суждение о конверсии в заказ, сильный сигнал, вход в список на разбор | автоматическое изменение ставки — этого нет в v1 вообще |

### 6.4 🔴 Распределение — пересчитано по корректным порогам

Ред. 1 содержала распределение по устаревшему порогу `views >= 300`, и гейт G12
требовал `137 + 14 = 151` — числа от порога, которого в логике уже не было.
Замечание принято. Пересчёт от якоря:

```
корзина                                      28d: пар / ₽ / %      90d: пар / ₽ / %
ACTIONABLE   (clicks ≥ 40)                     4 /  1 808 /  5,8%    22 / 29 569 / 22,8%
OBSERVATIONAL (clicks 10–39)                  48 / 13 976 / 44,8%   137 / 44 993 / 34,7%
OBSERVATIONAL (clicks < 10 и views ≥ 1000)     0 /      0 /  0,0%     0 /      0 /  0,0%
INSUFFICIENT                                 428 / 15 446 / 49,5%  1 273 / 55 096 / 42,5%
ИТОГО                                        480 / 31 230 / 100%   1 432 /129 658 / 100%
```

🔴 **Третья корзина пуста в обоих окнах.** Все 21 пара с `views ≥ 1000` на 90d имеют
и `clicks ≥ 10`, то есть ветка `views_sum >= 1000` в `evidence_status` на текущих данных
**никогда не повышает статус строки**. Ветка остаётся в контракте — она осмысленна
и сработает при росте CPM-размещений, — но её вклад в приёмке заявлен нулевым, а не
подразумеваемым. `can_compare_ctr` при этом непуст (21 пара) и гейтит CTR-сигналы
независимо от `evidence_status`.

Читается так: **ACTIONABLE-уровня на 28 днях почти нет.** Это свойство нашего трафика,
и витрина обязана показывать это явно.

## 7. Иерархические baseline

🔴 Значения §6.2 — **диагностический baseline текущего query-level массива**, а не
норматив рынка, категории или «хорошей рекламы». Они получены на нашем магазине,
на 19 SKU, при нашем миксе размещений, за наблюдаемый период. Как «норма WB»
не используются.

### 7.1 🔴 Baseline исключает саму пару

В ред. 1 пара сравнивалась с агрегатом своего SKU, включающим её же. Это утечка:
чем больше доля пары в трафике SKU, тем сильнее отношение искусственно притягивается
к 1,0 и тем хуже видны именно крупные выбросы — то есть те, ради которых витрина и нужна.

```
уровень 1 (основной)   SKU_EX_SELF   = агрегат SKU − текущая пара
уровень 2 (запасной)   STORE_EX_SELF = агрегат магазина − текущая пара
```

🔴 Запасной уровень тоже **исключает саму пару**. Если бы магазинный baseline включал
её, та же утечка воспроизвелась бы на уровне магазина — слабее, но по той же механике.
Поэтому уровень называется `STORE_EX_SELF`, а не `STORE`: имя обязано совпадать
со смыслом. Именно так реализовано в `sql/mart/ads4_funnel_v1.sql`.

Правило: сравнение с `SKU_EX_SELF`; если остаток после исключения пары сам не проходит
evidence gate соответствующего класса — откат на `STORE_EX_SELF` с явной пометкой
в `baseline_<класс>_level` и причиной в `baseline_fallback_reason`.

🔴 **Уточнение ред. 3.** Гейты у классов утверждений разные (CTR — 1000 показов,
CPC — 20 кликов, корзина — 60), поэтому один и тот же ряд может иметь SKU-baseline для
одного класса и store-baseline для другого. Отсюда: уровень и выборка хранятся ПО КЛАССАМ
(`baseline_ctr_level`, `baseline_cpc_sample_clicks`, …), сводная `baseline_level` может
принимать значение вида `SKU_EX_SELF,STORE_EX_SELF`, а колонки, существующие только для
SKU-варианта, названы `sku_ex_self_*` — прежние имена `baseline_sample_clicks` и
`baseline_pair_count` были бы семантически неверны на строках со store-baseline.

```sql
baseline_level          = 'SKU_EX_SELF' | 'STORE_EX_SELF' | 'SKU_EX_SELF,STORE_EX_SELF' | 'NONE'
baseline_fallback_reason  -- 'CPC:SKU_SAMPLE_TOO_SMALL,CTR:NO_BASELINE'; NULL = все классы на своём SKU
baseline_<класс>_level    -- ctr | cart | order | order_carts | cpc | cpo
baseline_<класс>_sample_* -- размер выборки того baseline, который реально применён
sku_ex_self_sample_clicks -- только для SKU_EX_SELF-варианта
sku_ex_self_pair_count    -- сколько пар SKU вошло бы в baseline без самой пары
ctr_vs_baseline         = SAFE_DIVIDE(ctr,             baseline_ctr)
cart_cr_vs_baseline     = SAFE_DIVIDE(cart_cr_clicks,  baseline_cart_cr)
order_cr_vs_baseline    = SAFE_DIVIDE(order_cr_clicks, baseline_order_cr)
cpc_vs_baseline         = SAFE_DIVIDE(cpc_calc,        baseline_cpc)
cpo_vs_baseline         = SAFE_DIVIDE(cpo_ads,         baseline_cpo)
```

### 7.2 Смещение измерено — оно существенное

Одни и те же сигналы на окне 90d, единственное отличие — baseline с парой внутри
против baseline без неё:

```
сигнал                    baseline с собой    baseline ex-self    изменение
CTR_BELOW_BASELINE        8 пар / 5 889 ₽     6 пар / 3 365 ₽     −2 ложных
CTR_ABOVE_BASELINE        2 пары /  730 ₽     4 пары / 4 397 ₽    +2 пропущенных, ×6 денег
CART_CR_BELOW_BASELINE    1 пара / 1 547 ₽    3 пары / 6 665 ₽    +2 пропущенных, ×4 денег
CPC_ABOVE_BASELINE       19 пар / 11 298 ₽   20 пар / 12 449 ₽    +1
```

Направление ровно то, что предсказывает теория: self-inclusion **и порождает ложные
срабатывания, и прячет настоящие**, причём сильнее прячет — крупная пара тянет свой
baseline к себе и перестаёт выглядеть выбросом. Замечание принято полностью.

На якоре откат на `STORE_EX_SELF` для CTR не потребовался ни разу: у всех 21 пары с
`views ≥ 1000` остаток SKU после исключения тоже имеет `views ≥ 1000`. Колонки
`baseline_level` и `baseline_fallback_reason` всё равно обязательны — данные вырастут.

## 8. Taxonomy диагностических сигналов

### 8.1 Список

Сигналы не взаимоисключающие: одна пара может нести несколько. Все пороги отклонения —
0,7 и 1,3 от baseline. Все baseline — `SKU_EX_SELF` с откатом на `STORE_EX_SELF`.

| код | условие | требуемое evidence | что означает |
|---|---|---|---|
| `CTR_BELOW_BASELINE` | `ctr_vs_baseline < 0,7` | `can_compare_ctr` у пары и у baseline | выдача видит карточку, но не кликает: первое фото, цена, рейтинг, релевантность запроса товару |
| `CTR_ABOVE_BASELINE` | `> 1,3` | то же | запрос попадает в товар лучше среднего — кандидат на изучение, не на автомасштабирование |
| `CART_CR_BELOW_BASELINE` | `cart_cr_vs_baseline < 0,7` | `can_judge_cart_cr` | кликнули, но не положили: контент карточки, цена против конкурентов, отзывы |
| `ORDER_CR_CARTS_BELOW_BASELINE` | `order_cr_carts < 0,7 × baseline` | `can_judge_order_carts` | положили, но не заказали: цена в корзине, сроки, остатки |
| `CPC_ABOVE_BASELINE` | `cpc_vs_baseline > 1,3` | `can_compare_cpc` | трафик дороже среднего по SKU: конкуренция или ставка |
| `CPC_BELOW_BASELINE` | `< 0,7` | то же | трафик дешевле среднего |
| `CPO_BELOW_BASELINE` | `cpo_vs_baseline < 0,7` | `can_judge_order_cr` и `orders_sum > 0` | заказ дешевле среднего по SKU — кандидат на разбор |
| `ZERO_ORDER_SPEND` | `orders_sum = 0 AND spend_sum > 0` | любое; сила = уровню evidence | расход без атрибутированных заказов |

🔴 **`POTENTIAL_WASTE` — не сигнал, а ярлык**, который `ZERO_ORDER_SPEND` получает
только при `evidence_status = 'ACTIONABLE'`. При OBSERVATIONAL и INSUFFICIENT строка
остаётся `ZERO_ORDER_SPEND` без ярлыка.

### 8.2 Почему «ноль заказов» не равно «жжёт деньги»

Три причины, каждая достаточна сама по себе:

1. **Выборка.** При базовой конверсии 7,31% пара с 15 кликами даёт ноль заказов
   в 32% случаев просто по случайности.
2. **Атрибуция.** `orders` — заказы в атрибуции WB (§10.1). Отсутствие
   атрибутированного заказа не равно отсутствию влияния показа на продажу.
3. **COGS.** Без себестоимости неизвестно, был ли заказ по этому запросу прибыльным.
   «Не принёс заказов» и «принёс убыток» — разные утверждения, второе мы сейчас
   не можем сделать ни для одной строки (§10.3).

Замер на 90d:

```
orders = 0 и spend > 0, всего                     1 045 пар · 62 336 ₽ · 48,1% расхода
   из них OBSERVATIONAL (10–39 кликов)               62 пары · 17 474 ₽ · 13,5%
   из них ACTIONABLE  (≥40 кликов)                    0 пар  ·      0 ₽ ·  0,0%
```

**Ни одна пара с достаточной выборкой не имеет нуля заказов.** Формулировка «42%
расхода сжигается» неверна: это масса мелких строк, про каждую из которых по отдельности
сказать нечего. Правильная подача — агрегат «расход без атрибутированных заказов»
с разбивкой по доказательности, а не список виновных.

### 8.3 Достижимость каждого сигнала — проверено на якоре

Окно 90d, 1 432 пары, 129 657,53 ₽, baseline `SKU_EX_SELF`:

| сигнал | пар | ₽ | статус в v1 |
|---|---|---|---|
| `CPC_ABOVE_BASELINE` (c ≥ 20) | 8 | 7 205 | ✅ в приёмке |
| `CPC_BELOW_BASELINE` (c ≥ 20) | 18 | 5 881 | ✅ в приёмке |
| `CTR_BELOW_BASELINE` | 6 | 3 365 | ✅ в приёмке |
| `CTR_ABOVE_BASELINE` | 4 | 4 397 | ✅ в приёмке |
| `CPO_BELOW_BASELINE` | 5 | 2 204 | ✅ в приёмке |
| `CART_CR_BELOW_BASELINE` | 3 | 6 665 | ⚠️ достижим, но выборка мала — считается, в гейт не входит |
| `ZERO_ORDER_SPEND` (агрегат) | 1 045 | 62 336 | ✅ в приёмке как агрегат |
| `ZERO_ORDER_SPEND` + `POTENTIAL_WASTE` | **0** | **0** | 🔴 **недостижим на текущем трафике** |
| `ORDER_CR_CARTS_BELOW_BASELINE` | **0** | **0** | 🔴 **недостижим**: ни одной пары с ≥40 корзин за 90 суток |

🔴 Два последних сигнала **определяются в коде, но объявляются ожидающими данных**:
не входят ни в один гейт приёмки и показываются как «нет строк, проходящих порог
доказательности», а не как «проблем нет». Разница принципиальная: первое — про нас,
второе — про рекламу.

Это применение урока §8 Ads-2 к самому Ads-4: критерий, математически дающий пустой
результат при нашем объёме трафика, не может быть критерием приёмки.

## 9. Обработка NULL, нулей и разреженности

### 9.1 🔴 Показов нет у двух третей расхода

```
строки без показов (views IS NULL)   22 644 · 146 732 ₽ · 67,5% query-level расхода
строки с показами                    16 533 ·  70 742 ₽ · 32,5%
```

У строк без показов `cpm` тоже NULL, а `cpc` и `avg_pos` присутствуют. Следствия:

* **CTR определён только для 32,5% расхода** — выводится колонкой
  `ctr_coverage_spend_share`, а не подразумевается;
* числитель CTR — `clicks_on_imp` (§4.2). Наивная `SUM(clicks)/SUM(views)` даёт
  **5,84%** вместо истинных **2,563%** — завышение в 2,3 раза. Ошибка была допущена
  при первом замере и найдена при проверке NULL; зафиксирована, чтобы не повторилась.
  Общее правило: **при NULL в знаменателе числитель обязан быть ограничен теми же
  строками** — `SUM()` игнорирует NULL только в своей колонке, это не согласованный фильтр;
* сигналы группы CTR не выставляются строкам без показов — не «выставляются как OK»,
  а именно не выставляются, с `signal_not_applicable_reason = 'NO_IMPRESSIONS'`.

Отдельно: единственный наблюдаемый `payment_type` в снимке ставок — `cpm`, при том что
две трети расхода идёт по строкам без показов. Это несоответствие не объяснено и
в v1 не объясняется; оно зафиксировано как открытый вопрос, а не как дефект.

### 9.2 Ноль ≠ NULL

| ситуация | как хранится | почему |
|---|---|---|
| показов не отдают | `views = NULL`, `ctr = NULL` | метрика неизмерима |
| показы были, кликов нет | `clicks = 0`, `ctr = 0` | метрика измерена и равна нулю |
| заказов нет | `orders = 0`, `cpo_ads = NULL` | заказы измерены; стоимость заказа неопределима |
| сутки не собраны | строки нет | видно через `V_ADV_QUERY_STATS_COVERAGE` |

🔴 `COALESCE(metric, 0)` запрещён для всех ставок конверсии и CPO: он превращает
«не знаем» в «ноль» и делает неизмеримое похожим на провал.

### 9.3 Воронка WB не вложена

```
clicks > views     17 строк
atbs   > clicks    50 строк
orders > atbs     162 строки
```

Причина — разные окна атрибуции: заказ может быть отнесён к показу позже, чем произошло
добавление в корзину. Это **не дефект загрузчика**, данные приходят такими из API.

* значения **не чинятся и не обрезаются**: `LEAST(atbs, clicks)` был бы подделкой данных
  ради красоты формулы;
* флаг `funnel_monotonic BOOL` = `clicks<=views AND atbs<=clicks AND orders<=atbs`
  (при NULL показов проверяются только доступные пары);
* строки с `funnel_monotonic = FALSE` **исключаются из сигналов о конверсии**, но
  остаются в суммах денег и в наблюдении;
* доля таких строк — телеметрия: её рост означает смену контракта API.

### 9.4 Разреженность

* пары без единой строки в окне в витрине **не появляются** — «нет данных» не то же,
  что «ноль показов»;
* `days_with_data` и `days_with_spend` обязательны: 40 кликов за одни сутки и за
  28 суток — разные наблюдения;
* сортировка по умолчанию — `spend_sum DESC`, не по конверсии: деньги — единственная
  величина, измеренная точно на разреженных данных.

## 10. Ограничения, названные заранее

### 10.1 Атрибуция WB

`orders`, `atbs`, `shks` — события **в атрибуции WB**: WB сам решает, какой показ считать
причиной заказа, по своим правилам, которые нам не раскрыты и могут меняться. Отсюда:
нельзя складывать query-level заказы с `FACT_ORDERS` и ждать совпадения; нельзя трактовать
`orders = 0` как «реклама не повлияла»; сравнение «этот запрос лучше того» законно только
внутри самого query-level. В `MART_SKU_DAILY` уже есть `ads_revenue_dedup_estimate_rub` —
признание той же проблемы на уровне SKU. Ads-4 её не решает.

### 10.2 Покрытие query-level ≈ 42%

```
2026-04  42 922 /  96 009 = 44,7%
2026-05  82 644 / 140 347 = 58,9%
2026-06  38 983 / 116 970 = 33,3%
2026-07  41 645 / 128 653 = 32,4%
2026-08  11 280 /  29 953 = 37,7%
итого   217 474 / 511 932 = 42,5%
```

Это не потеря данных, а свойство размещений: часть расхода идёт вне поиска, и запросов
там нет по определению. Следствие жёсткое: **сумма по всем запросам никогда не сойдётся
с рекламным расходом**, и формулировка «вся реклама разложена по запросам» ложна.
Колонка `query_spend_share_of_total` выводится в SKU-вью.

### 10.3 pre_cogs

Себестоимости в BigQuery нет (данные в листе `COST_HISTORY`, перенос — задача REF-Sync PR2).
Поэтому все показатели вклада наследуют суффикс `_pre_cogs` без переименования; Ads-4
**не вычисляет прибыль, маржу и окупаемость** ни на каком уровне; формулировки
«выгодно / невыгодно / убыточно» запрещены на уровне контракта. Разрешены
«дороже/дешевле среднего по SKU» — это утверждение о расходе, а не о марже.

### 10.4 Ставка — только с 14.08

```
V_ADV_QUERY_BIDS: 202 строки · снимки 14.08 и 15.08, оба snapshot_status = 'OK'
                  по 101 строке в снимке · payment_type = cpm · bid_type = manual
                  campaign_status 7/9/11 · bid от 510 до 2600
покрытие грейна витрины: 28d — 87 из 480 ключей (18,1% ключей, 51,2% расхода)
                         90d — 95 из 1 432 (6,6% ключей, 29,2% расхода)
```

История не достраивается и не интерполируется. Ставка — контекст с датой снимка,
в сигналах не участвует (§3.2).

## 12. Приёмка

### 12.1 Принцип

Каждый гейт сопровождается **предпроверкой достижимости** — запросом, показывающим,
что на фактических данных существует хотя бы одна строка, способная его пройти. Гейт
без такой предпроверки в документ не попадает. Два сигнала (§8.3) предпроверку не прошли
и в гейты не включены. Все ожидаемые числа гейтов взяты от якоря §0 и воспроизводимы
на нём — при сдвиге `as_of_date` числа изменятся, и это нормально: гейт формулируется
как «воспроизвести замер на своём якоре», а не как вечная константа.

### 12.2 Структурные гейты — безусловные

| # | проверка | ожидание |
|---|---|---|
| G1 | `as_of_date` в витрине = `MAX(period_from)` в `V_ADV_QUERY_STATS` | равенство; на якоре 2026-08-13 |
| G2 | дублей по ключу `(as_of_date, window_days, nm_id, norm_query)` | 0 |
| G3 | `SUM(spend_sum)` = `SUM(spend)` в `V_ADV_QUERY_STATS` за то же окно | до копейки |
| G4 | LEFT JOIN ставки не меняет число строк | `rows_after = rows_before` |
| G5 | `cpo_ads` при `orders_sum = 0` | всегда NULL |
| G6 | `ctr` при `views_sum IS NULL` | всегда NULL |
| G7 | строки с `funnel_monotonic = FALSE` не несут сигналов конверсии | 0 нарушений |
| G8 | baseline не включает саму пару | `sku_ex_self_sample_clicks = sku_clicks_total − clicks_sum` для строк с `baseline_cpc_level='SKU_EX_SELF'` (сводная `baseline_level` после ред. 3 составная и для тождества не годится — см. K5) |
| G8+ | согласованность `baseline_fallback_reason` | причина непуста тогда и только тогда, когда хотя бы один класс не на `SKU_EX_SELF` |
| G9 | `MART_SKU_DAILY`, `FACT_*`, heartbeat | идентичны baseline «до» |

### 12.4 Контрольные SQL

**K1 — сохранение денег (G3).**

```sql
WITH anchor AS (
  SELECT MAX(SAFE.PARSE_DATE('%Y-%m-%d', period_from)) AS as_of
  FROM `wb_raw.V_ADV_QUERY_STATS`
),
src AS (
  SELECT SUM(SAFE_CAST(spend AS FLOAT64)) AS s
  FROM `wb_raw.V_ADV_QUERY_STATS`, anchor
  WHERE SAFE.PARSE_DATE('%Y-%m-%d', period_from) > DATE_SUB(as_of, INTERVAL 28 DAY)
),
mart AS (SELECT SUM(spend_sum) AS s FROM `wb_mart.V_ADS_FUNNEL_QUERY_28D`)
SELECT src.s AS raw_spend, mart.s AS mart_spend, ROUND(mart.s - src.s, 2) AS delta
FROM src, mart;
-- ждём delta = 0.00; на якоре raw_spend = 31229.75
```

**K2a — настоящий join-gate: ставка не размножает строки (G4).**
Проверяется именно соединение, а не уникальность готовой витрины: ошибочный join мог
бы размножить строки, а последующая агрегация — снова их схлопнуть.

```sql
WITH base AS (
  SELECT nm_id, norm_query FROM `wb_mart.V_ADS_FUNNEL_QUERY_28D`
),
bids_at_grain AS (
  SELECT nm_id, norm_query
  FROM `wb_raw.V_ADV_QUERY_BIDS`
  WHERE snapshot_status = 'OK'
    AND snapshot_date = (SELECT MAX(snapshot_date) FROM `wb_raw.V_ADV_QUERY_BIDS`
                         WHERE snapshot_status = 'OK')
  GROUP BY nm_id, norm_query
),
joined AS (
  SELECT b.nm_id FROM base b
  LEFT JOIN bids_at_grain g ON b.nm_id = g.nm_id AND b.norm_query = g.norm_query
)
SELECT (SELECT COUNT(*) FROM base)   AS rows_before,
       (SELECT COUNT(*) FROM joined) AS rows_after,
       (SELECT COUNT(*) FROM joined) - (SELECT COUNT(*) FROM base) AS delta;
-- ждём delta = 0
```

**K2b — уникальность ключа витрины (G2), по колонкам, без конкатенации.**

```sql
SELECT COUNT(*) AS dup_keys FROM (
  SELECT as_of_date, window_days, nm_id, norm_query
  FROM `wb_mart.V_ADS_FUNNEL_QUERY_28D`
  GROUP BY 1,2,3,4 HAVING COUNT(*) > 1
);
-- ждём 0
```

**K3 — NULL-семантика CPO и CTR (G5, G6).**

```sql
SELECT COUNTIF(orders_sum = 0 AND cpo_ads IS NOT NULL) AS bad_cpo,
       COUNTIF(views_sum IS NULL AND ctr IS NOT NULL)  AS bad_ctr
FROM `wb_mart.V_ADS_FUNNEL_QUERY_90D`;
-- ждём 0 и 0
```

**K4 — распределение доказательности (G14, G15, G18).**

```sql
SELECT window_days, evidence_status, COUNT(*) AS pairs, ROUND(SUM(spend_sum),0) AS spend,
       COUNTIF(clicks_sum < 10 AND views_sum >= 1000) AS promoted_by_views_only
FROM (
  SELECT * FROM `wb_mart.V_ADS_FUNNEL_QUERY_28D`
  UNION ALL
  SELECT * FROM `wb_mart.V_ADS_FUNNEL_QUERY_90D`
)
GROUP BY window_days, evidence_status ORDER BY window_days, evidence_status;
-- на якоре: 28 → 4 / 48 / 428;  90 → 22 / 137 / 1 273
-- promoted_by_views_only = 0 в обоих окнах
```

**K5 — baseline не включает саму пару (G8).** Сверяется по классу CPC: сводная
`baseline_level` после ред. 3 может содержать несколько уровней и для тождества не годится.

```sql
SELECT COUNTIF(baseline_cpc_level = 'SKU_EX_SELF'
               AND ABS(sku_ex_self_sample_clicks + clicks_sum - sku_clicks_total) > 1e-9) AS leaks,
       COUNTIF(baseline_level = 'SKU_EX_SELF' AND baseline_fallback_reason IS NOT NULL) AS bad_reason_set,
       COUNTIF(baseline_level != 'SKU_EX_SELF' AND baseline_fallback_reason IS NULL)     AS bad_reason_missing
FROM `wb_mart.V_ADS_FUNNEL_QUERY_90D`;
-- ждём 0, 0, 0
```

### 12.5 🔴 K9 — постоянный гейт (ред. 3)

Гейта не было в ред. 2; он добавлен после того, как при первом выкате обнаружилось
расхождение между файлом репозитория и выкаченным объектом (пять пустых строк и один
пробел — смысловой ноль, но именно так начинается «в репозитории одно, в проде другое»).

**K9a — два оконных вью различаются только константами окна.** Берутся
`INFORMATION_SCHEMA.VIEWS.view_definition` обеих вью, нормализуются
(`INTERVAL 28|90 DAY` → `<W>`, `INTERVAL 56|180 DAY` → `<W2>`, имя вью, литерал
`window_days`) и сравниваются по SHA-256. Ожидание: хэши равны.

**K9b — файл репозитория идентичен выкаченному объекту.** SHA-256 тела каждой из пяти вью
из `sql/mart/ads4_funnel_v1.sql` (после снятия комментариев) сверяется с
`view_definition` в BigQuery. Ожидание: совпадение по всем пяти.

🔴 K9 прогоняется при КАЖДОМ выкате Ads-4, а не только при первом.

**K6 — сигналы непусты и не переопределены (G10–G13, G16).**

```sql
SELECT signal_code, evidence_status, COUNT(*) AS pairs, ROUND(SUM(spend_sum),0) AS spend
FROM `wb_mart.V_ADS_FUNNEL_SIGNALS`
WHERE window_days = 90
GROUP BY signal_code, evidence_status ORDER BY signal_code, evidence_status;
-- ждём CPC_ABOVE 8 / CTR_BELOW 6 / CTR_ABOVE 4 / CPO_BELOW 5
-- и ровно 0 строк ZERO_ORDER_SPEND с evidence_status = 'ACTIONABLE'
```

**K7 — контрольная пара, сквозная связь с Ads-2.**

```sql
SELECT nm_id, norm_query, clicks_sum, orders_sum, ROUND(spend_sum,2) AS spend,
       evidence_status, baseline_level, advert_count
FROM `wb_mart.V_ADS_FUNNEL_QUERY_90D`
WHERE nm_id = 438775437
ORDER BY spend_sum DESC LIMIT 10;
-- SKU из контроля §8.2 дизайна Ads-2 обязан присутствовать; сумма его spend
-- по всем запросам за пересекающиеся сутки должна совпасть с query-level Ads-2
```

**K8 — baseline «до».** Снимается ПЕРЕД выкатом: число строк и все суммы
`MART_SKU_DAILY`, `FACT_ADS_COSTS_DAILY`, статус heartbeat. «Не изменилось» есть
утверждение о разнице, и без снимка «до» доказать его нечем.

## 13. Что Ads-4 v1 сознательно НЕ делает

1. **Не рекомендует ставки** и не содержит правил вида «поднять на X%».
2. **Не делает write-вызовов в WB** — ни одного.
3. **Не считает прибыль и маржу** — нет COGS (§10.3).
4. **Не восстанавливает историю ставок** до 14.08 и не интерполирует её (§10.4).
5. **Не утверждает, что показанная ставка действовала в окне** (§3.2).
6. **Не аллоцирует выручку SKU по запросам** — нечем (§3.3).
7. **Не чинит немонотонность воронки** обрезкой значений (§9.3).
8. **Не создаёт таблиц и не трогает job витрины** — только вью (§11).
9. **Не вводит календарный месяц** как окно.
10. **Не разрезает диагностику по кампаниям** — `advert_id` выведен из ключа (§2.2).
11. **Не объединяет query-level заказы с `FACT_ORDERS`** — разные атрибуции (§10.1).
12. **Не расширяет pair discovery** — область видимости наследуется от Ads-2 §5.2.
13. **Не утверждает, что расход без заказов есть потери** — только `ZERO_ORDER_SPEND`
    с указанием доказательности (§8.2).
14. **Не строит дашборд** — v1 заканчивается на слое вью.
