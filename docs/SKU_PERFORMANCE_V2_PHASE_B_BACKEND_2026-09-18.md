## 2. Окончательный SKU metric contract

Грейн — **день × nm_id** (25 активных SKU, плотный календарь `MART_SKU_DAILY`). В таблице только суммы и количества.
Любое среднее, доля или изменение за период — **ratio-of-sums** из сумм, а не среднее дневных значений (`TVF_…_PERIOD`).
1 строка источника = 1 единица: это доказано для заказов, продаж и финотчёта. Вне покрытия источника значение `NULL`, не 0.

| Показатель | Поле(я) | Источник | База дат | Формула за период |
| --- | --- | --- | --- | --- |
| Заказы (брутто) | `orders_gross_units` | FACT_ORDERS | заказ | Σ |
| Отменено | `orders_cancelled_units` | FACT_ORDERS | заказ | Σ |
| Доля отмен | — | — | заказ | Σ отменено / Σ заказы |
| Выкупы (события) | `buyout_units` | FACT_SALES | выкуп | Σ |
| Когорта: заказы / выкуп / отмена / без исхода / конфликт / завершено | `cohort_*` | FACT_ORDERS × продажи по srid | заказ | Σ; методология Executive V2 на SKU |
| % выкупа по когорте | — | — | заказ | Σ выкуп / Σ (выкуп + отмена); незрелость — флаг |
| Реклама | `ads_attributed_rub` | FACT_ADS_SKU_DAILY (атрибуция) | активность | Σ; **не биллинг, не масштабируется** |
| ДРР | — | — | — | Σ реклама / Σ цена продавца по выкупам |
| Себестоимость | `cogs_rub` | V_MART_SKU_DAILY_COGS (operational) | **выкуп** | Σ (как Executive V2); `cogs_settlement_rub` — справочно по дате финотчёта |

`buyouts/orders` как % выкупа не используется нигде.

## 4. PRICE CHAIN

Финотчёт по дате финотчёта, строки «Продажа» — плюс, «Возврат» — минус (WB отдаёт возвраты с положительными суммами):

`fin_seller_price_rub − fin_spp_rub (= fin_buyer_paid_rub) − chain_wb_remuneration_rub − chain_wb_remuneration_vat_rub − chain_acquiring_rub − chain_pvz_reward_rub − chain_rounding_rub = credited_for_goods_rub`

- **С 13.07.2026** цепочка полная (`price_chain_complete`); тождество проверяется ASSERT S5 / V5 (≤ 0,005 ₽ на SKU-сутки).
- **До 13.07.2026** компоненты `chain_*` = **NULL**: нулей нет, частичных сумм нет (V6.chain_boundary).
  Цена продавца, СПП, цена покупателя и начисление при этом доступны с 13.04.2026.
- В функции периода компонент = NULL, если в окне есть хотя бы одни SKU-сутки без цепочки.
  Число таких суток — `cur_price_chain_missing_days`.

## 5. CONTRIBUTION CONTRACT

```
Вклад SKU до себестоимости   = начисление за товар (нетто возвратов)
                               − логистика SKU (продажа + отмены к/от клиента + возвраты + коррекции + без метки)
                               − хранение SKU (только где есть отчёт платного хранения; иначе не вычитается)
                               − реклама (атрибуция)
Вклад SKU после себестоимости = вклад до себестоимости − себестоимость (по дате выкупа)
Маржинальность вклада         = вклад после себестоимости / цена продавца (финотчёт, нетто)
Вклад на выкуп                = вклад после себестоимости / (продажи − возвраты финотчёта)
```

- **Не входят** и по SKU **не распределяются**: тарифная опция / минимальный платёж, штрафы, утилизация, прочие удержания, компенсации, хранение до 01.09.2026, разница «атрибуция − биллинг». Всё это — строки моста (§7).
- **Гейты:** вклад до себестоимости определён при `finance_covered ∧ ads_covered`; после себестоимости — дополнительно `sales_covered` и определённая себестоимость.
- **Смешанные даты:** начисление и логистика — по дате финотчёта (лаг 0–1 день от выкупа), реклама — по активности, себестоимость — по выкупу, как в Executive. Поэтому вклад по суткам «пилообразный»: для UI — неделя и больше (GAP-B4).
- **Хранение:** до 01.09.2026 вклад **не включает** хранение. Это видно по `storage_sku_covered` / `cur_storage_cov_days` / `storage_complete` и по причине в `data_status_reasons`.

## 7. Reconciliation с Executive

`V_SKU_PERFORMANCE_V2_EXEC_BRIDGE_DAILY`, суммируется за любой период:

```
  Σ вклада SKU до себестоимости                                   (l1)
+ хранение SKU (вычтено в SKU; в Executive вместо него хранение финотчёта)  (l2)
− хранение уровня счёта (финотчёт)                                  (l3)
− тарифная опция / минимальный платёж                               (l4)
− прочие расходы уровня счёта                                       (l5)
+ (атрибуция рекламы − биллинг WB)                                  (l6)
+ (выручка по дате выкупа − цена продавца по финотчёту)             (l7)  база дат выручки Executive
+ (2 × начисление по возвратам − цена продавца по возвратам)        (l8)  Executive считает «Возврат» поступлением (KI-2)
= результат Executive до себестоимости;  residual = Executive − мост
```

## 13. Спецификация UI для Phase C (НЕ развёрнута)

**Portfolio** (все блоки — одна TVF с фильтром периода):
1. **Статус данных:** одна строка «🟢/🟡/🔴 `data_status` · по `source_data_through` · причины `data_status_reasons` через « · »».
2. **KPI со сравнением:** заказы, выкупы, % выкупа 🟡, ср. цена продавца, реклама, ДРР, вклад после себестоимости, маржа. Значение и рядом Δ: `% ` для абсолютных, `п.п.` для долей. Если не сопоставимо — «н/с», если выборка мала — пометка.
3. **Требуют внимания:** правила Phase A §J, но уже на полях TVF. Пороги — решение GAP-B5; 10 шт — только минимальный объём.
4. **Таблица экономики SKU:** SKU · цена (Δ) · заказы (Δ) · выкупы · % выкупа · начисление · реклама · ДРР · логистика + хранение · COGS · вклад · маржа · статус/надёжность.
5. **Компактная динамика:** заказы и цена в заказах по неделям.

**SKU Detail** (drill-through по `nm_id`):
1. **Шапка:** SKU / nmId / товар / период / статус.
2. **Цена и спрос:** ср. цены продавца (заказы / выкупы), цена покупателя, заказы, выкупы, % выкупа, Δ; график «цена в заказах × заказы» по дням с наблюдателем цен.
3. **Экономика и цепочка цены:** waterfall от цены продавца до начисления.
4. **Расходы:** логистика по видам, хранение, реклама, COGS.
5. **Вклад:** до / после себестоимости, маржа, вклад на выкуп.
6. **Динамика:** вклад и ДРР по неделям.
