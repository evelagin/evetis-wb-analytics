Статус: OWNER ACK «PHASE B IMPLEMENTATION: OZON PAY-PER-ORDER VIA SEPARATE CLOUD RUN LOADER». Запись в боевой лист
Юнитки — **только** после отдельного «OWNER ACK — APPLY OZON CPO UNITKA + HISTORICAL BACKFILL» (флаг `OZON_UNITKA_CPO`).
Инвентаризация, из которой выросла фаза: `docs/finance/UNITKA_FIN_COMPLETENESS_PHASE_A_2026-10-08.md`.

## 1. Авторитет — один рубль, роли не смешиваются

| Роль | Источник | Объект |
|---|---|---|
| Итог CPO (сколько списано) | биллинг кампаний | `ozon_raw.RAW_OZON_ADS_EXPENSE_DAILY.expense_rub` |
| Атрибуция по заказам | Performance API, «Отчёт по заказам» | `ozon_raw.RAW_OZON_ADS_CPO_ORDERS` → `ozon_mart.V_OZON_ADS_CPO_ORDERS` |
| Независимая сверка | финансы, type 54, `unit_number` = campaign_id | `ozon_raw.RAW_OZON_FINANCE_ACCRUAL` (проводка отстаёт) |

Тождество (каждая CPO-кампания × дата списания): **биллинг = атрибутировано по SKU + несопоставлено + остаток**.
Остаток и несопоставленное — уровень магазина (`V_OZON_ADS_CPO_RESIDUAL_DAILY.store_level_rub`). Биллинговый рубль не
исчезает: `FCT_OZON_PNL_MONTHLY` вычитает весь биллинг кампаний и до, и после Phase B — перенос части CPO в SKU не меняет
чистую прибыль магазина.

**CPO определяет кампания, а не type_id**: `RAW_OZON_ADS_CAMPAIGNS.payment_type = 'CPO'` и `adv_object_type` = семейство
отчёта. В 2025-05…08 type 54 нёс и CPC-кампании `14933060`, `14957140`, `14984361`, `15010239` — 17 935,43 ₽ по живым
данным 08.10 (в фазе A было 17 738,02 ₽ — снимок до дозагрузки финансов; живая цифра — эта). Они остаются CPC (фаза D).

## 2. Источник — только чтение

| Семейство | Кампания | Заказ отчёта | Вид |
|---|---|---|---|
| `ALL_SKU_PROMO` | `24086250` «Оплата за заказ — все товары» | `GET /api/client/statistics/all_sku_promo/orders/generate?timeBounds.from/to` | `ALL_SKU_PROMO_ORDERS` |
| `SEARCH_PROMO` | `14503166` «Оплата за заказ: выбранные товары» | `POST /api/client/statistic/orders/generate {from,to}` | `SEARCH_PROMO_ORGANISATION_ORDERS` |

Статус — `GET /api/client/statistics/{UUID}`, скачивание — `GET /api/client/statistics/report?UUID=`. Клиент
(`cloud/src/loaders/ozon_cpo/perfApi.ts`) **физически** ограничен белым списком этих пяти маршрутов: запись кампаний,
ставок и товаров отклоняется до сети (`CPO_PERF_ROUTE_DENIED`, тест). Секреты `EVETIS_OZON_PERFORMANCE_CLIENT_ID/_SECRET`
читаются из Secret Manager в память; ни значения, ни токен, ни тело ответа на запрос токена не логируются.

CSV: BOM, «;», десятичная запятая; строка периода, шапка, строки, у SEARCH_PROMO — «Всего». Разбор fail-closed
(`parse.ts`): изменённая шапка, период ≠ запрошенному, строка вне периода, «Расход» ≠ «Ставка, ₽» × «Количество», сумма ≠
«Всего» — отказ всего прогона. Проверено на 36 живых выгрузках 2025-05…2026-10: **315 строк, 30 550,66 ₽, 0 дублей ключа**.

## 3. RAW, окно, журнал

`ozon_raw.RAW_OZON_ADS_CPO_ORDERS` — только факты отчёта и происхождение (семейство, дата списания, ID и номер заказа,
заказанный и продвигаемый SKU, артикул из отчёта, источник заказа, количество, цена, стоимость, ставка %/₽, расход, UUID,
запрошенный период, время выгрузки, run_id, `completeness_status`, исходная строка). **Отклонение от списка ACK, намеренно:**
кампания, offer_id/internal_sku обоих SKU, время и сутки МСК заказа вычисляются во вью на каждом чтении, а не замораживаются
при загрузке (урок `sku_match_status`): поздняя загрузка отправления или правка справочника лечат строку сами.

- **Ключ** `row_key` = SHA-256(семейство, дата списания, ID заказа, заказанный SKU, продвигаемый SKU). Ozon сам сводит
  несколько отправлений одного заказа в одну строку с количеством (14 строк истории — так).
- **Запись** — блок окна (≤ календарного месяца) × оба семейства в одной транзакции (`bq.ts`): stage → проверки → DELETE
  окна → INSERT → проверки → строка журнала CHUNK → COMMIT. Все проверки до COMMIT; провал = ROLLBACK, RAW прежний.
  Уникальность ключа проверяется по ВСЕЙ таблице — перекрытие окон и повтор не удваивают строку.
- **Исчезновение суток** (были в RAW, нет в новом отчёте) — отказ `CPO_ROWS_WOULD_DISAPPEAR`: сторно у CPO не
  наблюдалось ни разу, пропажа суток — признак сбоя выгрузки. Осознанный приём — разово `OZON_CPO_ACCEPT_REMOVALS=1`.
- **Окно DAILY** — 45 закрытых суток списания. Отчёт фильтруется датой СПИСАНИЯ; списание приходит через 0–41 сутки после
  заказа (замер 315 строк: p99 27, max 41 — шире, чем 2–16 в формулировке ACK: это и есть «наблюдённая задержка с запасом»).
  45 = максимум + запас = окно перезаписи Юнитки. Открытые сутки (сегодня МСК) не загружаются никогда.
- **BACKFILL** — `OZON_CPO_BACKFILL_FROM/TO` (с 2025-05-01, до вчера, ≤ 620 суток), месячные блоки.
- **Журнал** `ozon_raw.OZON_CPO_ORDER_RUNS`: CHUNK (в транзакции с данными: строка есть ⇔ данные легли) и RUN —
  COMPLETE (все блоки), PARTIAL (часть блоков легла, затем отказ; легшие верны и самодостаточны, повтор идемпотентен),
  ERROR (не легло ничего). PARTIAL и ERROR завершают Job ошибкой → алерт. Транзиентный отказ (5xx/429/сеть/очередь
  отчётов) повторяется один раз в том же часовом слоте (`retryTransient`).
- **Аренда** — `ozon_raw.LOADER_RUNS` (`BQ_RAW_DATASET=ozon_raw`): Job Ozon ничего не пишет в WB-датасеты.
- **Свежесть** — `MAX(window_to)` RUN COMPLETE. Юнитку **не блокирует никогда**: CPO приходит списаниями и
  перезаписывается окном 45 суток, отставание лечится следующим прогоном; отказ загрузчика ловит его алерт, Юнитка пишет
  `ozon_unitka_cpo_stale` (WARNING).

## 5. Юнитка Ozon

- «Реклама внутренняя» (смещение 11) = CPC-атрибуция (`RAW_OZON_ADS_SKU_DAILY`, при наличии статистики показов) +
  `cpo_expense_rub`. Двойного счёта нет: CPO-кампаний в `RAW_OZON_ADS_SKU_DAILY` нет (QA I2). Новой видимой колонки нет.
- Управляемая строка заметки той же ячейки: `CPC / attributed Ads: X / Оплата за заказ: Y / Итого: Z`. Движок ставит,
  заменяет и снимает только свою строку (узнаёт по форме); заметка владельца сохраняется дословно (тесты).
- ДРР (блок и магазин) берёт ту же ячейку → числитель = CPC + CPO на заказанном SKU. Маркетинговая эффективность по
  продвигаемому SKU — `V_OZON_ADS_CPO_PROMOTED_DAILY`. Магазинный P&L вычитает только остаток (фаза D покажет его в листе).
- Независимая QA плана: `ADS_IN_NOT_CPC_PLUS_CPO` (ячейка = CPC + CPO из фактов, не из сборщика).
- **Флаг `OZON_UNITKA_CPO`** (по умолчанию `0`): выключен — SQL фактов не упоминает `cpo_expense_rub` вовсе (новый образ
  работает и на вью до Phase B), CPO в лист не идёт, запись побайтно прежняя (тест); заметки читаются, и снимаются только
  управляемые строки разложения — откат флага не оставляет устаревших «Итого». Это и есть «стоп до записи боевого листа»: образ можно продвигать, загрузчик и вью —
  разворачивать, а лист меняется только после ACK владельца (`gcloud run jobs update ozon-unitka-prod
  --update-env-vars OZON_UNITKA_CPO=1`).

## 8. Выкат (порядок обязателен) и откат

Порядок задан зависимостями: вью читают таблицы Terraform, а новый образ Юнитки читает `cpo_expense_rub` из вью — поэтому
вью разворачиваются ДО образа (FCT поверх пустой RAW даёт `cpo_expense_rub = 0`, прежний образ хвостовую колонку не читает).

1. PR → CI (`ci`, `sql-current`) → слияние.
2. `infra.yml` **plan** с целями `ozon_cpo_orders.tf` + `terraform_apply_actas["ozon_cpo_loader"]` → сверка состава →
   **apply** (таблицы, SA, права, Job, Scheduler на паузе, алерт).
3. Вью: `python tools/ozon_cpo_views_deploy.py --project project-fa311fc0-4d87-4781-986 --token-command "gcloud auth
   print-access-token" --apply` (из слитого main; живые тела FCT и операционного слоя = тела отката — проверено 08.10).
4. `deploy-shadow` (сборка) → паритет образа → `deploy-prod` (тот же digest на все prod-Job'ы, включая новый). Флаг Юнитки
   выключен — лист не меняется.
5. Бэкфилл: `gcloud run jobs execute ozon-cpo-orders-prod --region europe-west1 --wait --task-timeout=3600s
   --update-env-vars OZON_CPO_BACKFILL_FROM=2025-05-01,OZON_CPO_BACKFILL_TO=<вчера МСК>`; затем один суточный прогон
   (перекрытие 45 суток — доказательство идемпотентности: строки и сумма не меняются). QA
   `sql/ozon/qa_cpo_orders_v1.sql` по живым объектам = PASS.
6. Read-only план записи Юнитки с `OZON_UNITKA_CPO=1` (запись перехвачена) → сверка двойного счёта и остатка → **STOP**.
7. После «OWNER ACK — APPLY OZON CPO UNITKA + HISTORICAL BACKFILL»: флаг `1` на `ozon-unitka-prod`; снять паузу Scheduler
   `ozon-cpo-orders-prod`; историю B — ограниченным манифестом.

**Откат** (обратный порядок): флаг `OZON_UNITKA_CPO=0` (лист вернётся к CPC штатным прогоном окна) → прежний образ на
prod-Job'ах → `tools/ozon_cpo_views_deploy.py --rollback --apply` (FCT и операционный слой — тела до изменения,
`sql/ozon/cpo_orders_2026-10-08/`; три новых вью остаются невостребованными) → пауза Scheduler. RAW и журнал не
удаляются (`deletion_protection`); удаление — отдельное решение. Новый образ на старых вью не работает (нет
`cpo_expense_rub`), поэтому образ откатывается раньше вью.

## 9. Безопасность и границы

- SA `sa-ozon-cpo-loader`: `dataEditor` только на 4 таблицы ozon_raw, `secretAccessor` только на 2 секрета Performance,
  `bigquery.jobUser`. Ни WB-датасетов, ни ozon_mart, ни ключа Seller API. `deployer` получает `actAs` только на этот SA
  (как на sa-loaders-prod); WIF-привязки не меняются (репозиторий публичный — проверено отдельно, см. PR).
- Образ Ozon runtime `24e3c6d6` и его Job'ы не трогаются. WB и Tenancy/client_001 не трогаются. Фазы C/D не начаты.
