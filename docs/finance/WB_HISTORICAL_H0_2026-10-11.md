## 1. Границы
- **P&L магазина**: исторический канонический слой — 2026-05..2026-07. Ранее — блокеры (реклама только по дате документа,

Формулы листа для истории — только сравнение. Из листа история берёт лишь ручной ввод «Внешняя реклама (блогеры,
самовыкупы)» (май −28 039 ₽), как и Phase C; поэтому окно снимка листа — с 2026-05 (`STORE_PNL_FROM`). Если последний
снимок начат позже 2026-05-01 (образ до H0 снимает с 2026-08), внешняя реклама истории НЕ читается как 0: месяц
`UNKNOWN_COST_PRESENT`, QA `HIST_INPUTS_COMPLETE` = FAIL. Снимок пишется в начале прогона, до чтения P&L, — прогон нового
образа сам закрывает это условие.

Защиты связок: nm → SKU и SKU × день → COGS сводятся к РОВНО одному значению (0 или >1 — себестоимость неизвестна, не 0) и
агрегируются до (сутки, nm) — размножения строк когорты нет по построению; дополнительно итог выручки и штук до и после
связок сверяется (`cohort_join_gap` > 0 → `UNKNOWN_COST_PRESENT`).

## 4. Себестоимость наборов
Две единицы проданы в день запуска набора раньше начала его интервала: `EVT-SET-TON-CREAM-ACNE` (01.05, интервал с 03.05)
и `EVT-SET-ACNE-TONIC-SERUM` (01.07, интервал с 09.07). Утверждено (ACK) сдвинуть `effective_from` строк состава BC-28/29
(05-03 → 05-01) и BC-30/31 (07-09 → 07-01); суммы не меняются (314,445 и 350,785 — проверено подстановкой в
`V_BUNDLE_COGS_DERIVED`). Инструмент `tools/cogs_bundle_start_fix.py`: PLAN по умолчанию (снимок «до», вычисленный снимок
«после», затронутые продажи = ровно 1 ед. на набор, отпечаток), APPLY — одна транзакция из 4 охраняемых UPDATE с
проверкой числа строк до COMMIT, только из слитого main и по отпечатку плана; ROLLBACK — по снимку «до». Снимок листа и
Executive V2 подхватят новые интервалы при пересборке. Сид `sql/ref/pr_ref_cogs_history.sql` обновлён теми же датами
(иначе повторный запуск сида откатил бы правку — прецедент `REF_COST_MAP`).

## 5. Налог 2 % и схема A:U
`management_tax_rub` — РАСШИФРОВКА налога, уже вычтенного внутри «Вклада SKU»: Phase C — Σ выкупы × налог на единицу листа
(август — наследие: от цены после СПП), история — 2 % от выручки по цене продавца. В чистую прибыль повторно не входит
(QA `TAX_NOT_DOUBLE_COUNTED`, тесты строки плана). Вкладка — 21 колонка A:U (18 по H0 + 3 колонки утраты товара), колонка D «Налог 2% (в составе вклада SKU)»;
заголовки и заметки ячеек — системный контракт в коде (`TAB_COLUMNS`, tabplan.ts), входят в отпечаток плана и в отпечаток
контракта `contractSha()`.

## 6. Управляемая миграция схемы (A:Q → A:U)
Публикатор хранит в developer metadata вкладки отпечаток содержимого и отпечаток контракта
(`evetis.store_pnl.contract_sha`). Если контракт во вкладке ≠ коду, публикация отказывает
(`STORE_PNL_CONTRACT_MIGRATION_REQUIRED`) — плановый прогон схему не мигрирует. Миграция — один ручной прогон с
`UNITKA_STORE_PNL_MIGRATE_CONTRACT = contractSha()` нового кода (по OWNER ACK), затем допуск удаляется. Запись —
один атомарный batchUpdate: значения A1:U, форматы строк данных, заметки 21 ячейки заголовка, два отпечатка;
перечитывание значений, отпечатков и заметок.

Порядок: выключить публикацию / пауза Scheduler → merge → `tools/unitka_store_pnl_h0_deploy.py --apply` (вью до образа) →
deploy-prod → правка наборов `tools/cogs_bundle_start_fix.py` → ближайшая публикация копии `sp_publish_unitka_cogs` (:50) →
QA `COGS_COVERAGE` = PASS → read-only preflight: точный план A:U → OWNER ACK → разовый прогон с допуском миграции →
обратное чтение → убрать допуск → включить публикацию и Scheduler.

Свойства миграции: при значениях, уже равных плану, прогон с допуском всё равно пишет (иначе отпечаток контракта не лёг бы и
перечитывание падало бы всегда); форматы строк данных A:U сначала сбрасываются (фон состояния из прежней P не переезжает в
маржу); нет колонки R в сетке — `appendDimension COLUMNS` в том же batchUpdate; ручная правка заметки заголовка
восстанавливается следующим прогоном (заметки сверяются каждый прогон).
