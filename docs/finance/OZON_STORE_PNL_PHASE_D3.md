# OZON STORE P&L — D3: управленческая чистая прибыль магазина Ozon (бэкенд)

Основание: OWNER ACK 2026-10-14 «EVETIS OZON D3 STORE P&L» (branch/PR only, без production). Проект и доказательства
(матрица покрытия 33 типов, проекция по месяцам, живые выгрузки) — `evetis-manifests/ozon-d3-blueprint-2026-10-13/` и
`evetis-manifests/ozon-d3-2026-10-14/` (вне Git: помесячные суммы в публичный репозиторий не кладутся).

## 1. Контракт

- Одна власть на месяц: `ozon_mart.V_OZON_STORE_PNL_MONTHLY`. Вкладка (D4) — только представление.
- **L1–L4 не переопределяются.** `FCT_OZON_PNL_MONTHLY`, `FCT_OZON_SKU_PNL_DAILY/MONTHLY` не меняются; L4 —
  справочная колонка `l4_fct_reference_rub` с явным мостом. Вторая финансовая система не создаётся: D3 читает тот же
  RAW, ту же карту SKU, ту же себестоимость и те же источники атрибуции, что FCT.
- Строится сверху вниз из леджера: каждая строка RAW финансов попадает ровно в одну колонку (карта
  `V_OZON_FINANCE_OPERATION_MAP`), экономический блок — в выручку (B) и комиссию (D).
- Два рекламных контракта не смешиваются: **биллинг** (финансовые начисления 41/75/33/54/47/96) уменьшает прибыль
  магазина; **атрибуция SKU** (`RAW_OZON_ADS_SKU_DAILY`, сопоставленный CPO) — только во вкладе SKU; разница — поправка AB.
- Расходы кабинета (ACCOUNT_LEVEL: 12, 77, 46, 76, 57, 52, 25) уменьшают прибыль магазина и **не распределяются** по SKU.
- Налоговый резерв 2 % — ровно один раз (W = 0,02 × B); провизорные единицы несут свой налог внутри X.
- Неизвестное ≠ ноль: тип вне карты → PENDING_CLASSIFICATION и блок публикации; доставлено без начисления → оценка X
  (PROVISIONAL) и состояние месяца, никогда не 0.

## 2. Даты (месяц P&L)

| date_basis | Что | Месяц |
|---|---|---|
| ORDER_MONTH | всё, что связано с отправлением: экономический блок, 32/29/28/98/30, 59/45/9/6, 1, 116/74/48, 39/38/10, сторно −1 | месяц заказа (сутки МСК `created_at`, как FCT) |
| BOOKING_MONTH | 78, 79, 15, 71, 47/96, 12/77/46/76/57, 25 | месяц начисления |
| SERVICE_DAY | CPC 41/75/33 | сутки услуги = начисления |
| CHARGE_DATE | 54 (CPO по CPO-кампаниям, CPC-кампании 2025-05…08) | дата списания |
| SERVICE_PERIOD | Premium 52 | дни периода `unit_number` (dd.mm.yy-dd.mm.yy, конец исключён), копейки наибольшим остатком |

Связь с отправлением: `posting_number` строки → `unit_number` как отправление → `unit_number` + sku как заказ.
Отправления заранее сводятся к одной дате на ключ, карта SKU — только однозначные соответствия: соединения не
размножают строк (Q04).

## 3. Колонки `V_OZON_STORE_PNL_MONTHLY`

Расходы положительны и вычитаются; выручка и компенсации — доход. Суммы без ROUND (как `FCT_OZON_SKU_PNL_DAILY`).

| | Колонка | Источник |
|---|---|---|
| B | `seller_base_revenue_rub` | Σ seller_base × количество экономических блоков (32/29/28 + −1 со знаком) + выкуп СНГ по документу |
| C | `product_cogs_rub` | `V_PRODUCT_COGS_EFFECTIVE` на дату заказа × проданные единицы; сторно не уменьшает (решение 12.10) |
| D | `commission_rub` | −Σ commission экономических блоков (сторно уменьшает) |
| E–K | логистика, последняя миля, обратная логистика, эквайринг, хранение SKU, продвижение SKU, прочие прямые | карта, §2 |
| L / M / N | CPC-биллинг, CPO-биллинг, реклама магазина 47/96 | карта; 54 → M, если кампания CPO (`RAW_OZON_ADS_CAMPAIGNS.payment_type`) |
| O–T | кросс-докинг, обработка, размещение FBO, страхование, прочие расходы Ozon, Premium | ACCOUNT_LEVEL |
| U | `marketplace_compensation_rub` | 25, доход |
| X | `provisional_open_rub` | `V_OZON_STORE_MONTH_STATE`, §5 |
| V | `store_contribution_pre_tax_rub` | B − C − D − E … − T + U + X |
| W | `management_tax_rub` | 0,02 × B |
| Y | `management_net_store_profit_rub` | V − W — **Management Net Store Profit** |
| Z | `management_net_store_margin` | Y ÷ (B + провизорная выручка) |
| AA | `sku_contribution_rub` | B − C − D − E … − K − атрибуция CPC − атрибуция CPO − W (как Юнитка) |
| AB | `ads_adjustment_rub` | атрибуция − (L + M + N); `unattributed_advertising_rub` = −AB |
| AC | `unattributed_account_net_rub` | U − (O + … + T); `account_level_expenses_rub` = O + … + T |
| AD/AE | `l4_fct_reference_rub`, `l4_bridge_rub` | L4 FCT и V − L4 = `delta_basis_rub` + `delta_premium_rub` + `l4_bridge_other_rub` |
| AF | `returned_units_cogs_not_reversed_rub` | COGS единиц сторно (справочно, не вычитается повторно и не сторнируется) |
| AG–AI | `financial_state`, `ads_attribution_state`, `source_freshness_state`, `month_closure_status` | §5 |

**Тождество I1:** Y = AA + AB + AC + X. Атрибуция сокращается, поэтому она не может войти дважды или потеряться;
налог — внутри AA и в Y = V − W, но не в AB/AC (Q17).

## 5. Состояния месяца (первое сработавшее)

Время — водяной знак финансов: по успешным загрузкам `finance_accrual` (`OZON_INGESTION_RUNS`, status OK, без кодов
контроля `OZON_FINANCE_*` в `error_message`) наибольшее из LEAST(`source_to`, сутки МСК завершения − 1) — поэтому
бэкфилл или перезагрузка старого окна водяной знак не двигают. Месяц закрыт, когда водяной знак ≥ конец месяца + 36
суток. Нет водяного знака — ни один месяц не закрыт (отказ в сторону «не окончательно»).

1. **PENDING_CLASSIFICATION** — строки детектора в месяце; публикация запрещена.
2. **PARTIAL_SOURCE_MISSING** — действующий известный дефект источника (реестр `known_defects`: месяц + код, без сумм:
   `D1_REVERSAL_NOT_LOADED` — 9 месяцев заказа плана ремонта D1, снимается сам, когда в месяце появились строки
   ремонта, в т. ч. частичного; `M2_SALE_AMOUNT_REPRESENTATION` — 2026-08); есть сутки начислений, последняя успешная
   загрузка которых несёт код контроля D1 (`OZON_FINANCE_ACCRUAL_QUARANTINED` / `OZON_FINANCE_CONTROL_MISMATCH`) — во
   **всех** месяцах, потому что месяц заказа пропавшего начисления из журнала не выводится; чистый перезапрос этих суток
   ворота снимает; загрузка с кодом и неразбираемым окном считается открытыми сутками; деньги без колонки или без
   отправления; COGS 0 или >1 интервала; SKU вне карты; **сильный признак незагруженного сторно** (у проданного
   отправления есть сбор за возврат 59/45/9, строки −1 нет); у оценки X нет входа (COGS, комиссия, логистика); после
   закрытия — доставлено без начисления / СНГ без документа / единицы в пути без начисления.
3. **UNPROVEN** — в месяце есть строки ремонта D1 (`ingestion_run_id` `ozd1-repair-*`) или **слабый признак сторно**
   (у проданного отправления только возврат эквайринга — так выглядит и частичная компенсация). Деньги не опровергнуты,
   но независимая сверка D0.5 не записана.
4. **PARTIAL_AWAITING_ACCRUALS** — месяц не закрыт и есть доставленные без начисления или единицы в пути.
5. **FINANCIAL_COMPLETE_WITH_TIMING_BRIDGE** — месяц не закрыт, остальные ворота PASS.
6. **FINANCIAL_COMPLETE**. Позднее начисление переоткрывает месяц: VIEW пересчитывается сам.

Детектор сторно сверен с планом ремонта D1 (вне Git): сильный признак находит 12 из 14 отправлений, вместе со слабым —
14 из 14, ложных — 1 (частичная компенсация, кандидат D0; отнесена к UNPROVEN, а не к пропаже денег). Детектор
остаётся сторожем на будущее; доказанные D1 месяцы держит реестр `known_defects`, поэтому месяц с известной пропажей
(в т. ч. найденный только слабым признаком) — PARTIAL_SOURCE_MISSING, а не UNPROVEN.

X (`provisional_open_rub`, PROVISIONAL): доставленные без экономического блока и без документа СНГ — выручка (цена
отправления × кол-во; для выкупа СНГ без документа — цена × минимальная доля выручки по документам СНГ) − комиссия
(цена × кол-во − выплата отправления: на всех 2 185 доставленных отправлениях с блоком начисления совпадает с комиссией
блока до копейки; `commission_amount_rub` отправлений пуст и не читается; у выкупа СНГ комиссии нет) − средняя логистика
SKU на единицу по начислениям − COGS − налог 2 %. Неизвестный вход не превращается в 0: месяц PARTIAL_SOURCE_MISSING.
Доставленное отправление с выплатой 0 считается выкупом СНГ без документа (сегодня так у всех 36 таких отправлений);
если статус «доставлено» придёт раньше выплаты, оценка открытого месяца временно пойдёт путём СНГ (выручка по
минимальной доле, комиссия и логистика 0) — направление ошибки X не определено, месяц открыт и PROVISIONAL.

`ads_attribution_state`: PARTIAL_ADS_UNAVAILABLE (сутки CPC-биллинга без SKU-статистики) → PROVISIONAL_OPEN (открытый
месяц) → SAFE_EXACT (|остаток CPC| ≤ 0,50 ₽) → PARTIAL_RESIDUAL. На прибыль магазина не влияет: меняет только
разложение AA ↔ AB. `source_freshness_state` — текущий статус `V_OZON_MART_FRESHNESS`.

## 8. Известные ограничения (раскрыты, не исправлены)

- **D1 не применён:** сторно реализации (−1) в RAW нет; 9 месяцев заказа — PARTIAL_SOURCE_MISSING (реестр). После
  слияния и выката D1 (отдельные ACK) и APPLY ремонта месяцы переходят в UNPROVEN до записи сверки D0.5.
- **UNPROVEN не снимается данными:** реестра доказательств D0.5 в BigQuery пока нет; его создание (таблица в `ozon_raw`) —
  отдельный шаг.
- **M2 (предел колонок, 2026-08)** в RAW не виден (хранится seller_price × количество, а не sale_amount): месяц держится в
  PARTIAL_SOURCE_MISSING реестром `known_defects` до PR загрузчика и перезагрузки.
- **D2 (CPC, окно МСК):** остатки CPC в AB/`ads_attribution_state` = PARTIAL_RESIDUAL; прибыль магазина (биллинг) верна.
- **Позднее начисление** в FINANCIAL_COMPLETE-месяце меняет суммы (VIEW), но отдельной колонки
  `late_restatement_rub` / флага LATE_ACCRUAL_RESTATEMENT нет — раскрытие поздних начислений остаётся follow-up.
- **PENDING_CLASSIFICATION** ставится на месяц; блокировка всей вкладки при любой строке детектора — гейт публикации D4.
- **`ads_attribution_state`** — упрощённый: без SAFE_BOUNDED_EDGE / PARTIAL_SYSTEMATIC чертежа, остаток CPO и прогоны
  CPO-отчёта (`OZON_CPO_ORDER_RUNS`) не учитывает; на прибыль магазина не влияет.
- **Слабый признак сторно** (ложное срабатывание — частичная компенсация) держит месяц в UNPROVEN до реестра D0.5.
- **X — оценка:** логистика — средняя по SKU за всю историю начислений; комиссия — из отправления; для выкупа СНГ без
  документа — нижняя граница доли выручки по документам.
- **Ручные входы Юнитки** (внешняя реклама, блогеры) не учитываются: снимка `OZON_UNITKA_MANUAL_INPUTS_DAILY` нет (D4).
- **Возвраты по количеству** (`/v1/returns/list`) не загружаются: количество возвратов — только из строк −1 после D1.
- Документальная сверка 2025-04…2026-04 с отчётами о реализации не выполнена (D5).
