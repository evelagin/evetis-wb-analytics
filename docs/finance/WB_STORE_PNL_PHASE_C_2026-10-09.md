# WB STORE P&L — Phase C (C1–C4): управленческая чистая прибыль магазина WB

OWNER ACK 2026-10-09 «PHASE C IMPLEMENTATION C1–C4». Доказательная база (read-only, до реализации) —
`WB_STORE_PNL_PHASE_C_EVIDENCE_2026-10-09.md`. Вкладка «WB Магазин P&L» этой фазой **не создаётся и не пишется**:
отдельное решение «OWNER ACK — CREATE/WRITE WB МАГАЗИН P&L».

## 1. Контракт

```
MANAGEMENT NET STORE PROFIT = Σ вклад SKU (лист Юнитки, как есть)
                            + поправки «представлено в SKU − факт площадки» (реклама, хранение, комиссия, цена)
                            + поправка созревшей когорты (логистика − вклад так и не проданных единиц; до созревания 0)
                            − затраты кабинета по МЕСЯЦУ УСЛУГИ (мин. платёж, утилизация, штрафы, транзит, приёмка, прочие)
                            + доходы кабинета (компенсации, возвраты авансов)
MANAGEMENT NET STORE MARGIN = прибыль ÷ выручка
```

Знак всех `*_adjustment_rub`: «+» увеличивает прибыль. «Управленческая», не бухгалтерская: COGS и налог 2 % —
управленческие, УСН 15 %, OPEX и фулфилмент не входят.

- **Реклама (FIN CONTRACT V2):** авторитет — биллинг WB по дате услуги (`V_DASH_FINANCE_CORRECTED_DAILY.ad_spend_financial_rub`);
  SKU несёт атрибуцию, магазин добавляет только разницу. Документы «WB Продвижение» — только сверка выплаты.
- **Выручка:** до созревания — выкупы листа по цене продавца, поправленной на факт; после — база финотчёта WB
  (`retail_price_withdisc × quantity`) по проданным единицам когорты.
- **Мост сроков (timing bridge):** пока когорта не созрела (FINAL-отчёты WB покрывают месяц + 46 суток), разница
  логистики и ожидаемый вклад непроданных единиц — только раскрытие, в прибыль не входят.
- **Окно:** с 2026-08 (вью и загрузчик). Раньше — наследие формул листа, оценочное хранение, LEGACY-слой финотчёта и
  неполный биллинг рекламы: такие месяцы этой моделью не считаются.

## 2. Р1 — месяц услуги

| Категория | Месяц услуги | Основание |
|---|---|---|
| Утилизация | из подписи «за <месяц> <год>» | `LABEL_PERIOD` |
| Остаток по минимальному платежу | предыдущий месяц проводки (13.08 → июль, 12.09 → август) | `INFERRED_PREVIOUS_MONTH` |
| Штрафы, транзит, приёмка, доходы | месяц проводки | `BOOKING_MONTH` |

Дата проводки (`booking_date`, `booking_month`) хранится рядом с `service_month` (`V_WB_STORE_ACCOUNT_LEDGER`).
Утилизация без «за <месяц> <год>» — `UNKNOWN` (месяц не закрывается молча).

Окно счетов месяца закрывается **по данным, не по календарю**: когда FINAL-отчёты WB покрывают месяц + 20 суток
(мин. платёж и утилизация проводятся ~10–13-го и попадают в недельный отчёт ~через неделю). Пока окно открыто и нет
счёта мин. платежа или утилизации — `PARTIAL_AWAITING_ACCOUNT_INVOICE`. **Правило +20 утверждено (OWNER ACK 09.10):**
отсутствующий счёт считается нулём, только когда FINAL-покрытие месяца полное, прошло 20 суток после конца месяца и счёта
за этот месяц услуги нет. Закрытие **не необратимо**: счёт, проведённый позже, ложится в свой месяц услуги, и P&L этого
месяца пересчитывается сам (вью считает кабинет по месяцу услуги при любой дате проводки; раскрытие —
`late_account_bookings` / `late_account_rub`; QA `LATE_INVOICE_RESTATEMENT`). В журнале три даты раздельно:
`service_month`, `source_operation_date` (= `booking_date`, дата операции в отчёте WB) и `report_date` (конец периода
отчёта WB, в котором строка пришла).

|---|---|---|---|---|---|

В каждой из 2 794 строк сумма возмещения погашена уменьшением вознаграждения WB до копеек (|Δ| ≤ 0,005 —
округление vw), к выплате 0, итоги отчёта WB (forPaySum и т. д.) их не содержат. Чистый эффект на деньги продавца —
0 → класс C, MEMO_NON_PNL (принято OWNER ACK 09.10). Раскрытие — `memo_reimbursement_rub`. QA `R2_REIMBURSEMENT_OFFSET`
проверяет это каждый раз. MEMO **не наследуется**: строка возмещения, не выполняющая тождество (|возмещение + vw + vwNds| >
0,01 ₽ или for_pay ≠ 0), — `PENDING_CLASSIFICATION` до доказательства (`V_WB_STORE_FINANCE_COVERAGE`, QA `R2_MEMO_ROW_GUARD`);
новая операция возмещения вне карты — NEW_FINANCE_OPERATION.

## 4. Карта операций финотчёта (C4)

`wb_mart.V_WB_FINANCE_OPERATION_MAP` — 22 утверждённые операции: DIRECT_SKU (продажа, возврат, логистика/доставка,
хранение и их коррекции, эквайринг), ACCOUNT_LEVEL (приёмка, штраф), BY_DEDUCTION_CLASS (удержание → класс
`V_WB_DEDUCTIONS_CLASSIFIED`; доходы кабинета — классы удержаний), MEMO_NON_PNL (3 возмещения), MEMO_ZERO (лояльность,
баллы за отзывы — денежных полей нет), PENDING_CLASSIFICATION (6 исторических операций, которые модель НЕ читает:
коррекция продаж и эквайринга, две компенсации, две операции лояльности). Утверждено только то, что модель читает:
появление компенсации ущерба (например, выплата по претензии) — разбор, а не молчаливо потерянный доход.
Операция вне карты → `V_WB_FINANCE_NEW_OPERATIONS` (NEW_FINANCE_OPERATION) → месяц `PENDING_CLASSIFICATION`,
загрузчик пишет `store_pnl_new_operations` (warn), QA FAIL.

## 5. Состояния месяца (порядок проверки)

0. `LEGACY_PARTIAL_KNOWN_DEFECTS` — месяцы до 2026-09 (август — только сравнение, OWNER ACK 09.10): известные дефекты
   Юнитки (отказы, оценочное хранение, формулы) Phase C не чинит, сумма справочная, месяц никогда не «закрыт»;
1. `UNKNOWN_COST_PRESENT` — неклассифицированное удержание (> 0,5 ₽); деньги когорты без SKU в листе; деньги
   утверждённых операций, которые модель не читает (`unconsumed_finance_rub`);
2. `PENDING_CLASSIFICATION` — операция вне карты или с классом PENDING в окне месяца (месяц + 20 суток проводки),
   в том числе с деньгами (их деньги — разбор, а не «неизвестный расход»);
3. `PARTIAL_AWAITING_ACCOUNT_INVOICE` — месяц ещё идёт в листе (или снимок отстал); окно счетов открыто и нет счёта
   мин. платежа или утилизации; FINAL-отчёты не покрывают все сутки месяца (пропавшая неделя видна); биллинг рекламы
   не финальный или отсутствует; источник счетов кабинета (`FACT_FINANCE`) расходится с финотчётом (отстал);
4. `FINANCIAL_COMPLETE_WITH_TIMING_BRIDGE` — всё выставлено, когорта дозревает;
5. `FINANCIAL_COMPLETE`.

Все флаги — по данным; NULL = «не закрыто» (`IFNULL(…, FALSE)`), календарь (`CURRENT_DATE`) не участвует.

## 6. Полнота и отсутствие двойного счёта (C2)

Независимое ревью (09.10) показало: тождество «сверху вниз» алгебраическое — оно доказывает, что ни одна поправка не
вошла в ФОРМУЛУ дважды и не выпала при правке вью, но не доказывает полноту ДАННЫХ. Поэтому оно оставлено как
`FORMULA_IDENTITY`, а полноту доказывают четыре независимые проверки:

| Проверка | Что доказывает | Где |
|---|---|---|
| Покрытие финотчёта | каждый рубль строки финотчёта в окне месяца прочитан моделью: нет операции без потребителя, когортной строки без srid / даты заказа / nm, денег в «чужом» поле | `V_WB_STORE_FINANCE_COVERAGE` → `unconsumed_finance_rub`, QA `FINANCE_COVERAGE` |
| Источники удержаний | классификатор удержаний (`FACT_FINANCE`) = удержания финотчёта по месяцу (месяц и следующий) | `deduction_source_gap_rub`, QA `DEDUCTION_SOURCE_RECONCILIATION` |
| Финансы без SKU | деньги когорты на сутки × nm, которых нет в снимке листа | `orphan_finance_*`, QA `ORPHAN_FINANCE` |
| Снимок = лист | по каждым суткам Σ W блоков = итог листа «Доходность (общая)», даты сводки совпадают, сутки месяца подряд | загрузчик (`parse.ts`), отказ `STORE_PNL_SHEET_ERROR` |

Расхождение покрытия, сиротские финансы или неклассифицированное удержание > 0,5 ₽ → `UNKNOWN_COST_PRESENT`; расхождение
источников удержаний → `PARTIAL_AWAITING_ACCOUNT_INVOICE` (обычно отставание `FACT_FINANCE`). Загрузчик также требует,
чтобы каждый месяц окна до месяца LCD был в листе.

**Перенос ACCOUNT_LEVEL → ALLOCATED_SKU (C5).** Мост «представлено в SKU − факт» нейтрален к переносу для статей,
у которых есть SKU-представление (реклама, хранение, логистика, комиссия). У статей кабинета (мин. платёж, утилизация,
штрафы, транзит) SKU-представления сейчас нет. C5 обязан вместе с распределением на SKU ввести поправку «SKU − факт»
для этой статьи в той же вью, иначе будет двойной счёт. Это требование к C5, а не свойство текущей вью.

## 10. Известные ограничения (раскрыты, не исправлены)

- Сутки, где продано больше, чем лист насчитал выкупов, при пустой цене листа: до созревания поправки цены и комиссии
  добавляют выплату без налога/COGS; после созревания `mature_cohort_adjustment` возвращает их. С 04.09 узко (заказы — из воронки).
- Права: лист — только чтение по OAuth-scope; `sa-loaders-prod` остаётся Редактором книги (нужен Engine). Таблица снимка
  «только добавление» — по коду загрузчика; `dataEditor` на таблице технически допускает удаление (как у соседних загрузчиков).
