# UNITKA Stage E4 — инцидент 14.09.2026 и доказательство синтаксиса

Свидетельство по первому production-прогону загрузчика платного хранения WB
(`wb-paid-storage-prod`) и по фиксу `c7ecc3f`. Документ фиксирует факты; решения
и план выката — в переписке с владельцем и в `docs/UNITKA_2_0_CHANGELOG.md`.

**TL;DR.** Дыра storage 10–13.09 закрыта, данные сверены с финансовым отчётом. Прогон
при этом завершился `ERROR`: запись прошла, а упал уже **post-write** QA из-за
зарезервированного слова в алиасе. Класс ошибки закрыт фиксом и доказан живым парсером
GoogleSQL. Семантика fail-closed исправлена: блокирующий QA переехал внутрь транзакции
до `COMMIT`.

## 3. Корневая причина

`StorageBq.qaWindow` собирал:

```sql
SELECT COUNT(*) AS rows, COUNT(DISTINCT date_msk) AS days, …
```

`ROWS` — зарезервированное слово GoogleSQL (оконная фраза `ROWS BETWEEN`), голым алиасом
недопустимо. Позиция сходится посимвольно: `SELECT COUNT(*) AS ` — 19 символов, `rows`
начинается с колонки 20, то есть `at [1:20]`.

Почему не поймали раньше: SQL лежит в шаблонной строке TypeScript — ни `tsc`, ни `eslint`
внутрь литерала не смотрят; прежние тесты покрывали только чистые функции (`storageWindow`,
`normalizePaidStorage`) и ни разу не конструировали `StorageBq`, хотя шов `bqClient` в
конструкторе для этого есть; парсера GoogleSQL в CI нет; теневого контура у загрузчика нет —
он `prodOnly` и вне prod падает с `STORAGE_PROD_ONLY`. Первым, кто разобрал запрос, стал
продовый BigQuery.

## 4. Фикс `c7ecc3f`

`fix(storage): E4 — SQL fix + fail-closed QA внутри транзакции до COMMIT`

1. **SQL.** `AS rows` → `AS row_count`. Контракт результата (`.rows`) сохранён, вызывающий
   код не менялся.
2. **Семантика fail-closed.** Блокирующий QA переехал внутрь той же транзакции:
   gate 1 (строки / окно / дни / сумма в stage) до `DELETE`; `DELETE + INSERT` строго по
   окну дат; gate 2 (строки / дни / сумма в target) после DML, но до `COMMIT`;
   `EXCEPTION WHEN ERROR THEN ROLLBACK TRANSACTION; RAISE`. Провал любой проверки
   откатывает окно — target остаётся в прежнем состоянии. Заполненный stage после отката
   нормален: следующий прогон перезапишет его `WRITE_TRUNCATE`.
   `qaWindow` остался пост-коммит телеметрией в `try/catch` — сбой замера больше не
   превращает успешную запись в `ERROR`.
3. Использованы `IF` / `RAISE`, а не `ASSERT`: базовые процедурные операторы с однозначным
   поведением внутри multi-statement transaction, плюс сообщение с ожидаемым и фактическим
   значением.
4. **Тесты** — `cloud/test/storage_bq_sql.test.ts`, 8 штук: отсутствие зарезервированных
   алиасов во всех запросах класса; все `RAISE`-гейты стоят до `COMMIT`, обработчик делает
   `ROLLBACK`; провал гейта до DML и после DML → нет `COMMIT`, target не изменён; успешный
   путь заменяет только `[start, end]`, строки 01–05 вне окна не тронуты; повтор того же
   окна идемпотентен. Негативный контроль пройден: с возвращённым `AS rows` тесты падают.
5. **`scheduler-control.yml`** — добавлен loader `wb-paid-storage` (prod-only; маппинг
   `wb-paid-storage` → `wb-paid-storage-prod`, имя Cloud Scheduler совпадает с именем Job).

Локально: lint PASS, typecheck PASS, **247 тестов PASS**, build PASS.

Не менялись: date-window policy, нормализация, экономика хранения, atomic window replacement,
`lookback = 8` для ежедневных прогонов, расписание 11:45 МСК, non-gating статус storage.

## 5. GOOGLESQL PARSER VALIDATION = PASS

Файл `e4_transaction_syntax_check.sql` (эта же папка) — точная копия продового скрипта
`StorageBq.replaceWindow` с реальными идентификаторами таблиц; проверено механически:
**все 39 значимых строк продового скрипта присутствуют в файле дословно**, отличие только
в заявленных подстановках (`@`-параметры → `DECLARE … DEFAULT` тех же типов).

**Результат проверки владельцем, 14.09.2026:**

| | |
|---|---|
| Что проверялось | **Часть A** файла `e4_transaction_syntax_check.sql` |
| Где | BigQuery Console, **location = EU** |
| Результат | Живой парсер GoogleSQL принял скрипт. Внизу редактора: `NOTE: Could not compute bytes processed estimate for script.` |
| Красные ошибки / `Syntax error` / `[line:column]` | **отсутствуют** |
| Кнопка Run | **не нажималась**; скрипт не исполнялся, данные не менялись |

Примечание про `Could not compute bytes processed estimate for script` — это штатное
поведение валидатора для multi-statement скриптов, а не ошибка: объём данных для скрипта
не оценивается заранее. Значим факт отсутствия синтаксической ошибки.

**Что этим доказано:** скрипт разбирается живым парсером GoogleSQL; имена столбцов
резолвятся в реальных таблицах; зарезервированных слов в роли алиасов нет.
**Класс ошибок `reserved alias / syntax`, который уронил `dxkt5`, закрыт.**

**Чего этим не доказано:** поведение транзакции в рантайме (изоляция, read-your-writes,
фактический откат) — это проверит только настоящий прогон; типизация query-параметров,
которую клиент задаёт в поле `types`; и что WB вернёт данные за запрошенное окно.

Файл защищён от исполнения тремя независимыми слоями (достаточно любого одного):
безусловный `RAISE` первым оператором до любой транзакции; недостижимые литералы
`p_expected_* = -1`, из-за которых первый же gate поднял бы ошибку до `DELETE`; оба DML
обёрнуты в `IF FALSE THEN … END IF` — парсер их разбирает, исполнение внутрь не заходит.

## 6. Что остаётся открытым

* PROD-образ ещё не содержит фикс — `wb-paid-storage-prod` продолжает работать на
  `sha256:4202c5c6…`. До промоушена **storage запускать нельзя**.
* Cloud Scheduler `wb-paid-storage-prod` остаётся **paused**.
* `LOADER_RUNS` для `logical_period = 2026-09-13` в статусе `ERROR`, поэтому guard
  (`isActive` блокирует только `COMMIT`-строки и свежий `STARTED`) повтор разрешает.
  Повтор ради данных не нужен — они корректны.
* Unitka Engine возобновлён; storage 10–13.09 уже виден в `V_WB_STORAGE_DAILY`, ближайший
  плановый прогон Engine сам запишет ожидаемые 96 ячеек (24 блока × 4 дня), для 10–12.09
  как правки закрытых дней.
* Архитектурное, вне рамок фикса: гарантия fail-closed теперь покрывает и стадию забора,
  и post-load QA, но откат выполняется обработчиком, а не проверен натурно.
