### 1.1 Признаю дефект формулировки в собственном probe

Итоговая строка `WbAdsProbeV4.gs` печатала: «для CPC кластерных ставок НЕТ». Это
глобальное утверждение из выборки в пять пар — ровно то, что аудитор снял пунктом 7.
Корректная формулировка: **в проверенных пяти CPC+manual парах `get-bids` не вернул
ни одной ставки при HTTP 200**.

Это третий раз, когда итоговая строка моего probe оказалась менее аккуратной, чем
разбор под ней: сначала «1 из 3» из-за зашитого порога, потом off-by-one в подписях
окон, теперь глобальный вывод из выборки. Разбор каждый раз был верным — врал именно
короткий вердикт. Вывод для себя: **строка вердикта должна цитировать наблюдение
и его границы, а не обобщать за пределы выборки.**

## 2. Ads-3 · окончательный дизайн

Цель одна: начать копить то, что невосстановимо. Ставка по кластеру истории не имеет —
она начинается с первого снимка.

### 2.1 🔴 Две поправки после чтения кода

Обе меняют мои же прежние рекомендации — сообщаю явно.

**Поправка 1: `WB_ADS_EXPECTED_SOURCES_` НЕ поднимать с 3 до 4.**
Раньше я предлагал добавить query-bids четвёртым элементом `results` и поднять
константу. Прочитав код, считаю это ошибкой.

`WbAdsDaily.gs:161-162` передаёт итоговый статус в `ingestFinalizeByStatus_`, а тот
кормит heartbeat-журнал, на котором стоит **freshness-гейт витрины**. Если query-bids
попадёт в `results`, то сбой нового некритичного источника уронит `overall` в ERROR →
heartbeat `ads` станет ERROR → **freshness-гейт может остановить ежедневную сборку
`MART_SKU_DAILY`**.

Витрина ставки по кластерам не потребляет. Делать её доступность зависимой от них —
создать ложную зависимость. Fail-closed должен применяться к тому, от чего потребитель
реально зависит.

**Решение:** `results` остаются тремя mart-критичными источниками, константа = 3.
Статус query-bids пишется отдельно — в `WB_ADS_STATUS` и в собственную run-log строку
(§2.4), и на `overall` не влияет.

**Поправка 2: 🔴 нельзя строить вью через существующий `makeView`.**
`WbAdsBigQuery.gs:257-268` делает `ROW_NUMBER() OVER (PARTITION BY <ключ>
ORDER BY load_ts DESC)` и оставляет `_rn = 1`. Если вызвать его так же, как для
остальных таблиц —

```js
makeView('V_ADV_QUERY_BIDS', 'RAW_WB_ADV_QUERY_BIDS', 'advert_id, nm_id, norm_query', null)
```

— вью оставит **по одной строке на ключ, то есть последний снимок**, и уничтожит ровно
ту историю, ради которой весь PR. Ловушка тихая: вью создастся, запросы отработают,
и обнаружится всё через месяц, когда истории не окажется.

🔴 **Ред. 3: добавления `snapshot_date` в ключ `makeView` НЕДОСТАТОЧНО.** Ред. 1
предлагала именно это — и ошибалась. Любой построчный дедуп, даже с `snapshot_date`
в ключе, канонизирует каждый `norm_query` независимо и потому смешивает снимки одного
дня (см. §2.8). `makeView` для этой таблицы не используется вообще; вью строится
отдельной функцией `wbAdsBqCreateQueryBidsView_`.

### 2.2 Схема `RAW_WB_ADV_QUERY_BIDS`

```
-- технические (как во всех RAW_WB_ADV_*)
load_ts              TIMESTAMP
run_id               STRING
source_method        STRING     -- 'adv/v0/normquery/get-bids'
processed_status     STRING     -- 'raw'
raw_json             STRING     -- элемент ответа целиком

-- снимок
snapshot_ts          TIMESTAMP  -- момент опроса, часть грейна
snapshot_date        DATE       -- партиция; дата снимка по Europe/Moscow

-- ключ
advert_id            INT64
nm_id                INT64
norm_query           STRING

-- ставка (configured query bid)
bid                  NUMERIC    -- ₽,      как отдал API
bid_kopecks          INT64      -- копейки, API отдаёт ОБА поля
currency             STRING     -- 'RUB'

-- контекст кампании на момент снимка (из справочника, не из get-bids)
payment_type         STRING     -- 'cpm' | 'cpc'
bid_type             STRING     -- 'manual' | 'unified'
campaign_status      INT64      -- 7 | 9 | 11
```

* **Грейн:** `run_id × snapshot_ts × advert_id × nm_id × norm_query`
  (`run_id` в грейне — см. §2.3: `snapshot_ts` один снимок не идентифицирует)
* **Партиционирование:** `snapshot_date` · **Кластеризация:** `advert_id, nm_id`
* **Вью `V_ADV_QUERY_BIDS`:** не дедуп, а выбор одного снимка на сутки целиком (§2.8)
* **Run-log:** отдельная таблица `RAW_WB_ADV_QUERY_BIDS_RUNS`, одна строка на прогон (§2.4)

🔴 **`payment_type` рядом со ставкой обязателен.** У CPC `bids_kopecks.search` = 12–55 ₽
(цена клика), у CPM — 130–590 ₽ (цена тысячи показов). Одно поле, разные единицы.
Без `payment_type` две модели смешаются в одной колонке и станут бессмысленными —
та же семья ошибок, что `cpm` ≠ ставка.

### 2.3 Идемпотентность

**Append-only. Никакого replace-slice, никакого DELETE по периоду.**

Это прямая противоположность `RAW_WB_ADV_SEARCH_CLUSTERS`, где replace-slice уместен
(статистика за период пересчитывается). Здесь перезапись вчерашнего снимка означала бы
потерю истории — того единственного, что PR создаёт.

🔴 **Идентичность снимка = `(snapshot_date, snapshot_ts, run_id)`, а НЕ один `snapshot_ts`.**
`snapshot_ts` имеет точность до секунды, поэтому сам по себе снимок не идентифицирует:
два execution, стартовавших в одну и ту же секунду (ручной запуск поверх триггера,
параллельный ретрай, повтор после таймаута), получат одинаковый `snapshot_ts` при разных
`run_id`. Настоящий ключ снимка — `run_id`: он уникален на execution. `snapshot_ts` несёт
время, `snapshot_date` — сутки. Все три поля пишутся в каждую строку снимка и в run-log.

| Сценарий | Поведение |
|---|---|
| Штатный суточный прогон | новые строки с новым `run_id` и своим `snapshot_ts` |
| Ретрай в те же сутки | ещё один снимок; вью выберет один целиком, RAW хранит оба |
| Повторный запуск вручную | то же; снимки различаются по `run_id` даже при равном `snapshot_ts` |
| Два запуска в одну секунду | разные `run_id` → два независимых снимка, не гибрид |
| Частичный сбой | записано то, что успело; статус `PARTIAL`, run-log покажет неполноту |

Таблицу добавить в allowlist `WB_ADS_BQ_TABLES_` (`WbAdsBigQuery.gs:46-52`) — иначе
`wbAdsBqAssertTable_` бросит «Запрещённая Ads BQ-таблица» (fail-closed работает).
То же для run-log таблицы `RAW_WB_ADV_QUERY_BIDS_RUNS`.

### 2.4 Run-log / наблюдаемость

Именно она, а не QC на объём, отличает «валидный пусто» от «лоадер не отработал».
Одна строка на прогон:

```
load_ts, run_id, source_method
snapshot_ts                 -- тот же, что в строках данных: связывает run с содержимым
snapshot_date               -- сутки снимка; вместе с run_id образует ключ снимка
requested_pairs             -- сколько пар отправлено
expected_batches            -- сколько запросов ТРЕБОВАЛОСЬ сделать
requested_batches           -- сколько запросов реально сделано (см. §2.5)
http_status                 -- код последнего/худшего ответа get-bids
http_success                -- 'TRUE'/'FALSE' по get-bids
returned_bid_rows           -- сколько строк ставок записано
distinct_pairs_with_bids    -- по скольким парам из запрошенных вернулись ставки
duration_ms
status                      -- OK | PARTIAL | EMPTY | FAILED | BLOCKED
error_message
```

`expected_batches` — не украшение: без него неполный прогон неотличим от полного.
Прогон, оборвавшийся по тайм-бюджету после первой удачной пачки, по всем остальным
полям выглядит успешным.

| Картина | Читается как |
|---|---|
| `requested>0`, `success=TRUE`, `returned=0`, `status=OK` | ✅ валидный пустой ответ — ставок нет |
| `requested=0`, `status=EMPTY` | ✅ валидный пустой scope — CPM+manual кампаний нет |
| `requested=0`, `status=FAILED` | 🔴 справочник не доехал (детали в `error_message`) |
| `status=PARTIAL` | 🔴 снимок неполон: пачки `get-bids` или пачки справочника |
| `success=FALSE` при `requested>0` | 🔴 сбой вызова `get-bids` |
| строки за сутки нет вовсе | 🔴 прогон не состоялся |

🔴 **`requested_pairs = 0` сам по себе не доказывает ни сбоя, ни пустоты** — он одинаково
получается и когда справочник не доехал, и когда CPM+manual кампаний действительно нет.
Различить их можно только по исходам самих вызовов `/promotion/count` и `/adverts`,
поэтому коллектор возвращает `countOk`, `idsFound`, `advBatchesTotal`, `advBatchesOk`,
а статус разводится на `EMPTY` и `FAILED`. Свести их обратно в один код нельзя: это либо
ложная тревога каждый день, когда CPM-кампании выключены, либо — что хуже — привычка
игнорировать статус и пропуск настоящего сбоя справочника.

Отдельный случай: **справочник неполон, а пар при этом ноль → `FAILED`, а не `EMPTY`.**
Непросмотренная пачка `/adverts` могла содержать CPM+manual, значит «пусто» не доказано.
Если пары есть, но часть пачек справочника не доехала, состав опрошенных пар заведомо
неполон → `PARTIAL`.

Без этих полей все перечисленные случаи выглядят одинаково — как отсутствие данных.

### 2.5 Batching

* API: **до 100 items** на запрос, rate limit `get-bids` **5 запросов/сек**.
* Текущий объём: **36 CPM+manual пар** → **один запрос в сутки**.
* Тем не менее чанкование заложить сразу, по 100, с паузой ≥ 250 мс между чанками —
  иначе рост числа кампаний однажды тихо упрётся в лимит.
* Запись в BQ идёт существующим путём `wbAdvRawAppendRows_`, батч NDJSON
  `WB_ADS_BQ_BATCH_ = 1000` (`WbAdsBigQuery.gs:43`) — трогать не нужно.

**Кого опрашивать:** пары `bid_type='manual' AND payment_type='cpm'` из свежего
справочника кампаний. CPC+manual (23 пары) в опрос **не включать** — по контракту v1.2
п. 3 они возвращают пусто; тратить на них запросы незачем. Если WB когда-нибудь начнёт
их отдавать, это обнаружится отдельной ре-проверкой, а не молча.

### 2.6 QC / acceptance gates

**Гейты прогона:**

| Гейт | Условие | Реакция |
|---|---|---|
| Справочник доехал | `countOk` и все пачки `/adverts` | иначе **FAILED** (см. §2.4) |
| Пары найдены | `requested_pairs > 0` | 0 при исправном справочнике → **EMPTY**, не ошибка |
| Все пачки `get-bids` сделаны | `requested_batches = expected_batches` | иначе **PARTIAL** |
| HTTP | 200 | ни одной удачной пачки → **FAILED**; часть → **PARTIAL** |
| Дубли в грейне внутри снимка | `COUNT(*) = COUNT(DISTINCT грейн)` | иначе **ERROR** |
| Согласованность единиц | `bid_kopecks = bid × 100` | расхождение → **WARN**, оба поля писать как есть |
| Run-log записан | строка ушла в `RAW_WB_ADV_QUERY_BIDS_RUNS` | иначе статус деградирует до **FAILED** |

Последний гейт неочевиден, но обязателен: run-log — это и есть контракт наблюдаемости.
Без него валидный пустой ответ неотличим от несостоявшегося прогона, то есть потеря лога
сама по себе делает снимок непригодным, каким бы удачным ни был вызов API.

Последний — детектор смены единиц. `spp_percent` уже трижды менял масштаб
([[wb-percent-fields-dimension]]); поймать это на первой же строке дешевле, чем через
полгода в отчёте.

🔴 **Чего гейтить НЕЛЬЗЯ:**

* **стабильность количества `norm_query`** — набор ключей меняется законно: WB
  переопределяет кластеры, владелец снимает и добавляет ставки, кампании
  останавливаются. Такой гейт давал бы ложные срабатывания на нормальной работе
  и приучал бы игнорировать красное;
* **пустой ответ** — валидный исход по контракту v1.2 (пп. 3, 4);
* **статус query-bids не должен влиять на `overall`** рекламного прогона (§2.1).

**Приёмка PR:**

1. Прогон записал run-log строку с `http_success = TRUE` и осмысленным `requested_pairs`.
2. `SELECT COUNT(*) FROM RAW_WB_ADV_QUERY_BIDS` > 0, грейн уникален.
3. **Через сутки — два разных `snapshot_date`, вчерашний снимок цел.**
   Это единственный настоящий тест: таблица должна **копить**, а не обновлять.
   Проверяется и на RAW, и на вью — вью обязана вернуть обе даты (§2.8).
5. Два прогона в одни сутки: вью возвращает строки **ровно одного** `run_id`,
   а не объединение. Ключ, снятый во втором прогоне, в вью не появляется (§2.8).
4. Отсутствие строк по каким-либо парам дефектом не считается.

### 2.7 Точное место вызова

Файл `apps-script/WbAdsDaily.gs`, функция `runWbAdsDaily()`.

```js
// три mart-критичных загрузчика — как сейчас:
results.push(loadWbAdsCampaignsRaw(runId));                    // DIM (дёшево)
results.push(loadWbAdsCostsRaw(rng.from, rng.to, runId));      // расходы (~сек)
results.push(loadWbAdsFullstatsRaw(rng.from, rng.to, runId));  // fullstats — последним

// ... расчёт overall, запись WB_ADS_STATUS ...
ingestFinalizeByStatus_(ingestRunIdAds, 'ads', overall, adsRowsTotal, adsRowsTotal, note);
heartbeatFinalized = true;   // ← дальше идёт ТОЛЬКО необязательная работа

// ← ВСТАВКА ЗДЕСЬ, СТРОГО ПОСЛЕ ingestFinalizeByStatus_.
var bidsResult = { source: 'raw_query_bids', status: 'SKIPPED', rows: 0, pairs: 0 };
try {
  if (typeof loadWbAdsQueryBidsRaw === 'function') {
    bidsResult = loadWbAdsQueryBidsRaw(runId) || bidsResult;
  }
} catch (eBids) { /* изолированный сбой, overall не трогаем */ }
```

🔴 **Почему после финализации heartbeat, а не до `overall`** (ред. 1 предлагала до — это
была ошибка): `try/catch` спасает от исключения, но **не** от жёсткого таймаута Apps
Script в 6 минут — тот убивает execution без всякого catch. Если бы Ads-3 стоял до
финализации и съел остаток бюджета, mart-критичный RAW был бы уже загружен, а heartbeat
`ads` остался бы незакрытым → freshness-гейт не увидел бы `COMPLETE` → сборка
`MART_SKU_DAILY` встала бы из-за необязательного источника. Теперь худший случай
таймаута здесь — отсутствие снимка ставок за день, и только это.

По той же причине в `catch` вызывающей функции стоит guard `if (!heartbeatFinalized)`:
после финализации catch не имеет права переписать успешный heartbeat в `ERROR` из-за
сбоя необязательной части — это остановило бы витрину ровно так же.

⚠️ **Список пар Ads-3 собирает своими вызовами `/adv/v1/promotion/count` и
`/api/advert/v2/adverts`, а не читает RAW, загруженный выше в этом же прогоне.** Это
дополнительные read-запросы, и состав пар может отличаться от загруженного справочника,
если кампании изменились между вызовами. Сделано намеренно: снимок ставок должен
опираться на состояние кампаний на момент снимка.

Сводка по ставкам уходит в `console.log` и в возвращаемое значение
(`query_bids: {status, rows, pairs}`), а **не** в `note` для `WB_ADS_STATUS`: `note`
формируется до финализации, и дописывать в него результат более поздней стадии значило
бы снова связать критичный путь с необязательным.

Константу `WB_ADS_EXPECTED_SOURCES_` (`WbAdsDaily.gs:32`) **не трогать**: `results`
по-прежнему три элемента, offline-самотест `wbAdsOverallStatus_` остаётся валидным.

### 2.8 Каноническая вью `V_ADV_QUERY_BIDS`

🔴 **Обычная дедуп-вью проекта (`makeView`) здесь не подходит принципиально.** Она
канонизирует каждый ключ независимо: дедуп по `(snapshot_date, advert_id, nm_id,
norm_query)` для ключа, у которого во втором прогоне дня ставка снята, подставит строку
из **первого** снимка. Получится гибрид — набор ставок, которого не существовало ни в
один момент времени. Для таблицы снимков это тихая порча данных.

Канонизация обязана быть **на уровне снимка**: выбрать один снимок за день и показать
строки только его, целиком.

```sql
WITH canon AS (                       -- один снимок на дату
  SELECT snapshot_date, snapshot_ts, run_id, status AS snapshot_status
  FROM (
    SELECT snapshot_date, snapshot_ts, run_id, status,
           ROW_NUMBER() OVER (
             PARTITION BY snapshot_date
             ORDER BY CASE status WHEN 'OK' THEN 0 WHEN 'PARTIAL' THEN 1 ELSE 2 END,
                      SAFE_CAST(snapshot_ts AS TIMESTAMP) DESC,
                      run_id DESC                       -- детерминированный тай-брейк
           ) AS _rn
    FROM RAW_WB_ADV_QUERY_BIDS_RUNS
    WHERE http_success = 'TRUE' AND status IN ('OK', 'PARTIAL')
  ) WHERE _rn = 1
)
SELECT * EXCEPT(_dup) FROM (
  SELECT b.*, c.snapshot_status,
         ROW_NUMBER() OVER (
           PARTITION BY b.run_id, b.snapshot_ts, b.advert_id, b.nm_id, b.norm_query
           ORDER BY b.load_ts DESC
         ) AS _dup
  FROM RAW_WB_ADV_QUERY_BIDS b
  JOIN canon c ON b.snapshot_date = c.snapshot_date
              AND b.snapshot_ts   = c.snapshot_ts
              AND b.run_id        = c.run_id            -- ключ снимка, а не только ts
  WHERE b.processed_status = 'raw'
) WHERE _dup = 1
```

Три решения, каждое из которых не косметическое:

1. **Источник выбора — run-log, а не сами данные.** У неуспешного прогона строк может
   не быть вовсе, и по данным его существование не восстановить.
2. **`run_id` в JOIN и во внутреннем дедупе.** Без него два execution одной секунды
   снова сливаются в гибрид (см. §2.3). Дедуп дублей строк допустим **только** внутри
   одного прогона, иначе он пересекает границу снимка.
3. **`snapshot_status` отдаётся наружу колонкой** — потребитель должен видеть, полон ли
   день, а не узнавать об этом из отдельной таблицы.

Приоритет `OK` над `PARTIAL` означает: полный снимок предпочитается неполному, даже если
неполный позже.

## 5. Ред. 1 → ред. 3: что нашёл аудит и почему это были дефекты

Пять из шести правок пришли от внешнего аудитора **до** коммита, на статическом чтении
кода. Записаны здесь не для отчётности, а потому что каждая — воспроизводимый класс
ошибки, а не опечатка.

| # | Дефект ред. 1 | Почему это дефект | Правка ред. 3 |
|---|---|---|---|
| BLOCKER 1 | Ads-3 вызывался **до** `ingestFinalizeByStatus_` | `try/catch` не ловит жёсткий таймаут Apps Script; необязательный источник мог оставить heartbeat незакрытым и остановить сборку витрины | Вызов перенесён строго после финализации + guard `heartbeatFinalized` в `catch` (§2.7) |
| BLOCKER 2 | Дедуп-вью по `(snapshot_date, advert_id, nm_id, norm_query)` | Канонизация каждого ключа независимо смешивает снимки: снятая ставка «воскресает» из более раннего снимка. Гибрид, которого не было ни в один момент | Канонизация на уровне снимка (§2.8) |
| BLOCKER 3 | Идентичность снимка по одному `snapshot_ts` | Точность до секунды: два execution одной секунды имеют разные `run_id`, но равный `ts` → снова гибрид | Ключ снимка `(snapshot_date, snapshot_ts, run_id)` (§2.3, §2.8) |
| BUG | Выход по тайм-бюджету не влиял на статус | Прогон, оборвавшийся после первой удачной пачки, получал `OK`; неполный снимок выглядел полным | `expected_batches` + `incomplete` → `PARTIAL` (§2.4, §2.6) |
| BUG | Сбой записи run-log оставлял статус `OK` | Потеря наблюдаемости делает снимок непригодным независимо от успеха API | Статус деградирует до `FAILED` (§2.6) |
| MINOR | `requested_pairs = 0` трактовался как сбой справочника | Валидное отсутствие CPM+manual кампаний давало бы ложную тревогу ежедневно → привычка игнорировать красное | Разведены `EMPTY` и `FAILED` по исходам вызовов (§2.4) |
| MINOR | Комментарий «пары из справочника этого прогона» | Коллектор делает **свои** вызовы `count`/`adverts`, а не читает RAW. Комментарий, описывающий систему неверными словами, — такой же дефект, как неверный код | Комментарий исправлен, следствие описано (§2.7) |

### 5.1 Как проверялись BLOCKER 2 и BLOCKER 3

Не рассуждением, а прогоном на синтетических данных в BigQuery (read-only, ничего не
создавалось). Данные: два прогона `ADS-A` и `ADS-B` с **одинаковым** `snapshot_ts` и
разными `run_id`, оба `OK`; в `ADS-A` есть ключ «снят» (777), в `ADS-B` его уже нет.

| Версия вью | Результат за 13.08 |
|---|---|
| Дедуп-вью ред. 1 (per-query) | 3 строки, включая «снят» из другого снимка — **гибрид** |
| Snapshot-level без `run_id` | 3 строки: «ключ А» 610 и «ключ Б» 620 из `ADS-B` + «снят» 777 из `ADS-A` — **гибрид** |
| Ред. 3 (`run_id` в JOIN и дедупе) | 2 строки, обе из `ADS-B`: «ключ А» 610, «ключ Б» 620 ✅ |

Во всех трёх случаях строка за 12.08 сохранилась — то есть исправление не достигнуто
ценой потери истории. Дефект воспроизводится на прежних версиях и не воспроизводится
на нынешней: это тест, а не аргумент.

### 5.2 Урок для метода

**Снимок и срез — разные сущности, и дедуп у них разный.** Для среза (статистика за
период) канонизация по бизнес-ключу верна. Для снимка канонизировать можно только
целиком: любая построчная канонизация конструирует состояние, которого не существовало.
Первое, что стоит спросить о новой RAW-таблице, — снимок это или срез.

**Идентификатор, у которого есть разрешающая способность, — не идентификатор.**
`snapshot_ts` с точностью до секунды выглядит уникальным ровно до дня, когда два запуска
попадут в одну секунду; дефект при этом проявится тихо, как странная ставка в отчёте.
