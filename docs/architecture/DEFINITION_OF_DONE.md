# Definition of Done, проверяемый машиной

Автономный агент останавливается не тогда, когда код запустился, а когда **каждая обязательная
проверка вернула ноль**. Этот файл — единственный источник того, что считать обязательным.

## Одна команда

```bash
python tools/verify_task.py --project <PROJECT> \
  --token-command "gcloud auth print-access-token" --task <имя-задачи>
```

Инструмент сам определяет, какие контракты обязательны: состав выводит
`tools/impact_analysis.py` из графа зависимостей по изменённым файлам, а не человек и не
модель. Он собирает шесть направлений и возвращает машинный вердикт:

| Направление | Значения |
|---|---|
| `REPOSITORY` | PASS · FAIL · BLOCKED |
| `SQL_VALIDATION` | PASS · FAIL · BLOCKED |
| `GIT_PROD_PARITY` | PASS · FAIL · PARTIAL · BLOCKED |
| `DATA_CONTRACTS` | PASS · FAIL · EMPTY · BLOCKED · NOT_APPLICABLE |
| `PIPELINE_HEALTH` | PASS · FAIL · UNKNOWN · BLOCKED |
| `REGRESSION` | PASS · FAIL · NOT_APPLICABLE |
| `UNRESOLVED_BUSINESS_RULES` | число открытых правил |

Вердикт: `PASS` (0) · `FAIL` (1) · `BLOCKED` (2) · `ERROR` (3). **`BLOCKED` — не успех.**
Он означает, что доказательство не получено: нет доступа, направление не покрыто, набор
вернул пустой результат или инструмент не запустился. Задача с `BLOCKED` не завершена —
разница с `FAIL` только в том, что чинить надо доказательство, а не код.

Артефакт прогона — `artifacts/verification/<задача>_<метка>/verification.json`; каталог
`artifacts/` не версионируется: он содержит значения данных.

Разделы ниже перечисляют то же самое по частям — они нужны, когда прогон надо разобрать
или выполнить вручную.

Правило: **при FAIL обязательной проверки задача не завершена.** Разрешён один путь —
исследовать → исправить → перезапустить. Объявить задачу готовой при красной обязательной
проверке нельзя ни при каких обстоятельствах, включая «проверка сломана» (тогда задача
превращается в починку проверки).

## 0. Предусловие сессии

| # | Проверка | Команда | Обязательна |
|---|---|---|---|
| S1 | Рабочее дерево чистое | `git status --porcelain` — пусто | да |
| S2 | Работа ведётся не на устаревшем `main` | `git fetch origin && git merge-base --is-ancestor origin/main HEAD` | да |
| S3 | Понятно, какая среда исполняет изменение | пять сред перечислены в `CURRENT_ARCHITECTURE.md` §2 | да (ревью) |

S2 существует потому, что локальный `main` отставал от `origin/main` на 40 коммитов: анализ
в таком дереве описывает систему, которой уже нет.

## 1. Код

| # | Проверка | Команда | Когда обязательна |
|---|---|---|---|
| C1 | Типы | `cd cloud && npm run typecheck` | изменения в `cloud/**` |
| C2 | Линт | `cd cloud && npm run lint` | изменения в `cloud/**` |
| C3 | Модульные тесты | `cd cloud && npm test` | изменения в `cloud/**` |
| C4 | Сборка образа | `cd cloud && npm run build && docker build .` | изменения в `cloud/**` |
| C5 | Компиляция и тесты Python | `python -m compileall -q …` + `pytest -q` | `services/**`, `pipelines/**` |
| C6 | Terraform | `terraform fmt -check -recursive` + `validate` | `infra/**` |
| C7 | Тесты инструментов | `pytest -q tools/tests` | `tools/**`, `sql/current/**`, `quality/**` |

Всё это уже исполняет CI (`.github/workflows/ci.yml`, `sql-current.yml`). Агент обязан
запустить их локально до открытия PR, а не полагаться на CI как на первый прогон.

## 2. Контракт SQL

| # | Проверка | Команда | Когда обязательна |
|---|---|---|---|
| Q1 | Канонический слой цел | `python tools/validate_current_sql.py` | любое изменение `sql/current/**` |
| Q2 | Нет нового `CREATE` канонического объекта вне `sql/current` | входит в Q1 (C17) | всегда |
| Q3 | Соответствие production (read-only) | `python tools/verify_current_sql_live.py --project … --token-command "gcloud auth print-access-token"` | перед и после развёртывания объекта |

Q3 требует явного токена и ничего не меняет. `UNPROVEN` никогда не считается за `MATCH`.

## 3. Данные

| # | Проверка | Команда | Когда обязательна |
|---|---|---|---|
| D1 | Ворота набора, покрывающего затронутую область | `python tools/run_data_checks.py --suite <имя> --project … --token-command "…"` | изменение любого объекта из `scope` набора |
| D0 | Какие наборы обязательны для этого изменения | `python tools/impact_analysis.py --git-diff origin/main` | всегда, до запуска ворот |
| D2 | Набор действительно исполним | `python tools/run_data_checks.py --suite <имя> --list` | изменение файлов проверок |
| D3 | Снимок инвентаря пересобран | `python tools/architecture_baseline.py --project … --with-gcloud && python tools/render_architecture_docs.py` | добавление/удаление объекта BigQuery, Job, расписания |

Коды выхода D1: `0` PASS · `1` FAIL · `2` EMPTY/UNPROVEN · `3` ошибка выполнения.
**Только 0 засчитывается.** Код 2 означает «проверка ничего не доказала» и разбирается так же,
как FAIL.

Что покрывает набор — в `quality/suites.json`; поадресный реестр проверок и граф
«объект → контракт → проверка → конвейер → потребитель» — в `quality/contract_registry.json`
(порождается `tools/build_contract_registry.py`). Наборы из `backlog` **не** ворота: пока
артефакт не подключён, изменения в его области не имеют автоматической защиты, и это должно
быть названо в отчёте прямым текстом, а не умолчено.

**Проверка, выведенная из ворот, обязана иметь доказательство.** Исключение
(`check_overrides` в реестре) объявляет статус — `superseded`, `stale_snapshot` или
`known_failing` — причину и ссылку на доказательство; исключение без доказательства роняет
тесты. Исключённая проверка продолжает исполняться, и её наблюдённый статус виден в отчёте:
молча выключенная проверка неотличима от несуществующей.

### Измерения, которые обязан покрывать набор-ворота

Список ниже — контракт на содержание набора, а не на конкретные пороги. Пороги берутся из
согласованного владельцем приёмочного документа; изобретать их при переносе запрещено.

- **зерно и уникальность** — ровно одна строка на объявленный ключ, ключ не NULL;
- **тождества** — заявленные в описании объекта равенства выполняются на всех строках;
- **сверка со старшим слоем** — суточное сходится с месячным, SKU-уровень с уровнем магазина;
- **контракт NULL** — NULL означает «не покрыто», а не «ноль»; где заявлен 0 — там 0;
- **идентичность** — каждый идентификатор площадки разрешается ровно в один `internal_sku`;
- **покрытие себестоимости** — у реализованной единицы есть COGS либо явно учтённое исключение;
- **непрерывность дат** — сутки, присутствующие в источнике, присутствуют в витрине;
- **свежесть** — отставание в пределах SLA конвейера из `OPS_PIPELINE_REGISTRY`.

## 6. Ворота владельца (не отменяются автоматикой)

Зелёные проверки разрешают **предложить** изменение, а не применить его. Отдельного решения
владельца требуют: любое изменение production-данных или DDL; `terraform apply`; смена
расписаний; развёртывание образов; изменение финансовой методологии; всё, что затрагивает
`services/wb-communications`; любое действие с правом записи во внешний маркетплейс.

Порядок остаётся: **аудит → дизайн → ACK владельца → реализация → валидация → STOP.**
Коммит и push — по разрешению.

---

## 7. Отчёт агента

Завершая задачу, агент сообщает: что проверено и чем (команда + код выхода), что **не**
покрыто проверками, какие допущения приняты, и что осталось владельцу. Утверждение «готово»
без кодов выхода не принимается.

## Runtime-доступ: обязательная предпроверка развёртывания

**Правило.** Любая миграция, добавляющая production-объекту зависимость на новый
датасет или таблицу, обязана ДО первой мутации доказать, что фактическая runtime
identity может эту зависимость прочитать. Проверка под правами владельца
недостаточна и не засчитывается.

**Почему правило существует.** UBR-012, 2026-09-22. Новое тело
`wb_mart.V_CT_ACTUAL_DAILY_LIVE` стало читать `ozon_mart.FCT_OZON_SKU_PNL_DAILY`.
Под правами владельца вью была полностью корректна: сверка сошлась по всей цепочке,
ворота 12/12, 11/11, 10/10 зелёные, паритет с Git подтверждён. Но плановая пересборка
исполняется `sa-ct-refresh`, у которого доступа к `ozon_mart` не было вовсе. Оба
последующих окна упали с `Access Denied`, и вместе с выручкой перестали обновляться
снимок остатков и очередь действий владельца. Ни одна существующая проверка этого не
увидела, потому что все они шли не от той личности.

**Машинная проверка.** `tools/check_runtime_access.py` сопоставляет датасеты, которые
упоминает тело объекта, с ACL этих датасетов для личности из
`quality/runtime_identities.json`. Только чтение. Ненулевой код выхода означает: объект
будет создан, но исполнитель его не прочитает — развёртывание не начинать.

```bash
python tools/check_runtime_access.py --project <PROJECT> \
  --token-command "gcloud auth print-access-token"
```

**Границы.** Инструмент видит доступ уровня датасета. Права уровня таблицы и
authorized views он не разбирает — если проект перейдёт на table-level модель,
проверку нужно расширить, а не считать её ответ достаточным.
