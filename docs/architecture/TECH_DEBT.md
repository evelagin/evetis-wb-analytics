# Технический долг

**Измерено:** 2026-09-21 против production и `origin/main` = `821a45e`. Каждый пункт содержит
проверяемое число или команду, которой он подтверждается. Пункты без доказательства сюда не
попадают: список долга, в котором есть догадки, перестаёт быть основанием для приоритетов.

Приоритет: **P1** — отсутствие контроля над production или необратимая потеря данных;
**P2** — замедляет разработку и повышает шанс ошибки; **P3** — гигиена.

## P1-1. 136 из 150 вью не имеют канонического Git-определения

**Доказательство:** `system_inventory.json` → `summary.views_without_canonical_sql = 136`.
Канонический слой `sql/current` покрывает `ozon_mart` (13) и `evetis_mart` (1).

**Почему это долг.** Production уже дважды опережал репозиторий (`REF_COST_MAP`,
`V_PRODUCT_COGS_EFFECTIVE`), и оба раза расхождение нашли случайно. Для 136 объектов сегодня
нет ни одного механизма, который заметит правку в BigQuery мимо Git. Автономный агент, которому
поручено «поправить вью», будет читать историческую миграцию и не узнает, что живое тело другое.

**Что делать.** Расширять `sql/current` датасет за датасетом по порядку из
[`MIGRATION_PLAN.md`](MIGRATION_PLAN.md). Инструменты уже есть, недостаёт записей политики
`EXTERNAL_DATASET_POLICY` и снятых тел.

**Риск действия:** низкий — снятие тел и запись в Git ничего не меняют в production.

## P1-2. Apps Script грузит production WB и не проходит ни одной автоматической проверки

**Доказательство:** 108 файлов `.gs`; ни один workflow в `.github/workflows/**` не содержит
пути `apps-script/**`. Развёртывание — через браузерный редактор.

**Почему это долг.** Заказы, продажи, финансы, реклама, остатки WB — то есть весь вход
критичных данных — меняются без тестов, без ревью в CI и без доказуемой связи развёрнутого кода
с коммитом. Каденс триггеров нигде не объявлен декларативно: реестр честно пишет
`cadence_definition_source = CODE`, а у `orders` — прямо `UNKNOWN`.

**Что делать.** Не переписывать. Сначала — сделать проверяемым: линт и офлайн-тесты чистых
функций в CI, `clasp` pull в CI для сверки развёрнутого с Git, объявление триггеров в одном
месте. Перенос в Cloud Run — отдельное решение с параллельной сверкой, а не часть этой работы.

## P1-3. Наблюдаемость покрывает 5 конвейеров из 16, Ozon — ноль

**Доказательство:**

```sql
SELECT r.pipeline_id, r.criticality,
       IF(c.pipeline_id IS NULL, 'NO_CHECK', 'covered') coverage
FROM `wb_ops.OPS_PIPELINE_REGISTRY` r
LEFT JOIN (SELECT DISTINCT SPLIT(scope_id,'/')[OFFSET(0)] pipeline_id
           FROM `wb_ops.OPS_HEALTH_STATE` WHERE scope='PIPELINE_CHECK') c USING (pipeline_id);
-- NO_CHECK: 11 из 16, включая CRITICAL orders и sales
```

Ozon в реестре отсутствует полностью, хотя грузит 11 сущностей ежедневно и ведёт
`ozon_raw.OZON_INGESTION_RUNS`.

**Почему это долг.** `orders` и `sales` объявлены CRITICAL и при этом не проверяются ничем.
Молчание системы сегодня не означает, что она здорова, — оно означает, что её никто не спросил.

## P1-4. Приёмочные проверки данных — мёртвый актив

**Доказательство:** 25 файлов `sql/**/*validation*.sql`; контракт `-- @check`, пригодный для
автоматического прогона, соблюдает **один** — `sql/scale1/fact_sku_daily_validation.sql`.
Остальные 24 перечислены в `quality/suites.json` → `backlog.files`.

**Почему это долг.** Каждый такой файл — уже написанная, уже согласованная владельцем проверка
экономики, которую прогнали один раз при сдаче этапа и больше никогда. Регрессия витрины,
которую они бы поймали, сегодня обнаруживается глазами на дашборде.

**Что сделано:** исполнитель `tools/run_data_checks.py` и реестр `quality/suites.json`;
набор `ozon_unit` переведён в ворота (11 проверок, прогон против production — PASS).
**Что осталось:** перевести остальные 24 файла, каждый — с подтверждением, что порог
согласован владельцем, а не придуман при переносе.

## P2-1. Локальное рабочее дерево отстаёт от `origin/main` на 40 коммитов

**Доказательство:** `git rev-list --left-right --count HEAD...origin/main` → `0 40`
на 2026-09-21 в основном рабочем каталоге репозитория (не в worktree).

**Почему это долг.** Любая сессия, начатая в этом каталоге без `fetch`, будет анализировать
систему, которой уже нет: `sql/current`, валидатор, CI `sql-current`, Unitka Fin Integrity и
SCALE 1 в нём отсутствуют. Это прямой путь к «починке» уже починенного и к конфликтующим PR.

**Что делать.** Работать из worktree от `origin/main`; проверку «HEAD достижим из origin/main»
внести в Definition of Done (сделано — см. [`DEFINITION_OF_DONE.md`](DEFINITION_OF_DONE.md)).

## P2-2. 21 git worktree и ~60 веток

**Доказательство:** `git worktree list` → 21 запись; большинство указывает на уже слитые ветки
(`r2a`, `r2b`, `r2c`, `r2d*`, `scale1`, `unitka-*`).

**Почему это долг.** Каждый worktree — отдельная копия дерева, в которой может незаметно
продолжаться работа; при разборе истории они создают ложное впечатление незавершённых работ.

**Что делать.** Удалить worktrees слитых веток (`git worktree remove`), оставить активные.
Действие обратимое (ветки остаются), но выполняет его владелец: в каталоге могут лежать
незакоммиченные файлы.

## P2-3. Расписание живёт в трёх несогласованных местах

Cloud Scheduler (Terraform), триггеры Apps Script (код) и `cadence_spec` в реестре конвейеров
заполняются независимо. Реестр это честно помечает (`runtime_verification_status` =
`VERIFIED` / `PARTIAL` / `NOT_VERIFIED`), но согласование ручное: у `orders`
`cadence_type = UNKNOWN`, и конвейер исключён из детектора пропущенных прогонов.

**Что делать.** Сделать реестр производным: сверять `cadence_spec` с фактическим Cloud Scheduler
и с наблюдёнными прогонами автоматически, а не заполнять руками.
