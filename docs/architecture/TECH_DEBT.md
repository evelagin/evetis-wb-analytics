## P1-1. 136 из 150 вью не имеют канонического Git-определения

**Доказательство:** `system_inventory.json` → `summary.views_without_canonical_sql = 136`.
Канонический слой `sql/current` покрывает `ozon_mart` (13) и `evetis_mart` (1).

поручено «поправить вью», будет читать историческую миграцию и не узнает, что живое тело другое.

**Что делать.** Расширять `sql/current` датасет за датасетом по порядку из
[`MIGRATION_PLAN.md`](MIGRATION_PLAN.md). Инструменты уже есть, недостаёт записей политики
`EXTERNAL_DATASET_POLICY` и снятых тел.

**Риск действия:** низкий — снятие тел и запись в Git ничего не меняют в production.

## P1-3. Наблюдаемость: закрыто по CRITICAL 2026-09-22, остаётся 9 конвейеров

**Доказательство:**

```sql
SELECT r.pipeline_id, r.criticality,
       IF(c.pipeline_id IS NULL, 'NO_CHECK', 'covered') coverage
FROM `wb_ops.OPS_PIPELINE_REGISTRY` r
LEFT JOIN (SELECT DISTINCT SPLIT(scope_id,'/')[OFFSET(0)] pipeline_id
           FROM `wb_ops.OPS_HEALTH_STATE` WHERE scope='PIPELINE_CHECK') c USING (pipeline_id);
-- NO_CHECK: 11 из 16 зарегистрированных (10 из 15 включённых), среди них CRITICAL orders и sales
```

Ozon в реестре отсутствовал полностью, хотя грузит 11 сущностей ежедневно.

**Почему это было долгом.** `orders` и `sales` объявлены CRITICAL и не проверялись ничем.
Молчание системы не означает, что она здорова, — оно означает, что её никто не спросил.

**Состояние после миграции 2026-09-22:** покрыто 18 конвейеров из 27, CRITICAL без проверки —
**0**, Ozon зарегистрирован (11 конвейеров, 21 проверка), различных проверок 7 → 31.

**Что осталось долгом:** 9 конвейеров без проверки, из них четыре снимочных с невосстановимым
пропуском; доставки оповещений нет; у новой процедуры нет расписания.

## P2-5. Performance API Ozon: границы суток и окна длиннее 62 суток (Tenancy T2, решение A4)

Отложено из T1/T2 решением владельца 2026-09-24. В T1/T2 не блокирует ничего.

- **Как сейчас.** `ads_sku_daily` заказывает асинхронный отчёт одним запросом на всё окно:
  `from = d0T00:00:00Z`, `to = d1T00:00:00Z`. Это UTC-моменты. Покрыт интервал
  `[d0 03:00 МСК, d1 03:00 МСК)`.
- **Как агрегирует Ozon.** Колонка «День» в отчёте — московские сутки. Поэтому первые три
  часа суток `d0` в окно не попадают, а сутки `d1` приходят только за 00:00–03:00.
  Замер EVETIS: UTC-окно 311,54 ₽ / 38 кликов против 359,22 ₽ / 44 кликов для
  МСК-окна по той же кампании и тем же суткам. Самые старые сутки окна при последнем
  пересчёте каждый раз теряют ночь.
- **Лимит.** Документация `POST /api/client/statistics` ограничивает `from/to` 62 днями.
  Окно длиннее отдаёт ноль строк при HTTP 200, то есть молча.
- **Почему наивное дробление опасно.**
  - Части по датам (`[a,b]`, `[b+1,c]` с текущими границами) оставляют разрыв около 24 часов
    на каждом стыке.
  - Части по моментам (`[a,b]`, `[b,c]`) кладут одни сутки в два отчёта. Получаются две
    частичные строки с ключом `(date, campaign_id, sku)`, и `merge_rows` падает с
    `MergeKeyConflictError` (или суммы расходятся, если слить иначе).
- **Неизвестно.** `dateFrom/dateTo` (формат `ГГГГ-ММ-ДД`) — альтернатива `from/to`, но
  документация не говорит, в каком поясе эти сутки.
- **Что нужно до исправления.**
  1. Живая проба, только чтение: одна кампания и одни сутки тремя способами — UTC-моменты,
     МСК-моменты, `dateFrom/dateTo`. Сверить с `/api/client/statistics/expense` и
     начислениями типов 41/54.
  2. Решение владельца о семантике.
  3. Паритетный прогон EVETIS: суммы `RAW_OZON_ADS_SKU_DAILY` до и после за общее окно,
     ожидаемое изменение — только на граничных сутках, в пользу полноты.
  4. Затем дробление окна по МСК-суткам.
- **Защита сейчас.** `STRICT_PAGE_CAPS=1` отвергает окно длиннее 62 суток до первого запроса.
  Поведение EVETIS не изменено.

## P2-6. Партия из одной кампании в отчёте Performance теряется молча (решение A5)

Отложено решением владельца 2026-09-24. Поведение EVETIS не менялось.

- `ads_sku_daily` разбирает ответ `GET /api/client/statistics/report` только как ZIP.
- Ozon отдаёт ZIP лишь для нескольких кампаний. Для одной кампании ответ — `text/csv`
  (документация метода).
- Партия из одной кампании (активных кампаний `N`, где `N mod 10 = 1`) падает в
  `except: continue`. Её строки не загружаются, а статус прогона — `OK`.
- Строгий режим (`STRICT_PAGE_CAPS=1`) ловит это как отказ. Суточный прогон EVETIS — нет.
- **Исправление:** разбирать и CSV по `Content-Type` или по отсутствию сигнатуры ZIP.
  Затем паритетный прогон EVETIS: строк станет больше ровно на потерянные партии.

## P2-8. Предохранитель журнала Ozon runtime: слабые места ревью PR #171 (L3, L4, L7, L8)

**Закрыто в T2.2 (ветка `feat/tenancy-t22-runtime-hardening`), доказательства — тестами.**
Образ с изменениями T2/T2.2 по-прежнему не выкачен; его выкат — отдельное решение владельца.

- **L3.** Сбой записи `OZON_INGESTION_RUNS` при обработке ошибки сущности больше не
  выпускает в stderr неявную цепочку с сырым текстом. Вместо неё — `JournalWriteError`:
  очищенная сводка обеих ошибок, поток управления прежний. Все необработанные исключения
  идут через `safe_excepthook`: трассировка сохраняется, секреты вырезаются.
  Воспроизведено до исправления: `test_l3_*` падают на runtime `main` ae61a0c.
- **L4.** СЕКРЕТЫ — Api-Key, client_secret, токен Performance. ИДЕНТИФИКАТОРЫ — client_id
  Performance API и Client-Id Seller API; они не вырезаются. Основания у них разные:
  - для OAuth client_id RFC 6749 §2.2 прямо говорит «The client identifier is not a secret»;
  - документация Ozon требует Client-Id вместе с Api-Key, но о его конфиденциальности
    прямо не говорит; идентификатор он — по **классификации платформы**, а не по
    утверждению Ozon.

  Событие больше не подавляется целиком: вырезается только значение секрета.
- **L7.** Вырезание идёт по структурированным значениям ДО сериализации, по всем
  экранированным формам (JSON, repr, unicode_escape, до трёх уровней вложенности,
  URL-кодирование). Поиск по готовой строке остался только страховкой.
- **L8.** Различающий прогон — в репозитории и в CI (`ci / ozon`):
  `pipelines/ozon/tests/test_differential_compat.py` против замороженного эталона до T2
  (`compat/baseline_pre_t2` — историческое тестовое доказательство, не исполняемый код; sha256 и git blob id в `PROVENANCE.json`). 14 сценариев, 2 перечисленные
  разрешённые разницы (D1 — вырезание секретов, D2 — вывод сбоя журнала).
- **Сверх находок.** Обрезка недоверенного текста до вырезания оставляла фрагмент ключа
  на границе. Это касалось `_request`, `promo`, `_drop_staging`, составов поставок и SQL
  манифеста акций. Теперь везде сначала вырезание, потом обрезка (`safe_error_text`).

**Решение владельца о выкате (2026-09-24).** Сначала слияние T2.2. T3 может идти на
синтетической инфраструктуре без выката нового runtime на EVETIS. EVETIS остаётся на
production-образе `sha256:24e3c6d6…` до отдельных ворот выката runtime. T3 может собирать новый
образ или ссылаться на него только после собственных ворот. В T2.2 никаких действий по
развёртыванию нет.

**Остаточные риски (не закрыты, приняты):** не узнаются записи секрета вне набора
экранирований — base64, hex, смена регистра, другая форма нормализации Юникода. Ozon не
возвращает ключи в таких формах. Идентификаторы (Client-Id) могут попасть в журнал — это
принятая классификация, а не утечка.

**Закрыто в T2.1 (ветка `feat/tenancy-t21-hardening`):**
- L1 — скрытый `tenant.json` в `_schema/`;
- L2 — повторяющиеся ключи JSON;
- L5 — неполное совпадение строк (`$` перед `\n`);
- L6 — неоднозначный суффикс ID проекта; грамматика заменена и заморожена (ADR-08);
- I1 — `schema_version: true` и `1.0`.

Контрольные цифры до и после — паритет AIE `ref28_*` против `V_ADS_SKU_ECONOMIC_LIMITS`
(проверка `AIE_E02`) и распределение завышения из Addendum.
