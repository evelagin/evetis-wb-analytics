# Канонический слой: классификация и измеренная граница расширения

**Измерено 2026-09-21.** Машиночитаемая классификация — [`../../quality/view_tiers.json`](../../quality/view_tiers.json),
правила — `tools/impact_analysis.py` (`TIER_RULES`), пересчёт — `python tools/impact_analysis.py --tiers`.

## 1. Зачем тиры, а не веса

Числовой вес («критичность × потребители × финансовая значимость») выглядит объективно, но
каждый коэффициент в нём — скрытое бизнес-решение, принятое инженером. Поэтому применяется
детерминированное правило принадлежности: объект либо удовлетворяет условию тира, либо нет.

| Тир | Правило | Вью |
|---|---|---:|
| TIER 0 | объект входит в `scope` набора с `severity = CRITICAL`, **либо** это витринный/дашбордный объект, который читает Metabase | 20 |
| TIER 1 | прямая зависимость объекта TIER 0 | 11 |
| TIER 2 | остальные вью витрин (`*_mart`) | 58 |
| TIER 3 | вью RAW, операционные и листовые контракты | 61 |

«Читает Metabase» — не предположение: карта потребления снимается из
`INFORMATION_SCHEMA.JOBS_BY_PROJECT` за 30 суток и лежит в `system_inventory.json`
(`objects[].external_readers`).

## 3. Почему `wb_mart` не канонизирован: измеренная граница контракта

Попытка снять 18 вью `wb_mart` выполнена и разобрана до конца. Инструмент —
`tools/capture_canonical_sql.py` (только чтение; тело, схема и описание берутся
`tables.get`, хеши считаются функцией валидатора, второй реализации `canonical_hash_v1`
в репозитории нет). Результат:

| Причина отказа | Объектов | Что это значит |
|---|---:|---|
| **C12: ссылка на объект своего датасета, который не является каноническим** | 14 | главный блокер, см. ниже |
| C17: исторические миграции определяют тот же объект | 8 файлов | лечится внесением в `historical_definitions.json` |
| C13: вью читает `ozon_raw` | 2 | нарушение изоляции маркетплейсов, см. §4 |
| C12: ссылка не полностью квалифицирована (`wb_raw.X` без проекта) | 2 | дефект самого production-SQL |
| У объекта нет `OPTIONS(description)` | 52 из 70 | контракт требует описание |

**Главный блокер сформулирован точно.** Проверка C12 требует, чтобы каждая ссылка на объект
того же датасета сама была каноническим объектом. В `ozon_mart` это выполнимо: там 13 вью и
**ноль базовых таблиц**. В `wb_mart` 27 базовых таблиц (`FACT_FINANCE`, `MART_SKU_DAILY`,
`EXECUTIVE_V2_DAILY`, …), и почти каждое вью читает хотя бы одну. Канонический слой в
редакции R2A/R2B описывает **только вью** — значит, в нынешнем виде он не масштабируется за
пределы датасета, состоящего из одних вью.

Измерение: вью `wb_mart`, у которых вся внутридатасетная цепочка состоит из вью **и** у всех
звеньев есть описание, — **3 объекта**, все TIER 2, и один из них дополнительно нарушает C12
по квалификации. Канонизировать два второстепенных вью значит увеличить сложность, не
увеличив взвешенное по риску покрытие. Поэтому снятие отменено, каталог `sql/current/wb_mart`
удалён, `validate_current_sql.py` снова зелёный.

### Два варианта расширения контракта (решение владельца)

**Вариант A — объявляемые табличные зависимости.** Разрешить манифесту перечислять
внутридатасетные зависимости-таблицы отдельным полем `internal_table_dependencies`. Тип
объекта известен на снятии (`tables.get` его отдаёт), поэтому поле заполняется фактом, а не
обещанием. C12 тогда требует канонического статуса только от вью.
*Плюс:* минимальное изменение, открывает 42 вью `wb_mart` сразу. *Минус:* офлайн CI не может
подтвердить, что объявленная зависимость действительно таблица — доказывает это R2C.

**Вариант B — канонизировать и таблицы.** Описывать `CREATE TABLE` в `sql/current`.
*Плюс:* полный охват. *Минус:* каноническое определение таблицы не равно её содержимому,
а `CREATE OR REPLACE TABLE` в слое запрещён правилом 2 — придётся вводить отдельный
тип объекта «таблица, определение только для сверки схемы».

**Рекомендация: A.** Он решает измеренную задачу и не вводит объект, который нельзя
безопасно применить.

Отдельно от обоих вариантов остаётся требование описания: 52 вью `wb_mart` его не имеют.
Честный путь — разрешить `null` для `sync_state = captured_live` (описываем production
таким, какой он есть) и сохранить обязательность для `pending_deploy` (новая работа обязана
документироваться). Выдумывать описание при снятии нельзя: канон разошёлся бы с production
по хешу описания в момент записи.

## 4. Найдено попутно: нарушение изоляции маркетплейсов

Шесть вью в `wb_mart` читают `ozon_raw` напрямую — 11 ссылок:

`V_CT_ACTUAL_DAILY_LIVE`, `V_CT_BUNDLE_STATUS`, `V_CT_FRESHNESS`, `V_CT_INVENTORY_TRUTH_LIVE`,
`V_CT_PLAN_VS_ACTUAL_DAILY`, `V_CT_SUPPLY_FLOW`.

Это Control Tower — он по замыслу межплощадочный, но живёт в датасете одной площадки.
Политика `EXTERNAL_DATASET_POLICY["wb_mart"] = {wb_raw, wb_ops, evetis_ref}` введена в
Phase 2 как **ревью-решение** и намеренно не содержит `ozon_*`: перечислить его значило бы
узаконить нарушение инварианта ради удобства снятия.

Следствие записано прямо: эти шесть вью не войдут в канонический слой, пока не переедут в
нейтральный датасет (`evetis_mart` или `evetis_ops`). Переезд — отдельная задача с
потребителями и откатом, не часть Phase 2.

## 5. Порядок дальнейшего расширения

1. Решение владельца по варианту A/B и по `null`-описанию.
2. `wb_mart` TIER 0 (15 вью) — вся отчётность Metabase.
3. `wb_mart` TIER 1 (11 вью).
4. `wb_raw` (35 вью) — там та же проблема таблиц: только 5 из 35 не читают таблиц своего датасета.
5. Переезд Control Tower в нейтральный датасет, затем его канонизация.

Цель по-прежнему не число объектов, а взвешенное по риску покрытие: 20 вью TIER 0 стоят
дороже 61 вью TIER 3.
