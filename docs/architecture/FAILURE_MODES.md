# Режимы отказа

Для каждого класса отказа: как проявляется, чем обнаруживается **сегодня**, что теряется
безвозвратно и что делать. Порядок — по цене ошибки, а не по вероятности.

Ключевое различение, уже зафиксированное в `wb_ops.OPS_PIPELINE_REGISTRY`:
`is_snapshot_only` + `missed_run_data_loss` означают, что **пропущенные сутки не
восстанавливаются ничем** — у источника нет эндпоинта истории. Для таких конвейеров
задержка реакции сама по себе является потерей данных.

---

## A. Необратимая потеря наблюдения (`missed_run_data_loss = TRUE`)

| Конвейер | Что теряется | Обнаружение сегодня |
|---|---|---|
| `stocks_snapshot` (Apps Script) | Суточный остаток WB | ⛔ проверки нет |
| `ads_query_bids` | Ставки по кластерам | ✅ `H4_BID_SNAPSHOT_MISSING` |
| `wb_prices_observer` | Цена в окне 20 мин | ⛔ проверки нет |
| `wb_tariffs_loader` | Тарифы и комиссия дня | ⛔ проверки нет |

Пропуски `stocks_snapshot` уже случались: 18–20.07.2026 и 03.09.2026 (HTTP 500
`analytics-open-api`). Эти сутки в истории остатков отсутствуют навсегда.

**Правило.** Прежде чем менять что-либо в этих четырёх конвейерах, убедись, что ближайший
успешный прогон уже состоялся. Откат кода не вернёт пропущенные сутки.

**Что нужно.** Сердцебиение на каждый snapshot-only конвейер с порогом меньше суток и
доставкой оповещения. Сейчас единственный такой детектор — у ставок.

---

## B. Тихий отказ загрузки (прогон «успешен», данных нет)

Наблюдался: инцидент `docs/ops/INCIDENT_2026-09-06_WB_MART_FAILURE.md`. Загрузчик возвращает
код 0, строки не пишутся, витрина пересобирается из вчерашних данных, дашборд показывает
правдоподобное число.

- **Обнаружение:** частично. `H2_MART_LAG` ловит отставание витрины; для RAW-таблиц проверки
  количества строк на сутки нет.
- **Чего не хватает:** проверки «покрытие суток» на каждом RAW: сутки есть и число строк в
  пределах исторического коридора. Порог коридора должен быть выведен из истории, а не назначен.

---

## C. Дрейф определения объекта BigQuery

Правка вью прямо в production мимо Git. Случалось дважды (`REF_COST_MAP`,
`V_PRODUCT_COGS_EFFECTIVE`); в третий раз (R2 preflight, 17.09) подозрение оказалось ложным —
расхождение было только в тексте CTE, схема и данные совпали.

- **Обнаружение:** `tools/verify_current_sql_live.py` — но только для 14 вью из 150, и только
  при ручном запуске.
- **Чего не хватает:** покрытие остальных 136 и регулярный прогон сверки.
- **Опасная сторона:** и обратный дрейф тоже реален — исторические миграции могут
  конфликтовать между собой. Применение `stage3_4d2` поверх `stage3_4d3` ломает агентную вью;
  порядок применения нигде, кроме `MANIFEST.rebuild_order`, не зафиксирован.

---

## D. Разрушительный откат

Откат, написанный вместе с миграцией, живёт дольше неё и к моменту применения удаляет данные,
которых в Git нет. Аудит всех откатов (сентябрь 2026) нашёл: `DROP SCHEMA evetis_ref CASCADE`
при том, что `REF_SKU_CHANNEL_MAP` и `REF_PRODUCT_MASTER` заполнены вручную владельцем;
`DROP TABLE RAW_OZON_SELLER_INFO`, которую daily пополняет; удаление истории цен WB.

- **Статус:** все P1 закрыты (PR #131–#138), опасные откаты превращены в `ASSERT FALSE`
  (RETIRED) — только forward-fix. Остаточные P2 — в `docs/ops/SECURITY_BACKLOG.md`.
- **Правило на будущее:** откат, удаляющий таблицу с данными ручного ввода или с историей
  наблюдений, не пишется вовсе. Обратимость обеспечивается forward-fix, а не `DROP`.

---

## E. Деплой, молча меняющий поведение

`services/wb-communications`: живая конфигурация расходится с `deploy/env.production.yaml`.
Деплой с `--env-vars-file` выключит публикацию ответов в WB, и сервис останется «зелёным».

- **Обнаружение:** обязательный гейт `deploy/preflight_env.py` — fail-closed, закрыт в Stage A.
- **Похожий класс:** Cloud Run Job, забытый в списке промоушена, остаётся на bootstrap-образе
  `hello`, который выходит с кодом 0 и ничего не делает. Уже случалось дважды (`wb-mart-prod`,
  `wb-prices-prod`); сейчас в `deploy-prod.yml` перечислены все Jobs явно.

## F. Расхождение экономики между слоями

Атрибуция рекламы против биллинга: `MART_SKU_DAILY.ad_spend` завышен относительно списанного
WB на +1,76 % (+9 476,42 ₽ за апрель–сентябрь 2026). Это **не ошибка**, а два разных контракта
(`docs/FIN_CONTRACT_V2_2026-09-16.md`), но их смешение даёт неверный вывод о доходности SKU.

- **Обнаружение:** `V_ADVERTISING_RECONCILIATION_DAILY` существует; в ворота не входит.
- **Чего не хватает:** сверка двух контрактов в наборе проверок с порогом, назначенным
  владельцем, а не выведенным из текущего расхождения.

---

## G. Инфраструктурный дрейф Terraform

Ресурсы загрузчика воронки (`wb_funnel_loader.tf`, `secrets.tf`) попали в production из
feature-веток. Полный `terraform plan` из `main` предложит их **удалить**, а `deploy-prod`
откатит образ.

- **Обнаружение:** только глазами в плане.
- **Правило до слияния:** допустимы только целевые apply с просмотренным планом
  (`docs/ops/STAGE_0_CLOSURE_2026-09-11.md` §5).

---

## H. Отказ внешнего API

WB `analytics-open-api` отдавал HTTP 500 (потеря суток остатков). WB `nm-report/downloads`
отдаёт 403 — это отсутствие подписки, а не проблема токена; воронка из-за этого доступна
только за неделю. Ozon Performance API возвращает ноль на окне > 62 дней и меняет формат
(ZIP или CSV).

- **Обнаружение:** ретраи и журналы прогонов есть в обоих Cloud Run контурах.
- **Правило:** отличать «источник не дал» от «загрузчик сломался» в журнале, иначе детектор
  здоровья будет поднимать инциденты на чужие отказы.

---

## I. Единственный канал записи во внешний мир

`services/wb-communications` публикует ответы на отзывы и вопросы WB и доступен из интернета
(F-18). Ошибка здесь видна покупателям и не откатывается.

- **Правило:** пока F-18 открыта, новые компоненты с правом записи не добавляются — включая
  репрайсер. Это ограничение записано в `CLAUDE.md` и действует для агентов тоже.
