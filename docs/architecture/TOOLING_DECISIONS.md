# Решения по инструментам (ADR)

Каждое решение содержит: что рассматривали, что проверено внешним источником, что решено и
**почему именно для этого проекта**. Отказ — тоже решение и записывается так же.

Проверка внешних фактов выполнена 2026-09-21 через Perplexity (web-grounded) с указанием
первоисточников. Где источник не подтвердил факт — так и написано; догадка не выдаётся за
проверку.

---

## ADR-01. Слой трансформаций: остаёмся на BigQuery-native + `sql/current`; Dataform и dbt — нет

**Рассмотрено:** Google Cloud Dataform, dbt Core, Dagster, текущий подход (процедуры BigQuery +
канонический слой `sql/current` + офлайн-валидатор).

**Внешние факты (проверены):**
- Dataform — GA, управляемый сервис Google Cloud; поддерживает assertions (nullability,
  uniqueness, произвольный SQL), инкрементальные таблицы, граф зависимостей через `ref()`,
  зависимости от assertions. Release notes обновлены 2026-08-31. Отдельной платы нет —
  платится подлежащая работа BigQuery. Часть новых возможностей помечена Preview.
  Источник: `docs.cloud.google.com/dataform/docs/*`.
- dbt Core — 1.x остаётся стабильной линией; **v2.0 alpha анонсирована 2026-06-01** как
  Rust-переписывание на базе движка Fusion, Apache 2.0; тогда же объявлено слияние
  Fivetran и dbt Labs. Источник: `github.com/dbt-labs/dbt-core/blob/main/docs/roadmap/2026-06-announcing-v2.md`.
- Dagster OSS — 1.13.23 / библиотеки 0.29.23 на 2026-09-17. Источник: `docs.dagster.io/about/changelog`.

**Решение: не мигрировать.** Обоснование — свойства этого проекта, а не свойства инструментов:

1. **Миграция 150 вью и 22 процедур — крупнейший из возможных blast radius**, а экономика
   этих объектов и есть ценность системы. Правило проекта «не усложнять» здесь совпадает с
   инженерным расчётом.
2. **Требуемое уже построено и строже.** `sql/current` + `canonical_hash_v1` + C1–C18 +
   read-only сверка дают то, чего ни dbt, ни Dataform не дают из коробки: доказательство
   побайтового соответствия Git и production, различение «Git опережает» и «production
   опережает», и запрет расширять доступ к чужому датасету мимо ревью.
3. **Оркестрация уже декларативна** (Cloud Scheduler в Terraform) и стоит дёшево.
   Dagster добавил бы сервис, который надо содержать, ради графа из 486 рёбер, который
   BigQuery и так исполняет.
4. **dbt Core в разгаре смены движка.** Начинать миграцию на 1.x за несколько месяцев до
   2.0 — гарантированная вторая миграция.

**Что взять вместо миграции** (идеи, не инструмент): декларативные assertions рядом с
определением объекта, обязательный `--dry-run` перед развёртыванием, документация,
порождаемая из метаданных. Всё три реализуемы на текущем стеке — см. ADR-03 и `MIGRATION_PLAN.md`.

**Условие пересмотра.** Вернуться к Dataform, если: появится второй арендатор и SQL придётся
параметризовать по проекту/датасету (Dataform умеет это нативно), **или** число вью превысит
~300, **или** понадобится инкрементальная материализация с управляемым backfill более чем для
трёх объектов.

## ADR-02. Оркестрация: Cloud Scheduler + Cloud Run Jobs остаются; Cloud Workflows — нет

**Решение.** Текущая схема покрывает потребность: 20 расписаний, две формы цели (Cloud Run Job
и BigQuery `CALL`), состояние в Terraform, управление паузами — отдельным workflow без Console.

Cloud Workflows понадобится, когда появится **межсервисная зависимость** («собери витрину
только после того, как все три загрузчика отчитались OK»). Сегодня такой зависимости нет: она
выражена временем (`mart` в 07:00 после загрузок в 05:xx). Это хрупко, но замена — не
оркестратор, а **проверка предусловия внутри самой сборки**: `sp_build_*` обязана отказаться
работать, если источник не свеж. Это дешевле и не добавляет компонента.

## ADR-03. Качество данных: собственный исполнитель `-- @check`, а не новый фреймворк

**Проблема.** 25 файлов приёмочных проверок; автоматически исполним был один. Пороги в них
согласованы владельцем при сдаче этапов — их нельзя переизобретать при переносе.

**Решение.** `tools/run_data_checks.py` — исполнитель уже существующего в репозитории
контракта `-- @check <ID>` + `status ∈ {PASS, FAIL}`. Только чтение, коды выхода
0/1/2/3, JSON-отчёт, реестр наборов `quality/suites.json`.

**Почему не Great Expectations / Soda / Dataform assertions.** Все три требуют переписать
проверки на свой язык. Переписывание проверки экономики — это переписывание бизнес-правила:
именно там теряется согласованный порог. Исполнитель существующего SQL сохраняет и правило, и
его происхождение.

**Специально принятое решение:** пустой результат — **не** успех (`EMPTY`, код 2). Проверка,
которая ничего не вернула, ничего не доказала. Явно объявить пустоту успехом можно строкой
`-- @expect empty_ok`.

## ADR-04. Автономная инженерия: Claude Code остаётся ведущим; отдельный сервер агентов — пока нет

**Внешние факты (проверены):** OpenHands — MIT, зонтичный релиз v1.20.0 (2026-09-17); Agent
Canvas влит в основной репозиторий (отдельный репозиторий архивирован 2026-07-27); Agent Server
1.49.1; OpenHands Automation v1.13.2 (cron и webhooks), MIT, позиционируется как сервис для
OpenHands Cloud. Источник: `github.com/OpenHands/*`.
Про Agent Client Protocol (Zed) подтверждено только то, что OpenHands заявляет совместимость;
данных о версии, лицензии и распространённости на сентябрь 2026 источники не дали — считаем
**непроверенным**.

**Решение.** Не разворачивать отдельный сервер агентов на этом этапе.

**Почему.** Узкое место этого проекта — **не пропускная способность агента, а доказуемость
результата**. Сегодня ни один агент не может машинно ответить «задача закончена»: ворота
данных существовали для одного набора из 25. Второй агент-ревьюер, запущенный поверх системы
без ворот, удвоит объём текста и не уменьшит риск.

Порядок обратный: сначала машинно проверяемый Definition of Done
([`DEFINITION_OF_DONE.md`](DEFINITION_OF_DONE.md)) и ворота данных, затем — автоматизация
запуска. Когда ворота покроют критичные области, добавление OpenHands Automation (cron +
webhook на GitHub Issue) станет механическим шагом, а его польза — измеримой.

**Независимый ревьюер.** Ценность второго мнения признаётся, но реализуется сначала дешёвым
способом: `/code-review` в отдельной сессии и обязательный прогон ворот на ветке. Вторая
модель подключается, когда есть что ей дать, кроме диффа, — отчёт ворот и снимок инвентаря.

## ADR-05. MCP: минимальный набор, всё с правом записи — вручную

**Уже подключено и полезно:** Perplexity (свежие внешние факты), Firecrawl (страницы
документации), Playwright (кабинеты WB/Ozon там, где API не отдаёт данные), Context7
(документация библиотек), Google Drive (структура книг), BigQuery MCP.

**Не подключать:**
- **MCP с правом записи в BigQuery.** Доступ к данным у инструментов этого каталога —
  через `tools/lib/bq_readonly.py`, который отклоняет не-SELECT **до отправки запроса**.
  Это и есть доказательство read-only для аудита; универсальный MCP такого доказательства
  не даёт.
- **MCP для Metabase.** Metabase живёт вне Git и часто выключен; сборка карточек уже покрыта
  `mb` CLI и скриптами `tools/metabase_*`.
- **Официальные Google MCP для BigQuery/Cloud Run.** Существуют (`google/mcp`, Apache-2.0),
  но сам репозиторий объявлен демонстрационным, а не поддерживаемым продуктом. Кроме того,
  на этой машине хост `bigquery.googleapis.com` фильтруется сетью — MCP, ходящий по нему,
  не заработает. Пересмотреть, если сетевое ограничение снимут.

**Правило.** Новый MCP-сервер подключается только с записью в этом файле: репозиторий,
сопровождающий, область прав, причина. Ненадёжные серверы не устанавливаются автоматически.

## ADR-06. Доступ к BigQuery — через legacy-хост, и это не временный костыль

С рабочей машины владельца `bigquery.googleapis.com` возвращает HTTP 403 (HTML Google
frontend) даже на неаутентифицированный discovery: из-за этого не работают `bq` CLI,
BigQuery MCP и BigQuery-провайдер Terraform. Хост `www.googleapis.com/bigquery/v2` с тем же
OAuth-токеном работает.

**Решение.** Все инструменты этого каталога ходят на `www.googleapis.com` по умолчанию, хост
задаётся флагом. Блокировка перемежающаяся (Terraform однажды прошёл через несколько часов),
поэтому единичный отказ не записывается в BLOCKED без повторной попытки.
