# Инженерный контур с участием агентов

Как агент работает в этом репозитории, что ему разрешено, и чем он доказывает результат.
Этот файл читают и человек, и следующий агент; он рассчитан на то, что читатель не помнит
предыдущую сессию.

---

## 1. Что агент обязан установить до первой правки

1. `git fetch origin` и проверка, что HEAD достижим из `origin/main`. Локальный `main`
   отставал на 40 коммитов — анализ в устаревшем дереве описывает несуществующую систему.
2. Свежий снимок системы: `docs/architecture/system_inventory.json`. Если он старше изменений,
   которые агент собирается делать, — пересобрать (`tools/architecture_baseline.py`).
3. **Какая из пяти сред** исполняет затрагиваемый код (`CURRENT_ARCHITECTURE.md` §2). Ответ
   «загрузчик WB» недостаточен: заказы грузит Apps Script, витрину — Cloud Run, слои — процедуры
   BigQuery по расписанию.
4. Живое определение объекта BigQuery, если его правят. Production дважды опережал Git.

---

## 2. Роли

| Роль | Кто | Отвечает за |
|---|---|---|
| Ведущий инженер | Claude Code | исследование, реализация, прогон ворот, отчёт |
| Независимый ревьюер | отдельная сессия / вторая модель | ищет то, что автор не мог увидеть: неверную трактовку денежной строки, пропущенного потребителя, необратимость |
| Data QA | `tools/run_data_checks.py` | вердикт по данным, без интерпретации |
| Владелец | человек | ACK дизайна, все необратимые действия, бизнес-решения |

Ревьюер — не второе мнение о стиле. Его вход: дифф + отчёт ворот + список потребителей
затронутых объектов из инвентаря. Без этого входа ревью вырождается в чтение кода.

---

## 3. Цикл

```
DISCOVER → UNDERSTAND → PLAN → ACK владельца → IMPLEMENT → TEST → VERIFY DATA
        → REVIEW → FIX → RETEST → DOCUMENT → STOP
```

`ACK владельца` стоит **до** реализации, а не после: в этом проекте цена неверно понятой
экономики выше цены задержки. `STOP` — тоже шаг: агент не переходит к следующей инициативе,
не получив её.

---

## 4. Что агент делает сам, без вопроса

- любое чтение: BigQuery через `tools/lib/bq_readonly.py`, `gcloud … list/describe`,
  репозиторий, история заданий;
- изменения файлов в рабочем дереве ветки;
- запуск тестов, валидаторов и ворот данных;
- пересборка снимка инвентаря и производной документации;
- исправление собственной ошибки и повторный прогон.

## 5. Что агент не делает никогда без явного разрешения

- `git commit` в общие ветки, `git push`, открытие PR;
- любой DDL/DML в BigQuery, включая «безобидный» `CREATE OR REPLACE VIEW`;
- `terraform apply`, изменение расписаний, развёртывание образов;
- запись во внешние сервисы (WB, Ozon) — запрещена полностью, пока открыта F-18;
- запуск Apps Script `wbAdsBqCreateViews()` — запрещён безусловно;
- применение файлов отката: часть из них исторически удаляла данные ручного ввода.

## 6. Обязательный read-only по построению

Инструменты анализа не «стараются» быть read-only — они физически отклоняют мутацию:
`tools/lib/bq_readonly.py` отвергает любой оператор, кроме `SELECT`/`WITH`, **до отправки
запроса**, и не принимает хост вне списка. Это формулировка, пригодная для аудита: доказательство
не в намерении, а в коде и в тестах `tools/tests/test_run_data_checks.py`.

Второе доказательство — со стороны BigQuery: запросы помечаются меткой `purpose`, и
`INFORMATION_SCHEMA.JOBS_BY_PROJECT` с группировкой по `statement_type` обязан содержать
только `SELECT`.

## 7. Чем агент доказывает, что закончил

[`DEFINITION_OF_DONE.md`](DEFINITION_OF_DONE.md). Коротко: команда + код выхода. Утверждение
«проверено» без команды не принимается; зелёный CI не заменяет ворота данных; красная
обязательная проверка означает, что задача не завершена.

Отдельно обязателен **отрицательный результат**: что осталось непокрытым. Область без набора
проверок называется прямо, а не обходится молчанием.

---

## 8. Дисциплина доказательств

- Различать: **подтверждённый факт** (есть команда и вывод), **вывод из источников**,
  **предположение**. Смешивать нельзя.
- Не выдавать знание модели за свежую проверку. Внешний факт — с источником и датой.
- Неудавшийся вызов инструмента сообщается, а не маскируется под успешное исследование.
- Ошибочная находка исправляется до попадания в документ. Пример из этой работы: первая
  автоматическая выборка образов Cloud Run показала «ни один Job не закреплён по digest» —
  причиной был неверный путь в ответе `gcloud`; после проверки одного Job вручную выяснилось,
  что закреплены все 14. Сборщик теперь падает, если путь не читается, вместо того чтобы
  тихо отдать ложь.

---

## 9. Память между сессиями

Репозиторий — авторитетный источник о системе. Постоянная память агента хранит то, чего в
репозитории нет: решения владельца, особенности внешних API, обходы сетевых ограничений,
уроки инцидентов. Если память называет файл, функцию или флаг — проверить, что они ещё
существуют, прежде чем на них опираться.

Порядок чтения в новой сессии: `CLAUDE.md` → `docs/architecture/CURRENT_ARCHITECTURE.md` →
`system_inventory.json` → `docs/CURRENT_PROJECT_STATE.md` → `CHANGELOG.md` с последней метки.

---

## 10. Когда добавлять автоматический запуск агентов

Не раньше, чем ворота данных покроют критичные области. Обоснование и проверенное состояние
внешних инструментов — `TOOLING_DECISIONS.md` ADR-04. Правило простое: **автоматизировать
можно только то, результат чего система умеет проверить сама.** Автономность без ворот
увеличивает не скорость, а радиус поражения.
