## Почему V3 объясняет мало

CURRENT snapshot/code: claim registry39 entries:13 PROHIBITED,10 MEDICAL_OR_HIGH_RISK,8 COSMETIC_CLAIM_PENDING,7 APPROVED_CANDIDATE,1 FACT_CLAIM. Последний — CLM032, rinse_off, не benefit. Это намеренное ограничение утверждённого знания, не ошибка наличие→claim.

- Ingredient matcher разделяет канонические Hyaluronic Acid / Sodium Hyaluronate, ambiguous alias не превращает в разрешённый ингредиент; совпадение ingredient token не доказывает процент/эффект.
- Product facts имеют source, fact_status, disclosure и conflict scope. PUBLIC recipe percentage — факт, RESTRICTED/DO_NOT_DISCLOSE и ODR07/20 — отдельные gates. Legacy KB/customer review не является source approval.
- Planner разрешает facts/templates по маршруту; ACK не получает состав автоматически; safety/service/identity сохраняют приоритет.
- V3 generator получает только allowed_facts, required_templates, unknown_facts, approved_guidance=[] и явный запрет cosmetic/general knowledge. Изначальный LLM generator не расширен глобально.
- Shared verifier применяется и к AI, и к manual text и перед write, независимо от shadow и cached generation policy. Cosmetic stem matcher ранее блокировал даже некоторые company words; renderer не добавляет такие fillers для искусственного score.
- Старый evaluator объявлял безопасные бедные answers GOOD. Теперь15 независимых осей; hard PASS не делает quality GOOD.

## Human voice / качество

Adaptive renderer слышит конкретные положительные и отрицательные сигналы, объединяет praise details, сохраняет оба полюса mixed feedback; relevant approved context≤1. Нет обязательного ingredient-presence filler. Без benefits source мягкость тоника остаётся полезным approval gap, а не выдуманным объяснением. Service: empathy + WB action, без маркетинга. Questions: direct first sentence. Emergency/mild templates неизменны.

15 diagnostic axes: acknowledgment_specificity, warmth, empathy, usefulness, product_relevance, factual_grounding, naturalness, brand_voice, future_buyer_value, personalization, repetition_penalty, robotic_language_penalty, unnecessary_defensiveness, overexplaining_penalty, missed_customer_signal_penalty. Это эвристики, не окончательная человеческая приёмка и не финансовый KPI. Penalty GOOD означает «штраф не обнаружен».

Internal recovery interface READY/HUMAN_REVIEW сохранён для consumers; operator_state отдельно READY/WARNING/BLOCK/HUMAN_REVIEW. NEEDS_IMPROVEMENT → WARNING, обычный policy BLOCK без repair→BLOCK, escalation→HUMAN_REVIEW. Quality не запрещает Publish безопасного текста.

Flow: original→shared hard policy→bounded one repair→independent hard policy again→quality→operator card→exact-version consent→CURRENT policy→existing publisher→readback. Если даже correction BLOCK, публикация не выполняется; original override только после двух новых разрешённых taps.

## Owner override

Новый flag defaultfalse. Чтобы получить complete corrected-card UX при активации, нужны отдельно reviewed recovery=true и override=true; этот PR env не меняет. Override разрешён только explicit nonempty Telegram user allowlist AND действующим chat/user auth. Existing empty-lists fail-open normal auth не переносится на override. Authorized chat alone недостаточно. UI может показывать shared-chat button, но unauthorized first/second callback не получает publication permission.

BLOCK card показывает причины, problematic spans и correction где доступна. Actions: Publish corrected/current version, edit, regenerate, request original anyway. Первый click показывает полный source text и второе confirmation. ZERO WB reads/writes. Pending consent содержит current generation/hash, original source version/hash, same actor, communication-context hash, nonce, expiry, policy+snapshot+expertise fingerprint. Source lookup не подменяет original последующей repair generation.

Второй click заново проверяет auth, safety, TTL, generation, current hash, source hash и CURRENT policy fingerprint. Actor change/stale/edit/regen/skip/expired/replaced nonce/policy drift→нет WB доступа, новая consent нужна. Firestore transaction сравнивает pending equality и consume ещё раз вместе с publish lease, source version append и audit. Duplicate second confirmation не имеет второй write. Между предварительной проверкой и network gate есть повторная policy/hash проверка на locked source. Validator failure НЕ override-able.

Audit в private Firestore: override=true, override_by, override_at, override_confirmed_at, policy_version, violations, violation_spans, answer_hash, source_version, knowledge_snapshot, knowledge_snapshot_sha256, expertise_sha256, reason_optional (null если не сообщена причина). Private spans не передаются в publication trace/outbox/log; trace хранит hashes/IDs. Callback и auth headers не логируются. Возврат204 или accepted не считается published: matching public WB readback обязателен. Existing uncertain write intent сохраняется; override не разрешает blind resend/overwrite чужого ответа.

Scope interpretation: серьёзные safety routes и любые существующие safety templates, включая mild/resolved burning, не override-able в этом PR. Это сохраняет §8 owner task, а не скрытая смена medical routing. Non-safety policy BLOCK override разрешён. HUMAN_REVIEW/unknown clinical answer не превращён в ordinary published answer.
