# Autonomous Engineering v1 — архитектура

Статус на 2026-09-24: **реализовано в Git, выключено** (`AE_ENABLED` не задан). Включение —
решение владельца после шагов `AE_V1_RUNBOOK.md` §2.

**Принцип.** ИИ исследует и предлагает изменения. Принимает или отвергает результат только
детерминированный код и существующие ворота Platform Baseline. Модель может ужесточить
итог, но не может ослабить ни один запрет.

## 1. Компоненты

| Компонент | Модуль | Модель | Отвечает за |
|---|---|---|---|
| **Watcher** | `tools/autonomy/watcher.py` | нет | прогоняет существующие ворота read-only, сравнивает с историей и реестром UBR, диспатчит только устойчивое новое падение |
| **Engineer** | `agents.ClaudeCliAdapter` + `orchestrator` | да | план, реализация, доработка по обратной связи |
| **Independent Reviewer** | отдельный вызов, отдельная машина | да | ищет неверные допущения, пропущенных потребителей, ложнопроходящие тесты, ослабление ворот |
| **Gatekeeper** | `tools/autonomy/gatekeeper.py` | нет | финальный вердикт по доказательствам; модель его не переопределяет |
| Policy | `tools/autonomy/policy.py` + `quality/autonomy/policy.json` | нет | бюджеты, запрещённые пути, детектор ослабления ворот, ACK плана |
| State | `tools/autonomy/state.py` | нет | машина состояний и долговременная запись |
| Evidence | `tools/autonomy/evidence.py` | нет | песочница, сбор доказательств существующими инструментами |
| Publisher | `tools/autonomy/publisher.py` | нет | единственная запись в Git: `refs/heads/ae/*`, только draft PR |
| Audit | `tools/autonomy/audit.py` | нет | число не-SELECT заданий идентичности AE по журналу BigQuery |

Существующая истина не дублируется: наборы — `run_data_checks.py`, здоровье —
`verify_task.stage_health`, влияние — `impact_analysis.py`, канон — `validate_current_sql.py`
и `verify_current_sql_live.py`, runtime-доступ — `check_runtime_access.py`.

## 2. Классы наблюдения (Watcher)

| Класс | Условие | Действие |
|---|---|---|
| HEALTHY | проверка проходит | ничего |
| KNOWN | падает, но в `blocked_checks` открытого UBR или вынесена из ворот | ничего |
| OBSERVING | упала впервые | ждать подтверждения; модель не вызывается |
| FLAPPING | ≥ 2 смены PASS↔FAIL в окне 10 | оповестить, не диспатчить |
| NEW_PERSISTENT | подряд ≥ 2 падения, не известна | **диспатч** |
| HEALTH_DEGRADED | детектор здоровья сообщает о нездоровье | **диспатч** |
| INFRA_BLOCKED | доказательство не получено | оповестить; это не здоровье |

Оповещение — только при смене класса. Здоровая система модель не вызывает никогда
(`llm_invocations: 0` в каждом отчёте).

## 3. Машина состояний

```
RECEIVED → DISCOVERING → PLANNING ──→ IMPLEMENTING → TESTING → REVIEWING → READY_FOR_PR
                             │               ▲           │           │             │ publish (draft PR +
                             │               └─ FIXING ◄─┴───────────┘             ▼  диспатч обязательного CI)
                             │                                           AWAITING_VERIFICATION
                             └→ WAITING_FOR_HUMAN   (ACK плана, TCB,              │ ci-verify: success ВСЕХ
                                                     решение владельца)            ▼ на опубликованном SHA
                                                                         READY_FOR_HUMAN_REVIEW → COMPLETED (человек)
                  любое → BLOCKED (бюджет, UNSAFE, провал/таймаут CI, нет доказательства) · FAILED (инфраструктура)
```

Допустимые переходы — `state.TRANSITIONS`; недопустимый переход — исключение. Каждый переход
пишется с причиной. Запись прогона (`quality/autonomy/run_state.schema.json`) валидируется
при каждой записи. `WAITING_FOR_HUMAN`, `BLOCKED` и `READY_FOR_HUMAN_REVIEW` — «припаркованы»: они блокируют дубликаты
по ключу дедупликации, пока человек не решит. `FAILED` — терминален, повтор по тому же ключу
запрещён 24 часа.

**ACK до реализации сохранён** (`AI_ENGINEERING.md` §3): если план касается TIER0, путей
экономики (`sql/current`, `sql/control_tower`, `sql/mart`, `sql/dash`, `sql/ref`) или заявляет
изменение бизнес-семантики — `WAITING_FOR_HUMAN`. ACK принимается только как sha256 **этого**
плана в `objective.owner_ack.plan_sha256`. Фактический дифф проверяется повторно.

## 4. Гейткипер

Порядок вердиктов (худший побеждает):
`UNSAFE > BLOCKED_BY_TEST > BLOCKED_BY_RUNTIME_ACCESS > BLOCKED_BY_DATA > HUMAN_DECISION_REQUIRED > INCONCLUSIVE > READY_FOR_PR`.

- **UNSAFE**: production-мутация > 0; запрещённый путь; признак ослабления ворот в диффе;
  ревьюер обнаружил ослабление.
- **BLOCKED_BY_TEST**: красный тест репозитория — всегда, даже если красный и на базе
  (кандидат мог не починить именно то, что должен был); `validate_current_sql` FAIL.
- **BLOCKED_BY_RUNTIME_ACCESS**: исполнитель не прочитает новую зависимость.
- **BLOCKED_BY_DATA**: проверка данных, бывшая PASS на базе, стала FAIL; дрейф паритета.
  Падение, которое есть и на базе, не блокирует, но сообщается — данные отражают production.
- **HUMAN_DECISION_REQUIRED**: нужен ACK плана; изменение касается открытого UBR;
  устранение исходного сигнала не доказано; кандидат пуст; ревьюер просит решение человека.
- **INCONCLUSIVE**: нет доказательства (BLOCKED/ERROR), нет ревью, аудит мутаций недоступен,
  ревьюер требует изменений.

## 5. Модель доверия в CI

Каждая роль — отдельный job, то есть отдельная эфемерная ВМ.

| Job | Доверие | Права | Что делает |
|---|---|---|---|
| prepare | доверенный | contents: write (только `autonomy-state`), id-token | открыть прогон, доказательства базы |
| engineer | **недоверенный** | contents: read, id-token | агент на черновой копии состояния → ответы + sha256 |
| ingest | доверенный | contents: write | сверить sha256, воспроизвести план/реализацию |
| test | **недоверенный** | contents: read, id-token | исполнить ворота на коде кандидата → доказательства + sha256 |
| verify | доверенный | contents: write | сверить sha256, воспроизвести доказательства → переход |
| review | **недоверенный** | contents: read, id-token (только Claude API) | вердикт + sha256 |
| gate | доверенный | contents: write | воспроизвести вердикт, решить гейткипером |
| publish | доверенный | contents: write, pull-requests: write | `refs/heads/ae/*` + draft PR |
| persist | доверенный | contents: write, actions: write, issues: write | решение о следующем проходе, итог |

Авторитетное состояние (ветка `autonomy-state`) пишут **только доверенные** jobs, и ни один
из них не исполняет код агента или кандидата. Недоверенный вывод передаётся артефактом, его
sha256 — через outputs job'а-производителя (их другой job подделать не может). Доверенный job
читает из артефакта только файлы с известными именами и объявленными хешами; подложенные
«состояние» или «зелёный гейт» не читаются вообще (`test_autonomy_ci_trust.py`).

**Предел, названный прямо.** Доказательства, полученные исполнением кода кандидата, корректны
против ошибающегося кандидата, но не против злонамеренного: код теста может подделать свой
результат. Против злонамеренного кандидата остаются независимое ревью диффа и слияние только
человеком. Структурная гарантия V1 — не «корректность доказательств», а **ноль мутаций
production и ноль записи в main**.

## 6. Бюджеты (`policy.json`)

Итераций инженера — 3; циклов ревью — 3; время прогона — 90 мин; ходов — 60/25; бюджет модели —
$15/$5 на вызов; инфраструктурных повторов — 2; проходов workflow — 8; активных прогонов — 1;
cooldown после FAILED — 24 ч. Семантический отказ не повторяется автоматически никогда.

## 7. Схемы

`quality/autonomy/`: `incident.schema.json`, `objective.schema.json`, `engineer_report.schema.json`,
`review_verdict.schema.json`, `run_state.schema.json`; примеры — `examples/`. Валидатор —
`tools/autonomy/schema.py`: строгое подмножество JSON Schema, неизвестное ключевое слово —
ошибка, невалидный документ дальше не проходит.
