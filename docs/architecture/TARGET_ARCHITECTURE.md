# Целевая архитектура

Целевая — не «другая система», а та же система с закрытыми пробелами. Ни один пункт ниже не
требует переписать работающий контур; каждый добавляет **контроль** над тем, что уже работает.

Проверка целевого состояния: три вопроса, на которые сегодня нельзя ответить командой, а
должно стать можно.

1. **«Совпадает ли production с репозиторием?»** — сегодня для 14 объектов из 150.
2. **«Здорова ли платформа прямо сейчас?»** — сегодня для 5 конвейеров из 16, Ozon не покрыт.
3. **«Закончена ли задача?»** — сегодня ворота данных есть у одной области из ~десяти.

---

## 1. Принципы

1. **Git описывает то, что есть сейчас.** Для каждого production-объекта существует ровно один
   канонический файл, и его соответствие живому объекту доказывается, а не предполагается.
2. **Проверка рядом с объектом.** Утверждение об экономике живёт как исполнимая проверка, а не
   как абзац в отчёте о сдаче этапа.
3. **Пять сред остаются пятью, но становятся одинаково наблюдаемыми.** Не «всё переписать в
   Cloud Run», а «у каждой среды есть журнал прогонов, реестровая запись и проверка здоровья».
4. **Read-only по умолчанию.** Инструменты анализа физически не умеют менять production;
   мутация — только через объявленный путь развёртывания с решением владельца.
5. **Канонический слой сосуществует с площадочным.** `evetis_mart` не заменяет `wb_mart` и
   `ozon_mart`, а приводит их к одному контракту. Специфика площадки не уничтожается.

---

## 2. Слои данных (целевое)

```
                     источники                       контракт                потребитель
WB API ───────────┐
Google Sheets ────┼──► wb_raw   ──► wb_mart   ──┐
                  │                              │
Ozon API ─────────┼──► ozon_raw ──► ozon_mart ──┼──► evetis_mart ──► Metabase
                  │                              │   (нейтральный    Sheets
ручной ввод ──────┴──► evetis_ref ───────────────┘    канонический    агенты
                                                      слой)
                       wb_ops / evetis_ops: реестр конвейеров, здоровье, инциденты, операции
```

**Что меняется в `evetis_mart`.** Сегодня там один объект. Целевой состав канонической модели —
сущности, общие для любого маркетплейса:

| Сущность | Есть сейчас | Откуда собирается |
|---|---|---|
| `FACT_SKU_DAILY` | ✅ | `wb_mart.SKU_PERFORMANCE_V2_DAILY` + `ozon_mart.FCT_OZON_SKU_PNL_DAILY` |
| `FACT_ORDERS` | — | адаптеры площадок |
| `FACT_RETURNS` | — | WB есть, Ozon не грузится (ограничение V1) |
| `FACT_ADVERTISING` | — | различать **атрибуцию** и **биллинг** явным полем, не смешивать |
| `FACT_INVENTORY` | — | остатки обеих площадок + журнал ФФ `evetis_ops` |
| `DIM_PRODUCT` | частично (`evetis_ref.REF_PRODUCT_MASTER`) | ручной ввод владельца |
| `DIM_SKU_CHANNEL` | частично (`REF_SKU_CHANNEL_MAP`) | ручной ввод + сверка с площадками |

Порядок добавления — по спросу продукта, не по полноте модели. Сущность без потребителя не
создаётся: у `FACT_SKU_DAILY` потребителей пока нет, и второй такой объект добавлять рано.

## 3. Контроль соответствия (целевое)

- `sql/current` покрывает **все** вью production, по одному датасету за шаг.
- `EXTERNAL_DATASET_POLICY` расширен записями для `wb_mart`, `wb_raw`, `evetis_ops`, `evetis_ref`
  — каждая запись проходит ревью отдельно, потому что она и есть правило изоляции доменов.
- Процедуры (`sp_*`) получают тот же канонический контракт, что и вью. Сегодня они описаны
  только историческими миграциями, а исполняются планировщиком каждый час.
- `verify_current_sql_live.py` прогоняется по расписанию под отдельной учётной записью с
  `roles/bigquery.metadataViewer`; расхождение открывает инцидент, а не правит production.

## 4. Наблюдаемость (целевое)

**Единый статус платформы.** Один объект отвечает на вопрос «как система себя чувствует»:

```
HEALTHY   — все обязательные проверки зелёные
DEGRADED  — есть отклонение, но данные не теряются и потребитель не сломан
FAILED    — потребитель получает неверные данные либо наблюдение теряется безвозвратно
```

Состав целевого покрытия:

- реестр конвейеров включает **Ozon** (11 сущностей) и **сборки слоёв** (`executive_v2`,
  `sku_performance_v2`, `unitka`, `ct_refresh`) наравне с загрузчиками WB;
- у каждого конвейера с `missed_run_data_loss = TRUE` — сердцебиение с порогом меньше суток;
- у каждого RAW — проверка покрытия суток (сутки есть, объём в историческом коридоре);
- ворота данных из `quality/suites.json` входят в статус платформы: красный набор — это
  `FAILED`, а не отдельная новость.

**Реакция.** HEALTHY — ничего. DEGRADED — диагностика и запись. FAILED — инцидент с
контекстом: журнал прогона, отчёт ворот, затронутые объекты и их потребители. Автоматическое
исправление production не предусмотрено ни на одном уровне: агент готовит forward-fix,
применяет владелец.

## 5. Инженерный контур (целевое)

```
задача / GitHub Issue
      │
      ├─ снимок инвентаря + карта зависимостей (машиночитаемые)
      ├─ реализация (Claude Code)
      ├─ код-ворота:    typecheck · lint · тесты · docker · terraform validate
      ├─ SQL-ворота:    validate_current_sql · verify_current_sql_live (read-only)
      ├─ ворота данных: run_data_checks --suite … (код выхода 0 обязателен)
      ├─ независимое ревью (вторая сессия / вторая модель) — на входе дифф + отчёты ворот
      └─ PR + краткий отчёт владельцу: что доказано, чем, и что осталось непокрытым
```

Автоматизация запуска (cron/webhook поверх Issue) добавляется **после** того, как ворота
покрывают критичные области, — обоснование в `TOOLING_DECISIONS.md` ADR-04.

---

## 6. Мультиарендность (целевое, кратко)

Полностью — в [`TENANCY_DESIGN.md`](TENANCY_DESIGN.md). Целевой инвариант: подключение нового
продавца — это **конфигурация**, а не копирование кода. Идентификатор аренданта становится
частью ключа данных и частью имени секрета; GCP-проект перестаёт быть синонимом арендатора.

---

## 7. Чего целевая архитектура НЕ предусматривает

- переписывания Apps Script на Cloud Run как самоцели — только при доказанной выгоде и с
  параллельной сверкой суток;
- отдельного оркестратора (Dagster/Airflow) — см. ADR-02;
- миграции трансформаций на dbt/Dataform — см. ADR-01;
- автоматического исправления production агентом;
- новых компонентов с правом записи во внешние сервисы, пока открыта F-18.
