# UBR-012 · Приведение Control Tower к каноническому источнику выручки Ozon

Дата: 2026-09-22 · Git-side завершён, production не изменён · `impact_analysis`: **TIER0**, 42 объекта

## 1. Природа дефекта

Control Tower самостоятельно реконструировал выручку Ozon из `ozon_raw`:

```sql
SUM(IF(p.status = 'delivered', IFNULL(f.sp_unit, p.price_rub) * p.quantity, 0))
```

`IFNULL(..., p.price_rub)` подставлял цену заказа везде, где начисления реализации нет.

Ключевое наблюдение, определившее решение: **для обычных продаж подстановка безвредна.** По
2 008 строкам из 2 008 цена заказа равна цене продавца до копейки — расхождение 0,00 ₽, строк с
отличием ноль. То есть fallback не был «приблизительной оценкой»: он давал точный ответ везде,
кроме одного класса. Ошибка возникала там, где действует другая хозяйственная форма — выкуп CIS,
где Ozon покупатель, а не агент, и выручка равна цене заказа минус дисконт 21–44 %.

Поэтому это не ошибка формулы, а **ошибка уровня**: Control Tower решал задачу классификации
операций, которая уже решена в `ozon_mart` и утверждена контрактом Gate 5K/5M.

## 2. Что сделано

### 2.1 Control Tower перестал реконструировать выручку

`sql/control_tower/ct_ubr012_revenue_2026-09-22.sql` — новое тело
`wb_mart.V_CT_ACTUAL_DAILY_LIVE`. Выручка читается из
`ozon_mart.FCT_OZON_SKU_PNL_DAILY.seller_base_revenue_rub`, fallback удалён полностью.

Почему это безопасно, доказано измерением, а не рассуждением:

| величина | Control Tower | каноническая витрина |
| --- | ---: | ---: |
| расходы площадки | 883 992,77 | 883 992,77 |
| реклама | 477 143,07 | 477 143,07 |
| себестоимость | 459 822,42 | 459 822,42 |
| продано, шт | 2 044 | 2 044 |
| заказано, шт | 2 092 | 2 092 |
| строк | 3 737 | 3 737 |
| **выручка** | **1 897 522,00** | **1 884 733,16** |

Совпадало всё, кроме выручки. Зерно одно (`order_date × internal_sku`, подтверждено
`fact_date_semantics`), множества строк тождественны в обе стороны. Поэтому подстановка
источника выручки — операция ровно на одну величину.

### 2.2 Fail-closed для недоказанного выкупа

Три факта `ozon_mart` (`FCT_OZON_SKU_PNL_DAILY`, `FCT_OZON_SKU_PNL_MONTHLY`,
`FCT_OZON_PNL_MONTHLY`) больше не подставляют цену заказа выкупу без документа:

```sql
CASE WHEN p.buyout_proceeds_rub IS NOT NULL THEN p.buyout_proceeds_rub * p.quantity
     WHEN p.op_type='CIS_BUYOUT' THEN NUMERIC '0'          -- UBR-012: fail-closed
     ELSE IFNULL(p.sp_unit, p.price_rub) * p.quantity END
```

Классификация выкупа идёт по **структурной сигнатуре** (`delivered` + нет начисления выручки +
`payout_rub = 0`), а не по членству в реестре, поэтому новый выкуп распознаётся автоматически и
сразу попадает под fail-closed. Величина не прячется: она остаётся в
`buyout_revenue_unproven_qty/_rub`.

Сегодня недоказанных нет, поэтому изменение **не двигает ни одной суммы** — оно меняет гарантию.

### 2.3 Что сознательно НЕ сделано

**Путь обычной продажи без начисления оставлен как есть.** Формально это тоже подстановка цены
заказа, но:

- владелец требует, чтобы экономика обычных продаж не изменилась (AC5);
- начисление приходит с лагом (p95 = 11 дней, максимум 32): обнуление выручки на время лага
  занижало бы свежие периоды, тогда как цена заказа там доказанно точна;
- «молчаливость» снята иначе — `commission_missing_qty` выведен в `contribution_covered`
  Control Tower и проверяется воротами. Использование этого пути теперь **обнаруживается**,
  а не происходит незаметно.

**Счётчики недоказанности в месячные факты не добавлены.** Это сохранило бы симметрию, но
потребовало бы изменения схемы двух витрин ради состояния, которое ловится контрактом U01 и
названо в суточном факте. Выбран меньший по риску вариант; ограничение зафиксировано здесь явно.

### 2.4 Базовый файл Control Tower приведён к production

`sql/control_tower/ct_04a_views_base.sql` не получал ни UBR-010, ни UBR-012 — повторный прогон
этого файла молча откатил бы **оба** решения владельца. Тело `V_CT_ACTUAL_DAILY_LIVE` в нём
синхронизировано с production; дневные патч-файлы остаются исторической записью.

## 3. Детекционный контракт вместо выдуманной классификации

`quality/suites.json` → набор `ubr012_revenue_source` (CRITICAL, ворота),
`sql/scale1/ubr012_revenue_reconciliation.sql`, 12 проверок.

Центральная — **U01**: доставленная строка без начисления выручки и без первичного документа.
Сегодня таких нет ни одной; появление хотя бы одной роняет CRITICAL-ворота и называет сумму под
риском. Это и есть требуемый detection contract: реестр заполняется руками и сам не растёт, но
его неполнота теперь **обнаруживается автоматически**, а не маскируется ценой заказа.

Остальные: U02 выручка выкупа = документ · U03 Control Tower ≡ витрина · U04/U05 якоря поправки
12 788,84 и 986,04 · U06 сигнатура ≡ реестр · U07 нет двойного счёта · U08 обычные продажи не
тронуты · U09 недоставленные не создают выручку · U10 недоказанное не становится выручкой ·
U11 множества строк тождественны · U12 UBR-010 не регрессировал.

Инварианты сформулированы как отношения и верны при любых данных; якоря ограничены закрытым
окном `order_date <= 2026-08-31` — по уроку UBR-010 ворота не прикалываются к суммам портфеля,
которые меняются от каждой продажи.

## 4. Остающийся долг: Control Tower всё ещё читает `ozon_raw`

Перенесена только выручка. Количества, GMV, комиссия, расходы по `type_id` и реклама
по-прежнему реконструируются из `ozon_raw` в `wb_mart` — это нарушение изоляции площадок
(политика: `wb_mart` вправе читать только `wb_raw`, `wb_ops`, `evetis_ref`).

Полный перенос здесь невозможен без нового контракта: **`gmv_ordered` не существует ни в
`ozon_mart`, ни в `evetis_mart`**, а Control Tower считает по нему ДРР на пяти экранах владельца.
Изобретать величину в обход контракта — ровно та ошибка, которую исправляет UBR-012.

Кроме того, `wb_mart` вообще не входит в канонический слой `sql/current/`, поэтому эти вью не
покрыты ни политикой внешних датасетов, ни проверками C1–C18.

Правильная цель — перенести Control Tower в `evetis_mart`: по действующей политике именно этот
слой вправе читать и `wb_mart`, и `ozon_mart`, и он уже является нейтральной точкой пересечения
площадок. Это отдельная работа с собственным обоснованием.

## 5. Как заменить hardcoded `UNNEST` из 35 документов (предложение, не реализация)

`ozon_mart.V_OZON_CIS_BUYOUT` — литерал `UNNEST` с 35 строками, перенесёнными руками из
«Отчётов о выкупленных товарах». Он не расширяется сам, и каждый новый документ требует правки
SQL и развёртывания вью.

Предлагаемый путь — по возрастанию стоимости; **ни один шаг не выполнять без отдельного ACK**:

**Шаг 1 (минимальный, рекомендуемый первым).** Перенести данные как есть в таблицу-справочник
`evetis_ref.REF_OZON_CIS_BUYOUT_DOC` с тем же зерном и колонками, а `V_OZON_CIS_BUYOUT` сделать
тонкой вью над ней. Тогда новый документ — это `INSERT` одной строки, а не правка и развёртывание
SQL. Схема потребителей не меняется, экономика не меняется, откат тривиален. Это устраняет
операционный риск, не создавая нового источника данных.

**Шаг 2 (если поток документов вырастет).** Загрузка `RealizationReportCIS-*.xlsx` в
`ozon_raw.RAW_OZON_BUYOUT_REPORT` существующим загрузчиком Ozon, с провенансом номера документа
и периода, и построение справочника поверх сырья. Оправдано только если выкупы перестанут быть
единичными: сейчас это 35 строк за 16 месяцев, примерно два документа в месяц.

**Чего делать нельзя.** Выводить сумму выкупа ставкой — ни «средней», ни «соседней». Ставка 21 %
встречается ровно один раз и ни из чего не следует; любая экстраполяция дала бы там неверную
сумму. Пока документа нет, правильное состояние — `UNPROVEN`, и теперь оно обеспечено кодом.

До шага 1 операционный риск закрыт детекцией U01: незарегистрированный выкуп не пройдёт молча.
