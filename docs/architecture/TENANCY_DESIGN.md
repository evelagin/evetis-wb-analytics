# Мультиарендность: что мешает и как перейти

> **Авторитет — [ADR-08](ADR-08_TENANT_ISOLATION.md).** Решение об изоляции принято 2026-09-24:
> гибридная модель D, у каждого внешнего клиента выделенный GCP-проект, EVETIS остаётся в
> текущем проекте. Если этот документ где-то расходится с ADR-08, прав ADR-08. Редакция
> 2026-09-21 рекомендовала `tenant_id` в общем контрактном слое и имена секретов вида
> `<tenant>/<marketplace>/<key>`. Обе рекомендации заменены: первая — ADR-08, вторая
> недопустима, потому что символ `/` в ID секрета Secret Manager запрещён.

Система выросла на данных одного продавца. Цель — поддерживать многих, **не ломая** текущего.
Документ описывает, где зашит один арендатор и в каком порядке это снимается.

и реестр арендаторов.

## 2. Модель (ADR-08, кратко)

- **Граница безопасности — проект.** Каждый внешний арендатор получает проект `mpa-t-<slug>`
  (или `mpa-t<r>-<slug>`, если базовый ID занят в GCP; грамматика заморожена в T2.1, см. ADR-08).
  Код, образ по digest и правила имён у всех общие. EVETIS — унаследованный арендатор в своём
  проекте.
- **`tenant_id` в данных — логическая метка, а не граница.** Он нужен для межарендаторной
  аналитики платформы и появится в `analytics_share` (T4/T6). Защищать данные одного клиента от
  другого он не может и не должен: это делает проект. Row-level security для разграничения между
  организациями Google не рекомендует.
- **Почему отвергнуты общий проект с датасетом на арендатора (B) и общие таблицы с `tenant_id`
  (C)** — см. ADR-08. Коротко: имена датасетов зашиты в канон, хеши, политику изоляции и IAM.
  Три широкие идентичности EVETIS видят весь свой проект. Пропущенный предикат `tenant_id` в
  любой из ~150 вью дал бы неверные числа, а не ошибку.

## 3. Целевая иерархия

```
tenant           — юридическое лицо / бренд (EVETIS = tenant_id 'evetis')      ← граница: GCP-проект
 └─ marketplace  — WB | OZON
     └─ account  — кабинет продавца (у Ozon это Client-Id; хранится только в Secret Manager)
         └─ sku  — marketplace_sku
tenant └─ product — internal_sku (независим от площадки, живёт в DIM_PRODUCT)
```

Уровень `tenant` с T1 существует в конфигурации (`tenants/<tenant_id>/tenant.json`). В данных
его пока нет, и внутри выделенного проекта он не нужен: там один арендатор. Уровень `account`
не существует нигде. В v1 он и не нужен: один кабинет Ozon на арендатора.

**Выкат runtime и T3 (решение владельца 2026-09-24).** T2.2 сливается первым. T3 может идти на
синтетической инфраструктуре без выката нового runtime на EVETIS. EVETIS остаётся на
production-образе `sha256:24e3c6d6…` до отдельных ворот выката runtime. Новый образ T3
собирает или использует только после собственных ворот.

## 4a. T3 — физическая изоляция (2026-09-25)

```
organizations/1043233412973
├── project-fa311fc0-4d87-4781-986   EVETIS (lien на удаление, T3.1A; Terraform — infra/terraform)
├── mpa-platform (#777428383056)     плоскость управления (T3.1B)
│   ├── gs://mpa-platform-tfstate-777428383056   platform/*  ·  tenants/<tenant_id>/*
│   ├── mpa-runtime (europe-west1, неизменяемые теги)   общий образ runtime по digest
│   ├── tenant-infra-pool / github-tenant-infra          только tenant-infra.yml@main, workflow_dispatch
│   ├── sa-tenant-provisioner                            права только на tenants/
│   ├── sa-runtime-builder (T3.2b)                        запись только в mpa-runtime; Cloud Build
│   └── gs://mpa-platform-runtime-build-777428383056     архивы исходников сборок (провенанс)
└── folders/881419274207 "tenants"   проекты арендаторов mpa-t-<slug>
```

**Контракт реестр → Terraform (T3.2).** Оператор задаёт только `tenant_id`:
`python tools/tenancy/tenant_infra.py plan <tenant_id>`. Всё остальное выводит реестр
(`registry.py terraform-inputs`): проект, префикс state, датасеты, таблицы со схемами из Git
(`pipelines/ozon/schema/`), job'ы и расписания (`tools/tenancy/ozon_contract.py` — единственное
место каденции для выделенных арендаторов), имена секретов и SA, утверждённый образ
(`infra/tenant/runtime_release.json`). Корень `infra/tenant/` один для всех арендаторов;
`client_002` — это новый дескриптор, а не новый код. Проект и биллинг создаёт человек; корень
работает внутри готового проекта и проверяет до изменений: проект существует, ACTIVE, лежит прямо
в `tenants/`, с биллингом, не EVETIS и не платформа.

**Выпуск образа runtime (T3.2b, 2026-09-25).** Образ один на всех арендаторов; отличаются
только окружение, проект и идентичности. Выпуск — ворота, а не деплой:
1. Квалификация runtime (`pipelines/ozon/tests`: differential T2/T2.2, пустые секреты,
   переносимость, вырезание учётных данных, strict caps, состав образа).
2. Источник — архив ровно одного коммита `main`:
   `git archive --format=tar.gz <SHA> pipelines/ozon/runtime` (детерминирован, SHA коммита в
   pax-заголовке). Рабочее дерево в сборку не попадает.
3. Cloud Build в `mpa-platform` по `infra/tenant/releases/ozon-runtime.cloudbuild.yaml` от
   `sa-runtime-builder`. Первый шаг сверяет идентичность сборки с metadata server и отказывает,
   если это не `sa-runtime-builder`. Образ пушится, только если прошли шаги состава `/app` и отказа
   без `GCP_PROJECT_ID`. Сборщик закреплён по digest, build args и секретов нет, тег = SHA коммита
   (теги репозитория неизменяемы).
4. `tools/tenancy/runtime_image_check.py <образ@digest> --source-sha <SHA>` — опубликованный образ
   локально, без сети, с конфигурацией `client_001` и эфемерного `client_002`: отказ без проекта,
   отказ без версий секретов до HTTP, секреты и BigQuery только своего проекта, EVETIS не упомянут.
5. PR: digest в `infra/tenant/runtime_release.json` и запись провенанса
   `infra/tenant/releases/ozon/<sha7>.json` (исходник, дерево, хеши файлов и архива, сборка,
   идентичность, базовый образ, пакеты, проверки, «EVETIS не развёрнут»). Конфиг сборки привязан к
   записи хешем: изменить его можно только вместе с новым выпуском. Откат — PR с прежним digest.

Права `sa-runtime-builder` (постоянные): `roles/artifactregistry.writer` только на `mpa-runtime`,
`roles/storage.objectViewer` только на бакет исходников сборки, `roles/logging.logWriter` на
`mpa-platform`. Ни EVETIS, ни папки `tenants`, ни state, ни Secret Manager, ни IAM org/folder, ни
биллинга. Роль `roles/cloudbuild.builds.builder`, которую Google автоматически выдаёт устаревшему SA
`777428383056@cloudbuild.gserviceaccount.com` при включении Cloud Build, снята (решение владельца
2026-09-25): сборка без явного `--service-account` не получает доступа ни к state, ни к реестру.
Запускать сборки может только владелец (`cloudbuild.builds.create` и `actAs` на SA). Первый выпуск —
`ozon-runtime@sha256:884ee5dd…` из `08f9438` (сборка `dc72ca9f`). Образ инертен, пока план и
применение T3.3 на него не сошлются; на EVETIS он не выкатывается (EVETIS остаётся на `24e3c6d6`).

**State.** Эксперимент T3.2 (провижионер, префикс `tenants/_t32_backend_probe`, удалён): init,
plan, apply, refresh, `state pull/push`, блокировка и `force-unlock` работают только с правами на
объекты `tenants/*`, без `storage.objects.list`. Список нужен лишь командам `terraform workspace`,
а workspaces запрещены (изоляция — префиксом). Поэтому решение — один бакет платформы и
провижионер с условием на префикс; бакетный листинг не выдаётся. Восстановление версий
объектов — у владельца (список версий), провижионер восстанавливает `state push -force` из копии.

**Безопасность расписаний (ADR-08 И2).** Задание Scheduler создаётся ENABLED и ставится на паузу
вторым вызовом; пауза — не механизм безопасности. Механизм — отсутствие права: у `sa-ozon-scheduler`
нет `run.invoker`, у runtime SA нет `run.jobs.run`, поэтому сработавшее задание получает 403, а
не загрузку. Права вызова выдают только ворота активации.

**Секреты (ADR-08 И1).** Terraform ведёт только контейнеры секретов и их IAM; версий и значений —
никогда; учётные данные вносятся вне Terraform и его state (T5).

**Решения к T3.3 (не применено; `tools/tenancy/iam_proposals.py`).**
- **Роль провижионера** `mpaTenantProvisioner` — 27 разрешений вместо admin-ролей T3.1B, каждое с
  классом (нужно всегда / только при онбординге / доказать на живом плане / удалить). Прямые права:
  создание ресурсов арендатора, обновление образа job'а, IAM датасетов и секретов, jobUser на проект.
  **Косвенные возможности (остаются):** `cloudscheduler.jobs.create` + `actAs` дают исполнение —
  созданное задание активно и может вызвать API Google от имени runtime SA (например, выгрузить
  строки арендатора наружу через BigQuery EXPORT DATA); `setIamPolicy` на датасеты и секреты
  выдаёт доступ членам, которых допускает org policy; `run.jobs.update` подменяет код, который
  исполнится после активации. **Предотвращено:** значения секретов, вызов job'ов, удаление, токены и
  ключи SA, IAM папки/организации/EVETIS/платформы, state `platform/*`. Текущие живые admin-роли
  T3.1B сильнее: `run.admin` запускает job'ы, `bigquery.admin` читает строки (P2-9).
- **Сдерживание членов IAM** — org policy `iam.managed.allowedPolicyMembers` на `tenants/`:
  набор принципалов организации + владелец. Закрывает выдачу внешним принципалам, `allUsers`,
  `allAuthenticatedUsers`. Не закрывает выдачу SA внутри организации (её ловит сканер плана) и
  вынос через EXPORT DATA.
- **Необязательно:** deny-политика на провижионера против чтения строк и значений секретов.
- **WIF:** предлагаемое условие добавляет `job_workflow_ref == workflow_ref`; живое условие не
  менялось, наличие claim у обычного job'а — проверить пробным токеном.
- Для пользовательских ролей нужен `roles/iam.organizationRoleAdmin` у владельца.

**Проверка биллинга.** Провайдер Terraform заполняет `billing_account` из `billingAccountName` и
`billingEnabled` не читает. Поэтому guard в Terraform проверяет только привязку (null и пусто —
отказ), а `tools/tenancy/tenant_infra.py` до плана читает `projects.getBillingInfo` (нужно лишь
`resourcemanager.projects.get`) и требует `billingEnabled == true`; любая ошибка чтения — отказ.

**Префикс state в условиях IAM.** Ключ backend — `tenants/<tenant_id>` (backend сам добавляет
`/default.tfstate`). Любое будущее условие IAM по арендатору строится от
`naming.terraform_state_iam_prefix` = `tenants/<tenant_id>/` со слэшем: иначе `tenants/abc`
покрыл бы `tenants/abc_x/…`.

**WB.** Проектная граница не зависит от площадки. WB добавится соседним модулем (`sa-wb-*`,
`wb_raw`/`wb_mart`, свои секреты и job'ы) и расширением `tenant.v1` (датасеты и `secret_refs`
WB). Корень не предполагает, что площадка одна: датасеты, API и модули площадок приходят из
контракта.

## 4b. Клиентский интерфейс данных (принято 2026-09-25)

`analytics_share` — единственный официальный интерфейс данных VTS для клиента: BI, AI-ассистенты
клиента и одобренные внешние аналитические инструменты.

```
AI-ассистент / BI клиента
          ↓ ТОЛЬКО ЧТЕНИЕ
     analytics_share (проект арендатора)
```

Клиентскому AI не нужен и не выдаётся доступ к: репозиторию VTS, Terraform, `ozon_raw`,
внутренним справочным и операционным датасетам, Secret Manager, Cloud Run, Cloud Scheduler,
`mpa-platform`, EVETIS, другим арендаторам. Реализация — T4/T6; в T3 не создаётся ни
`analytics_share`, ни доступ клиента.

Прежние шаги этого документа, которые больше не нужны или заменены:

- **«убрать проект из SQL»** — канон сохраняет полную квалификацию, проект подставляется
  рендером (T4);
- **«`tenant_id` в `FACT_SKU_DAILY` и справочники EVETIS»** — справочники EVETIS не
  мигрируют, у арендатора свой `ref` в его проекте;
- **«параметр арендатора в Metabase»** — Metabase EVETIS не становится клиентским доступом.

## 5. Подключение нового продавца (целевой сценарий)

```
PR: tenants/<tenant_id>/tenant.json (status NEW) → ворота ci / tenancy
  → T3: проект строго naming.derive_project_id (mpa-t-<slug>, при занятом ID — mpa-t<r>-<slug>),
        датасеты ozon_raw/ref, контейнеры секретов, job'ы (расписания без права вызова, И2)
  → владелец вносит значения ключей в секреты проекта арендатора (stdin, не Git, не чат):
        ozon-seller-client-id, ozon-seller-api-key, ozon-perf-client-id, ozon-perf-client-secret
  → проверка ключей read-only вызовом каждого API
  → исторический backfill с STRICT_PAGE_CAPS=1 (Performance: окна ≤ 62 суток)
  → ворота данных арендатора
  → analytics_share + доступ клиента
  → READY → ACTIVE (решение владельца)
```

Имена ресурсов, секретов и датасетов выводит **только** `tools/tenancy/naming.py`. Terraform,
рендер и провижининг свои правила имён не заводят.

**Правило авторитета реестра (T2.1).** Потребители узнают арендаторов только через API реестра:
`registry.valid_tenants()`, `registry.load_tenant()` или `python tools/tenancy/registry.py list`
и `runtime-env`. Это касается Terraform и провижининга T3, рендера T4 и любых скриптов.
- Перебирать `tenants/*/tenant.json` самостоятельно и разбирать файлы своим парсером запрещено.
- Реестр отдаёт данные только целиком валидным: при любом нарушении — ни одного документа.
- Файлы читаются строгим загрузчиком: повторяющиеся ключи и NaN/Infinity отвергаются.
- Состав `tenants/` задан белым списком: только `_schema/tenant.schema.json` и каталоги
  `<tenant_id>/tenant.json`; символических ссылок нет.

Инфраструктурный код получает на вход проверенный вывод реестра, а не файлы.

**Контракт имён обязателен для физического провижининга.** После T2.1 любой физический
проект арендатора создаётся только с ID, выведенным `naming.derive_project_id`. Грамматика
заморожена: ADR-08, раздел T2.1. EVETIS — единственное исключение: это унаследованное
состояние, его проект не выводится и не переименовывается.

На момент T2.1 ни одного физического проекта арендатора нет. `client_001` — синтетика, T3 не
начат, образ Ozon runtime с изменениями T2 не выкачен.

**Что остаётся ручным:**

| Шаг | Сейчас | Чем снимается |
|---|---|---|
| Значения ключей | владелец, вручную | остаётся ручным в MVP; интерфейс передачи ключей отложен (D5) |
| Конфигурация | PR в `tenants/` | уже конфигурация (T1) |
| Backfill | режим загрузчика + строгие лимиты | T2 (лимиты), T5 (оркестрация) |
| Справочник товаров | ручной ввод продавца | бутстрап из каталога (T4) + форма ввода |
| Себестоимость | ручной ввод по партиям | остаётся ручной; без неё — режим PRE_COGS |
| Доступ клиента | нет | T6 |

Справочник товаров и себестоимость не автоматизируются: их знает только продавец. Задача в том,
чтобы свести участие человека к одной форме ввода вместо правки кода.

## 6. Коммерческий MVP и самообслуживание

**MVP (сейчас):** первых клиентов подключает владелец. Ключи вносит владелец. Провижининг идёт
по реестру через ворота. Клиент получает только чтение `analytics_share`: без репозитория, без
Terraform, без IAM платформы.

**SaaS с самообслуживанием (позже, после T8):** портал подключения, биллинг, конфигурация силами
клиента. В архитектуре v1 под это ничего не строится.

## 7. Ограничения, которые мультиарендность не снимет

- Лимиты API у каждого арендатора свои и считаются отдельно.
- WB и Ozon по-разному датируют деньги; нейтральный слой обязан продолжать называть базис даты
  (`fact_date_semantics`), а не усреднять его.
- Изоляция маркетплейсов остаётся инвариантом: `tenant_id` добавляет измерение, но не отменяет
  запрет читать `wb_*` из `ozon_mart`.
- Ozon runtime грузит заказы только FBO. Клиент на FBS/rFBS требует отдельного решения (D3).
