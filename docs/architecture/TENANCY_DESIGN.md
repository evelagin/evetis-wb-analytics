# Мультиарендность: что мешает и как перейти

Система выросла на данных одного продавца. Цель — поддерживать многих, **не ломая** текущего.
Этот документ не предлагает включить мультиарендность: он называет, где именно зашит один
арендатор, и описывает порядок, в котором это снимается.

---

## 1. Где зашит арендатор (измерено 2026-09-21)

| Место | Масштаб | Доказательство |
|---|---|---|
| GCP-проект в SQL, Terraform, скриптах | **220 файлов** | `git grep -l 'project-fa311fc0' \| wc -l` |
| Имена секретов содержат бренд | `EVETIS_OZON_CLIENT_ID`, `EVETIS_OZON_API_KEY`, `EVETIS_OZON_PERFORMANCE_CLIENT_ID`, `WB_TOKEN_*` | `pipelines/ozon/runtime/common.py:101` |
| Датасеты как пространство имён арендатора | `wb_raw`, `ozon_raw`, `evetis_ref` — без поля арендатора | `system_inventory.json` |
| Ключи данных | зерно везде `date × sku` или `date × marketplace × sku`; арендатора в ключе нет | `evetis_mart.FACT_SKU_DAILY` |
| Справочники ручного ввода | `REF_PRODUCT_MASTER` (25), `REF_SKU_CHANNEL_MAP` (47), `REF_SKU_COGS_HISTORY` (17) — данные одного бренда | инвентарь |
| Google Sheets | ID книг зашиты в Apps Script | `apps-script/**` |
| Дашборды Metabase | 3 дашборда, 57 карточек, запросы без параметра арендатора | `metabase/manifest.json` |
| Расписания | по одному на загрузчик, без размерности арендатора | Cloud Scheduler, 20 заданий |

**Вывод: сегодня арендатор = GCP-проект.** Это работоспособная модель изоляции, и она же —
потолок: второй продавец означает второй проект, второй Terraform-стейт, второй Metabase и
ручную синхронизацию кода между ними.

---

## 2. Две возможные модели

**A. Проект на арендатора (то, что есть).** Максимальная изоляция данных и прав, ноль
изменений в SQL. Цена: копирование инфраструктуры и кода на каждого клиента, дрейф между
копиями неизбежен, общей аналитики нет.

**B. Общий проект, арендатор в ключе.** `tenant_id` — часть первичного ключа всех фактов,
изоляция — через авторизованные вью и политики доступа на уровне строк. Цена: миграция схем и
риск утечки между арендаторами при ошибке в одном предикате.

**Рекомендация.** Двигаться к B **в слое контрактов** (`evetis_mart`, `evetis_ref`) и оставить
A **в слое сырья** (`wb_raw`, `ozon_raw`) до тех пор, пока не появится второй реальный клиент.
Причина: сырьё несёт наибольший риск утечки и наименьшую пользу от объединения, а канонический
слой — наоборот. Это позволяет подготовиться без миграции 283 объектов «на всякий случай».

## 3. Целевая иерархия

```
tenant           — юридическое лицо / бренд (EVETIS = tenant_id 'evetis')
 └─ marketplace  — WB | OZON
     └─ account  — кабинет продавца (сегодня один на площадку; у Ozon это client_id)
         └─ sku  — marketplace_sku
tenant └─ product — internal_sku (независим от площадки, живёт в DIM_PRODUCT)
```

Сегодня реализованы только два нижних уровня (`internal_sku` ↔ `marketplace_sku` через
`REF_SKU_CHANNEL_MAP`). Уровни `tenant` и `account` не существуют нигде — ни в данных, ни в
конфигурации.

## 4. Порядок перехода (ни один шаг не ломает текущего арендатора)

**T0 — назвать арендатора, ничего не меняя.** Ввести константу `tenant_id = 'evetis'` в одном
месте конфигурации. Нигде не использовать. Смысл: появляется единственное место, куда смотреть.

**T1 — убрать проект из SQL.** 220 файлов ссылаются на проект по имени. Канонический слой уже
хранит полностью квалифицированные имена намеренно (C12 требует квалификации). Переход: имя
проекта подставляется при развёртывании, а канонический файл продолжает хранить его дословно
для сверки хешей. Это надо продумать как изменение контракта `canonical_hash_v1`, а не как
`sed` по репозиторию.

**T2 — секреты по схеме, а не по бренду.** `EVETIS_OZON_CLIENT_ID` → `<tenant>/<marketplace>/client_id`.
Загрузчик получает `tenant_id` параметром запуска и собирает имя секрета сам. Изменение
локально: `pipelines/ozon/runtime/common.py` и Terraform, доступ выдаётся по префиксу.

**T3 — `tenant_id` в канонический слой.** Добавить колонку в `evetis_mart.FACT_SKU_DAILY` со
значением по умолчанию `'evetis'` и включить её в объявленное зерно. Пока арендатор один,
проверки зерна не меняются; когда появится второй — ключ уже готов.

**T4 — справочники с арендатором.** `REF_PRODUCT_MASTER`, `REF_SKU_CHANNEL_MAP`,
`REF_SKU_COGS_HISTORY` получают `tenant_id`. Это данные ручного ввода: миграция требует
решения владельца и резервной копии, потому что восстановить их из источника нельзя.

**T5 — конфигурация вместо кода.** Реестр арендаторов: площадки, учётные записи, имена
секретов, расписания, признак активности. Загрузчики читают реестр, а не константы.

**T6 — дашборды с параметром.** Карточки Metabase получают параметр арендатора; сегодня они
фильтруются неявно тем, что в данных один продавец.

**T7 — onboarding.** Только после T5: см. §5.

## 5. Подключение нового продавца (целевой сценарий)

```
создать tenant в реестре
  → владелец кладёт ключи площадок в Secret Manager по схеме <tenant>/<marketplace>/<key>
  → автоматическая проверка ключей (read-only вызов каждого API)
  → создать конфигурацию: площадки, кабинеты, валюта, налоговый режим
  → исторический backfill в пределах лимитов API
        (WB: воронка только 7 суток; Ozon Performance: окно ≤ 62 суток)
  → включить расписания
  → прогнать ворота данных набора арендатора
  → создать дашборды из шаблона
  → READY
```

**Что сегодня требует рук и почему:**

| Шаг | Сейчас | Чем снимается |
|---|---|---|
| Ключи | вручную, имена с брендом | T2 |
| Конфигурация | правка кода и Terraform | T5 |
| Backfill | одноразовые скрипты в `docs/**/audit_*/raw/` | вынести в `pipelines/<домен>/runtime/` как режим загрузчика |
| Справочник товаров | ручной ввод владельца | остаётся ручным — это бизнес-данные, но форма ввода должна быть одна |
| Себестоимость | ручной ввод по партиям | остаётся ручным |
| Дашборды | копирование карточек | T6 |

Честно: **справочник товаров и себестоимость не автоматизируются** — их знает только продавец.
Целевая задача не «убрать человека», а свести его участие к одной форме ввода вместо
редактирования кода.

## 6. Ограничения, которые мультиарендность не снимет

- Лимиты API у каждого арендатора свои и считаются отдельно.
- WB и Ozon по-разному датируют деньги; нейтральный слой обязан продолжать называть базис даты
  (`fact_date_semantics`), а не усреднять его.
- Изоляция маркетплейсов остаётся инвариантом: `tenant_id` добавляет измерение, но не отменяет
  запрет читать `wb_*` из `ozon_mart`.
