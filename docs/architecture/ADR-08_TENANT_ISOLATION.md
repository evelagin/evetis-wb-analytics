# ADR-08. Изоляция арендаторов: гибридная модель D

Дата решения: 2026-09-24 · Статус: **принято (D1). Реализовано: T1 (контракт и реестр), T2
(переносимость Ozon runtime), T2.1 (грамматика проектов), T2.2 (безопасность runtime); T3.1A/T3.1B
(lien на EVETIS, папка `tenants/`, проект платформы `mpa-platform`) — 2026-09-25. Проектов
арендаторов нет; корень Terraform арендатора — T3.2 ([`TENANCY_DESIGN.md`](TENANCY_DESIGN.md) §4a).**

Этот ADR авторитетен. Если [`TENANCY_DESIGN.md`](TENANCY_DESIGN.md) или другой документ ему
противоречит, прав этот ADR.

## Решение

**Каждый внешний клиент получает выделенный GCP-проект. EVETIS остаётся в текущем проекте как
унаследованный арендатор `evetis`. Отдельный проект платформы (плоскость управления) появится
позже, в T3.**

| Слой | Где живёт | Что делит между арендаторами |
|---|---|---|
| Плоскость управления | Git (`tenants/*/tenant.json`, `tools/tenancy/`), позже — проект платформы | реестр, правила имён, ворота CI |
| Код и образы | один репозиторий, один образ по digest | всё: код один для всех арендаторов |
| Плоскость данных | проект арендатора `mpa-t-<slug>` | ничего |
| Секреты маркетплейсов | Secret Manager в проекте арендатора | ничего |
| Доступ клиента | только `analytics_share` в проекте арендатора (D2) | ничего |

Граница безопасности — **GCP-проект**. `tenant_id` внутри данных — логическая метка для будущей
межарендаторной аналитики платформы, а не граница безопасности: от утечки он не защищает и
на него нельзя полагаться как на фильтр доступа.

## Почему выделенный проект

1. **Код уже устроен так, что проект — пространство имён арендатора.** Имена датасетов
   зафиксированы в SQL, в хешах канона (`canonical_hash_v1`), в `EXTERNAL_DATASET_POLICY`,
   в Terraform и в условиях IAM. Отдельный проект сохраняет все имена внутри неизменными.
2. **Широкие идентичности EVETIS видят весь свой проект.** `metabase-read-only`
   (`dataViewer` на проект), `sa-terraform-plan` (`viewer` на проект), AE v1
   (`resourceViewer`, `logging.viewer` на проект). В общем проекте они автоматически
   видели бы данные клиента. В отдельном проекте у них нет ни одной роли.
3. **Коллизии данных исчезают без миграции.** Ни одна таблица `ozon_raw` не несёт продавца.
   В общем датасете второй продавец перезаписал бы `RAW_OZON_SELLER_INFO` (ключ — только
   `snapshot_date`), а его снимок акций терялся бы как `REUSED` (id load-задачи без продавца).
   Внутри своего проекта этих коллизий нет.
4. **Удаление клиента — одна операция** (`projects delete`, 30 дней на восстановление). Её
   невозможно направить на EVETIS: у идентичности онбординга нет ролей в проекте EVETIS, а на
   проекте EVETIS ставится lien (T3).
5. **Стоимость на старте — около нуля.** Проект бесплатен, BigQuery и Cloud Run оплачиваются
   по факту, данные Ozon одного продавца — около 15 МБ.

## Отвергнутые варианты

**B. Датасет на арендатора в общем проекте.** Google рекомендует эту схему для масштаба
в тысячи арендаторов. У нас масштаб — единицы. Цена для нас:

- переименование датасетов во всём SQL и новая версия хеша канона;
- `EXTERNAL_DATASET_POLICY` пришлось бы строить на ролях датасетов, а не на именах;
- точные условия IAM вместо префиксных. Нынешнее `startsWith(".../datasets/ozon_raw")` у
  `sa-ozon-ingestion` совпало бы и с `ozon_raw_client001`;
- сужение трёх проектных идентичностей EVETIS.

Выигрыш на нашем масштабе не окупает этой работы и этого риска.

**C. Общие таблицы с обязательным `tenant_id`.** Безопасность зависела бы от предиката в
каждом из ~150 вью. Витрины Ozon уже содержат пулинг без продавца: глобальный
`MAX(snapshot_date)`, мода комиссии, p70 логистики, одна строка `seller_info`, поэтому
пропущенный предикат дал бы неверные числа, а не ошибку. Google прямо не рекомендует
row-level security для разграничения между организациями.

**A в чистом виде** (проект на арендатора без плоскости управления). Онбординг задевал бы
проект EVETIS: реестр образов, state и WIF. Модель D добавляет к нему отдельный проект
платформы.

## Путь роста

Когда арендаторов станут десятки и управление проектами станет узким местом, данные можно
перенести в модель B (датасет на арендатора в одном проекте данных). Это возможно, потому что
схемы и канон одинаковы у всех проектов, а объём данных мал. Условия перехода:

1. `canonical_hash_v2` нормализует проект и датасет перед хешированием;
2. `EXTERNAL_DATASET_POLICY` переходит на роли датасетов;
3. все проектные идентичности сужены до датасетов.

Контракт арендатора (`tenant.v1`) к этому готов: поле `data_boundary.kind` расширяется новым
видом без изменения остальных полей.

## Коммерческий MVP и самообслуживание — разные цели

**Сейчас (MVP):** владелец вручную подключает первых клиентов. Ключи вносит владелец в Secret
Manager проекта клиента. Провижининг идёт по реестру через ворота с решением владельца.
Клиент получает только доступ на чтение к `analytics_share`.

**Не сейчас:** портал самообслуживания, где клиент сам подключает ключи, биллинг, изменение
конфигурации клиентом. Эти задачи не планируются до завершения T8.

## Что сделано в T1/T2

- `tenants/_schema/tenant.schema.json` — контракт `tenant.v1`. Полей для значений секретов в
  нём нет: разрешены только ссылки на секреты по ID Secret Manager (`[A-Za-z0-9_-]{1,255}`,
  без `/`).
- `tenants/evetis/tenant.json` — только описание (`LEGACY_EXISTING_CONFIG`). Авторитетом
  остаётся Terraform. Любая правка дескриптора против зафиксированного факта — ошибка CI.
- `tenants/client_001/tenant.json` — синтетика. Проект не создан, секретов нет.
- `tools/tenancy/naming.py` — единственное место вывода имён: проект (грамматика — ниже, в
  разделе T2.1), нейтральные имена секретов и датасетов внутри проекта, метки, префикс state.
- `tools/tenancy/validation.py` и `registry.py` — ворота CI `ci / tenancy`.
- `pipelines/ozon/runtime`:
  - проект задаётся только явно (fail-closed);
  - имена секретов берутся из `OZON_SECRET_*`; значения по умолчанию равны прежним именам
    EVETIS;
  - справочник берётся из `BQ_REF_DATASET`;
  - `STRICT_PAGE_CAPS` включает строгий режим;
  - учётные данные не попадают в журнал.

  Поведение EVETIS не изменилось; доказательство — тесты.

## T2.1: грамматика ID проекта — ЗАМОРОЖЕНА для провижининга внешних арендаторов

Независимое ревью PR #171 нашло неоднозначность: форма `mpa-t-<slug>[-<суффикс>]` давала
`client` + суффикс `001` = базовый ID арендатора `client_001` (L6). До создания первого
физического проекта грамматика заменена:

```
ревизия 1 (по умолчанию):  mpa-t-<slug>
ревизия r ∈ {2..9}:        mpa-t<r>-<slug>
slug = tenant_id, «_» → «-»
```

- **Почему нет коллизий.** Признак ревизии стоит на фиксированной позиции: шестой символ ID.
  В базовой форме там всегда `-`, в ревизии — цифра. Поэтому ревизия не пересекается ни с
  одним slug, а slug взаимно однозначен с `tenant_id` (в `tenant_id` нет `-`, нет `__` и `_`
  в конце). Отображение `(tenant_id, ревизия) → ID` инъективно и обратимо
  (`naming.parse_project_id`). Это доказано исчерпывающим перебором и случайным поиском
  коллизий (`tools/tests/test_tenancy_hardening.py`).
- **Почему не `--`.** Официальная документация о двойном дефисе не говорит ничего: ни запрета,
  ни гарантии. Схема с фиксированной позицией обходится одиночными дефисами.
- **Что требует Google, а что — политика платформы.** Источник: Resource Manager, «Create
  projects», https://docs.cloud.google.com/resource-manager/docs/creating-managing-projects
  (страница обновлена 2026-09-18 UTC, прочитана 2026-09-24).

  | Ограничение | Статус |
  |---|---|
  | 6–30 символов | требование Google Cloud |
  | только строчные буквы, цифры, дефис | требование Google Cloud |
  | первый символ — буква | требование Google Cloud |
  | последний символ — не дефис | требование Google Cloud |
  | нет подстрок `google`, `ssl` | требование Google Cloud (список «such as» — не исчерпывающий) |
  | нет подстрок `null`, `undefined` | в списке требований — «avoid», но раздел API: `projects.create()` отвергает их с `INVALID_ARGUMENT` → считаем требованием |
  | ID не занят и не использовался ранее | требование Google Cloud; проверяется только при создании (T3) → ревизия |
  | двойной дефис | Google не регулирует; в нашей грамматике не встречается (политика платформы) |
  | префикс `mpa-t`, ревизия на 6-й позиции | политика платформы |
  | `tenant_id` = `[a-z][a-z0-9_]{2,30}`, без `__` и `_` в конце | политика платформы (контракт `tenant.v1`) |
  | зарезервированные `tenant_id` и префиксы | политика платформы |
  | отказ вместо обрезки: slug ≤ 24, с ревизией ≤ 23 | политика платформы (следствие лимита 30 и префикса) |

  Всё это проверяется при выводе ID. Список запрещённых подстрок Google не исчерпывающий:
  неизвестное слово может отвергнуть только `projects.create()` в T3. Тогда арендатору
  выбирают другой `tenant_id` до создания проекта.
- **Ревизия** нужна только если базовый ID глобально занят в GCP (ID общие для всех
  клиентов Google и не освобождаются после удаления проекта).
  - Выбирает её владелец платформы при создании проекта; случайных суффиксов нет.
  - Хранится в `data_boundary.project_id_revision` (целое 2–9; отсутствие поля = 1).
  - Валидатор требует, чтобы `gcp_project_id` был ровно каноническим выводом из
    `(tenant_id, ревизия)`.
  - Коллизии между арендаторами исключены грамматикой, а реестр дополнительно проверяет
    уникальность проектов.
  - Занятость ID в GCP выясняется в T3 при создании проекта.
- **ID проекта не зависит** от отображаемого и юридического имени.
- **`client_001` сохраняет `mpa-t-client-001`** (ревизия 1). EVETIS не затронут: его проект —
  зафиксированное унаследованное состояние вне этого пространства имён.

**Грамматика заморожена.** После того как T3 создаст первый физический проект, любое её
изменение возможно только через отдельный ADR миграции. Эталонные значения закреплены
тестом `test_frozen_grammar_golden_vectors`. Физический провижининг после T2.1 обязан брать ID
проекта только из `naming.derive_project_id`.

**Реестр как единственный источник (T2.1).**
- **Авторитет.** Потребители (Terraform и провижининг T3, рендер T4, скрипты) получают
  арендаторов только через `registry.valid_tenants()`, `registry.load_tenant()` или
  `registry.py list` и `runtime-env`. Данные отдаются только из целиком валидного реестра.
  Собственный перебор `tenants/*/tenant.json` запрещён.
- **Строгий JSON.** Единственный загрузчик — `validation.parse_tenant_json`: повторяющиеся
  ключи на любой вложенности и NaN/Infinity отвергаются, чтобы разные парсеры не прочли разное.
- **Зарезервированный каталог.** Состав `tenants/` задан белым списком:
  - `_schema/` содержит только `tenant.schema.json`;
  - остальные каталоги названы допустимым `tenant_id` и содержат только `tenant.json`;
  - символических ссылок нет.
- **Точность.** Идентификаторы проверяются полным совпадением строки, а `schema_version` —
  ровно целым `1`.

## Обязательные инварианты провижининга арендатора (T3.2, 2026-09-25)

**И1. Секреты и state Terraform.** Terraform может управлять контейнерами Secret Manager и их
IAM-метаданными, но **никогда** — версиями секретов и их значениями.
- Ресурс `google_secret_manager_secret_version` в Terraform арендатора запрещён (тест
  `test_secret_state_invariant_*`, сканер плана `tools/tenancy/plan_scan.py`).
- Учётные данные маркетплейсов вносятся **вне Terraform и вне его state** — отдельным
  контролируемым шагом жизненного цикла (T5), не этим корнем.
- Значения учётных данных никогда не появляются в дескрипторах реестра (`tenant.v1` допускает
  только ID секретов), в переменных Terraform, в плане, state и выводах Terraform.

**И2. Активация расписаний.** Базовый провижининг не даёт никому права вызвать Cloud Run
job арендатора: у SA планировщика нет `run.invoker` (и вообще ролей), у runtime SA нет
`run.jobs.run`. Задание Cloud Scheduler создаётся API всегда ENABLED и ставится на паузу
отдельным вызовом — пауза не атомарна и механизмом безопасности не считается; безопасность
держится на отсутствии права вызова. Пустые секреты (runtime отказывает) — третий слой.
`run.invoker` для SA планировщика и снятие паузы выдают только будущие ворота активации (T5/T6)
после ключей, сверки и решения владельца.

**И3. Цель провижининга.** Производственный экспорт контракта начинается только с `tenant_id`:
канонический `tenants/` → строгий загрузчик → `naming` → контракт. Ни готовый документ, ни
другой корень реестра на вход не принимаются.

## Клиентский интерфейс данных (решение владельца 2026-09-25)

`analytics_share` — единственный официальный интерфейс данных VTS для клиента: BI, AI-ассистенты
клиента, одобренные внешние аналитические инструменты. Доступ — только чтение, только этот датасет
в проекте арендатора. Клиентскому AI не требуется и не выдаётся доступ к исходному коду VTS,
Terraform, `ozon_raw` и другим внутренним датасетам, Secret Manager, Cloud Run, Cloud Scheduler,
проекту платформы, EVETIS и другим арендаторам. Реализация — T4/T6.
