## Minimal implementation

`response_quality` is a pure deterministic planner/renderer/evaluator. It resolves identity, facts and hard routes from the same immutable current snapshot. Hard failures remain separate from quality diagnostics (`GOOD` / `NEEDS_IMPROVEMENT`). Budget is a maximum of 0/1/2 facts, never a quota. Service complaints use zero product facts. Questions begin with a direct answer or an explicit factual unknown. The local voice rules cover the observed broken-cap and ordinary age phrasing missed by the conservative rules classifier; serious safety, legal, identity and conflict routes continue to dominate. Frequency/amount unknown wording gives no invented directions.

A snapshot-grounded ingredient-presence fact may accompany a relevant positive experience. Causal softness is separately rejected by V-CLAIM. Canonical hyaluronic acid and sodium hyaluronate names outrank the shared stem. The shared generic stem stays ambiguous; a related ingredient never inherits product presence. Add missing exact English Salicylic Acid detection. Snapshot/policy/ODR-07 values and safety templates remain byte-for-byte unchanged.

Shadow runs inside the existing bounded V3 runner. Comparison metadata and candidate text are stored only in its existing `v3_shadow_runs` Firestore ledger; BQ schema unchanged. Existing ledger hashes without a recoverable V3 draft yield V3 baseline UNPROVEN. Repetition is checked against candidates in the bounded ledger scan and current batch. Quality errors and ledger backfill errors are isolated; backfill consumes the item budget. V2 documents and WB/Telegram are not reachable from this component.

## Activation and operator recovery

- `V31_QUALITY_SHADOW_ENABLED` defaults true and only runs inside enabled V3 shadow.
- `V31_OPERATOR_RECOVERY_ENABLED` defaults false. First deployment preserves absent env flags and leaves operator recovery inactive. A later explicit ACK must select an activation revision/config.
- No new runtime dependency, cloud schema, scheduler, IAM, service account, ingress or scaling change.

Inactive recovery preserves existing primary generation and cards. Ingredient detection and the additional causal-claim check apply to the existing publication verifier after code promotion.

When separately enabled: initial AI, manual edit and regenerated candidates pass current policy plus hard-route planning. One corrected candidate can be created from allowed facts and the V3 plan; dry V3 text is never blindly installed. The final candidate is independently hard-verified again. A failed style-only improvement keeps an already safe original with NEEDS_IMPROVEMENT; quality does not create a BLOCK. A hard failure with an unsafe replacement yields HUMAN_REVIEW and no Publish button.

Original/repaired generations are retained. Edit/regenerate commits use one existing fenced transaction. A stale Publish hits the current gate; repair is saved under the publication lease and returns a readable card with reasons, without WB GET/write. Its Publish includes the new generation. Legacy and stale-version callbacks cannot approve the changed text; even legacy lease acquisition binds the observed generation atomically. A new operator click still goes through current policy, durable intent and existing review/question read-before-write/read-back verification. Unknown/accepted outcomes retain their existing semantics; no automatic customer publication is added.

Cards retain customer context and the ready text; repair reasons are secondary. Serious cases remain HUMAN_REVIEW, with no ordinary generated replacement. Mild discomfort thresholds/routes/templates were not recalibrated.
