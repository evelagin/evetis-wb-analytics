# Задача для Claude Code: СПП Wildberries в Юнитку (WB_Юнит_2025, колонка AB)

Дата постановки: 28.09.2026. Владелец: Евгений (EVETIS).

## Цель

Колонка `AB` «СПП %» в листе `WB_Юнит_2025` сейчас MANUAL (см. `docs/UNITKA_2_0_COLUMN_MAP.md`, смещение 15) и почти всегда пустая. От неё зависят `AC` (цена с СПП), `Z` (ДРР), налог `AH`, итоги `AC767`, `Z767`, `K767` (`SPP_DEPENDENT_FIELDS` в `cloud/src/loaders/unitka/integrity.ts`). Нужно, чтобы каждое утро за прошедшие дни в `AB` попадала фактическая СПП WB по каждому SKU с понятной меткой источника.

## Что уже известно (проверено 27–28.09 в облаке и на сайте WB)

- **Источник 1 — выкупы, уже есть в BigQuery.** `wb_raw.V_WB_SALES_RETURNS` содержит `spp`, `finished_price`, `price_with_disc` по каждому выкупу. Средняя СПП по дате выкупа: 01–08.09 — 12–19 %, 13–20.09 — 21–29 %, 24–27.09 — 35–39 %; разброс в один день 0…45 %. Медиана 21–28.09 по товарам: сыворотка анти-акне 33 %, крем анти-акне 35 %, пудра 33 %, тоник увлажняющий 35 %, тоник анти-акне 32 %, крем для рук 33 %. Минус: выкуп приходит с задержкой, дата выкупа ≠ дата заказа (R5 §3).
- **Источник 2 — заказы: поле есть в API, но мы его не сохраняем.** `apps-script/ingestion/WbOrdersLoader.gs` пишет только `price_with_disc`, в шапке стоит долг «D1.1: totalPrice / finishedPrice пока НЕ сохраняются». Statistics API `/api/v1/supplier/orders`, по документации WB, отдаёт в каждой строке `totalPrice`, `discountPercent`, `spp`, `finishedPrice`, `priceWithDisc`. Это даёт СПП на дату заказа в тот же день и снимает главный вывод R5 («на дату заказа СПП неизвестна»): R5 проверял только отчёт о реализации, а не заказы. **Наличие и заполненность полей надо подтвердить живым ответом API (гейт T3 в `Wbapitestrunner.gs`), а не документацией.**
- **Источник 3 — витрина (справочно).** На сайте WB без входа, регион Москва, цена покупателя = цена продавца × 0,5915 у всех товаров одинаково (витринная СПП 40,9 % на 28.09). Реальная СПП покупателей ниже на 6–8 п.п., потому что она индивидуальная. Витрина годится как индикатор, но не как «СПП дня» для Юнитки.
- Тождество из R5: `retailAmount = retailPrice × (1 − spp/100)`, СПП финансирует WB и не уменьшает выплату продавцу. Бывают строки с отрицательной СПП (рассрочка с наценкой) и с нулевой.

## Что сделать

### Этап 1. Сохранять СПП в заказах

1. Живой пробой `supplier/orders` за 2–3 последних дня: какие ценовые поля пришли, доля пустых/нулевых `spp`, проверка тождества `finishedPrice ≈ priceWithDisc × (1 − spp/100)`. Отчёт с цифрами — до изменений схемы.
2. `RAW_WB_ORDERS` (лист и BigQuery): добавить nullable-колонки `total_price`, `discount_percent`, `spp`, `finished_price`. Сырые значения API без преобразований. Схему менять аддитивно, как в прошлых стейджах, с записью в `CHANGELOG.md`.
3. `WbOrdersLoader.gs` → `set(...)` для новых полей; `WbOrdersBigQuery.gs` и дедуп-вью `wb_raw.V_WB_ORDERS` — пробросить поля.
4. Бэкфилл: перезагрузить окно, которое держит API (проверь фактическую глубину), штатным replace-slice. Число строк за период расти не должно.

### Этап 2. Витрина дневной СПП

Новая вью `wb_mart.V_WB_SPP_DAILY` (ключ `nm_id` × `day` по МСК):

- `spp_orders_weighted_pct = (1 − Σ finished_price / Σ price_with_disc) × 100` по заказам дня, включая отменённые (брутто, как `Q`); плюс медиана, `n_orders`, min/max, доля строк с отрицательной и нулевой СПП;
- fallback, если заказов за день нет: СПП по выкупам из `V_WB_SALES_RETURNS` (по дате выкупа, взвешенная) за скользящие 7 дней, с отдельной меткой;
- `spp_source`: `ORDERS` | `SALES_ROLLING_7D` | `NONE`;
- для наборов и SKU без продаж — `NONE`, ничего не выдумывать.

Предложи владельцу, что делать с аномалиями (отрицательная СПП, выбросы) — отдельный вопрос, не решай молча.

### Этап 3. Запись в Юнитку

1. `cloud/src/loaders/unitka/`: режим колонки `AB` MANUAL → AUTO (`model.ts`, `monthprep.ts`, `monthrollback.ts`, `visual.ts`; метка «ручной ввод» в визуале снимается). Запись только за дни ≤ LCD (последний закрытый день), как у других AUTO-колонок.
2. Значение — `spp_orders_weighted_pct` с округлением до 0,1; при `SALES_ROLLING_7D` — то же, но с пометкой источника (примечание к ячейке или служебная колонка, согласовать с владельцем). При `NONE` — ячейку не трогать, `SPP_MISSING` в `integrity.ts` остаётся только для этого случая.
3. Уже введённые владельцем значения `AB`: перед первой записью выгрузи их в отчёт и спроси, перезаписывать или сохранять. Решение не принимать самостоятельно.
4. Тесты: новые кейсы в `cloud/test/unitka_*.test.ts` (AUTO-режим AB, fallback, `NONE`, откат), сверка: пересчитанные `AC`, `Z` по сентябрю до/после — отчёт с дельтами по каждому SKU.
5. Shadow-прогон на копии или в режиме dry-run по сентябрю → отчёт владельцу → после «да» запись в живую книгу.

### Этап 4 (по отдельному решению владельца). Снимки витрины 8–10 раз в день

Цель — видеть витринную СПП и цену на полке в течение дня, пока заказов ещё нет.

- Сначала проверь, доступен ли публичный `https://card.wb.ru/cards/v4/detail?appType=1&curr=rub&dest=-1257786&nm=<id;id;...>` из Cloud Run. Если WB блокирует — остановись и доложи, обход не строить.
- Если доступен: Cloud Run job + Scheduler каждые ~2 часа → `wb_raw.RAW_WB_STOREFRONT_PRICES` (`observed_at`, `nm_id`, `price_basic`, `price_product`, `total_quantity`, `dest`); витринная СПП = `1 − price_product / seller_effective_price` (из `RAW_WB_PRICES` на тот же момент).
- В Юнитку этот источник не пишется, он для дашборда и решений по цене.
