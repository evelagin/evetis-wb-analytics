## 1. Отступления от спеки — приняты аудитором PR #100

О-1…О-7 предъявлялись к ред. 4 и приняты без изменений; правка run-лога Ads-2
(бывшая находка Н-1) вошла в дизайн **ред. 5** и отступлением больше не является.

**О-1 · `run_state = 'UNMAPPED'`.** Карта §1.5 покрывает все фактические значения, но не задаёт
поведение для будущего нового статуса. Добавлена ветка `ELSE 'UNMAPPED'` → `status = 'ERROR'`,
reason «статус вне карты §1.5: X». Альтернатива (молча считать успехом или падать в NULL) хуже:
светофор соврал бы зелёным. Гейт F7 при этом становится проверяемым запросом, а не обещанием.

**О-2 · слой с попытками, но без единого успеха.** §1.9 такой случай не описывает: `last_success`
пуст, `success_age_hours` = NULL, ни одна ветка `CASE` не срабатывает — слой был бы `OK`.
Добавлено `WHEN success_run_id IS NULL THEN 'ERROR'` («нет ни одного успешного прогона»).

**О-3 · `V_ADV_COSTS.updDate` — не TIMESTAMP.** §1.2 обещает `DATE(updDate)`. Факт: колонка
`STRING`, значения ровно 10 символов `'YYYY-MM-DD'` (1 995 строк, `SAFE.PARSE_DATE` даёт 0 NULL).
Реализовано `SAFE.PARSE_DATE('%Y-%m-%d', updDate)`. **Форматов фактически три, а не четыре:**
`period_from`, `snapshot_date`, `updDate` одинаковы; отдельный только ISO у fullstats.
Правка §1.2 **внесена в ред. 5**; на код не влияет.

**О-4 · состав колонок `V_ADS_SCREEN_SKU`.** §2.1 ссылается на «как в ред. 2 §2.1», но
файл ред. 2 в git не коммитился и дословный список не восстанавливается. Список собран явно из
`V_ADS_FUNNEL_SKU_28D` + атрибуты справочника и приведён в коде — прошу сверить глазами.

**О-5 · две колонки справочника в `V_ADS_SCREEN_QUERY`** (`internal_sku`, `product_name_short`).
Не вычисление, а подпись строки: без них Looker пришлось бы делать blend, чего §0 избегает.

**О-6 · `ref_rows_for_nm_id` в SKU-вью.** Справочник дедуплицируется `ROW_NUMBER` **до** join
(инвариант 7 — fan-out структурно невозможен), но число исходных строк остаётся видимым: дубль
в `REF_SKU_MASTER` не должен исчезнуть молча. На замере 0 дублей.

**О-7 · `run_source` в выдаче `V_DATA_FRESHNESS`** — видно, какой именно лог отвечает за слой.
Прямое следствие находки Н-1.

## 2. 🔴 Находки из данных — к коду не относятся, но требуют решения

**Н-1 · журнал `ads_query_stats` — собственный. ЗАКРЫТО в коде; формулировка уточнена.**

🔴 Первая редакция этой находки утверждала, что ежедневный ads-прогон вовсе не собирает
query stats. **Это было слишком сильно, и я это опровергаю сам.** Прогон в журнал Ads-2 пишет:

```
INGEST_RUNS  ads    INS_ADS_20260815050726_12ec8b3f   started 15.08 05:07:26
BIDS_RUNS           ADSRAW_20260815_050726_940       load_ts 15.08 05:11:37  ← тот же запуск
STATS_RUNS          ADSRAW_20260815_050726_940       load_ts 15.08 05:12:04  ← и сюда тоже:
                                                     3 суточных среза 08, 09, 10.08
STATS_RUNS          ADSPROBE_20260815_105136_581     load_ts 15.08 10:52:19  ← ручной добор
```

Верное утверждение мягче и всё равно требует правки: ежедневный прогон закрывает **хвост**
окна (D−7…D−5), свежие сутки приносят ручные `ADSPROBE_*`, а журнал у слоя **другой**.
Смотреть на `INGEST_RUNS` нельзя по причине аудитора: слой, чей смысл — ловить тихую
остановку Ads-2, не может брать признак жизни из чужого успеха.

**Сделано:** `run_source = 'ads_query_stats_log'` поверх `RAW_WB_ADV_QUERY_STATS_RUNS`;
строка лога = запрошенные сутки, поэтому попытка собирается по `run_id`
(`started_at = MIN(load_ts)`, `completed_at = MAX(load_ts)`, статус — худший из суточных
в порядке неизвестный → `FAILED` → `PARTIAL` → `OK`).

**Порог не задан, и это измерение, а не пропуск.** «133 OK-прогона» — это 133 **строки**,
то есть запрошенные сутки; прогонов `run_id` — **23**, и все они укладываются в **12,4 часа**
(14.08 22:29 — 15.08 10:52), из них 22 — один ручной добор и 1 — ежедневный прогон.
Правило §1.8 дало бы 8 ч из наблюдённого `max_gap` 5,6 ч, но окно наблюдения короче
ожидаемого интервала между прогонами: `max_gap` **не оценим**, порог был бы выдумкой.
Поэтому `success_age_ok_hours = NULL` + `success_age_is_sla = FALSE`; пересчёт после
≥ 14 суток истории. До тех пор слой гейтит возраст данных (сейчас `data_age = 3` при пороге 3).

Вариант `run_log_is_proxy = TRUE` отклонён вместе с аудитором: раз собственный журнал есть,
надо смотреть в него.

**Н-2 · `LOADER_RUNS.stocks` живёт с `environment = 'shadow'`** (27 строк), `mart` — с `'prod'` (8).
Фильтра по `environment` в реализации **нет намеренно**: фильтр `prod` обнулил бы слой `stocks`
(`NO_RUN` → `ERROR`). Фиксирую как известное свойство контура, а не как недосмотр.

**Н-3 · якорь дизайна заморожен на 15.08, сухой прогон — 16.08 МСК.** Все `data_age` на +1 сутки
относительно таблицы якоря. Все 12 слоёв по-прежнему `OK`.
