## 0. Что сломано и почему это чинится в SQL

С cutover 13.07.2026 новый загрузчик пишет в `RAW_WB_FINANCE` только те колонки, которые
`finDailyMapRow_` формирует явно — 54 ключа. Четыре производных поля, которые заполнял старый
нормализатор, остались пустыми у всех 2 922 строк нового контура:

| Поле | LEGACY | DAILY/WEEKLY | Кто потребляет |
|---|---|---|---|
| `operation_type_normalized` | 201 211 / 201 211 | **0 / 2 922** | `op_key` → `REF_COST_MAP` |
| `sku_match_status` | 201 211 | **0** | `is_sku_row` в `V_WB_FINANCE_AMOUNTS_LONG` |
| `internal_sku` | 155 758 | **0** | отчётность по внутреннему SKU |
| `commission_amount` | 201 211 | **0** | `cost_category = 'commission'` |

Вью `V_WB_FINANCE_COMPLETE` и `V_WB_FINANCE_CANONICAL` — чистый pass-through (`SELECT *` +
дедуп + фильтр слоёв, проверено по DDL). Поля физические в RAW, RAW append-only. Значит правка
маппера заполнит их только для будущих строк, а 2 922 уже загруженные останутся с NULL навсегда,
и полная пересборка витрины их не поднимет.

**Поэтому вычисление переносится в SQL-слой.** Тогда:
RAW хранит то, что реально прислал WB → SQL приводит поколения API к единой семантике →
Mart получает один финансовый контракт. Июль и август восстанавливаются сами при следующей
полной сборке `wb-mart-prod`, без перезаливок.

Дополнительный довод: маршрут «починить маппер + перезалить отчёты» упрётся в
`finDailyOrphanGuard_` — на перезапросе он увидит `other_run > 0` и выдаст `ORPHANED_RAW_REPORT`.
То есть потребует staging-таблицы или обхода собственной защиты, введённой в PR-A.

## 1. 🟢 Находка, которая делает SQL-маршрут полноценным: `raw_json`

`finDailyMapRow_` сохраняет **весь detailed-объект WB одной строкой**: `raw_json: JSON.stringify(o)`.
Проверено на всей популяции нового контура:

```
строк нового контура                       2 922
raw_json заполнен                          2 922
JSON_VALUE(raw_json,'$.vw') не NULL        2 922
JSON_VALUE(raw_json,'$.ppvzSalesCommission')  2 922
JSON_VALUE(raw_json,'$.sellerOperName')       2 922
JSON_VALUE(raw_json,'$.nmId')                 2 922
```

Ни одно поле не потеряно физически. Всё, что заполнял старый нормализатор, восстанавливается
из `raw_json` ретроактивно, без единого обращения к WB API.

## 2. Поля по отдельности

### 2.1 `operation_type_normalized` — не нормализация, а копия

На всей legacy-истории 18 различных значений, **каждое отображается само в себя**,
201 211 из 201 211:

```
Возмещение издержек по перевозке/…  → Возмещение издержек по перевозке/…   98 158
Логистика                          → Логистика                            44 414
Продажа                            → Продажа                              38 700
Возмещение за выдачу и возврат…    → Возмещение за выдачу и возврат…      17 561
Коррекция логистики / Хранение / Удержание / … (ещё 14 значений, все identity)
```

Предлагаемая форма: `COALESCE(operation_type_normalized, supplier_oper_name)`.
Проверяется как точное равенство на 201 211 строках — расхождений быть не должно ни одного.

### 2.2 `sku_match_status` — самое нагруженное поле, важнее `internal_sku`

`V_WB_FINANCE_AMOUNTS_LONG` содержит гейт:

```sql
COALESCE(f.nm_id > 0 AND f.sku_match_status = 'matched', FALSE) AS is_sku_row
```

При `sku_match_status IS NULL` → `is_sku_row = FALSE` → **ни одна сумма не привязывается к SKU**.
Именно поэтому в `MART_SKU_DAILY` нули по финансам, даже когда категория затрат определилась.

Текущее распределение:

```
matched     155 758   (internal_sku заполнен у всех 155 758)
not_found    45 453   (из них 44 690 — строки, где nm_id отсутствует в принципе)
NULL          2 922   ← новый контур
```

Важно для приёмки: `not_found` в подавляющем большинстве — законные строки без товара
(логистика, хранение, возмещения). Реально несматченных с `nm_id` — 763.

Предлагаемая форма: `LEFT JOIN wb_raw.REF_SKU_MASTER` по `nm_id`;
`sku_match_status = IF(nm_id IS NULL OR nm_id = 0, 'not_found', IF(m.internal_sku IS NULL, 'not_found', 'matched'))`.
Точная форма должна воспроизвести legacy побитово — это критерий приёмки, а не пожелание.

### 2.3 `commission_amount` — 🔴 требует решения аудитора

Источник восстановлен по коду: `commission_amount` ← `ppvz_vw` ← поле API `vw`
(`WbFinanceApiV1.gs:263`; комментарий `WbFinanceAuditBQ.gs:91` прямо называет его
«ppvz_vw — нативная комиссия WB»).

Но данные говорят, что содержимое этой колонки **не является комиссией маркетплейса**:

```
LEGACY, supplier_oper_name = 'Продажа':
  SUM(commission_amount)                        −888 652,59 ₽
  совпадает с sales_commission построчно        19 963 из 38 700 (51,6 %)
  комиссионный спред по REV2.4 (srev − for_pay)  ≈ 7 897 000 ₽

LEGACY, 'Возмещение за выдачу и возврат товаров на ПВЗ':
  SUM(commission_amount)                        −127 892,00 ₽
```

Две вещи, которые надо назвать вслух:

1. −888 652,59 ₽ на порядок меньше реального комиссионного спреда. По REV2.4 комиссия WB
   **не является отдельной строкой** — она сидит внутри разницы `srev − for_pay` вместе
   с эквайрингом (тождество `srev − for_pay ≡ srev × commission_percent/100 + acquiring_fee`,
   доказано на 100 % строк в 21 из 24 месяцев). Отдельная колонка `commission_amount` —
   это `vw`, вознаграждение WB по конкретной операции, другая сущность.
2. −127 892,00 ₽ по строкам ПВЗ — это **ровно та цифра**, которую REV2.4 пометил как
   `REVIEW_REQUIRED` и оставил вне утверждённого P&L.

Следствие: сейчас в витрине `cost_category = 'commission'` означает `vw`, а не комиссию
маркетплейса в смысле REV2.4. Терминология Mart расходится с зафиксированным контрактом.

**Вопрос аудитору (блокирующий для §3):** PR-B должен
(A) восстановить `commission_amount = vw` как есть, сохранив расхождение терминологии,
и переименовать категорию в `wb_reward`, либо
(B) восстановить `vw` под честным именем и **дополнительно** ввести производную
`commission_native_rub` по формуле REV2.4, сделав её единственным носителем слова «commission».

Рекомендация — (B), но это решение о семантике, а не о коде, и принимать его должен аудитор.
Знак: legacy хранит `vw` отрицательным (−888 652,59), в `raw_json` нового контура он
положительный (+20 660,58 по `Продажа`). Инверсию надо воспроизвести и закрепить тестом.

## 3. 🔴 Отдельная находка: `REF_COST_MAP` получил заглушку `__NULL__`

После аварии витрины 08.08 (`MART_ERROR: unknown money-pair (cost_category IS NULL)
в LONG_MAPPED — расширить REF_COST_MAP`) в справочник добавлены пять строк:

```
op_key     amount_field      economic_direction  cost_category
__NULL__   acquiring_fee     COST                acquiring
__NULL__   deduction         COST                deduction
__NULL__   logistics_amount  COST                logistics
__NULL__   penalty           COST                penalty
__NULL__   storage_fee       COST                storage
```

`op_key = COALESCE(operation_type_normalized, '__NULL__')`, то есть эти пять строк ловят
**ровно строки нового контура**. Последствия:

* fail-closed ASSERT «unknown money-pair» **нейтрализован** именно там, где он был нужен —
  авария 08.08 не исправлена, а заглушена;
* теряется семантика `ADJUSTMENT`: `Коррекция логистики` и `Корректировка эквайринга`
  в legacy обрабатываются со знаком (`field_normalization_sign`), а через `__NULL__`
  попадают в обычный `COST` с `ABS()`;
* `commission_amount` в заглушке отсутствует вовсе — комиссия нового контура не доезжает
  ни в каком виде;
* деньги при этом всё равно не видны в `MART_SKU_DAILY`, потому что `is_sku_row = FALSE` (§2.2).

**Требование PR-B:** пять строк `__NULL__` удаляются в том же PR, что и восстановление
`operation_type_normalized`. Порядок обязателен: сначала поле, потом снятие заглушки, иначе
ближайшая сборка витрины упадёт. После снятия ASSERT снова становится fail-closed.

## 5. Критерии приёмки

1. **Ретроспективная эквивалентность.** Новый SQL, применённый к legacy-строкам, обязан дать
   **точное совпадение** с уже записанными значениями: 201 211 строк, расхождений 0.
   Отдельно по каждому из четырёх полей.
2. **Полнота нового контура.** У всех 2 922 строк нового контура четыре поля непустые
   (кроме законных случаев `not_found` без `nm_id`).
3. **Регрессия PR-A** — 20/20 PASS, ни одна контрольная цифра REV2.4 не сдвинулась.
4. **Инварианты PR-A** — 7/7 нулей.
5. **`REF_COST_MAP`** — ни одной строки `op_key = '__NULL__'`; ASSERT «unknown money-pair»
   не срабатывает на полной истории.
6. **Контрольная пересборка Mart** — после ручного прогона `wb-mart-prod`
   `MART_SKU_DAILY` показывает ненулевые финансы за период 13.07 … текущая дата,
   а суммы за период до 12.07 **не изменяются ни на копейку**.
