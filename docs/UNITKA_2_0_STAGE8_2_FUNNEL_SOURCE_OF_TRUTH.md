## 1. Сверка воронки: что с чем сходится

Официальный XLSX «Воронка продаж» из ЛК WB за 01–09.09.2026
(`11-9-2026 сентябрь с 01-09-2026 по 09-09-2026.xlsx`, 196 строк, 22 артикула, детализация по дням)
сверен по `nmID × дата` с тремя источниками.

### 1.1 Главный результат

**Эндпоинт `POST /api/analytics/v3/sales-funnel/products/history` воспроизводит официальный
XLSX ТОЧНО.** За 04–09.09 (глубина, доступная API на 11.09) по всем 22 артикулам выгрузки и
всем трём метрикам — «Переходы в карточку», «Положили в корзину», «Заказали товаров, шт» —
**расхождений 0**. Ни одной ячейки `nmID × день`.

Прежняя оценка «переходы сходятся в пределах +2..+5 в день» была **артефактом самой выгрузки**:
в XLSX был выбран явный список из 22 артикулов продавца («Общая информация → Артикулы»), а
`252441968`, `252442341` и `909951444` в него не вошли. Их переходы за 04–09.09 дают ровно
**+18** к API и **+15** к листу (в листе нет блока `909951444`).

| дата | XLSX переходы | API переходы | дельта | чем объясняется |
|---|---|---|---|---|
| 04.09 | 698 | 700 | +2 | 252441968 (0) + 252442341 (2) + 909951444 (0) |
| 05.09 | 721 | 726 | +5 | 2 + 3 + 0 |
| 06.09 | 671 | 674 | +3 | 1 + 1 + 1 |
| 07.09 | 518 | 520 | +2 | 1 + 1 + 0 |
| 08.09 | 302 | 304 | +2 | 1 + 0 + 1 |
| 09.09 | 427 | 431 | +4 | 1 + 2 + 1 |
| **итого** | **3337** | **3355** | **+18** | 6 + 9 + 3 |

Корзины и заказы за те же дни сходятся **побайтово**: 342 и 342, 87 и 87.

### 1.2 Решение

Authoritative для **«Переходы»**, **«Положили в корзину»** и **«Заказы факт»** — воронка.
`FACT_ORDERS` остаётся для финансового и операционного контура, но в визуальную воронку
больше не примешивается.

Приоритет источников на каждый день, печатается в лог каждым прогоном `s82data()`:

```
1. FUNNEL_API     wb_raw.V_WB_FUNNEL_DAILY            04.09 и позже
2. XLSX_BACKFILL  wb_raw.RAW_WB_FUNNEL_XLSX_BACKFILL  ТОЛЬКО 01-03.09
3. ORDERS_API     wb_mart.FACT_ORDERS                 если нет ни того ни другого
```

Фактический лог прогона:

```
2026-09-01  XLSX_BACKFILL 22 + ORDERS_API 3
2026-09-02  XLSX_BACKFILL 22 + ORDERS_API 3
2026-09-03  XLSX_BACKFILL 21 + ORDERS_API 4
2026-09-04  FUNNEL_API 25
...
2026-09-10  FUNNEL_API 25
```

## 2. Почему `FACT_ORDERS` не воспроизводит воронку 1:1 (§3 задания)

Это **разные продукты WB**, а не ошибка витрины.

За 01–09.09: XLSX **137** заказов, `FACT_ORDERS` **127**. Разница раскладывается точно:

* **−12 заказов**, которых в ленте `/supplier/orders` нет **физически**. Проверено на
  `RAW_WB_ORDERS` (сырой слой, до витрины): за 05.09, 07.09 и 08.09 по `305101361` в сыром
  слое **ноль строк**, при том что загрузчик отработал в эти дни 10–22 раза. То же по
  `252442517` (04.09: XLSX 5, лента 3) и ещё по 6 SKU. Финотчёт не содержит **ни одного**
  `srid` с `order_dt` в окне, которого не было бы в `FACT_ORDERS`, — то есть витрина ничего
  не теряет, данные не отдаёт сама лента.
* **+2 заказа**, отменённых **в день заказа** (`cancel_dt = order_dt`): `535580776` от 02.09
  и от 09.09. WB не считает такой заказ **ни заказом, ни отменой** — в XLSX по этому SKU
  в эти дни стоят нули. В ленте заказов строка есть, с `is_cancel = true`.

Отмена **не** в день заказа считается обоими источниками одинаково: `252442517`, заказ 02.09,
`cancel_dt = 06.09` — и XLSX, и `FACT_ORDERS` дают 11 заказов и 1 отмену.

**Исключено проверкой:** сдвиг часового пояса (дельта односторонняя +13 за 04–10, соседние дни
не компенсируют), дубли `srid` (число `srid` = числу строк), `sku_match_status` (100 % matched),
пропуски загрузчика (загрузки есть каждый день), WB Клуб и юрлица (в листе «Промосервисы»
выгрузки все 13 колонок — нули), отсутствие 25-го SKU (`909951444` за 04–09 имел 0 заказов).

## 3. Отмены — единственная колонка со смешанной семантикой (§4)

В ответе `history` **полей отмен нет вообще**. Полный перечень полей дня:
`openCount, cartCount, orderCount, orderSum, buyoutCount, buyoutSum, buyoutPercent,
addToCartConversion, cartToOrderConversion, addToWishlistCount`. В загрузчике
(`cloud/src/loaders/funnel/normalize.ts`) `cancel_count` и `cancel_sum_rub` поэтому жёстко
`null`; в `V_WB_FUNNEL_DAILY` они **NULL на 100 % строк** — замерено.

Вывести отмены нельзя и арифметически: `заказы − выкупы` ≠ отмены, потому что выкуп приходит
позже (01.09 по крему: заказов 11, выкупов 9, отмен 0 — 2 ещё в пути даже спустя 10 дней).

**Принятое правило:**

| период | источник «Отменили товаров» |
|---|---|
| 01–03.09 | официальное значение из `RAW_WB_FUNNEL_XLSX_BACKFILL` |
| 04.09 и позже | прокси `is_cancel` из `FACT_ORDERS` |

**Мера расхождения прокси** за 04–09.09 — 3 SKU-дня из ~150:

* `+2` отмена в день заказа, которую WB не считает (`535580776` от 02.09 и 09.09);
* `−1` невыкуп/возврат: в ленте заказов `is_cancel = false`, в воронке учтён как «Отменили»
  (`773170315` от 07.09). Контракт WB прямо это описывает: «Отменили товаров» = отменён,
  **не выкуплен или возвращён**.

Итог за 01–09: XLSX 5, лист 5. По дням совпадают 01, 02, 03, 04, 05, 06, 08; расходятся 07 и 09.

## 4. Backfill 01–03.09 (§5)

01–03.09 из API **не достать никогда**: без «Джема» глубина `history` — 7 дней
(`MAX_DEPTH_DAYS = 7` в `cloud/src/loaders/funnel/wbApi.ts`), на 11.09 окно начинается с 04.09.
Данные **не выдуманы**, а один раз загружены из официального XLSX.

Таблица: `project-fa311fc0-4d87-4781-986.wb_raw.RAW_WB_FUNNEL_XLSX_BACKFILL`
65 строк, 22 nmID × 3 дня (у `1083392113` нет строки за 03.09 — в выгрузке её нет).

Колонки провенанса в каждой строке:

```
source      = 'WB_OFFICIAL_XLSX_BACKFILL'
source_file = '11-9-2026 сентябрь с 01-09-2026 по 09-09-2026.xlsx'
loaded_on   = 2026-09-11
note        = разовый контролируемый исторический backfill, не использовать там, где есть API
```

Контроль сходимости с цифрами владельца:

```
01.09  переходы 789  корзины 68  заказы 22  отмены 1
02.09            728           69          18         2
03.09            528           44          10         0
```

**Для Engine этот путь закрыт.** Backfill ограничен окном 01–03.09 и стоит в приоритете
НИЖЕ API: как только у даты появляется строка воронки, она побеждает.

## 5. Изменчивость и политика обновления (§6)

Доказать или опровергнуть ретроспективный пересчёт **нечем**: в `V_WB_FUNNEL_DAILY` существует
ровно один снимок (`observation_id = WBFN_prod_20260904_20260910`, `observed_at = 2026-09-10`).
Сравнивать не с чем — это констатация, а не вывод.

Поэтому политика задаётся **проспективно** и по риску, а не по наблюдению:

1. Загрузчик воронки тянет **скользящее окно D-7…D-1**, а не только D-1. Глубина эндпоинта
   ровно 7 дней, то есть окно берётся максимально доступное и стоит ровно ноль дополнительных
   запросов сверх лимита (1–20 nmID на запрос, 3 запроса в минуту).
2. Каждая загрузка пишется **новым `observation_id`**, старые снимки не перезаписываются.
   Через две недели работы появится материал, на котором вопрос об изменчивости решается
   замером, а не предположением.
3. Лист перезаписывается по последнему снимку на дату. Расхождение старого и нового снимка
   пишется в лог прогона.
