## 3. Корневая причина — точная

Snapshot-слой по правилу 2 своего контракта
(`sql/raw/adv_costs_snapshot_v1.sql`) считает авторитетными **только** те строки RAW,
у которых есть финальный commit-marker в журнале окон. Строки без маркера остаются в
таблице, но в canonical не попадают никогда.

История 13.04 … 12.08 снималась **до** появления журнала, поэтому маркеров у неё нет.
Единственный предусмотренный механизм её «оживления» — перечитать историю через
журналируемый загрузчик:

```
apps-script/WbAdsRawLoader.gs:355
function loadWbAdsCostsBootstrapPass()      // run_id префикс ADSBACKFILL_
```

Это шаги **A7–A9** роллаута (`docs/ADS_COSTS_SNAPSHOT_ROLLOUT_2026-08-20.md`).
**Они никогда не выполнялись** — ни одного рана `ADSBACKFILL_` не существует.

Фаза A остановилась после A5 (подмена `V_ADV_COSTS` на `UNION_PREBOOTSTRAP` —
выполнена) и A6 (наблюдение штатных journaled-прогонов — идёт с 14.08 и работает).

Риск №3 §7 того же документа предсказал ровно это:
> «historical coverage целиком держится на трёх bootstrap-проходах, а не на "доборе" из прошлого».

## 4. Почему это нельзя доделать в одну сессию

Из docstring самой функции:

> Запускать **ТРИ РАЗА, по одному разу в сутки три дня подряд**: проходы внутри одного
> дня не независимы — WB публикует списания в течение суток, и три чтения подряд
> измерили бы один и тот же момент, а не три наблюдения.

Плюс `billed_complete` требует `stable_ok` — совпадения `N_STABLE` последовательных
чтений. Это структурно ≥ 3 календарных суток, и сжать их нельзя, не разрушив смысл
проверки стабильности.

Кроме того, `loadWbAdsCostsBootstrapPass()` — функция Google Apps Script, запускаемая
из проекта владельца. Автоматического пути её запуска из этого репозитория нет.

## 7. Почему нельзя развернуть Stage 3B в обход Фазы B

Гейт `sql/mart/pr_mart1_facts.sql:74-78` — fail-closed ASSERT, проверяющий фактическое
`view_definition` production-объекта `V_ADV_COSTS`. Сейчас он даёт `FALSE`, и деплой
файла останавливается **до** замены `sp_bootstrap_facts`.

Гейт обходить нельзя, и не только формально. Stage 3B берёт флаг `billed_complete`
исключительно из `V_ADV_COSTS_DAY_COVERAGE`, а на сутках с `billed_complete = FALSE`
все billed-KPI по контракту равны **NULL, а не 0**. Сегодня таких суток 138 из 148.
Развёрнутый сейчас Stage 3B дал бы витрину, где рекламная экономика неизвестна на
93 % истории, — это хуже текущего состояния, а не лучше.

  SELECT SAFE.PARSE_DATE('%Y-%m-%d', SUBSTR(updDate,1,10)) AS date,

FROM new_canon n FULL OUTER JOIN old_fact o USING (date);
