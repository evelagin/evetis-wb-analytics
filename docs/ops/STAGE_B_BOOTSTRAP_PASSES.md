# GATE NOT PASSED — открыт ровно один пункт

### Что именно даёт `I2 = 3`

Все три нарушения — одна и та же пара, повторённая в каждом проходе:

```
ADSBACKFILL_20260908_190645_927 | 2026-07-12 | 2026-06-12…2026-07-11[w2] + 2026-07-12…2026-08-10[w3]
ADSBACKFILL_20260909_184946_692 | 2026-07-12 | то же
ADSBACKFILL_20260910_083850_614 | 2026-07-12 | то же
```

Это тот самый «вне окна 1» из каждого лога: окно `w2` (12.06…11.07) получило от
WB одну строку с датой 12.07 на 108 ₽, а окно `w3` (12.07…10.08) вернуло по этой
дате законные 16 строк на 3 986 ₽. Внутри одного рана дата 12.07 оказывается
покрыта двумя окнами — и `I2` это считает нарушением.

### Почему это не дефект данных

1. **Так ведёт себя WB, и код это знает.** Комментарий в загрузчике:
   «WB иногда отдаёт строки за день, который мы не просили (наблюдалось 3 раза
   из 5026). Считаем их явно: canonical их отбросит, но факт должен быть виден
   в журнале». Загрузчик пишет `rows_out_of_window` именно для этого. Сейчас
   таких строк 5 на 6 900 журналированных.
2. **Canonical их действительно отбрасывает.** `I4` — проверка того же свойства
   на слое canonical — даёт **0**: каждая дата снапшота происходит ровно из
   одного `(run_id, window_index)`. Разбор 12.07 построчно это подтверждает:
   снапшот берёт 3 986 ₽ окна `w3`, а 108 ₽ окна `w2` не берёт.
3. **Тот же `I2`, ограниченный строками внутри окна, даёт 0.**

То есть `I2` в нынешней формулировке проверяет не «одна дата — одно окно в
canonical», а «WB не прислал ничего лишнего» — свойство, которое контракт
проекта явно **не** требует и которое от нас не зависит.

### Почему четвёртый проход не поможет

`I2` не про число наблюдений. Каждый следующий bootstrap-проход добавит ещё одно
такое же нарушение: после PASS 4 `I2` станет 4, после PASS 5 — 5. Правило §6
«не прошёл гейт → сделай ещё проход» здесь неприменимо: причина не в нехватке
данных.

### Предложение — решение владельца, не моё

Сузить `I2` до строк внутри запрошенного окна, оставив число out-of-window строк
отдельным наблюдаемым показателем (он уже есть в журнале как
`rows_out_of_window`):

```sql
-- I2. Внутри (run_id, date) — ровно одно окно СРЕДИ строк, попавших в своё окно.
--     Строки, присланные WB вне запрошенного окна, canonical отбрасывает (см. I4);
--     их количество отслеживается отдельно через RAW_WB_ADV_COSTS_RUNS.rows_out_of_window.
SELECT COUNT(*) AS run_days_with_two_windows FROM (
  SELECT run_id, SUBSTR(updDate,1,10) d
  FROM `project-fa311fc0-4d87-4781-986.wb_raw.RAW_WB_ADV_COSTS`
  WHERE source_method='adv/v1/upd'
    AND SAFE.PARSE_DATE('%Y-%m-%d', SUBSTR(updDate,1,10))
        BETWEEN SAFE.PARSE_DATE('%Y-%m-%d', SUBSTR(period_from,1,10))
            AND SAFE.PARSE_DATE('%Y-%m-%d', SUBSTR(period_to,1,10))
  GROUP BY run_id, d
  HAVING COUNT(DISTINCT FORMAT('%t|%t', period_from, period_to)) > 1);
```

🔴 **Правка `sql/raw/adv_costs_snapshot_validation.sql` без явного ACK владельца
не вносится.** Ослабить проверку ради продвижения этапа — ровно то, что запрещено
и контрактом Stage B, и §6 рунбука. Здесь есть основание считать формулировку
ошибочной, а не данные плохими, но решение об изменении гейта принимает владелец.
