# Ozon-Юнитка — эксплуатация

Лист `OZON_Юнит_2025` книги `Юнитка_Evetis Cosmetics`. Обновляется сам. Этот документ —
единственное место, где записано как именно; в переписке ничего искать не нужно.

## 1. Что происходит за сутки

| МСК | что | чем |
|---|---|---|
| 05:00 пн | кластеры Ozon | `ozon-weekly` |
| 06:30 | каталог, цены, **начисления**, реклама, поставки | `ozon-daily` → `ozon-runtime-daily` |
| ~06:42 | суточная загрузка закончена | |
| 07:00 / 13:00 / 19:00 | отправления и остатки | `ozon-fast` → `ozon-runtime-fast` |
| ~07:01 | отправления свежие | |
| **10:00** | **пересчёт и запись Ozon-Юнитки** | `ozon-unitka-prod` → `ozon-unitka-prod` Job |

Запас между последним источником и записью — около трёх часов.

## 2. Три окна. Их нельзя путать

| окно | сколько | где задано | почему столько |
|---|---|---|---|
| загрузка начислений | **30 суток** | `pipelines/ozon/runtime/entities.py`, `REGISTRY` | начисление возникает через 4–25 суток после заказа; прежние 14 суток работали без запаса |
| перезапись Юнитки | **45 суток** | `cloud/src/loaders/unitka/ozon/window.ts` | наименьшее окно, накрывающее всю наблюдённую задержку видимости (максимум 36) |
| глубокая сверка | **120 суток** | там же, включается 1-го числа | втрое перекрывает максимум; ловит редкие поздние правки |

Общей константы `LOOKBACK_DAYS` нет и заводить её нельзя: это три разных величины трёх
разных слоёв, и совпадение любых двух из них было бы случайностью.

## 3. Провизорная экономика: как оценка становится фактом

Ozon публикует деньги не сразу. Пока их нет, строка суток всё равно показывает экономику:

| составляющая | пока факта нет | когда приходит факт |
|---|---|---|
| цена продавца | `price_rub` отправления — известна в момент заказа | не меняется |
| комиссия | `цена − выплата` у доставленных, тариф у единиц в пути | заменяется фактом |
| логистика | оценщик `SKU_P70_120D` | заменяется фактом |
| себестоимость | справочник на дату заказа | не меняется |
| цена покупателя, СПП | **пусто** — источника до доставки не существует | появляются |
| хранение, прочие прямые | **пусто** — оценщика нет и быть не может | появляются |

Замена происходит сама: окно 45 суток переписывает эти сутки каждый день, и как только
начисление опубликовано, оценка исчезает. Проверено на живом примере 21.09.2026: пять
комиссий, оценённых накануне в 3 447,08 ₽, пришли на сумму 3 447,08 ₽ — совпадение до копейки.

Ячейка с оценкой несёт **примечание** с суммой, методом и обещанием замены. Цветом оценка
не выделяется сознательно: язык цвета Юнитки занят смыслом метрики.

## 4. Новый месяц

Ничего делать не нужно. Первый прогон, чей окно захватывает новый месяц, сам:
создаёт секцию по шагу Calendar V2 (`дни + 4`), дописывает строки листа, переносит состав
SKU, ставит формулы, оформление, условное форматирование и полную строку итога.

Сентябрь → октябрь 2026 проверен регрессией (`OZON adapter — Gate 9: новый месяц создаётся сам`),
включая 31 день октября, 30 ноября и 29 февраля 2028.

## 5. Новый SKU

Тоже сам. Идентичность берётся из `evetis_ref.REF_SKU_CHANNEL_MAP`, а не из подписи в листе:
подпись — это текст, и она уже содержит опечатку (`9099514444` при каноническом `909951444`,
объявлена явно в `OZON_UNITKA_OFFER_ALIASES`). Первая активность определяется по витрине.

Новый SKU получает свободный слот, полный блок из 25 колонок, формулы, оформление и итог.
Порядок существующих блоков не меняется никогда: SKU живёт в своём слоте всю жизнь листа.

## 6. Если свободного слота нет

Размечено **22** слота. 23-й SKU — это событие ёмкости, а не рядовая активация.

Прогон **ОТКАЗЫВАЕТСЯ** (`NO_FREE_SKU_SLOT`) и не пишет ничего. Переписать чужой блок он
не имеет права: лист потеряет историю SKU, и восстановить её будет неоткуда. В логе — сколько
слотов нужно, сколько есть и какой SKU не поместился.

Что делать владельцу: расширение листа — отдельная миграция с ростом геометрии (как Gate 6B),
а не суточный прогон.

## 7. Если источник не обновился

Перед записью прогон смотрит в `ozon_raw.OZON_INGESTION_RUNS` и требует успешной загрузки
`finance_accrual`, `fbo_postings`, `ads_sku_daily`, `prices` не старше суток.

Если хоть один отстал — **`SOURCE_STALE`, запись отменена**. Обновить лист устаревшими
данными хуже, чем не обновить: владелец увидит вчерашнюю картину с сегодняшней датой.
Повтор — следующее окно расписания; сбои наблюдались (1 из 32 у рекламы, 1 из 59 у отправлений),
поэтому барьер не декоративный.

## 8. Ручной запуск

Штатный пульт — workflow `scheduler-control` (GitHub Actions), `environment=prod`,
`loader=ozon-unitka`:

* `run-now` — выполнить прогон немедленно;
* `resume` / `pause` — включить или остановить суточное расписание 10:00 МСК.

Он ходит под тем же привилегированным SA, что и Terraform, и оставляет след в Actions.
Прямой `gcloud run jobs execute ozon-unitka-prod --region europe-west1 --wait` делает то же
самое, но мимо журнала — им пользоваться только когда Actions недоступны.

Глубокая сверка (120 суток) включается сама первого числа месяца. Вне этой даты её можно
вызвать, подставив дату в `G8_TODAY`-эквивалент прогона — отдельного Job для неё нет
сознательно: это тот же канонический писатель с большим окном, а не вторая экономика.

## 9. Развёртывание и промоушен образа

Ресурсы создаёт `infra` (`action=apply`) ЦЕЛЕВЫМ планом — только четыре адреса Ozon, чтобы
чужой дрейф не поехал вместе с ними:

```
google_cloud_run_v2_job.ozon_unitka_prod,google_cloud_scheduler_job.ozon_unitka_prod,
google_bigquery_dataset_iam_member.ozon_unitka_read_mart,
google_bigquery_dataset_iam_member.ozon_unitka_read_raw
```

Terraform создаёт Job с BOOTSTRAP-образом `hello` и держит `image` в `ignore_changes`.
**Пока образ не продвинут, Job запускать нельзя**: `hello` выходит с кодом 0 и молча ничего
не пишет — прогон выглядит зелёным, а лист не обновляется. Образ продвигает `deploy-prod`
парой `(image_digest, source_git_sha)` из summary сборки `deploy-shadow`.

Порядок ровно такой: `infra apply` → `deploy-prod` → `scheduler-control run-now` (первый
прогон) → `run-now` ещё раз (проверка идемпотентности) → `scheduler-control resume`.

Проверить, что Job действительно на боевом образе:

```
gcloud run jobs describe ozon-unitka-prod --region europe-west1 \
  --format='value(spec.template.spec.template.spec.containers[0].image)'
```

## 10. Откат

Сам прогон идемпотентен: повтор на неизменном источнике не меняет ни одной ячейки
(проверено двумя прогонами подряд, 108 089 ячеек, 0 расхождений). Поэтому «откат прогона»
как операция не нужен — нужен откат ИЗМЕНЕНИЯ.

* оформление «Прочих прямых» — `artifacts/gate7/pre7_other_direct_formats.json`;
* состояние листа до Gate 8 — `artifacts/gate8/pre8_sheet_snapshot.json.gz`;
* объекты BigQuery — `sql/current/ozon_mart/`, пересборка по `rebuild_order` манифеста;
* расписание — снять с паузы/поставить на паузу в Cloud Scheduler, код при этом не трогается.

Остановить автоматику мгновенно: поставить `ozon-unitka-prod` в Cloud Scheduler на паузу.

## 11. Что делать владельцу в обычной работе

Ничего.

Исключения — только бизнес-решения, которые никакая автоматика принять не может:
появление 23-го SKU (нужна миграция геометрии), смена тарифа, которую Ozon не отразил
ни в начислениях, ни в снимке тарифов, и перенос `LAST_CLOSED_DATE` в `ZZ_CONFIG!B2`.
