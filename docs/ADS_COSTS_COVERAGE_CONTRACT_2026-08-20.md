# Coverage-контракт adv/v1/upd — почему полноту суток сегодня доказать нельзя

**Дата:** 20.08.2026 · **Повод:** ревью Stage 3B потребовало доказательства для `billed_complete`
**Вывод:** доказать невозможно. Ниже — четыре факта из данных и минимальный контракт, который это чинит.

---

## 1. Вопрос

Day-level completeness обязана различать два состояния, которые внешне выглядят одинаково:

* **успешный день с 0 ₽ расхода** — реклама не крутилась или не списалась, данные полные;
* **день, который не был загружен или не закрыт** — данные неполные, KPI по нему считать нельзя.

Сегодня в витрине эти два состояния неразличимы. Живой пример: 18.08 и 19.08 не имеют ни одной
строки в `FACT_ADS_COSTS_DAILY`, при этом атрибутированный расход есть (2,57 ₽ и 2,81 ₽).

---

## 2. Что вообще есть в качестве доказательств

| Источник | Что даёт | Чего не даёт |
|---|---|---|
| `RAW_WB_ADV_COSTS.(run_id, period_from, period_to, load_ts)` | запрошенное окно каждой строки | ничего о ранах, вернувших ноль строк |
| `INGEST_RUNS(loader_name='ads')` | 18 ранов с 03.08, все COMPLETE | грейн — загрузчик целиком, не сутки и не расходы; истории до 03.08 нет |
| `RAW_WB_ADV_QUERY_STATS_RUNS`, `RAW_WB_ADV_QUERY_BIDS_RUNS` | полноценные журналы ранов | **у расходов такого журнала нет** |

Проверено read-only 20.08.2026: 129 суток (13.04–19.08), 37 ранов, 5 026 строк RAW.

---

## 3. Четыре факта, каждый из которых ломает правило «day <= MAX(date)»

### 3.1 Журнала ранов у `adv/v1/upd` нет
Ран, вернувший ноль строк, не оставляет следа вообще. Поэтому «успешные сутки с 0 ₽» и
«сутки не загрузились» неразличимы **в принципе**, а не по недосмотру запроса.
18.08 запрошен дважды (19.08 и 20.08), 19.08 — один раз; оба раза пусто. Что это — ноль или пропуск,
данные ответить не могут.

### 3.2 WB отдаёт строки ВНЕ запрошенного окна
Ран от 02.08 с окном 26.07–01.08 вернул строки с `updDate = 02.08`. Значит `period_from/period_to` —
это то, что **мы просили**, а не то, что **нам ответили**. Строить на нём покрытие нельзя.

### 3.3 Биллинг не финален на D+1 и не монотонен
Ряд ответов WB по одним и тем же суткам (суммы дедуплицированных ключей внутри одного рана):

```
02.08:   61 → 2544 (×7 ранов подряд) → 2483    ← изменился на СЕДЬМОМ повторном чтении
04.08:    4 → 1463 (×6)              → 1459
05.08: 1117 → 1309 → 1117 (×5)                 ← разовый выброс и откат
06.08: 1858 → 2050 (×6)                        ← дозапись на D+2
```

Никакое окно стабильности `K` не спасает: 02.08 и 04.08 изменились **после семи одинаковых чтений**.
А после D+7 сутки просто перестают перечитываться — текущее окно загрузчика D−7…D−1 заканчивается
ровно там, где изменения ещё происходят. «Стабильность» дальше D+7 — следствие того, что никто
больше не спрашивает, а не доказательство закрытия.

### 3.4 Канонический слой не умеет выражать отзыв записи
`V_ADV_COSTS` дедуплицирует по `(advertId, updTime, updSum)` и **накапливает** всё, что когда-либо
приходило. Строка, которую WB перестал отдавать, остаётся навсегда. Следствие на 20.08:

```
FACT_ADS_COSTS_DAILY завышен на 334,00 ₽ по 4 суткам против последнего ответа WB
  10.07: FACT 3676 / WB 3599
  02.08: FACT 2544 / WB 2483
  04.08: FACT 1463 / WB 1459
  05.08: FACT 1309 / WB 1117   ← в FACT попал разовый выброс
```

0,065 % от 514 064,00 — мало по величине, но механизм неограничен, и это отдельный дефект,
существующий независимо от Stage 3B.

## 4. Минимальный coverage contract

Четыре шага, каждый маленький и проверяемый.

### C1. Журнал ранов `wb_raw.RAW_WB_ADV_COSTS_RUNS` *(обязателен)*
По строке на каждое **окно** каждого рана, **включая пустой ответ**. Поля — как у существующего
`RAW_WB_ADV_QUERY_STATS_RUNS` (все STRING, по конвенции RAW):

```
load_ts, run_id, source_method, period_from, period_to, window_index,
http_status, http_success, returned_rows, returned_days,
min_upd_date, max_upd_date, duration_ms, status, error_message
```

Правка в `apps-script/WbAdsRawLoader.gs` — рядом с существующей записью журнала для query stats,
порядка 30 строк. **Это единственный шаг, без которого нулевые сутки не станут наблюдаемыми.**

### C2. Окно перечитывания шире наблюдаемого хвоста дозаписи
Наблюдаемый хвост — до D+7 включительно. Минимум: `WB_ADS_RAW_COSTS_WINDOW_DAYS_` с 7 до 14,
либо отдельный еженедельный ран-аудит на 30 суток. Без этого доказательство стабильности
структурно невозможно: окно кончается раньше, чем данные перестают меняться.

### C3. Канонический слой = последний полный ответ, а не объединение
`V_ADV_COSTS` переопределить: сутки берутся из **последнего успешного рана, полностью покрывшего
эти сутки** (по журналу C1), а не как union всех ранов. Тогда отзыв записи выражается сам собой,
и дефект §3.4 закрывается. ⚠️ Ломающее изменение семантики RAW-слоя — отдельный PR, отдельная приёмка.

### C4. Вью `wb_raw.V_ADV_COSTS_DAY_COVERAGE`, грейн `date`

```
date
requested_runs           -- успешных ранов, запросивших сутки не раньше D+1
last_successful_read_at
answer_rows              -- строк в последнем полном ответе (0 — легитимно)
answer_sum_rub
stable_reads             -- сколько последних подряд полных чтений дали идентичный набор ключей

billed_complete = requested_runs >= 1
              AND DATE(last_successful_read_at) >= DATE_ADD(date, INTERVAL SETTLE_DAYS DAY)
              AND stable_reads >= 2

zero_spend_day  = billed_complete AND answer_rows = 0    -- «успешный день с 0 ₽»
not_loaded      = NOT billed_complete AND requested_runs = 0
```

`SETTLE_DAYS` ≥ 8 по наблюдениям §3.3 — константа контракта, пересматриваемая по журналу,
а не по памяти. `MART_SKU_DAILY.billed_complete` читает **только** эту вью, с
`IFNULL(..., FALSE)`: нет строки покрытия — сутки не закрыты.

---

## 5. Порядок и промежуточное состояние

1. **C1** — журнал (маленькая правка Apps Script, ничего не ломает).
2. Накопить ≥ `SETTLE_DAYS + 2` суток наблюдений.
3. **C2** — расширить окно.
4. **C3** — переопределить канонический слой (отдельная приёмка, чинит 334,00 ₽).
5. **C4** — вью покрытия. После неё Stage 3B разблокируется без единой правки в MART:
   зависимость уже прописана.

**Промежуточный вариант**, если структуру хочется раскатать раньше семантики: создать
`V_ADV_COSTS_DAY_COVERAGE` сразу, возвращающей `billed_complete = FALSE` для всех суток.
Stage 3B тогда деплоится целиком, billed-KPI везде NULL, витрина не утверждает ничего
недоказанного, а включение семантики сводится к замене тела одной вью.
