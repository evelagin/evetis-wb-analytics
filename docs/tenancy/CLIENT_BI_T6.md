# T6 — клиентский отчёт поверх `analytics_share` (client_001)

Статус на 2026-10-26: витрины, спецификация отчёта, ссылка Linking API, проверка изоляции и
локальный предпросмотр готовы как код. **Ничего не развёрнуто и никому не выдано**: вью в
BigQuery не созданы (нужен ACK владельца на деплой пакета SQL), отчёта в Looker Studio нет,
`bi_access.mode = NONE`. Доступ к данным — по `docs/tenancy/CLIENT_ACCESS_T6.md`.

## 1. Выбор интерфейса — Looker Studio

| Вариант | Изоляция | Новая инфраструктура | Итог |
|---|---|---|---|
| **Looker Studio**, BigQuery-коннектор, учётные данные просматривающего | права BigQuery самого клиента: видит ровно `analytics_share` | нет (бесплатно, Google-аккаунт клиента) | **выбран** |
| Metabase EVETIS | общий сервис-аккаунт владельца, риск увидеть EVETIS; Metabase живёт локально у владельца | хостинг, авторизация, бэкапы | отклонён |
| Свой веб-интерфейс (Cloud Run) | писать и сопровождать авторизацию самим | новый сервис с доступом к данным | отклонён: «не усложнять» |
| Connected Sheets | права клиента, но нет страниц и фильтров отчёта | нет | запасной вариант для выгрузок |

Почему Looker Studio:
1. Источник с **учётными данными просматривающего** (Viewer's credentials) выполняет каждый запрос
   от имени того, кто смотрит. Изоляция обеспечивается BigQuery (READER на `analytics_share` +
   роль `vtsClientQueryRunner`), а не настройкой отчёта: даже скопировав отчёт или источник,
   клиент не прочитает ничего, кроме `analytics_share`.
2. **Linking API** (`tools/client_bi/report.py url`) делает копию шаблона под каждого арендатора
   одной ссылкой: `ds.*.projectId`, `ds.*.datasetId = analytics_share`, `ds.*.billingProjectId` —
   проект арендатора. По документации Linking API источник новой копии получает учётные данные
   того, кто открыл ссылку (проверено 2026-10-26 по developers.google.com/looker-studio/integrate/linking-api,
   Firecrawl). Поэтому ссылку открывает **сам клиент** под своей идентичностью.
3. Запросы тарифицируются в проекте арендатора, не EVETIS и не платформы.

Ограничение: отчёт с графиками в Looker Studio создаётся только в интерфейсе (API для разметки
отчёта нет). Шаблон один раз собирает владелец по спецификации ниже; дальше — только ссылки.
Источники шаблона — тоже «учётные данные просматривающего»: иначе любой, кому дали шаблон,
увидел бы данные client_001 под учётными данными владельца.

## 2. Спецификация отчёта

Машиночитаемая спецификация — `tools/client_bi/report.SPEC` (`python -m tools.client_bi.report spec`).
Тест `test_every_field_in_the_report_spec_exists_in_the_share_contract` сверяет каждое поле с
`sql/tenant/ozon/analytics_share/CONTRACT.json`. Кратко:

| Раздел | Источники | Элементы | Фильтры |
|---|---|---|---|
| 1. Продажи и заказы | `sales_daily`, `sku_daily`, `orders`, `data_freshness` | плашка свежести заказов; карточки (заказано ₽/шт., отмены, доставлено, в пути); столбцы по суткам заказа (неполные сутки — бледные, пропуски — «нет данных»); таблицы товаров и складов отгрузки | период, артикул, склад |
| 2. Остатки | `inventory_cover`, `inventory_current` | плашка: дата снимка и база скорости; карточки остатка; таблица «запас в днях» (< 14 дн. красный); остаток по кластерам; товар × склад | кластер, статус скорости |
| 3. Реклама | `advertising_daily`, `sku_daily`, `store_costs_daily`, смешение `sales_daily`+`advertising_daily` по суткам | карточки (расход, CTR, CPC, ACOS); ДРР магазина только по суткам, где полны и заказы, и реклама; «Списано Ozon за продвижение» — биллинг отдельно; кампании; товары с подписью статуса | период, кампания |
| 4. Экономика SKU | `profitability_daily`, `store_costs_daily` | плашка «предварительно»; комиссия, логистика, эквайринг, возвраты; **вклад до себестоимости (PRE_COGS)** — пусто = «не вычисляется»; начисления вне заказов по классам | период, степень расчёта Ozon |
| 5. Покрытие данных | `data_freshness`, `data_coverage` | таблица сущностей: сегодня, последние полные сутки, отставание, дни по статусам за 30 суток; тепловая карта 45 суток | — |

Правила подписи (во всех разделах): статус `COMPLETE` — «Полные данные», `PARTIAL` — «Неполные
данные», нет строки или `UNKNOWN` — «Нет данных (не загружено)», `FAILED` — «Ошибка загрузки».
Нули не подставляются. Вклад до себестоимости — не прибыль; вклад после себестоимости не
показывается, пока `cogs_coverage ≠ COMPLETE` (себестоимость не передана клиентом).
