**Дата:** 24.08.2026
**Статус:** дизайн, ревизия 1 — на аудит, кода ещё нет
**Автор блока:** ассистент, по запросу владельца

## 1. Что обнаружено

### 1.1. Данные, которые уже есть

| Источник | Что даёт | Чего не даёт |
|---|---|---|
| `V_WB_SUPPLIES_CURRENT` | 115 поставок с 03.09.2024 по 28.07.2026, 20 861 принятая единица, склады, статусы, `factDate` | — |
| `V_WB_SUPPLIES_GOODS_CURRENT` | состав поставки: штрихкод, `nmID`, количество, **`needKiz`** | **самих кодов маркировки нет** |
| `REF_SKU_MASTER` | 24 SKU (11 single + 13 bundle), штрихкод ↔ `nmID` ↔ название | GTIN «Честного знака» отсутствует |

**Поставок с маркированным товаром (`needKiz = true`, принято > 0): 63.**
Период — 18.08.2025 … 28.07.2026, объём в поставке от 1 до 600 единиц.

### 1.2. Ключевой разрыв

`supplies-api` **не отдаёт коды маркировки**. Сейчас списки КИЗ владелец качает
поштучно из ЛК WB (файлы `chestniyznak<supplyId>.csv`). На 63 поставки это 63
ручных скачивания, и повторять это ежемесячно нерабочая схема.

### 1.3. Правило выбытия — не то, что предполагалось

Разбор правил площадки даёт последовательность для **FBW (короб)**:

1. Продавец вводит коды в оборот и физически отгружает товар на склад WB.
2. После приёмки продавец формирует **УПД с функцией ДОП** — этим коды
   передаются маркетплейсу.
3. **Вывод из оборота при розничной продаже делает сам Wildberries.**
   Он сканирует коды на приёмке и указывает их в чеке.

Продавец выводит коды самостоятельно только на FBS / DBS / C&C.

**Отсюда:** массово «списывать» коды, ушедшие на WB по FBW, — неверное
действие. Если коды висят у владельца «в обороте», причина не в том, что их
забыли вывести, а в том, что их **не передали по УПД**. Лечится передачей,
а не выбытием.

Со слов владельца УПД ДОП формировались **не систематически** («иногда / не
уверен»). Это и есть наиболее вероятный источник накопившейся каши.

### 1.4. Сгоревшее — самый крупный контур, а не частный случай

По зафиксированным потерям на 17.08.2026 (см. `losses-2026-08-17`):
**утрачено 3 492 единицы = 717 400 ₽, это 72,8 % всего товара на WB.**
Серия пожаров на складах с 17–18.07.2026, добавилось Коледино 16.08.

| Склад | Единиц |
|---|---:|
| Коледино | 1 158 |
| Тула | 700 |
| Электросталь | 685 |
| Краснодар | 415 |
| Самара (Новосемейкино) | 168 |

Эти единицы физически не существуют, но их коды в ГИС МТ **никто не выведет
сам собой**: WB подаёт выбытие только при розничной продаже, а продажи не
будет. То есть 3 492 кода будут висеть в обороте бессрочно, пока их не
вывести вручную с причиной «утрата».

**Это делает КИЗ-контур не гигиенической задачей, а обязательной.**

### 1.5. Ограничение на стороне «Честного знака»

True API авторизуется **только через УКЭП**: запрос данных на подпись →
подпись строки сертификатом (CMS, base64) → обмен на токен. Токен живёт
до 10 часов, долгоживущего ключа не предусмотрено.

Практический вывод: **полностью автономный ежедневный загрузчик ЧЗ в Cloud Run
невозможен** без отдельного узла подписи с сертификатом. Варианты — в §4.3.

## 2. Почему это проблема

1. **Нельзя ответить на вопрос «где код».** По каждому из тысяч эмитированных
   кодов сейчас невозможно быстро сказать: уехал на WB, продан, лежит на
   складе, испорчен или потерян.
2. **Риск расхождения с ГИС МТ.** Коды, физически проданные через WB, но
   числящиеся в обороте за ИП, — это несоответствие фактического оборота
   данным системы мониторинга.
3. **Объём растёт.** 63 поставки за год, дальше больше. Чем позже начать,
   тем дороже разбор.
4. **Уже был инцидент.** История с энзимной пудрой (`)Oup)` вместо `)OUp)`)
   показала: расхождения между файлами фулфилмента и реальными кодами
   существуют и молча ломают процессы.

---

## 3. Границы работы

**Входит:**
- загрузка списков КИЗ по принятым поставкам WB в BigQuery;
- загрузка состояния кодов из «Честного знака»;
- витрина сверки «код → где он по данным WB → где он по данным ЧЗ → что делать»;
- инвентаризация УПД ДОП по 63 поставкам.

**Не входит:**
- автоматическая подача документов в ГИС МТ (вывод, передача) — только
  подготовка списков, действие выполняет владелец;
- изменение существующих потоков (финансы, реклама, заказы, продажи, остатки);
- Ozon.

## 4. Что предлагается

### 4.1. Модель данных

Новые объекты в `wb_raw`, по действующим правилам проекта
(RAW-слой сырой, версионирование через `run_id`, дедуп по ключу):

| Объект | Назначение | Ключ |
|---|---|---|
| `RAW_WB_KIZ_SUPPLY` | коды маркировки по поставкам WB | `supply_id` + `kiz` |
| `RAW_WB_KIZ_DOCS` | журнал скачанных документов-источников | `service_name` |
| `RAW_CHZ_CIS_STATE` | состояние кодов в ЧЗ на дату среза | `cis` + `snapshot_ts` |
| `V_KIZ_RECON` | витрина сверки | `cis` |

Поля `RAW_WB_KIZ_SUPPLY`: `snapshot_ts`, `run_id`, `supply_id`, `kiz`,
`gtin`, `serial`, `source_document`, `row_hash`.

Поля `RAW_CHZ_CIS_STATE`: `snapshot_ts`, `run_id`, `cis`, `gtin`,
`status`, `owner_inn`, `parent_cis`, `emission_dt`, `introduced_dt`,
`withdrawn_dt`, `withdraw_reason`, `raw_json`, `row_hash`.

### 4.2. Загрузка КИЗ со стороны WB

Гипотеза: списки доступны через `documents-api.wildberries.ru`
(`/api/v1/documents/categories`, `/list`, `/download`). Спецификация полный
перечень категорий не приводит — его отдаёт только живой метод.

**Поэтому первым шагом идёт проба `WbDocumentsProbe.gs`** (написана, только
чтение). Она устанавливает: перечень категорий, наличие КИЗ-документа,
привязку документа к `supplyID`, формат выгрузки.

Развилка по результату пробы:
- **КИЗ-документ есть** → загрузчик `kizdocs` в `cloud/src/loaders/`
  по образцу `stocks`: список документов → скачивание → распаковка →
  нормализация → append в `RAW_WB_KIZ_SUPPLY`.
- **КИЗ-документа нет** → остаётся ручная выгрузка из ЛК, но разовая:
  63 файла один раз, дальше по одному файлу на новую поставку.
  Загрузчик тогда читает файлы из папки Drive, как уже сделано для
  финансовых отчётов (`Wbfinanceimportfromdrive`).

### 4.3. Загрузка состояния со стороны ЧЗ

Три варианта, в порядке роста стоимости:

| Вариант | Как | Плюс | Минус |
|---|---|---|---|
| **A. Ручные выгрузки** | владелец выгружает коды по GTIN из ЛК ЧЗ (как делал по пудре), файлы кладутся в Drive, загрузчик разбирает | работает сегодня, ноль зависимостей | руками, 17 GTIN |
| **B. Полуавтомат** | владелец получает токен True API (≤10 ч) и кладёт в Secret Manager, загрузчик отрабатывает окно | полноценное API, точные статусы | токен живёт 10 ч, нужен запуск владельцем |
| **C. Узел подписи** | сервис с УКЭП обновляет токен сам | полная автономность | сертификат в облаке, отдельный контур безопасности |

**Рекомендация: начать с A**, поскольку задача сейчас — разовое наведение
порядка, а не ежедневный мониторинг. Переход на B делать, когда контур
устоится и понадобится регулярная сверка.

### 4.4. Витрина сверки

`V_KIZ_RECON` соединяет две стороны и присваивает каждому коду
**одно** состояние:

| Состояние | Условие | Что делать |
|---|---|---|
| `OK_ПРОДАН` | есть в поставке WB, в ЧЗ выведен из оборота | ничего |
| `ЖДЁТ_УПД` | есть в поставке WB, в ЧЗ в обороте за ИП | сформировать УПД ДОП по поставке |
| `НА_СКЛАДЕ_WB` | есть в поставке WB, передан по УПД, ещё не продан | ничего, ждать продажи |
| `НЕ_ОТГРУЖЕН` | в ЧЗ в обороте, ни в одной поставке не встречается | остаток — проверить физически |
| `УТРАЧЕН_ПОЖАР` | есть в поставке на сгоревший склад, в ЧЗ не выведен | вывод из оборота, причина «утрата» |
| `ПОТЕРЯН` | в ЧЗ в обороте, физически отсутствует, в поставках нет | вывод из оборота, причина «утеря» |
| `ИСПОРЧЕН` | помечен владельцем как брак | вывод из оборота, причина «порча» |
| `ПРИЗРАК` | есть в поставке WB, но в ЧЗ не найден | разбор: битый код, как было с пудрой |
| `ДУБЛЬ` | один код в двух поставках | разбор, ошибка отгрузки |

Категории `ПОТЕРЯН` / `ИСПОРЧЕН` автоматически не проставляются — это
решение владельца по физической инвентаризации. Витрина только выделяет
кандидатов.

### 4.5. Как вычислить сгоревшие коды поимённо

Ни поставки, ни продажи не несут КИЗ в API, поэтому «какой именно код сгорел»
напрямую не читается. Но связка выводится вычитанием:

```
КИЗ поставок на сгоревшие склады
  МИНУС коды, уже выведенные из оборота в ЧЗ (проданы до пожара)
  = кандидаты на вывод по причине «утрата»
```

Склады отгрузки известны из карточки поставки (`warehouse_name`), список
сгоревших — из `losses-2026-08-17`. Контроль: количество кандидатов должно
сойтись с 3 492 единицами по складам ±дрейф; расхождение больше 5 % означает
ошибку метода, а не «примерно так».

🔴 **Развилка, которую нужно закрыть до любых действий.** Кто вправе выводить
сгоревшие коды, зависит от того, был ли по поставке УПД ДОП:

- **УПД был** → коды на балансе WB, продавец вывести их не может.
  Действие — требование к WB списать утраченное, вместе с заявкой на
  компенсацию.
- **УПД не был** → коды остались на балансе ИП, продавец выводит сам
  с причиной «утрата».

Поэтому §4.6 (инвентаризация УПД) выполняется **до** массовых выводов.

### 4.6. Инвентаризация УПД ДОП

Отдельным шагом: по каждой из 63 поставок установить, был ли сформирован
УПД ДОП. Источник — ЭДО/раздел документов ЛК WB. Результат — таблица
«поставка → УПД есть/нет → сколько кодов зависло».

Это самая ценная часть: она отвечает на вопрос, почему коды не выбыли,
и даёт конкретный список того, что надо доформировать.

## 5. Этапы

| Этап | Содержание | Результат |
|---|---|---|
| **Проба-0** | `WbDocumentsProbe.gs` | известно, есть ли КИЗ в API документов |
| **PR-Kiz1** | таблицы `RAW_WB_KIZ_SUPPLY`, `RAW_WB_KIZ_DOCS` + загрузчик по итогу пробы | коды поставок в BQ |
| **PR-Kiz2** | `RAW_CHZ_CIS_STATE` + разбор выгрузок ЧЗ | состояние кодов в BQ |
| **PR-Kiz3** | `V_KIZ_RECON` + отчёт по состояниям | что с каждым кодом делать |
| **PR-Kiz4** | инвентаризация УПД + список к доформированию | план действий владельца |
| **PR-Kiz5** | поимённый список сгоревших КИЗ | что выводить как утрату / что требовать с WB |

Порядок важен: **Kiz4 идёт до Kiz5**, потому что от наличия УПД зависит,
кто вообще вправе выводить сгоревшие коды.

## 6. Контрольные цифры для приёмки

- Поставок с `needKiz = true`: **63**; загружено КИЗ-документов ≥ 63,
  либо явно перечислены поставки, по которым документа нет.
- По поставкам 41047776 и 41047801 (есть ручные выгрузки для сверки):
  **129** и **125** КИЗ соответственно, пересечение между поставками — **0**.
- Дублей `cis` внутри одной поставки: **0**.
- Каждый код в `V_KIZ_RECON` получает ровно одно состояние; сумма по
  состояниям равна числу уникальных кодов.
- Коды из наборов не смешиваются с кодами единичек: набор — самостоятельный
  КИЗ, его компоненты не считаются отгруженными отдельно.

## 7. Риски

| Риск | Митигация |
|---|---|
| КИЗ-документа в API нет | fallback на выгрузку из Drive, схема данных не меняется |
| Токен ЧЗ живёт 10 ч | вариант A (ручные выгрузки) на старте, B — позже |
| Массовое ошибочное выбытие | витрина **не** выполняет действий, только готовит списки; `ПОТЕРЯН`/`ИСПОРЧЕН` ставит владелец |
| Битые коды в источниках | состояние `ПРИЗРАК` ловит их явно (прецедент с пудрой) |
| Вывод чужих кодов | если по поставке был УПД, коды на балансе WB — продавец их вывести не может; §4.6 закрывает это до действий |
| Сгоревшие коды сочтены неверно | контроль: сходимость с 3 492 ед по складам, порог расхождения 5 % |
| Нагрузка на API документов | пагинация по 50, пауза 700 мс, потолок страниц |

## 8. Что нужно от владельца, чтобы двигаться

1. Запустить `WbDocumentsProbe.gs` и прислать Execution log.
2. Уточнить, какой именно токен ЧЗ есть на руках (True API по УКЭП или
   доступ через стороннего интегратора).
3. Сказать, велась ли где-то фиксация испорченного / утерянного товара,
   или это восстанавливать с нуля.
4. Вспомнить (или проверить в ЭДО), формировались ли УПД ДОП по поставкам
   на сгоревшие склады — Коледино, Тула, Электросталь, Краснодар, Самара,
   Сарапул, Волгоград, Шушары. От этого зависит, кто выводит 3 492 кода.
