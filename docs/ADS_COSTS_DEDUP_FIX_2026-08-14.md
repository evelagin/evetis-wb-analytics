# Ads-Costs · исправление ключа дедупа `V_ADV_COSTS`

Дата: 2026-08-14 · автор материала: ассистент · статус: **ждёт APPROVE аудитора**
Затрагивает: `apps-script/WbAdsBigQuery.gs` (одна вью), `wb_mart.FACT_ADS_COSTS_DAILY` (пересобирается сама).
НЕ затрагивает: Ads-1/Ads-2/Ads-3, финансовый контур, `MART_SKU_DAILY.ad_spend`, ни одного листа.

---

## 1. Что обнаружено

Дедуп-вью `V_ADV_COSTS` схлопывает строки по ключу `TO_HEX(SHA256(raw_json))`.
Ключ не работает: одно и то же списание попадает во вью многократно.

Доказательство — восемь строк одного платежа:

```
advertId 37727999 · updTime 2026-07-20T19:25:24.576382+03:00 · updSum 307
загружено 8 прогонами (22.07 … 27.07), скользящее окно 7 дней
различие ТОЛЬКО в двух полях raw_json:
  updNum        0 → 308185986    номер документа: WB присваивает его позже
  advertStatus  9 ↔ 11           статус КАМПАНИИ на момент загрузки
```

Ни `updNum`, ни `advertStatus` не являются свойствами платежа: первый появляется
при выпуске документа, второй описывает кампанию и меняется сам по себе.
Скользящее окно перезагружает один день до семи раз — каждое изменение любого из
этих полей рождает новый хэш и новую строку во вью.

### Масштаб (замер 14.08.2026)

```
RAW_WB_ADV_COSTS                                   4 478 строк
V_ADV_COSTS (сейчас)                               2 484 строки   621 461,00 ₽
различных (advertId, updTime, updSum)              1 938 строк    497 546,00 ₽
завышение                                            546 строк    123 915,00 ₽
```

| месяц | сейчас | после | завышение |
|---|---:|---:|---:|
| 2026-04 | 96 009 | 96 009 | — |
| 2026-05 | 140 347 | 140 347 | — |
| 2026-06 | 116 970 | 116 970 | — |
| **2026-07** | **218 172** | **116 015** | **+102 157 (+88%)** |
| **2026-08 (по 13-е)** | **49 963** | **28 205** | **+21 758 (+77%)** |

Апрель–июнь совпали до рубля: там номера документов уже были присвоены, а статусы
кампаний в окне перезагрузки не менялись. Именно поэтому дефект не был виден раньше —
он проявляется только на «живых», недавно закрытых днях.

### Побочный результат: fullstats оправдан

После исправления ключа расход по fullstats сходится с расходом по балансу:

```
2026-04  101,9%     2026-05  102,8%     2026-06  102,9%
2026-07   82,7%     2026-08   99,8%
```

Весь недобор июля (20 111 ₽) лежит в 05–14.07 — там же известная дыра сбора
(11.07: 4 кампании и 0 ₽; 12–14.07 строк нет вовсе). Системной ошибки в fullstats нет,
`MART_SKU_DAILY.ad_spend` этим дефектом **не затронут** (он берётся из fullstats,
а не из costs).

## 2. Почему это проблема

`FACT_ADS_COSTS_DAILY.actual_spend_rub` — контрольная величина «сколько реально ушло
с рекламного баланса». Она задумана как независимая проверка расхода из fullstats.
Сейчас она завышена почти вдвое, то есть в роли контроля не просто бесполезна, а вредна:
сверка будет показывать расхождение там, где его нет. Дальше по обычному сценарию
контроль, который «всегда врёт», перестают читать — и он не сработает, когда расхождение
станет настоящим.

Отдельно: любой будущий расчёт ДРР или маржинальности от «расхода по балансу» унаследует
завышение и занизит прибыль.

## 3. Что предлагается изменить

Одно выражение — ключ партиционирования дедуп-вью:

```js
// было
makeView('V_ADV_COSTS', 'RAW_WB_ADV_COSTS',
  "TO_HEX(SHA256(COALESCE(raw_json, '')))", null);

// стало
makeView('V_ADV_COSTS', 'RAW_WB_ADV_COSTS',
  'advertId, updTime, updSum', null);
```

`ORDER BY` внутри `makeView` не меняется (`load_ts DESC, run_id DESC`) — из группы
остаётся самая свежая строка, то есть с уже присвоенным `updNum` и актуальным статусом.

### Почему ключ безопасен

Ключ схлопывает строки, а значит может уничтожить данные, если два РАЗНЫХ платежа
дадут одинаковые три поля. Проверено на всей истории:

```
групп с ≥2 строками (advertId, updTime, updSum) внутри ОДНОГО run_id:  0
лишних строк в таких группах:                                          0
```

То есть в одном ответе API такая пара не встречается никогда: `updTime` идёт с точностью
до микросекунды, а суточные списания приходят одной строкой на кампанию в 23:59:59.
**Все** дубли пересекают границу прогона — то есть являются перезагрузками, и схлопывать
их не только можно, но и нужно.

Схема RAW не меняется. `raw_json` продолжает храниться целиком — ничего не теряется,
меняется только правило выбора строки.

## 4. Какие файлы и объекты затронуты

| объект | что происходит |
|---|---|
| `apps-script/WbAdsBigQuery.gs` | одно выражение + комментарий |
| `wb_raw.V_ADV_COSTS` | пересоздаётся (`CREATE OR REPLACE VIEW`) |
| `wb_mart.FACT_ADS_COSTS_DAILY` | пересобирается сама на ближайшем прогоне витрины |
| всё остальное | не трогается |

`FACT_ADS_COSTS_DAILY` собирается полным `CREATE OR REPLACE TABLE … FROM V_ADV_COSTS`
(`sql/mart/pr_mart1_facts.sql:371`), backfill не нужен: ночной прогон 07:00 МСК
подхватит исправленную вью сам. Все четыре `ASSERT` этой FACT останутся зелёными —
они проверяют грейн и парсинг, а грейн не меняется (см. контрольные цифры).

### Порядок выката

1. Владелец: ветка `fix/ads-costs-dedup-key`, коммит, PR, merge.
2. Ассистент: **точечный** `CREATE OR REPLACE VIEW wb_raw.V_ADV_COSTS` тем же SQL,
   который генерирует изменённый код.
   🔴 `wbAdsBqCreateViews()` для этого НЕ запускать: она пересоздаёт **все шесть** вью,
   включая `V_ADV_QUERY_BIDS` (проверено 14.08 — `creation_time` меняется у всех).
   Данные при этом целы, но лишнее действие на живом контуре не нужно.
   🔴 `wbAdsBqInit()` не запускать никогда на работающем контуре — при любой ошибке
   внутри он выключает рекламный BQ-sink целиком.
3. Ассистент: read-only проверки (ниже).
4. Следующий прогон витрины (07:00 МСК) — повторная проверка `FACT_ADS_COSTS_DAILY`.

### Откат

Вернуть прежнее выражение и пересоздать вью. Данные не пострадают ни в одну сторону:
RAW не меняется, вью считается на лету.

## 5. Как проверить результат

### Baseline «до» (снят 14.08.2026 до изменений)

```
RAW_WB_ADV_COSTS                       4 478 строк
V_ADV_COSTS                            2 484 строки · 621 461,00 ₽
FACT_ADS_COSTS_DAILY                   1 749 строк  · 621 461,00 ₽
различных (date, advert_id) в V_ADV_COSTS   1 749
```

### Ожидание «после»

```
V_ADV_COSTS                            1 938 строк · 497 546,00 ₽
различных (date, advert_id)            1 749          ← НЕ меняется
FACT_ADS_COSTS_DAILY (после прогона)   1 749 строк  · 497 546,00 ₽
```

🔴 Ключевой инвариант: **число строк `FACT_ADS_COSTS_DAILY` обязано остаться 1 749.**
Дедуп убирает копии, а не события; если число строк упало — ключ схлопнул что-то лишнее,
и изменение надо откатывать. Падает только сумма.

Помесячно после исправления: 96 009 / 140 347 / 116 970 / 116 015 / 28 205.

### Проверочный SQL

```sql
-- 1. Строки и сумма вью
SELECT COUNT(*) AS n_rows, ROUND(SUM(SAFE_CAST(updSum AS FLOAT64)),2) AS sum_rub
FROM `wb_raw.V_ADV_COSTS`;                        -- ждём 1938 · 497546.00

-- 2. Грейн витрины не изменился
SELECT COUNT(DISTINCT FORMAT('%t|%t',
         SAFE.PARSE_DATE('%Y-%m-%d', SUBSTR(updDate,1,10)),
         SAFE_CAST(advertId AS INT64)))
FROM `wb_raw.V_ADV_COSTS`;                        -- ждём 1749

-- 3. Дублей по бизнес-ключу больше нет
SELECT COUNT(*) FROM (
  SELECT advertId, updTime, updSum FROM `wb_raw.V_ADV_COSTS`
  GROUP BY 1,2,3 HAVING COUNT(*) > 1);            -- ждём 0

-- 4. Помесячно
SELECT FORMAT_DATE('%Y-%m', DATE(updDate)) AS ym,
       ROUND(SUM(SAFE_CAST(updSum AS FLOAT64)),0) AS spend
FROM `wb_raw.V_ADV_COSTS` GROUP BY ym ORDER BY ym;

-- 5. Контроль после прогона витрины
SELECT COUNT(*) AS n_rows, ROUND(SUM(actual_spend_rub),2) AS spend, MAX(built_at) AS built
FROM `wb_mart.FACT_ADS_COSTS_DAILY`;              -- ждём 1749 · 497546.00
```

## Что этот случай говорит о методе

**Хэш всей записи — не ключ дедупа, а ключ «побайтовой одинаковости».** Он молча
превращается в «ключ отсутствия изменений где угодно в записи», включая поля, которые к
сущности не относятся. Дедуп по хэшу безопасен только тогда, когда доказано, что в записи
нет ни одного изменчивого поля, — а такое доказательство почти никогда не делают.

Ровно тот же класс ошибки, что урок №10 по Ads-3 («универсальный дедуп-хелпер может тихо
уничтожить историю»), но с обратным знаком: там ключ схлопывал лишнее, здесь — не схлопывал
нужное. Общее у них одно: **ключ выбирали от удобства реализации, а не от того, что
именно идентифицирует сущность.**

И третье: дефект существовал с апреля, а проявился только в июле — потому что до этого
изменчивые поля случайно не менялись. **Зелёная сверка на спокойных данных не проверяет
ключ.** Ключ проверяется там, где данные шевелятся.
