## 1. Контракты метрик

### 1.1 Реклама — два раздельных контракта

| Контракт | Величина | Источник | Где используется |
|---|---|---|---|
| **A. Executive / управленческий P&L** | **биллинг WB по дате оказания услуги** | `V_DASH_FINANCE_CORRECTED_DAILY.ad_spend_financial_rub` ← `wb_mart.FACT_ADS_COSTS_DAILY` (`adv/v1/upd`), покрытие `wb_raw.V_ADV_COSTS_DAY_COVERAGE` | результат периода, карточки «Реклама», «ДРР», «От выручки к результату», «Прочие расходы WB» |
| **B. SKU Performance / рекламная аналитика** | атрибуция рекламной статистики на SKU | `MART_SKU_DAILY.ad_spend` ← `FACT_ADS_SKU_DAILY.stats_spend_rub` | ДРР по артикулам, эффективность кампаний и SKU |
| Сверка выплаты (settlement) | документы «Оказание услуг WB Продвижение» в финотчёте | `ad_spend_billed_rub` / `ad_billing_reconstructed_rub` | карточка «Реклама: биллинг WB», мост выплаты |

Правила:
- в результате периода ровно **один** рекламный расход — биллинг по дате услуги;
- биллинг **не распределяется** по SKU: методологии нет;
- ДРР Executive = биллинг / выручка (ratio-of-sums на одном множестве суток);
- ДРР SKU = атрибуция / выручка SKU — явно другой контракт;
- документы WB Продвижения режут сутки по времени документа, а не по полуночи. Их разница с биллингом — отсечка, а не ошибка.

**Покрытие и финальность биллинга.**
- `ads_billing_covered` = сутки явно запрошены успешным раном (`requested_ok`) **И** `FACT_ADS_COSTS_DAILY` совпадает со снапшотом покрытия до копейки. Второе условие защищает от гонки: снапшот уже обновлён, а факт ещё не пересобран.
- `ads_billing_is_final` = `billed_complete`: SLA 15 суток × 3 стабильных чтения.
- Незакрытые сутки **входят** в результат и помечаются `ads_billing_provisional_day = 1`. Это прецедент `contains_provisional_finance`: финансы устроены так же.
- ⚠️ Решение о включении предварительных суток принято при реализации по прецеденту финансов. Строгий режим — одна правка: `covered` → `is_final` в гейте `period_result_eligible`.

Сверка трёх величин за 31.08–13.09.2026:
```
атрибуция   20 862,25 ₽   (контракт B)
биллинг     20 750,00 ₽   (контракт A — в результате)
документы   20 818,00 ₽ = 20 750 + 1 641 (30.08 в док. 313648363) − 1 573 (часть 13.09 без документа)
```

### 1.2 Возмещения WB — техническая проводка, эффект 0

Операции (поле `commission_amount`):
- «Возмещение издержек по перевозке/по складским операциям с товаром»;
- «Возмещение издержек по перемещению и операционной обработке товара» (имя с 01.09.2026);
- «Возмещение за выдачу и возврат товаров на ПВЗ».

Тождество, доказанное на всей истории (118 715 строк, 0 нарушений):
```
vw + vwNds + rebillLogisticCost + ppvzReward = 0 (±2 коп.)
forPay = deliveryService = paidStorage = deduction = penalty = additionalPayment = paidAcceptance = 0
```
Это перераспределение вознаграждения WB в пользу ПВЗ или перевозчика. Денежного потока продавцу нет. В официальной сверке выплаты (27.07–23.08, Δ = 0,00 ₽) эти строки не участвуют.

Реализация: `REF_COST_MAP.economic_direction = 'MEMO'` → `V_WB_FINANCE_AMOUNTS_LONG_MAPPED.cost_amount_positive = 0` (явный ноль, а не NULL). Категории `reimbursement_logistics` и `reimbursement_pvz` сохранены для наблюдаемости. Переход в MEMO защищён ASSERT §0.2 миграции и DQ-1a валидации: появление строки, нарушающей тождество, роняет проверку.

### 1.3 Минимальный платёж по тарифной опции — расход

«Остаток по минимальному платежу» — доплата до минимального платежа за опцию «Конструктора тарифов». Владелец подтвердил опцию «Общий рейтинг по карточке» (+0,75 %). Случаи: 13.08.2026 — 1 714,74 ₽, 12.09.2026 — 2 382,00 ₽. Ни одной обратной проводки.

- Каноническая колонка: `V_DASH_FINANCE_CORRECTED_DAILY.tariff_option_minimum_payment_rub`.
- `minimum_payment_adjustment_rub` сохранена для совместимости, значение идентично.
- Остаётся в результате: входит в `account_level_total_corrected_rub` (DQ-10b).
- Название для экрана (Executive Dashboard v2): «Минимальный платёж по тарифной опции».

### 1.4 Себестоимость — действующая политика по дате, не FIFO

`evetis_ref.V_PRODUCT_COGS_EFFECTIVE`, метод `EFFECTIVE_DATE`: одна действующая запись на SKU × дату (DQ-4).
- Партии проданных единиц не определяются: прослеживаемость партий отсутствует.
- Себестоимость набора = сумма действующих компонентов (DQ-5).

## 2. Формула результата

**До (v1):**
```
period_result_pre_cogs_corrected = contribution_pre_cogs
                                 − (account_level_total − ad_billing_documents − force_majeure)
contribution_pre_cogs = buyouts_rub − marketplace_fee − logistics − ad_spend_ATTRIBUTED
account_level_total  ∋ возмещения как CREDIT (доход)
```

**После (v2):**
```
period_result_pre_cogs_corrected = contribution_pre_cogs + ad_spend_attributed − ad_spend_financial
                                 − (account_level_total − ad_billing_documents − force_majeure)
                                 = buyouts_rub − marketplace_fee − logistics − ad_spend_BILLING_SERVICE_DATE
                                   − (account_level_total − ad_billing_documents − force_majeure)
account_level_total  ∌ возмещения (MEMO = 0)
period_result_eligible = contribution_covered ∧ finance_covered ∧ ads_billing_covered
```

Не изменились: `MART_SKU_DAILY`, процедуры, `V_DASH_KPI_DAILY` (кроме нулевых возмещений через карту), `V_DASH_SETTLEMENT_DAILY`, `V_DASH_EXECUTIVE_ECONOMICS_DAILY` (читает corrected-слой), себестоимость, SKU Performance, раскладка дашбордов.
