## 2. Закон и доказательство присутствия

Воронка агрегирована по суткам × SKU: srid в ней нет. Присутствие отменённого заказа в Q доказывается арифметикой суток:

```
room = Q(воронка) − заказы Orders API без отмены − доказанные отказы вне Orders API − продажи вне Orders API
```

`room` — сколько мест в Q остаётся отменённым заказам. Отмены с логистикой занимают места первыми, отмены без логистики — оставшиеся.

Проверка на 04.09–31.10.2026:
- закон «Q = заказы без отмены + отмены с логистикой + доказанные заказы вне Orders API (+ ещё не объяснённые)» без противоречий;
- суток, где воронка меньше заказов Orders API без отмены, не найдено ни разу.

Это не правило `S = MIN(S, Q)`:
- заказы без отмены и доказанные заказы вне Orders API вычитаются из Q до распределения мест;
- места распределяются по классу логистики конкретного srid.

Неразличимый случай: места ровно столько, сколько отмен без логистики. Тогда в Q может стоять:
- либо сам отменённый заказ;
- либо заказ вне Orders API, у которого нет следа в финотчёте.

На зрелом финотчёте экономика у них одна: единица без продажи и без логистики, вклад 0. Поэтому оба варианта дают V = 1.

Прямое доказательство — собственный счётчик отмен воронки по дате заказа (`cancel_count`). Сейчас загрузчик воронки его не заполняет, а v3 API отдаёт историю только за 7 суток. Когда загрузчик начнёт заполнять счётчик, он станет вторым независимым источником. Это отдельная задача, в этот PR не входит.

## 3. Модель на листе

Формула W строки (без изменений для всех суток, кроме восстановленных):

```
W = Q·AI − X − AG − S·(AI + AF + REVERSE_LEG_RATE) + Y
```

| Класс отмены | S | Поправка W | Вклад единицы |
|---|---|---|---|
| С логистикой, в Q | входит (как раньше) | — | −AF − REV |
| Без логистики, в Q (V) | входит | `+V*(AF+REVERSE_LEG_RATE)` в конце формулы строки | 0 |
| Без логистики, вне Q | не входит | — | 0 |
| С логистикой, вне Q | на листе не представима | — | ANOMALY: лист не меняется, только журнал |

Изменение W при восстановлении:
- **18.10:** ΔW = −(AI + AF + REV) + (AF + REV) = −AI. Результат не зависит от суточной ставки обратного плеча.
- **24.10:** ΔW = +(AI + AF + REV) при ставке на момент записи.

## 5. Зрелость финотчёта (аудит PR #394, BLOCKER 1)

«Последний FINAL `_rr_date`» покрытия не доказывает: пропущенная в середине неделя давала бы ложную зрелость. Новое правило строится из реестра финотчёта.

- **Интервал окончательного финотчёта** — загрузка `wb_raw.FINANCE_REPORT_LOADS`, у которой одновременно:
  - `report_period = 'WEEKLY'`, отчёт типа 1, статус `COMPLETE`, обе даты заданы;
  - неделя (с понедельника) окончательна по ОБОИМ типам отчёта 1 и 2 в `wb_raw.FINANCE_WEEK_STATUS` (`weekly_final = TRUE`).
- **Неделя, разрезанная границей месяца** — два интервала одной недели, например 28–30.09 и 01–04.10. Нужны оба.
- **Сутки заказа d зрелы**, если выполнены три условия:
  - день d покрыт интервалом;
  - день d + 46 покрыт интервалом;
  - у каждого интервала, который кончается внутри горизонта, есть интервал, покрывающий следующий день.
- **Не зрело (IMMATURE, никогда FINAL):** NULL, пропуск недели, неизвестный статус или тип, слой DAILY, незагруженная половина разрезанной недели. То же при пустом реестре: строк зрелости нет, и класс остаётся IMMATURE.
- **Исполнение.** Тексты обеих вью исполняются на SQLite-фикстурах: `tools/tests/test_unitka_cancel_maturity.py`, 9 случаев — полная история, пропуск недели, тип 2 не окончателен, NULL, `DISCOVERED`/`DAILY`, половина разрезанной недели, пустой реестр.
- **Production 02.11** (только SELECT): интервалы непрерывны с 13.07 по 01.11, разрезанные недели учтены, зрелы заказы по 15.09.

Зрелость (≥ 46 суток) всегда старше окна сверки (35 суток, `[LCD−34, LCD]`). Поэтому:
- в окне писателя и сверки класс всегда `IMMATURE`, и S там прежний. Проверка на production: DAILY 25/25 и RECON 875/875 строк совпадают с живыми вью, FINAL = 0;
- восстановленные сутки лежат вне окна: Engine их не адресует;
- если V > 0 когда-нибудь окажется в окне, это отказ до записи (`CANCEL_VOID_OUTSIDE_RESTORE`), а не тихая запись.

## 6. Аномалии, атомарность, производительность (аудит PR #394)

**BLOCKER 2 — аномалии.**
- Аномалии класса (`ANOMALY_*`) входят в отпечаток манифеста (ключ `nmID|дата|статус`).
- Запись при любой аномалии, которую владелец не принял поимённо (`UNITKA_CANCEL_RESTORE_ACCEPT_ANOMALIES`), — отказ `CANCEL_RESTORE_ANOMALY` до первой записи.
- Аномалия, появившаяся после просмотра плана, меняет отпечаток, и запись упадёт с `CANCEL_RESTORE_DIGEST_MISMATCH`.

**BLOCKER 3 — атомарность.**
- Все поля всех суток пишутся одним `spreadsheets.batchUpdate` из `updateCells`:
  - S — значение и заметка одной ячейкой (`fields: userEnteredValue,note`, формат не трогается);
  - W — формула в локали книги, тем же способом, каким `unitka-month-prep` создаёт месяцы в production.
- Пакет применяется целиком или не применяется вовсе. Поэтому ни лист, ни снимок Store P&L не видят S без W или W без S.
- Каждый запрос пакета обязан быть одной ячейкой S или W суток манифеста на листе манифеста (`assertConfined`), иначе отказ без записи.
- Ошибка или таймаут пакета — исход неизвестен:
  - перечитывание и диагноз состояния `ALL_BEFORE` / `ALL_AFTER` / `MIXED` в журнале;
  - отказ `CANCEL_RESTORE_UNKNOWN_OUTCOME`, повтора нет.

  Если перечитывание показало `ALL_AFTER`, это значит, что пакет применён: следующий план покажет `already_applied`. `ALL_BEFORE` значит, что пакет не применён. Решение о повторе — за владельцем.

**PERFORMANCE.** Замер на тестовой копии книги (`1HTgd__…`, 803 × 623), только чтение, по 3 прогона:

| Вариант чтения формул | Время | Объём |
|---|---|---|
| Вся сетка A1:WY803 | ≈ 2,3 с | 7,46 МБ |
| Только колонки W 25 слотов, одним `batchGet` | ≈ 0,95 с | 0,87 МБ |

Store P&L читает только колонки W.
