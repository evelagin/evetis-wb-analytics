# Юнитка WB — классы отмен: присутствие в воронке и логистика (cancel_class_v1)

Основание: OWNER ACK «EVETIS WB UNITKA — CANCEL RECONCILIATION / DESIGN & TEST ONLY», 02.11.2026.
Решения владельца 02.11.2026:
- поправка W пишется в формуле строки;
- отмена видна в S, а её особенность описана в заметке ячейки;
- колонки, листы и реестры не добавляются;
- «логистики нет» доказывается только зрелым финотчётом (46 суток).

**Статус: не развёрнуто.** До отдельного OWNER ACK не выполняются DDL, Terraform apply, deploy, запись в лист и изменения расписаний.

Суммы в рублях и srid в этом документе не приводятся: репозиторий публичный. Приёмка на живых значениях и выгрузки по srid лежат в приватном архиве доказательств владельца.

## 1. Что не так

Сверка октября 2026 с официальной выгрузкой воронки WB по всем 25 SKU:
- переходы, корзины и заказы совпали до штуки по каждому SKU-дню;
- отмены расходятся в трёх SKU-днях.

Два из трёх расхождений — ошибки модели Юнитки.

| Сутки / nmID | Что было | Ошибка в W |
|---|---|---|
| 18.10 / 535580776 | Заказ отменён через 26 минут, логистики нет. Воронка оставила его в Q, а S считает только отмены следующих дней | Отмена посчитана продажей: W завышен на AI |
| 24.10 / 252442517 | Заказ отменён на следующий день, логистики нет. Воронка его не посчитала (Q = 0), но в S он есть | Вычтена полная стоимость отмены, хотя заказа в Q нет: W занижен на AI + AF + REV |

Третье расхождение (01.10 / 252442517) — разница методик, а не ошибка. В графу «Отменили» кабинета WB попадают возвраты после выкупа. В Юнитке возвраты в S не входят: P&L магазина берёт их из финотчёта.

Почему по времени отмены судить нельзя. Зрелая история 13.04–17.09.2026:

| Когда отменили | Всего отмен | Из них с обоими плечами логистики | Без логистики |
|---|---|---|---|
| В день заказа | 147 | 7 | — |
| На следующий день | 23 | — | 5 |

## 2. Закон и доказательство присутствия

Воронка агрегирована по суткам × SKU: srid в ней нет. Присутствие отменённого заказа в Q доказывается арифметикой суток:

```
room = Q(воронка) − заказы Orders API без отмены − доказанные отказы вне Orders API − продажи вне Orders API
```

`room` — сколько мест в Q остаётся отменённым заказам. Отмены с логистикой занимают места первыми, отмены без логистики — оставшиеся.

Проверка на 04.09–31.10.2026:
- закон «Q = заказы без отмены + отмены с логистикой + доказанные заказы вне Orders API (+ ещё не объяснённые)» без противоречий;
- суток, где воронка меньше заказов Orders API без отмены, не найдено ни разу.

Это не правило `S = MIN(S, Q)`:
- заказы без отмены и доказанные заказы вне Orders API вычитаются из Q до распределения мест;
- места распределяются по классу логистики конкретного srid.

Неразличимый случай: места ровно столько, сколько отмен без логистики. Тогда в Q может стоять:
- либо сам отменённый заказ;
- либо заказ вне Orders API, у которого нет следа в финотчёте.

На зрелом финотчёте экономика у них одна: единица без продажи и без логистики, вклад 0. Поэтому оба варианта дают V = 1.

Прямое доказательство — собственный счётчик отмен воронки по дате заказа (`cancel_count`). Сейчас загрузчик воронки его не заполняет, а v3 API отдаёт историю только за 7 суток. Когда загрузчик начнёт заполнять счётчик, он станет вторым независимым источником. Это отдельная задача, в этот PR не входит.

## 3. Модель на листе

Формула W строки (без изменений для всех суток, кроме восстановленных):

```
W = Q·AI − X − AG − S·(AI + AF + REVERSE_LEG_RATE) + Y
```

| Класс отмены | S | Поправка W | Вклад единицы |
|---|---|---|---|
| С логистикой, в Q | входит (как раньше) | — | −AF − REV |
| Без логистики, в Q (V) | входит | `+V*(AF+REVERSE_LEG_RATE)` в конце формулы строки | 0 |
| Без логистики, вне Q | не входит | — | 0 |
| С логистикой, вне Q | на листе не представима | — | ANOMALY: лист не меняется, только журнал |

Изменение W при восстановлении:
- **18.10:** ΔW = −(AI + AF + REV) + (AF + REV) = −AI. Результат не зависит от суточной ставки обратного плеча.
- **24.10:** ΔW = +(AI + AF + REV) при ставке на момент записи.

## 5. Почему суточный прогон не перезапишет восстановленное

Зрелость (финотчёт окончателен ≥ 46 суток от заказа) всегда старше окна сверки (35 суток, `[LCD−34, LCD]`). Поэтому:
- в окне писателя и сверки класс всегда `IMMATURE`, и S там прежний. Проверка на production 02.11: DAILY 25/25 и RECON 875/875 строк совпадают с живыми вью, FINAL = 0;
- восстановленные сутки лежат вне окна: Engine их не адресует;
- если V > 0 когда-нибудь окажется в окне, это отказ до записи (`CANCEL_VOID_OUTSIDE_RESTORE`), а не тихая запись.

## 6. Проверка на истории (только SELECT, 02.11.2026)

- **Класс сентябрь–октябрь.** 71 SKU-день с отменами Orders API. Сегодня 16 из них зрелые, изменений 0. Прежний S класса совпадает с S листа в 71 из 71 SKU-дня.
- **Модель «всё зрело»** (зрелость 0) меняет ровно три SKU-дня:
  - 18.10 / 535580776: S 0 → 1, V 1;
  - 24.10 / 252442517: S 1 → 0;
  - 27.10 / 952068582: S 1, V 1 — кандидат. Он станет восстановлением, только если до 12.12 в финотчёте не появится логистика.

  Ни одной аномалии. Не меняются:
  - 01.10 (отказ вне Orders API и возврат после выкупа);
  - 20.10 / 252442517 (возврат брака продавцу: отдельный srid финотчёта с одним плечом, проведён 26.10, это не отмена Orders API — в слое его нет).
- **Store P&L, октябрь** (снимок с поправкой):
  - вклад SKU меняется ровно на сумму ΔW;
  - логистика модели — на AF + REV по каждой из двух строк;
  - полная прибыль (чистая + мост сроков) — без изменений;
  - тождество «сверху вниз» сходится (невязка 0).

  Пока когорта октября незрела, управленческий чистый результат меняется на ΔW. После зрелости изменение уходит в 0: поправка переходит из моста сроков в зрелую поправку.

## 7. Выпуск — два отдельных OWNER ACK

### ACK 1 — код и DDL (поведение листа не меняется)

1. Перед merge в общий `main` написать Heldi. Затем merge.
2. Terraform: targeted plan по `google_bigquery_table.store_pnl_snapshot` и `store_pnl_snapshot_stage`. Ожидается 2 in-place update (добавляется NULLABLE-колонка в конец), 0 destroy. Apply только после просмотра плана.
3. DDL BigQuery по порядку, после каждого шага — паритет:
   1. `cancel_class_v1.sql`;
   2. `V_UNITKA_DAILY_FACT` и `V_UNITKA_RECON_FACT` — строки совпадают с прежними, FINAL в окне 0;
   3. `V_WB_STORE_PNL_MONTHLY` — месяцы совпадают, невязка 0.
4. Образ из merge-коммита. Обновить digest ТОЛЬКО у `unitka-engine-prod` и `unitka-store-pnl-prod`. До этого — квалификация разницы `cloud/src` между боевыми коммитами и merge-коммитом.
5. Приёмка:
   - плановый Engine — PASS, без `CANCEL_VOID_OUTSIDE_RESTORE`;
   - Store P&L — `void_cancels` = 0 во всех строках, месяцы без изменений.

### ACK 2 — восстановление истории (не раньше 09.12.2026, когда созреют оба дня; 18.10 — с 03.12)

1. **План:**

   ```
   gcloud run jobs execute unitka-engine-prod --args=unitka-cancel-restore
   ```

   В журнале `unitka_cancel_restore_plan`:
   - `manifest_digest`, `manifest_b64`;
   - строки «S до → после, V»;
   - `expected_delta_w`;
   - `refusals` = [], `anomalies`.
2. **Владелец сверяет** план с приёмкой ниже и даёт ACK с отпечатком.
3. **Запись** — вне часа Engine и Store P&L:

   ```
   --update-env-vars UNITKA_CANCEL_RESTORE_WRITE=1,UNITKA_CANCEL_RESTORE_DIGEST=<digest>
   ```

   Отпечаток пересчитывается из живого листа в момент записи. Изменилось хоть одно поле — отказ без записи. В отпечаток не входит `REVERSE_LEG_RATE`, поэтому суточное обновление ставки план не ломает.
4. **Перечитывание** — в журнале `unitka_cancel_restore_done.verify_failed = 0`:
   - S, формула W и заметка совпадают с планом;
   - W совпадает с моделью по живым ячейкам.

   Неизвестный исход — только чтение и диагностика, повторной записи нет.
5. **Store P&L:** плановый прогон. В снимке `void_cancels` = 1 у 18.10, вклад октября меняется на ΔW, невязка 0.
6. **Откат листа:**

   ```
   UNITKA_CANCEL_RESTORE_DIRECTION=rollback, UNITKA_CANCEL_RESTORE_MANIFEST=<manifest_b64>, WRITE=1, DIGEST=<digest>
   ```

   Каждое поле должно стоять «после» или «до». Иное — DRIFT, отказ.

   Откат кода: прежние digest образов и `cancel_class_v1_rollback.sql`. Колонка `void_cancels` остаётся: она NULL-able и прежней вью не читается.

Условия STOP:
- `refusals` ≠ 0;
- новая аномалия;
- ΔW плана расходится с приёмкой;
- `verify_failed` > 0;
- `CANCEL_RESTORE_DIGEST_MISMATCH`;
- любой неизвестный исход записи.
