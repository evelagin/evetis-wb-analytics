## 3. K9 — и дефект в самом инструменте сверки

**Результат: PASS ×2, побайтно.**

```
V_DASH_COVERAGE_DAILY     4 932 симв. · 88 строк · sha256 71362bb5261c6ef9…1d2525ae
V_DASH_FRESHNESS_HEADER   2 972 симв. · 49 строк · sha256 9e041c85b0822028…6e1451f0
```
(нормализация: снять строки-комментарии, пустые строки, хвостовые пробелы, терминатор `;`)

### 🔴 Первый прогон K9 дал расхождение — и виноват был не выкат

`V_DASH_COVERAGE_DAILY`: файл 4 933 симв., BigQuery 4 932. **Ровно один символ.**
Построчное сравнение длин локализовало его мгновенно: строка 88,
файл `'FROM daily d;'` (13), BigQuery `'FROM daily d'` (12).

Причина — **в моём скрипте сверки**. При делении файла по `CREATE OR REPLACE VIEW`
первый стейтмент тянет за собой хвостовой блок комментариев, стоящий перед вторым
`CREATE`. Поэтому `body.rstrip().endswith(';')` возвращал `False`, и терминатор
статемента оставался приклеенным к последней содержательной строке. У второго
стейтмента тот же код сработал верно — просто потому, что за ним ничего не следует.

Исправление: терминатор снимается **после** нормализации, когда последняя
содержательная строка гарантированно последняя. После правки хэши совпали.

**Это третий случай, когда K9 падает на механике инструмента, а не на смысле** —
и второй раз подряд на способе деления файла на стейтменты. Урок PR #100 «инструмент
сверки сам должен быть проверен, прежде чем его вердикт считать фактом о production»
подтверждён ещё раз. Ранее в этой же сессии я отдельно фиксировал, что в файле
**восемь** точек с запятой внутри комментариев (проверено командой: строки 47, 48, 51,
134, 199–202), — деление по `;` сломало бы K9 гарантированно.

⚠️ **В файлах PR1 ничего чинить не потребовалось.** Гейт C13 в
`dashboard_contract_v1_validation.sql` выводит sha256 определения и предполагает
внешнюю нормализацию — дефекта в нём нет. Исправленный скрипт нормализации в репозиторий
**не добавлялся**: это расширило бы scope PR1. Если хотите закрепить процедуру —
скажите, добавлю отдельным PR.

## 4. Подтверждение NULL / fail-closed семантики на живых данных

Не декларация, а строки из выкаченного объекта:

| день | orders | sales | ads | finance | stocks | `finance_is_final` | `contribution_covered` | что доказывает |
|---|---|---|---|---|---|---|---|---|
| **2026-03-30** | false | **false** | false | true | false | true | false | 🔴 одиночная строка `FACT_SALES` **не создаёт покрытия** — `CORRECTION-1` работает |
| 2026-04-05 | false | false | false | true | false | true | false | середина разрыва 31.03–12.04 закрыта |
| 2026-04-12 | false | false | false | true | false | true | false | последние сутки перед границей |
| **2026-04-13** | **true** | **true** | **true** | true | false | true | **true** | три потока открываются одной датой |
| 2026-07-19 | true | true | true | true | **false** | true | true | дыра снимков — снимок ≠ поток |
| 2026-08-16 | true | true | true | true | true | **true** | true | последние `FINAL`-сутки |
| **2026-08-17** | true | true | true | true | true | **false** | true | PROVISIONAL: значение разрешено, финальность отрицается |
| **2026-08-18** | true | true | true | true | true | **false** | true | последние сутки контрибуции |
| **2026-08-19** | true | true | true | **false** | true | **NULL** | **false** | 🔴 финансовых строк нет ⇒ контрибуция гасится |
| **2026-08-20** | true | **false** | **false** | false | true | NULL | false | сегодня: заказы ежечасные, продажи и реклама — D-1 |

Три правила контракта видны прямо в таблице:

1. **Вне покрытия — `FALSE`, а не «ноль событий».** 585 суток до 13.04 не покрыты рекламой
   ни одни; витрина за те же сутки продолжает отдавать `ad_spend = 0`, и именно эта вью
   отличает одно от другого.
2. **`finance_is_final` трёхзначен по замыслу.** `NULL` = финансовых строк нет,
   `FALSE` = PROVISIONAL, `TRUE` = FINAL. C2 намеренно **не** требует отсутствия `NULL`
   в этой колонке — `NULL` здесь часть контракта.
3. **Агрегируемость для произвольного Date Range.** Булев флаг Looker сложить не может,
   поэтому каждый признак продублирован счётчиком `*_days`.
   `SUM(contribution_provisional_days)` на 13–19.08 = **2**, на закрытом периоде
   13.04–12.08 = **0**. Требование владельца «период не должен выдавать себя за
   полностью финализированный» выполняется одним `SUM` без изменения SQL.

## 5. Отклонения от контракта Stage 4A

**Отклонений в реализации — ноль.** Все объекты, колонки, правила и границы совпали
с §3 и §6 контракта. Ниже — два наблюдения, требующие вашего решения, но **не**
являющиеся расхождением с принятым текстом.

### OBSERVATION-1 — заголовочная дата тянется слоем, которого MVP не читает

`data_as_of_min` = минимум по **всем 13** слоям, поэтому шапка говорит «данные актуальны
на **17.08**». Эту дату задаёт `ads_costs` — рекламный биллинг, который по вашему же
решению на дашборд не выводится (Stage 3B заблокирован). Фактически заказы актуальны
на сегодня, витрина — на 19.08.

Это **работает как задумано** (fail-closed: худший слой выигрывает), но для пользователя
звучит хуже, чем есть. Развилка — на PR2, не на сейчас:

* оставить как есть — честнее всего, шапка описывает весь контур;
* добавить `data_as_of_min_used` — минимум только по слоям, которые реально питают
  страницы MVP, оставив общий минимум рядом.

Рекомендация: **добавить вторую колонку в PR2**, не убирая первую. Ничего не прятать.

### OBSERVATION-2 — «сегодня» в календаре

Календарь доходит до `CURRENT_DATE('Europe/Moscow')`, поэтому последняя строка — сегодняшние
неполные сутки (`is_current_day = TRUE`). Для заказов это осмысленно (ежечасный загрузчик),
для продаж и рекламы сутки честно помечены непокрытыми. Отдельного решения не требует —
флаг для интерфейса уже есть.
