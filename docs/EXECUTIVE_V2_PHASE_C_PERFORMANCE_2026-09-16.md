### 2.4 Корневые причины

1. **Каждый запрос пересчитывает весь стек view с нуля.** View не материализованы и не партиционированы, поэтому фильтр периода применяется уже после расчёта по всей истории. Каждый из 36 запросов читает `FACT_FINANCE`, `FACT_SALES`, `FACT_ORDERS`, `FACT_ADS_SKU_DAILY`, `MART_SKU_DAILY` и даже `FACT_STOCKS_SNAPSHOT` (через покрытие `V_DASH_COVERAGE_DAILY`). 29 из 36 запросов разбирают сырой финотчёт `RAW_WB_FINANCE` (JSON).
2. **Дублирование.** За одно открытие `V_DASH_KPI_DAILY` вычисляется 32 раза, `V_DASH_EXECUTIVE_ECONOMICS_DAILY` — 12, `V_DASH_SETTLEMENT_DAILY` — 12, `V_DASH_FINANCE_CORRECTED_DAILY` — 7. Внутри одного запроса вложенные view тоже пересчитываются повторно: ECONOMICS → CORRECTED → KPI; SETTLEMENT → V_WB_FINANCE_SEMANTIC ×2 + классификатор.
3. **Карточка 164 (цепочка цены) выполняется 7 раз** одним и тем же SQL — по разу на каждую плитку.
4. **Кэш BigQuery не срабатывает:** view содержат `CURRENT_TIMESTAMP()` (`generated_at`) и `CURRENT_DATE()`, результат недетерминирован.
5. **Сравнение с прошлым периодом** — не причина: окно в 2 раза длиннее почти ничего не добавляет, потому что пересчитывается вся история.
6. **Параллелизм Metabase ≤ 5.** 36 запросов по ~6 с дают ~60 с «стены» независимо от BigQuery.

Самые дорогие карточки: 53 «Результат до себестоимости» (3 865 slot-с, 13,6 с, 476 стадий), 169 «Логистика» (3 707), 173 «Хранение» (3 703), 177 «Себестоимость» (3 078). У всех — окно сравнения поверх `V_DASH_EXECUTIVE_ECONOMICS_DAILY`.

## 3. Предлагаемая архитектура

**Один предагрегированный дневной слой**, который пересчитывается один раз за сборку, а читается всеми карточками.

```
существующие канонические view (без изменений)
  V_DASH_KPI_DAILY · V_DASH_FINANCE_CORRECTED_DAILY · V_DASH_EXECUTIVE_ECONOMICS_DAILY
  V_DASH_SETTLEMENT_DAILY · V_DASH_EXECUTIVE_BREAKDOWN_DAILY · V_DASH_BUYOUT_COHORT_DAILY
  V_DASH_FRESHNESS_HEADER
          │  один проход при сборке (pass-through, без новых формул)
          ▼
  wb_mart.EXECUTIVE_V2_DAILY            таблица, грейн day, ~750 строк, ~60 колонок
          │
          ▼
  wb_mart.V_DASH_EXECUTIVE_V2_DAILY     view-контракт: календарь до CURRENT_DATE
          │                             + пересчёт признаков, зависящих от даты
          ▼
  Metabase dashboard 2 (31 карточка)    FROM-источник заменён механически
```

### 3.1 Почему таблица, а не просто view
Обычный view ничего не ускорит: стек пересчитывался бы так же. Materialized view в BigQuery здесь недоступен: инкрементальных агрегатов нет, есть join view-на-view и недетерминированные функции. Остаётся таблица, собираемая процедурой.

### 3.2 Состав слоя
Ровно 60 колонок, которые читают карточки dashboard 2 (список извлечён из SQL всех 31 карточки). Имена совпадают с исходными view — это позволяет перевести карточки механической заменой источника. Тело: `sql/dash/proposals/executive_v2_daily_PROPOSAL.sql`.

### 3.3 Признаки, зависящие от даты (обязательная часть view-контракта)
Снимок таблицы «замораживает» то, что в живых view зависит от `CURRENT_DATE`:
- `is_current_day`, который делает сутки неполными;
- финальность биллинга (`billed_complete`: возраст ≥ 15 дней);
- строку текущих суток, которой в таблице вчерашней сборки ещё нет.

Поэтому `V_DASH_EXECUTIVE_V2_DAILY`:
1. строит календарь до `CURRENT_DATE('Europe/Moscow')`; сутки без строки в таблице → `executive_incomplete_day = 1`, денежные поля NULL (как сейчас у текущих суток);
2. сутки = сегодня → принудительно INCOMPLETE;
3. финальность биллинга не «додумывает»: сутки, ставшие финальными после сборки, остаются PROVISIONAL до следующей сборки. Это консервативное отставание не больше одного интервала сборки, и оно документируется.

### 3.4 Сборка и свежесть
- **Процедура `wb_mart.sp_build_executive_v2_daily(in_run_id)`:**
  - строит `EXECUTIVE_V2_DAILY__BUILD` из тела предложения;
  - fail-closed ASSERT'ы: грейн (одна строка на сутки), число суток = `V_DASH_KPI_DAILY`, выборочная сверка сумм ключевых денег с исходными view на всей истории;
  - атомарная замена `CREATE OR REPLACE TABLE … AS SELECT * FROM __BUILD`;
  - метаданные в каждой строке: `layer_built_at`, `layer_run_id`, `mart_build_as_of_date`.
- **Стоимость одной сборки** (замер на прототипе): 20 с, 354 МБ, 6 009 slot-с. Это ≈ 18 % одного сегодняшнего открытия dashboard.
- **Когда запускать** (решение владельца):
  - **(А) рекомендовано:** шагом в конце существующего mart-джоба после `sp_build_mart_sku_daily` + scheduled query раз в час 07:00–23:00 МСК. Так в течение дня подхватываются загрузки Apps Script: продажи, финансы, реклама;
  - (Б) только в конце mart-джоба. Дешевле, но продажи, загруженные днём, появятся на Executive только завтра;
  - в текущей схеме view всегда «живые». Любой вариант вводит задержку до следующей сборки; статусная зона покажет `layer_built_at`.
- ⚠️ **Изменение mart-джоба или scheduled query — это инфраструктура.** По `CLAUDE.md`: только целевой `terraform apply` с просмотренным планом, никакого `deploy-prod` из `main`.

### 3.5 Metabase
- **SQL 31 карточки:** замена `wb_mart.V_DASH_*` → `wb_mart.V_DASH_EXECUTIVE_V2_DAILY`. Доказано равенство результатов (§4).
- **Фильтр периода:** template-tag `day` нужно перепривязать к полю `day` нового view. Нужен `mb db sync` и новый field id; без этого field-filter подставит таблицу старого view.
- **Плитки цепочки (7 запросов карточки 164)** можно оставить: каждый запрос станет ~1 с.
- **Дополнительно, по желанию:** кэширование результатов карточек в Metabase. Даёт мгновенные повторные открытия, но первое открытие всё равно платит полную цену. Без слоя это не решение.

## 6. План миграции (после подтверждения)

1. DDL слоя + процедура + view; первая сборка; ASSERT-сверка всей истории.
2. Регрессия на уровне SQL: 31 карточка × 5 окон (31.08–13.09, 17–30.08, 27.07–23.08, последние 30 дней, с текущими сутками) — старый SQL против нового, 0 расхождений.
3. Тест датозависимых признаков: слой, собранный «вчера» (имитация через `mart_build_as_of_date`), против живых view «сегодня».
4. Переключение карточек (сначала V2-копии в отдельной коллекции), приёмка `--format-rows` против базовой линии Phase C (`pc/before_*.txt`, `pc/after_*.txt`).
5. Замер загрузки в браузере; цель ≤ 15 с.
6. Оркестрация сборки — отдельным шагом с целевым apply.

## 7. Решения, нужные от владельца
1. Подтвердить архитектуру: таблица + процедура + view-контракт.
2. Выбрать частоту сборки: (А) mart-джоб + ежечасно или (Б) только mart-джоб, и принять задержку данных до следующей сборки.
3. Способ переключения карточек: переписать текущие или создать V2-копии.
