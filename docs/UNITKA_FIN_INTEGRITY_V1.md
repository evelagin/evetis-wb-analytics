## 0. Правила, которые нельзя забыть

> **ЗАКАЗ БЕЗ ЦЕНЫ — ЭТО НЕ УБЫТОК, ЭТО НЕДЕЙСТВИТЕЛЬНАЯ СТРОКА.** Формулы листа при пустой цене считают заказ
> убытком «логистика + себестоимость» (контрольный случай 17.09 / 930334396: −466,97 ₽ вместо +122,15 ₽). Такая строка
> получает `DATA_ERROR` и `financial_valid = false`; в итог она входит, но итог помечен недостоверным.

> **НИКАКОЙ ВЫДУМАННОЙ ЦЕНЫ.** Источников цены ровно два: Orders API (основной) и сумма заказов той же строки
> воронки — только при согласных счётчиках. Соседний день, цена карточки, средняя, MTD, другой SKU, константа —
> запрещены и закреплены тестами (`unitka_recon_sql.test.ts`, `unitka_reconcile.test.ts`).

> **ДЕЙСТВИТЕЛЬНОСТЬ ОПРЕДЕЛЯЕТ ЛИСТ, А НЕ ИСТОЧНИК.** Если источник цену уже знает, а в ячейке её нет (режим
> `observe`, отказ секции), строка остаётся `DATA_ERROR` — правило `PRICE_NOT_ON_SHEET`.

> **БЕЗ ЖУРНАЛА РЕМОНТА ИСТОРИЯ НЕ ПРАВИТСЯ.** `UNITKA_RECONCILE_MODE=write` до применения таблиц Terraform даёт
> отказ `LEDGER_UNAVAILABLE` до любой записи (проверено на тестовой копии).

> **COGS 252442517 В ЭТОЙ ФАЗЕ НЕ ИСПРАВЛЯЕТСЯ** (решение владельца 5). Расхождение 240 ↔ 231,38 теперь `ERROR` и
> делает 18 SKU-дней недействительными; ремонт — после выбора архитектуры, см.
> `docs/UNITKA_COGS_ARCHITECTURE_2026-09.md`.

## 1a. Решения владельца по финальному ревью (20.09.2026)

**Эпоха сверки — утверждена.** `RECONCILIATION_EPOCH = 2026-09-01` — явная граница миграции домена, которым управляет
Engine: сентябрь 2026 — первый месяц под Engine; август 2026 и раньше писали прежние процессы, новая сверка их не
меняет никогда. Начало окна = `max(начало скользящих 35 дней, RECONCILIATION_EPOCH)`. Параметр задан один раз в SQL
(CTE `cfg` во `V_UNITKA_RECON_WINDOW`, колонка `reconciliation_epoch`) и один раз в коде (`reconcile.ts`); Engine
сверяет оба при каждом прогоне. Три линии защиты августа: окно (`RECON_WINDOW_INCONSISTENT`), строки источника и
ячейки плана раньше эпохи (`RECON_BEFORE_EPOCH`), поиск секций только по месяцам окна. Доказано тестами: из октября
сентябрь сверяется, секция августа остаётся побайтно прежней, с LCD 06.10 окно становится чисто скользящим.

**Расхождение счётчиков — правило «14 дней → WARNING» отклонено; возраст ничего не доказывает.** Итоговая семантика
(пороги — из замеров аудита, не из головы):

| Случай | Основание | Состояние | `financial_valid` |
|---|---|---|---|
| Orders API отстаёт (`FUNNEL_GT_FACT`, `ONLY_FUNNEL`), возраст ≤ 14 дней | запаздывание Orders API: 907 заказов авг.–сен. 2026, p99 = 13,9 дня, максимум 21,0; позже 14 дней — 1,0 % | `LATE_DATA` | `true`, если деньги уже подтверждены суммой воронки; иначе `false` (результат предварительный) |
| то же, старше 14 дней, деньги подтверждены: `\|orders_sum_rub − Q × цена\| ≤ 0,5 ₽ × Q` | доказано: выручка строки равна выручке источника, задающего Q; непришедший заказ шёл по той же цене | `WARNING` | `true` |
| то же, старше 14 дней, деньги НЕ подтверждены | финансовая истина не разрешена; цена не выдумывается | `DATA_ERROR` | `false` |
| Orders API опережает (`FACT_GT_FUNNEL`, `ONLY_FACT`) | у воронки нет окна запаздывания: 0 изменений на 1 575 значениях при 7–9 перечитываниях → порог 0 дней | `DATA_ERROR` сразу | `false` |

Порог 14 дней выбран в сторону fail-closed: 1 % опоздавших заказов даёт временный `DATA_ERROR`, который снимается сам
— окно 35 дней длиннее максимума 21 день.

🔴 **Находка ревью: воронка не считает заказ, отменённый в день заказа.** Замер 04–18.09.2026 на всей популяции слоя:
361 SKU-день с равными счётчиками — ни одной отмены дня заказа; все 4 случая «Orders API больше воронки» объясняются
ею точно (`fact − same_day_cancel = funnel`); отмены следующих дней воронка не вычитает (5 из 5). Лист при этом берёт
Q из воронки (заказа нет), а S — из Orders API (отмена есть): формула `W` вычитает `S·(AI + AF + REV)` за заказ,
которого в Q не было. Оригинал, 4 строки: 09.09 / 535580776, 10.09 / 535581674, 11.09 / 438775617 (Q = 0, S = 1,
W = −581,96 ₽), 18.09 / 535580776 — результат занижен минимум на 672,92 ₽ (Σ AI), максимум на 1 011,27 ₽.
В PR #146 это только **обнаруживается** (`ORDERS_SOURCE_DIVERGENCE`, `verdict=SAME_DAY_CANCEL_OUTSIDE_Q`,
диагностическая колонка `same_day_cancel_qty`); Q, S и цена листа не меняются. Исправление контракта отмен —
отдельное решение владельца (кандидат: не включать в S отмены дня заказа, пока Q берётся из воронки).

**COGS.** Обнаружение остаётся в PR #146 (расхождение при активности → `ERROR`, `financial_valid = false`).
Архитектура D, ремонт 252442517, правка `$R$45`, число 231,38 в формулах — НЕ в этом PR; отдельный следующий PR.

**Fallback цены.** Иерархия прежняя. Ни один путь кода не делит `orders_sum_rub` на `orders_count` при несогласных
счётчиках: в SQL деление одно, под шестью условиями через AND; в TypeScript сумма воронки только сравнивается
(`amountConfirmedByFunnel`) и не делится нигде; вторая линия — `reconFacts()` отвергает строку `FUNNEL_FALLBACK`
вне условий (`BQ_SHAPE`, до любой записи).

**`PRICE_NOT_ON_SHEET` — остаётся.** Пока ремонт не записан, строка говорит `repair_available = true`,
`sheet_financial_valid = false` (поле issue `repairAvailable`, `diagnostic_value`, счётчик сводки
`repair_available_sku_days`, колонка вью `repair_available_not_written`). Работает и до записи (SHADOW, PRE_WRITE):
ячейки, которые прогон сам запишет, дефектом не считаются.

## 2. Контракт финансовой полноты SKU-дня

Состояния **не схлопываются** — каждое считается отдельно и в сводке прогона, и в `V_UNITKA_INTEGRITY_STATUS`.

| Состояние | Когда | `financial_valid` | Что делать |
|---|---|---|---|
| `DATA_ERROR` | заказ без цены; цена 0; цена не в ячейке; COGS ≠ канону при активности; нет канона при активности; расхождение счётчиков, не разрешённое после срока зрелости; Orders API опережает воронку (отмена дня заказа вне Q) | `false` | чинит сверка (цена) или владелец (COGS, контракт отмен) |
| `LATE_DATA` | Orders API отстаёт от воронки, возраст ≤ 14 дней; хранение до срока 12:15 МСК | считается отдельно: `false`, пока деньги строки не подтверждены | ждать — сверка доберёт сама |
| `MANUAL_REQUIRED` | СПП не введена при заказах | `true` (прибыль не затронута; неполны ДРР и цена с СПП) | ввести СПП |
| `NOT_AVAILABLE` | источника за дату законно нет (снимок остатков 03.09) | `true` | ничего; не ошибка системы |
| `WARNING` | латентное расхождение COGS без заказов; расхождение счётчиков, про которое ДОКАЗАНО, что на результат оно не влияет (§1a) | `true` | к сведению |
| `AUTO_REPAIRED` | считается из журнала ремонта, только `status = REPAIRED` | — | к сведению |

Финансовая действительность считается **независимо от состояния** (`financially_invalid_sku_days` — по
`financial_valid = false` при любом состоянии). `financial_health` в `V_UNITKA_INTEGRITY_STATUS` смотрит только на
`DATA_ERROR`: сколько бы ни было ожидаемых `MANUAL_REQUIRED` и `NOT_AVAILABLE`, автоматический контур «сломанным» они
не делают; ручной ввод — отдельным флагом `manual_input_pending`. Строка с `financial_valid = false` не может дать статус `PASS`
(тест `unitka_fin_contract.test.ts`).

## 3. Окно сверки

`[max(LCD − 34, RECONCILIATION_EPOCH), LCD]`, эпоха `2026-09-01` (§1a). Параметры заданы один раз — CTE `cfg` во
`V_UNITKA_RECON_WINDOW`; код считает окно независимо (`reconcileWindow`) и сверяет с вью границы, длину и эпоху:
расхождение = отказ `RECON_WINDOW_INCONSISTENT` до записи; дата раньше эпохи в источнике или плане — `RECON_BEFORE_EPOCH`.

- **Месяц LCD** — как в Engine 2.0 (`buildPlan`): факты закрытых дней, ставки на все дни месяца, якоря LCD. Факты
  берутся из слоя сверки (только активные SKU — правило `BLOCK_MISSING` сохранено).
- **Прошлые месяцы окна** — только ФАКТ-ячейки дней окна: смещения блока {2, 3, 4, 5, 6, 7, 11, 14, 20}
  (показы, переходы, заказы, корзины, отмены, остаток, реклама, цена, хранение). Ставки, якоря, формулы, СПП,
  блогеры, внешняя реклама, план — никогда (`assertFactCellsOnly`, код `RECON_PLAN_NOT_CONFINED`).
- **Изоляция секций.** Прошлая секция не найдена / двусмысленна / не прошла `validateSection` — отказ только этой
  секции с кодом (`RECON_SECTION_MISSING | AMBIGUOUS | INVALID | FAILED`); месяц LCD пишется как обычно. Блок без
  полного покрытия источником за дни окна пропускается целиком (`skipped_blocks`).

## 4. Цена: детерминированное разрешение с происхождением

```
ORDERS_API       FACT_ORDERS дал хотя бы одну строку за SKU-день → Σ(price_with_disc × qty) / Σ qty
FUNNEL_FALLBACK  orders_api_price IS NULL AND fact_order_qty = 0 AND orders_source = 'FUNNEL_API'
                 AND funnel_orders > 0 AND funnel_orders = orders AND funnel_orders_sum > 0
                 → orders_sum_rub / orders_count
NULL             иначе. Строка — DATA_ERROR (PRICE_MISSING_WITH_ORDERS).
```

Почему сумма воронки — та же цена: на 91 SKU-дне сентября с равными счётчиками `orders_sum_rub` = Σ Orders API
(134 051,00 ↔ 134 050,46 ₽; воронка округляет заказ до рубля, максимум 0,09 ₽ на единицу).
При несогласных счётчиках (Orders API дал строки, но их число ≠ воронке) цена остаётся ценой Orders API, деления
суммы воронки нет — только статус (§1, §2). Позднее появление заказа в Orders API заменяет fallback ценой Orders API
(`SOURCE_REVISED`, запись в журнале ремонта) — тест «late Orders API replaces fallback».

## 5. Поток прогона и правила записи

```
LCD → окно и эпоха (SQL ↔ код) → слой сверки → план месяца LCD + планы прошлых секций
   → [observe] журнал «что изменил бы write», записи нет; Guard: repair_available = true, лист недействителен
   → [write]   проба журнала ремонта → план ремонта в лог → ОДИН values.batchUpdate (LCD + история)
              → перечитывание → QA месяца LCD + QA каждой прошлой секции
              → REPAIRED в журнал ремонта (только после QA PASS) → снимок issue → журнал прогона
```

**Состояния записи ремонта — «ремонт состоялся» означает только `REPAIRED`:**

| Стадия записи листа | Что произошло | Запись в журнале ремонта |
|---|---|---|
| не предпринималась | режим `observe`; отказ до записи (`LEDGER_UNAVAILABLE`, `RECON_*`, `BQ_SHAPE`) | нет (план — в событии `unitka_reconcile_plan`) |
| вызов ушёл и упал | Sheets API вернул ошибку; `values.batchUpdate` применяется целиком или не применяется вовсе | `WRITE_FAILED`, `repaired_at = NULL` |
| лист подтвердил запись, проверка не пройдена или не завершилась | перечитывание упало / QA FAIL («потерянная запись», частичная запись) | `APPLIED_UNVERIFIED`, `repaired_at = NULL` |
| лист подтвердил запись и перечитывание прошло QA | ремонт состоялся | `REPAIRED`, `repaired_at` заполнено |

Порядок жёсткий: обнаружить → спланировать → попытаться записать → перечитать и проверить → `REPAIRED`. Записи
`WRITE_FAILED` / `APPLIED_UNVERIFIED` — best-effort и исход прогона не маскируют (прогон остаётся FAILED с исходным кодом);
план ремонта выводится в лог (`unitka_repairs_planned`) ДО мутации листа, поэтому происхождение не теряется ни при
каком исходе. Повтор после сбоя записи: расхождение остаётся → следующий прогон выполняет тот же ремонт и только тогда
пишет `REPAIRED`. После `APPLIED_UNVERIFIED` значения уже в листе: следующий прогон расхождения не видит и `REPAIRED`
задним числом не выдумывает. Вью статуса считает `auto_repaired_*` только по `REPAIRED`; неподтверждённые попытки —
отдельно (`repair_attempts_unconfirmed_7d`).

- Ремонтом (запись в журнал) считается только `LATE_SOURCE_CORRECTION` факт-ячейки: значение закрытого дня изменилось
  или появилось позже. Первое заполнение нового закрытого дня — обычная работа Engine, в журнал ремонта не идёт.
- Причины: `PRICE_FUNNEL_FALLBACK`, `LATE_FIRST_FILL`, `SOURCE_REVISED`, `SOURCE_WITHDRAWN`.
- Сбой журнала после успешной и проверенной записи → `LEDGER_WRITE_FAILED` (прогон FAILED, алерт); сами записи уже
  выведены в лог события `unitka_repairs` — происхождение не теряется.
- Повторный прогон при тех же источниках — `NO_CHANGE`: 0 ячеек, 0 записей журнала.
- Значение, введённое руками в факт-ячейку, Engine по-прежнему заменяет значением источника (поведение Engine 1.x);
  ручные колонки (СПП, блогеры, внешняя реклама) не трогаются.

## 6. Граф зависимостей: что пересчитывается после ремонта

Формулы листа (проверено на 432/432 строках сентября): `AC = AA − AA·AB%`, `AE = AA − AA·AD`, `AH = AA·2 %`,
`AI = AE − AF − AH − COGS`, `Y = −(COGS + 100 + AF)·N`, `W = Q·AI − X − AG − S·(AI + AF + REVERSE_LEG_RATE) + Y`, `V = W/Q`, `Z = X/((Q−N)·AC)`
(`N` — блогеры и самовыкупы, `S` — отмены).
Ремонт цены `AA` пересчитывает `AC, AE, AH, AI, Y, V, W, Z` строки, строку MTD блока, дневной и месячный итог листа —
всё формулами листа, Engine их не пишет. Доказательства: тест «dependency graph» (ссылки `blockDayFormulas` +
эмулятор формул) и репетиция §9.

## 7. Журнал ремонта и снимок issue (`wb_ops`; таблицы применены 20.09.2026, Rollout Gate 2)

- `UNITKA_REPAIR_LEDGER` — append-only: `repair_id, run_id, environment, engine_version, git_sha, detected_at,
  repaired_at, month_key, business_date, nm_id, field, cell_a1, old_value, new_value, source, source_as_of, reason,
  status (PLANNED_NOT_WRITTEN | WRITE_FAILED | APPLIED_UNVERIFIED | REPAIRED)`. Партиции по `detected_at`, кластер `environment, business_date, nm_id`.
  Пишется ТОЛЬКО в режиме `write`.
- `UNITKA_INTEGRITY_ISSUES` — **append-only снимки по прогонам** (не «последнее состояние»). Прогон пишет свои issue,
  а последней, отдельным оператором — строку-маркер (`issue_key = NULL, code = RUN_MARKER`, в `source_value` —
  `reconcile_mode=…; issue_rows=…`). Маркер означает «оценка завершена и записана целиком»:
  оборванный снимок без маркера вью статуса не видит; прогон без единой issue всё равно оставляет маркер.
  Пишется в режимах **`observe` и `write`**: это состояние наблюдаемости, а не ремонт.
- **Что пишет `observe`:** только этот снимок. Лист он пишет ровно так же, как `off` (обычная суточная работа Engine —
  побайтно тот же набор ячеек), ремонт сверки не добавляет ни одной ячейки; журнал ремонта не пишется и даже не
  опрашивается; автоматические и ручные факты не меняются.

### 7a. Три независимые способности прогона (Rollout Gate 4.1)

До этой правки все три заменял один флаг `writeMode = prod && UNITKA_WRITE_ENABLED`. Из-за этого контролируемый
production-`observe` с `UNITKA_WRITE_ENABLED=0` уходил в ветку SHADOW, оценивал целостность, считал план ремонта —
и до записи снимка не доходил вовсе: таблица оставалась пустой, статус `NO_RUN_YET` (обнаружено в Gate 4).
Теперь способности разделены в `index.ts`:

| Способность | Условие | Что даёт |
|---|---|---|
| `SHEET_BUSINESS_WRITE` | `environment = prod` И `UNITKA_WRITE_ENABLED=1` | обычная суточная запись фактов в книгу; выбор scope Sheets (иначе `spreadsheets.readonly`) |
| `OBSERVABILITY_WRITE` | `environment = prod` И режим сверки ≠ `off` | снимок issue в `wb_ops.UNITKA_INTEGRITY_ISSUES` |
| `REPAIR_EXECUTION` | `SHEET_BUSINESS_WRITE` И режим сверки = `write` | исторические поправки окна и записи журнала ремонта |

Итоговая матрица:

| Прогон | лист | ремонт | снимок |
|---|---|---|---|
| prod, режимы `off`, запись разрешена | да | нет | нет |
| prod, `observe` + Guard `observe`, запись разрешена | да | нет | **да** |
| prod, `observe` + Guard `observe`, **запись запрещена** (контролируемый observe) | нет | нет | **да** |
| prod, `write` | да | да (прежние правила) | да |
| настоящая среда `shadow` | нет | нет | нет |

Среду различает канонический сигнал `config.environment` (`prod` \| `shadow`, проверяется в `config.ts`), а не имя
задания. Настоящая `shadow`-среда подавляет снимок **намеренно** (`issue_snapshot = SKIPPED_NOT_PRODUCTION`);
отсутствие прав IAM у её SA остаётся второй линией защиты, а не механизмом управления потоком.
- Снимок строится из оценки Guard. При `UNITKA_INTEGRITY_MODE=off` оценки нет — снимок не пишется, в логе
  предупреждение `unitka_issue_snapshot_skipped`, статус остаётся `NO_RUN_YET`. Включение `observe` в production
  поэтому требует и `UNITKA_INTEGRITY_MODE=observe` (Guard в этом режиме запись никогда не блокирует).
- Сбой записи снимка прогон не роняет (`issue_snapshot = FAILED` в `qa_json.reconcile`); маркера нет → оценка
  считается незавершённой, статус со временем честно станет `STALE`.
- IAM: `roles/bigquery.dataEditor` на ЭТИ ДВЕ ТАБЛИЦЫ для `sa-loaders-prod`. SHADOW прав не получает и снимок не
  пишет никогда. Прав на датасет не добавляется.

## 8. Наблюдаемость

Сводка прогона (`qa_json.integrity`, событие `unitka_integrity`): счётчики по состояниям, `affected_sku_days`,
`financially_invalid_rows` (независимо от состояния), `repair_available_sku_days`, `oldest_unresolved_data_error`, `oldest_unresolved`, `price_provenance`
(`FUNNEL_FALLBACK | UNRESOLVED | NOT_ON_SHEET`), `error_keys`. `qa_json.reconcile`: окно, секции, отказы,
`repairs_planned / repairs_recorded`, `issue_snapshot` (`PERSISTED | FAILED | SKIPPED_GUARD_OFF | SKIPPED_GUARD_FAILED`).

Вью `wb_mart.V_UNITKA_INTEGRITY_STATUS` всегда даёт ровно одну строку по **последней завершённой оценке prod**
(маркер с наибольшим `evaluated_at`; строки issue берутся строго по его `run_id`, прогоны не смешиваются).
`financial_health` — ровно четыре значения, по убыванию приоритета:

| Значение | Когда | Что со счётчиками |
|---|---|---|
| `NO_RUN_YET` | завершённой оценки prod нет вообще | `NULL` («неизвестно»), не 0 |
| `STALE` | оценка есть, но старше 1320 минут | показаны, но это не текущее состояние |
| `ERROR` | свежая оценка с хотя бы одним `DATA_ERROR` | текущие |
| `OK` | свежая оценка без `DATA_ERROR` | текущие |

`MANUAL_REQUIRED`, `NOT_AVAILABLE`, `LATE_DATA` и `WARNING` здоровье не портят, сколько бы их ни было: ручной ввод —
флаг `manual_input_pending`, действительность — `financially_invalid_sku_days`.

**Порог свежести 1320 минут (22 часа) выведен из рабочего ритма.** Engine ходит в 10:00 и 12:30 МСК. Самый длинный
штатный разрыв между оценками — с 12:30 до 10:00 следующего дня, 1290 минут. Плюс предельная длительность прогона
(timeout Job'а 600 с = 10 минут) и 20 минут на старт планировщика, Cloud Run и запись снимка: 1290 + 10 + 20 = 1320.
Смысл: `STALE` наступает, если утренний прогон не дал завершённой оценки примерно к 10:30 МСК. Тест
`unitka_status_view.test.ts` пересчитывает порог из расписания в Terraform: сменится расписание — тест упадёт.

Прочие колонки: `run_id`, `evaluated_at`, `reconcile_mode` (режим прогона, давшего оценку), `evaluation_age_minutes`,
`stale_after_minutes`, `completed_evaluations`, `auto_repaired_cells / sku_days` (только `REPAIRED` и только того же
прогона), `repair_available_not_written`, `repair_attempts_unconfirmed_7d`, `new_since_previous_run`,
`resolved_since_previous_run` (оба `NULL`, пока нет прошлой завершённой оценки).
Шесть состояний модели: `DATA_ERROR`, `LATE_DATA`, `MANUAL_REQUIRED`, `NOT_AVAILABLE`, `WARNING`, `AUTO_REPAIRED`.

⚠ На 20.09.2026 в BigQuery опубликована прежняя редакция этой вью (Gate 2): на пустых таблицах она показывает
`financial_health = OK`. Новая редакция лежит только в Git; публикация — отдельным гейтом после слияния.
