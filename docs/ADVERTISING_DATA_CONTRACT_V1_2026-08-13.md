### 1.4 🔴 Три находки из сырого лога — обязательны к соблюдению

**A. `cpm` в `normquery/stats` — это ФАКТИЧЕСКИ УПЛАЧЕННЫЙ CPM, а НЕ ставка.**
Классическая ловушка «имя поля ≠ его смысл», та же семья, что `commission_amount` = `vw`.
Доказательство из лога: у кампании `37669244` ставка поиска 130 ₽, а `cpm` по кластерам —
123,14 / 125,97 / 123,35 / 125,32 / 127,01 / 130,00. Значения *плавают вокруг* ставки,
а не равны ей. У `37727969` при ставке кампании 520 ₽ `cpm` кластеров идёт от 519 до 673 —
потому что там действуют **индивидуальные ставки кластеров** (§B).
**Контракт: `cpm` — метрика результата (SOURCE-FAITHFUL). Ставка — только из `get-bids`
и `bids_kopecks`. Никогда не использовать `cpm` как ставку.**

**B. `get-bids` возвращает ставки только для `bid_type = manual`.**
Запрошено 4 пары — вернулось 39 ставок, и все по двум manual-кампаниям:
`37727969` — 25 кластеров, `37727999` — 14. Обе **unified**-кампании (`37669244`,
`37727876`) вернули **ноль строк**. Это логично: у unified одна ставка на всё,
кластерных ставок не существует.
**Контракт: отсутствие строк для unified — норма, а НЕ пропуск данных.
QC не должен на это алертить.**

🔴 **Уточнение ред. 1.2 — я сам сформулировал это неточно в ред. 1.1.** Прежняя фраза
«возможность управления ключами существует только в manual» смешивала **доступность
данных** с **возможностью управления**. Это разные вещи:

| | manual | unified |
|---|---|---|
| `normquery/stats` (статистика по запросам) | ✅ есть | ✅ **есть** — probe v2 доказал для unified с search-трафиком |
| `normquery/get-bids` (ставка по запросу) | ✅ есть | ⛔ пусто — управлять нечем |

То есть **query-level диагностика доступна не только для manual**. Отличие manual —
доказанная возможность query-level **bid management**. Смешение этих двух вещей привело
бы к тому, что диагностику по ключам не стали бы строить для unified-кампаний, хотя
данные для неё есть.

Побочно: ставки кластеров у `37727969` идут 510–650 ₽ при ставке кампании 520 ₽ —
то есть **кампанийная ставка не является операционной для search-кластеров**
в manual-режиме. (Оговорка: снимки взяты в разное время, строгого соотношения не вывожу.)

**C. Множества `norm_query` в `stats` и в `get-bids` НЕ совпадают.**
`против чёрных точек` имеет ставку, но не попал в статистику; `сужение пор на лице`
набрал 576 показов и 373 ₽ расхода, но ставки по нему нет.
**Контракт: связывать `stats` и `bids` только LEFT JOIN по
`(advert_id, nm_id, norm_query)`. Ставка есть там, где её выставили; статистика — там,
где были показы. Пересечение — не гарантия.**

**D. CPC+manual: `get-bids` → HTTP 200 и пустой `bids[]` — валидный исход** (probe v4).
Запрошено 5 CPC+manual пар, вернулось 0 строк; в том же запросе позитивный контроль
CPM+manual (`37727969/305101361`) вернул 25 ставок. Контроль и доказывает, что дело не
в запросе или токене.

🔴 **Границы этого утверждения.** Проверено 5 пар из 23 существующих CPC+manual.
Глобальное «у CPC кластерных ставок нет» отсюда **не следует** и в контракт не входит.
Доказано ровно одно: **в проверенных пяти CPC+manual парах `get-bids` не вернул ни одной
ставки при HTTP 200.** Практическое следствие для Ads-3: не тратить запросы на CPC.
Если WB когда-нибудь начнёт их отдавать, это обнаружится отдельной ре-проверкой на
оставшихся 18 парах, а не молча.

### 1.2 DERIVED — считается нами, ни одно не хранится как «факт»

| Метрика | Формула | Знаменатель существует для |
|---|---|---|
| click→cart CR | `atbs / clicks` | CPM и CPC |
| cart→order CR | `orders / atbs` | CPM и CPC |
| view→order CR | `orders / views` | **только CPM** (на уровне запроса) |
| CTR (day-level) | `clicks / views` | day-level всегда |
| CPO | `spend / orders` | CPM и CPC |
| cost per cart | `spend / atbs` | CPM и CPC |
| CPC (расчётный) | `spend / clicks` | всегда |
| CPM (расчётный) | `spend / views × 1000` | только там, где есть views |
| revenue / ROAS / ACOS | после связывания с экономикой SKU | см. 1.3 — вынесено |

Правило: **метрику называть по её знаменателю.** `view→order CR` по запросу для CPC
не существует — не «равен нулю», а не определён.

### 1.3 НЕ ДОКАЗАНО / ОГРАНИЧЕНО — в контракт v1 не входит

| Пункт | Статус | Что с этим делать |
|---|---|---|
| Историческая ставка по `norm_query` до начала snapshotting | **невозможно** — эндпоинта истории нет | ставка по кластеру существует только с даты запуска Ads-3 |
| Историческая ставка кампании | есть с 11.07.2026, 🔴 **дыра 13–21.07** | не интерполировать через разрыв |
| Семантика `appType` | 🟡 **OPEN** | никакой семантики до сверки с кабинетом |
| Органические показы/клики | источника нет | отдельный ingestion, вне контура |
| Разделение полки / search / recommendations по факту показов | API не доказывает | известна только **конфигурация** (`placements` + ставка на площадку) |
| Attribution order→buyout и рекламная выручка | **вынесено** | отдельный контракт атрибуции, не смешивать с contract v1 |

## 3. Историчность `normquery/stats` — и главная находка по стоимости backfill

### 3.1 Что документировано

| Параметр | Значение | Комментарий |
|---|---|---|
| **Пар на запрос** | **до 100 items** | 🔴 **наш код шлёт ПО ОДНОЙ** — см. 3.2 |
| Rate limit `normquery/stats` | 10 запросов / мин (burst 20 / 6 с) | наш throttle 6,5 с ≈ ровно в лимит |
| Rate limit `get-bids` | 5 запросов / сек (burst 10 / 200 мс) | на два порядка свободнее |
| Максимальный период запроса | **явно не документирован** для normquery; для `fullstats` — 31 день | принять 31 день и **проверить эмпирически** |
| Статусы кампаний | 7, 9, 11 | все наши 430 кампаний попадают |
| Глубина хранения истории | **не документирована** | 🔴 **ключевой незакрытый вопрос** |

### 3.2 🔴 Находка: batching даёт ×100

Существующий код (`WbAdsClustersJob.gs:175`) отправляет один элемент в `items`.
API принимает 100. При тех же rate limits это меняет стоимость backfill на два порядка:

```
Пар кампания×товар за всю историю (13.04–12.08):      760
Окон по 31 дню на период 13.04 … 13.08:                 4

Backfill ПО ОДНОЙ ПАРЕ (как сейчас):   760 × 4 = 3 040 запросов × 6,5 с ≈ 5 ч 30 мин
Backfill ПАЧКАМИ ПО 100:                        ≈ 32 запроса × 6,5 с ≈ 3,5 минуты
```

Если брать реально активные пары помесячно, ещё дешевле:

| Месяц | Пар активно | Пар с кликами | Запросов пачками по 100 |
|---|---|---|---|
| 2026-04 | 322 | 54 | 4 |
| 2026-05 | 280 | 44 | 3 |
| 2026-06 | 298 | 70 | 3 |
| 2026-07 | 170 | 45 | 2 |
| 2026-08 | 110 | 21 | 2 |
| **итого** | — | — | **14 запросов ≈ 1,5 минуты** |

**Вывод: backfill query-level статистики с 13.04.2026 стоит полторы минуты,
а не полдня.** Это снимает главный аргумент против полной истории и меняет
приоритет: собирать надо не «с сегодня», а сразу всю доступную историю.

### 3.3 Что обязательно проверить ДО проектирования таблицы

🔴 **Глубина хранения на стороне WB не документирована.** Прежде чем закладывать
партиционирование и грейн, нужен один дешёвый тест:

> запросить `normquery/stats` на одну активную CPM-пару за окно **13.04–13.05.2026**
> и посмотреть, вернутся ли строки.

Три исхода и что каждый значит:

| Исход | Что значит | Следствие для схемы |
|---|---|---|
| Данные вернулись | история доступна с апреля | грейн `period × advert × nm × query`, backfill сразу за 4 месяца |
| Пусто, но HTTP 200 | WB хранит короткое окно | таблица только «вперёд», история начинается с даты Ads-2 |
| Ошибка / отказ по периоду | жёсткое ограничение окна | подобрать максимум бинарным поиском |

Тест добавляется в тот же probe одной функцией. **Проектировать таблицу до этого
ответа я не буду** — иначе рискуем заложить грейн под историю, которой нет.

### 3.4 ✅ Ответ получен (probe v3, ред. 1.2)

Тест выполнен на трёх реальных парах. **Историчность подтверждена: 3 из 3** — данные
за апрель возвращаются, статусы кампаний 7/9/11 все отдают историю, фильтр периода
работает.

🔴 **Ограничение окна: `to − from ≤ 30`** — это **разница дат**, а не календарные сутки
включительно. Окно 13.04–13.05 API отклоняет с `"date range must not exceed 30 days:
31 days"`. Мои первоначальные подписи окон в probe считали дни включительно и потому
были на единицу больше — off-by-one в подписях, не в данных.

**Следствие для схемы:** грейн `period × advert × nm × query`, backfill сразу за
доступную историю, окна нарезать по 30 дней разницы.

⚠️ В итоговой строке probe v3 стояло «1 из 3» вместо 3/3 — из-за зашитого порога
`views > 1000` в критерии вердикта. Корректный критерий — `clusters > 0`. Разбор под
вердиктом был верным; врал именно короткий вывод.

## 4. Предлагаемые схемы RAW-таблиц

Стиль тот же, что у действующих `RAW_WB_ADV_*`: технические колонки, плоские поля,
плюс `raw_json` целиком. Дедуп — во вью, как принято в проекте.

### 4.1 `RAW_WB_ADV_QUERY_STATS` — статистика по поисковым запросам

Заменяет нынешнюю `RAW_WB_ADV_SEARCH_CLUSTERS` (её схема расходится с реальностью).

```
-- технические
load_ts, run_id, source_method, processed_status, raw_json
-- окно запроса
period_from, period_to
-- ключ
advert_id, nm_id, norm_query
-- payment_type кампании на момент сбора: определяет, какие поля обязаны быть NOT NULL
payment_type                       -- 'cpm' | 'cpc'
-- метрики, приходят всегда
clicks, cpc, spend, avg_pos, atbs, orders, shks, currency
-- метрики ТОЛЬКО для CPM (для CPC — NULL по контракту, НЕ нули)
views, ctr, cpm
```

* **Грейн:** `period_from × period_to × advert_id × nm_id × norm_query`.
* **Партиционирование:** по `period_to` (дата).
* **Кластеризация:** `advert_id, nm_id`.
* Идемпотентность — **BQ-native**: `DELETE` по `(period_from, period_to)` + вставка,
  либо `MERGE` по грейну. Никаких `getLastRow`.
* 🔴 Обязательный QC: `views IS NULL` при `payment_type='cpc'` — норма;
  `views IS NULL` при `payment_type='cpm'` — **алерт**, контракт нарушен.

### 4.2 `RAW_WB_ADV_QUERY_BIDS` — ставки по кластерам (snapshot)

**Ред. 1.2: ниже — фактически реализованная схема PR Ads-3.** Подробное обоснование
каждого решения — `docs/ADS3_FINAL_DESIGN_2026-08-13.md` (ред. 3).

```
load_ts, run_id, source_method, processed_status, raw_json
snapshot_ts                        -- момент снимка, ключевой: истории у WB нет
snapshot_date                      -- сутки снимка, партиция
advert_id, nm_id, norm_query
bid                                -- ₽, как отдаёт API (подтверждено логом)
bid_kopecks                        -- копейки, API отдаёт ОБА поля
currency                           -- 'RUB'
payment_type                       -- 'cpm' | 'cpc', из состояния кампании
bid_type                           -- 'manual' | 'unified', из состояния кампании
campaign_status                    -- 7 | 9 | 11, на момент снимка
```

Плюс отдельная run-log таблица `RAW_WB_ADV_QUERY_BIDS_RUNS` — одна строка на прогон,
пишется **всегда**, включая нулевой результат. Без неё валидный пустой ответ неотличим
от несостоявшегося прогона.

🔴 **`payment_type` рядом со ставкой обязателен.** У CPC ставка — цена клика (12–55 ₽),
у CPM — цена тысячи показов (130–590 ₽). Одно поле, разные единицы: без `payment_type`
две модели смешаются в одной колонке и станут бессмысленными.

🔴 Ставки приходят только для `bid_type='manual'` (§1.4B), а из manual — только для
CPM (§1.4D, в границах проверенного). Отсутствие строк — норма контракта, QC на это
алертить не должен. Опрашивать имеет смысл только `payment_type='cpm' AND
bid_type='manual'`, чтобы не тратить запросы впустую.

* **Грейн:** `run_id × snapshot_ts × advert_id × nm_id × norm_query`, **append-only**.
* 🔴 **Идентичность снимка — `(snapshot_date, snapshot_ts, run_id)`, а не один
  `snapshot_ts`:** его точность — секунда, и два execution одной секунды получат равный
  `ts` при разных `run_id`. Канонизация в вью идёт **на уровне снимка целиком**, иначе
  снятая ставка «воскресает» из более раннего снимка и получается набор ставок, не
  существовавший ни в один момент времени.
* **Партиционирование:** по `snapshot_date`.
* 🔴 Принципиально: **истории ставок по кластеру у WB нет** — она начинает существовать
  с первого снимка. Чем раньше запустим, тем раньше начнётся история. Это аргумент
  сделать Ads-3 не последним, а сразу после Ads-2.
* Частота: rate limit 5 req/s позволяет хоть ежечасно. Начать с суточного вместе
  с ads-прогоном, пересмотреть по факту частоты изменений.

### 4.3 `RAW_WB_ADV_CAMPAIGN_SETTINGS` — состояние кампании и ставки

Не заменяет `RAW_WB_ADV_CAMPAIGNS`, а извлекает то, что уже лежит в её `raw_json`.
**Данные существуют с 11.07.2026 — таблицу можно заполнить ретроактивно, без API.**

```
load_ts, run_id, source_method, processed_status, raw_json
snapshot_date                      -- дата снимка
advert_id, nm_id                   -- nm_id из nm_settings[]
payment_type, bid_type, status
bid_search_kopecks, bid_rec_kopecks
placement_search, placement_recommendations   -- BOOL
campaign_name, subject_id, subject_name
created_at, started_at, updated_at, deleted_at
```

* **Грейн:** `snapshot_date × advert_id × nm_id`.
* Заполняется **разбором `raw_json` существующей таблицы** — новых вызовов API не нужно.
* 🔴 QC полноты обязателен: календарь снимков против фактических дат,
  **известный разрыв 13.07–21.07.2026 (9 суток)** должен отражаться как разрыв,
  а не затираться.

история ставок по кластеру не существует до первого снимка, каждый день отсрочки
это безвозвратно потерянный день истории. У query-stats такой срочности нет: если
тест §3.3 покажет, что WB хранит апрель, эта история никуда не денется.
