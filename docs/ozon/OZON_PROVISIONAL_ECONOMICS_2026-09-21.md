# Gate 8 — провизорная экономика Ozon и полная строка итога

Дата: 2026-09-21. Решение принято по замерам, перечисленным ниже; каждое число воспроизводимо
запросом к `ozon_raw` / `ozon_mart`.

## 1. Задача

Лист показывал за свежие сутки мнимую прибыль: выручка есть, комиссии и логистики нет.
Причина не в ошибке расчёта, а в сроках: Ozon эти расходы ещё не опубликовал.

## 2. Замер сроков (328 начислений, привязанных к отправлениям, после бэкфилла)

| величина | p50 | p90 | p95 | p99 | max |
|---|---|---|---|---|---|
| публикация Ozon (извлечено − дата операции) | 14 | 14 | 14 | 14 | **14** |
| начисление (дата операции − дата заказа) | 5 | 12 | 13 | 19 | 25 |
| **видимость (извлечено − дата заказа)** | 18 | 23 | 25 | 33 | **36** |

Публикация ДЕТЕРМИНИРОВАНА: ровно 14 суток, без разброса. Загрузчик тянет скользящее окно
14 суток по дате операции и каждый прогон находит ровно одни новые сутки — то есть работает
с НУЛЕВЫМ запасом. Пропуск одного суточного прогона потерял бы день начислений безвозвратно.
Это отдельный риск; он записан в §7 и в этом гейте не устранялся.

## 3. Комиссия — не статистика, а точная величина

`commission_ratio` по дате ЗАКАЗА даёт лестницу тарифов:
0,18 → 0,23 → 0,275 → 0,30 → 0,34 → 0,39 → 0,41 → **0,52**.
Последний переход: 27.08.2026 — смешанные сутки (6 заказов по 0,41, 1 по 0,52), с 28.08 —
только 0,52. Память владельца («27/28 августа») подтвердилась замером.

База ставки — **цена продавца**: `commission_rub / seller_base_price_rub = −commission_ratio`
на 2002 строках из 2003. Цена покупателя базой не является.

Ставка едина для всех SKU: из 456 суток только 3 содержат более одной ставки, и все три —
сутки перехода. `V_OZON_COMMISSION_POLICY` всё равно ведёт её поSKU-но, чтобы разошедшийся
по товарам тариф стал виден сразу.

**Главная находка: комиссию вообще не нужно оценивать.** В отчёте по отправлениям есть
`payout_rub`, и тождество

```
(price_rub − payout_rub) × quantity = комиссия
```

выполняется на **600 урегулированных отправлениях из 600, расхождение 0,00 ₽**. Ozon сообщает
будущую выплату в момент отправления — то есть комиссия известна ТОЧНО за две недели до
финансового документа. Она просто не читалась из источника, который уже загружается.

Состояние такой величины всё равно `ESTIMATED`: источник — отчёт по отправлениям, а не
финансовый документ. Подменять факт оценкой запрещено, даже когда оценка точна.

У выкупов СНГ комиссии не существует как факта: `NOT_APPLICABLE`, тариф не применяется.

## 4. Логистика — статистика, выбранная бэктестом

Детерминированного источника нет. Ставка СМЕНИЛА РЕЖИМ: медиана на единицу держалась около
50 ₽ по февраль 2026 и с марта-апреля встала на 78–89 ₽, поэтому оценщик на полной истории
систематически переоценивает (p75 по всей истории — 105 ₽ там, где факт около 86).

Бэктест out-of-sample, прогноз строится только по наблюдениям строго ДО прогнозируемых суток.
«Занижение» = оценка меньше факта = мнимая прибыль сегодня и убыток потом.

| окно | кв | MAE | смещение | занижений | RMSE |
|---|---|---|---|---|---|
| **120** | **p70** | **14,08** | **+1,26** | **35,7 %** | **23,63** |
| 90 | p70 | 14,83 | +3,41 | 34,1 % | 24,15 |
| 60 | p65 | 14,33 | +1,33 | 40,9 % | 24,21 |
| 180 | p70 | 15,60 | +3,64 | 32,8 % | 24,28 |
| вся история | p70 | 15,87 | −5,61 | 53,9 % | 25,66 |

На установившемся режиме (цель — заказы с 01.06): **120/p70 — MAE 9,54, смещение +0,42,
RMSE 14,61**, лучший результат среди оценщиков без систематического занижения.

Выбран **SKU_P70_120D**. Медиана и p60 дают MAE на рубль-два меньше, но занижают расход в
50–70 % случаев и на 5–7 ₽ систематически — ровно та мнимая прибыль, которую владелец просил
не допускать.

## 5. Что оценщика НЕ имеет

Хранение, прочие прямые, продвижение и реклама — **только факт**. Это событийные начисления
(утилизация, вывоз, упаковка, сбор отзывов), а не переменная на единицу: предсказывать их
нечем. Выдуманный ноль здесь запрещён так же, как выдуманная оценка: до зрелости периода
состояние `UNKNOWN`, после — `NOT_APPLICABLE`.

## 6. Старшинство и сходимость

```
есть факт                           → effective = факт,   ACTUAL
расход ожидается, оценщик доказан   → effective = оценка, ESTIMATED
доказано, что расхода не существует → effective = 0,      NOT_APPLICABLE
иначе                               → effective = NULL,   UNKNOWN
```

Проверка сходимости на всей истории: **3289 созревших строк, расхождений с фактом 0**.
Операционный результат созревшего периода тождественно равен фактическому.

## 7. Окно перезаписи

| окно | покрытие видимости |
|---|---|
| 14 | 19,8 % |
| 21 | 85,1 % |
| 30 | 97,6 % |
| 35 | 99,4 % |
| **45** | **100 %** |
| 60 | 100 % |

Выбрано **45 суток** — наименьшее окно, накрывающее ВСЮ наблюдённую задержку (максимум 36)
с запасом 9 суток. Окно 35 дешевле и даёт 99,4 %, но оставляет измеренный хвост снаружи:
день, чья комиссия пришла на 36-е сутки, навсегда остался бы с оценкой вместо факта — ровно
тот отказ, ради предотвращения которого окно и существует.

Глубокая сверка — **раз в месяц, 120 суток**: тот же горизонт, на котором построен оценщик
логистики, втрое перекрывает наблюдённый максимум.

**Открытый риск (не устранён в Gate 8):** окно ЗАГРУЗКИ `finance_accrual` — 14 суток по дате
операции при публикации ровно через 14 суток. Запаса нет. Один пропущенный прогон теряет
сутки начислений навсегда. Лечится расширением окна загрузки до 30 суток (дедупликация уже
есть); это изменение Cloud Run Job загрузчика Ozon, а не Юнитки.

## 8. Строка итога месяца

Политика — `OZON_UNITKA_SUMMARY_POLICY`, по одному правилу на каждое из 25 смещений.
Никаких `AVERAGE(дневные ячейки)`: среднее средних уравняло бы сутки с одной продажей и
сутки с двадцатью. Вес — реализованные единицы («заказы − отмены»), тот же счётчик, которым
уже пользуется принятый итог «Доходность на 1 шт». Все агрегаты отсечены по `LAST_CLOSED_DATE`.

| метрика | политика |
|---|---|
| цена | средняя реализации = вся выручка / все единицы |
| комиссия | эффективная ставка = вся комиссия / вся выручка |
| СПП | 1 − цена покупателя периода / цена продавца периода |
| логистика | **средняя на реализованную единицу**, а не сумма |
| хранение, прочие прямые, доходность общая, реклама | сумма |
| налог | сумма периода, собранная взвешиванием (дневная ячейка поединична) |
| доходность 1 шт | вся доходность единиц / все реализованные единицы |
| остаток | последний ДОКАЗАННЫЙ снимок (с 31.08.2026) |
| оборачиваемость | конечный остаток / средний суточный темп заказов |
| дата, день недели | итога не существует |

Остаток намеренно НЕ берётся из легаси-половины апреля: там лежит отвергнутая синтетическая
проекция, местами отрицательная (Gate 4.1). Показать её как «остаток на конец месяца» значило
бы вернуть в лист величину, которую проект признал невоспроизводимой.

## 9. Что осталось

* Расписание суточного прогона **не создано**. Загрузчик `ozon-unitka` зарегистрирован и
  исполняется, но Cloud Run Job и Cloud Scheduler под него требуют `terraform apply`, а
  `CLAUDE.md` запрещает его из неслитой ветки (именно так ресурсы загрузчика воронки попали
  в production мимо `main`). Включение расписания — отдельный шаг владельца.
* Подпись блока в листе остаётся `9099514444` при каноническом `909951444` (решение D-5E-3).
  На экономику не влияет: идентичность берётся из справочника.
