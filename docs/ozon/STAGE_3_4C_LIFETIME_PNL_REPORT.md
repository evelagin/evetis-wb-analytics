Дата: 2026-09-04. READ-ONLY. Витрины не создавались.

## 17.1 🔴 Исправление ошибки §16

Владелец обнаружил противоречие, и оно подтвердилось.

В §16 указано `CONTRIBUTION_BEFORE_ADS = 498 073,17 ₽`. **Это неверно.**
Арифметика восстановления: +30 905,00 выручки − 9 637,60 комиссии = **+21 267,40**,
значит 465 222,73 + 21 267,40 = **486 490,13 ₽**.

Разница **11 583,04 ₽** — ровно `OTHER_MARKETPLACE_COSTS`.

**Причина:** Stage 3.4C считал «до рекламы» **включая** прочие расходы площадки,
а в §16 я посчитал ту же метрику **исключая** их. Одно имя, два определения —
ровно то, что политика теперь запрещает.

**Итог L4 при этом был верен:** −117 283,53 ₽ считался по полной цепочке
с включением 11 583,04 ₽. Ошибка жила только в промежуточном слое.

### Что из-за этого было сказано неверно

§16.2 утверждал, что реклама «укладывается в порог». **Это следствие ошибки.**
При правильном `CONTRIBUTION_BEFORE_ADS = 486 490,13`:

| | § 16 (ошибочно) | **§ 17 (верно)** |
|---|---:|---:|
| variable break-even DRR | 28,11 % | **27,4538 %** |
| actual DRR | 27,91 % | **27,9138 %** |
| вывод | реклама ниже порога | **реклама выше порога на 0,46 п.п.** |

`CONTRIBUTION_AFTER_ADS_BEFORE_FIXED = −8 149,66 ₽` — **отрицателен**.
Реклама съедает вклад ещё до постоянных расходов.

## 19.1 🔴 REFRESH_GAP: найден и закрыт

Завтра после прихода новых postings, финансов и рекламы таблицы
остались бы прежними и **молча разошлись бы с источником**.
Статус на момент аудита: **REFRESH_GAP**.

**Что сделано — вариант A.** Оба факта переведены в `VIEW`.

Почему именно так, а не процедура с расписанием:

| Критерий | VIEW | TABLE + refresh job |
|---|---|---|
| стоимость полного пересчёта | ~0,9 МБ обработано, ~865 КБ, единицы секунд | та же плюс запись |
| может устареть относительно `ozon_raw` | **физически нет** | да, если job не сработал |
| поздние корректировки финансов (lookback 14 дн) | попадают немедленно | нужен пересчёт прошлых месяцев |
| гонка с частично обновлённым raw | **невозможна** | нужно упорядочивание |
| дубли month/SKU при повторе | **невозможны** | нужен MERGE/DELETE+INSERT |
| новые сущности для отказа | нет | планировщик, job, IAM, порядок |

Требование «Do NOT create a second independent ingestion system»
выполняется буквально: **ни одной новой сущности не создано** —
ни планировщика, ни job, ни процедуры, ни прав IAM.

**Порядок и консистентность (раздел 3 задания) снимается сам собой.**
Запроса-обновления не существует, поэтому нет и момента, когда он мог бы
опередить загрузку. Марты читают `ozon_raw` таким, какой он есть
в момент чтения, атомарно на уровне запроса.

## 19.2 🔴 Настоящая причина устаревания: планировщики Ozon сломаны

Аудит свежести вскрыл действующий инцидент, к Stage 3.4C отношения
не имеющий, но делающий любую витрину бессмысленной.

**Все три планировщика Ozon не срабатывают с 2026-09-03.**

```
ozon-fast    последняя попытка 2026-09-04T10:00:50Z   status.code = 7  PERMISSION_DENIED
ozon-daily   последняя попытка 2026-09-04T03:30:00Z   status.code = 7  PERMISSION_DENIED
ozon-weekly  ещё не срабатывал после изменения
```

За окно журнала: **4 попытки, 4 отказа, 0 успехов.**
Последнее успешное выполнение `ozon-runtime-ingest` — 2026-09-03T15:23Z,
и это был ручной запуск Stage 3.3B, а не планировщик.

**Причина установлена точно.** Все три задания передают
`overrides.containerOverrides` (переменная `ENTITIES`) через
v1-эндпоинт Admin API:

```
https://europe-west1-run.googleapis.com/apis/run.googleapis.com/v1/
  namespaces/<project>/jobs/ozon-runtime-ingest:run
```

Запуск с overrides требует права `run.jobs.runWithOverrides`.
У `sa-ozon-scheduler` есть только `roles/run.invoker`, а в него входят
`run.instances.invoke`, `run.jobs.run`, `run.routes.invoke` —
**`run.jobs.runWithOverrides` в нём нет**.

Сравнение с работающим соседом подтверждает диагноз: `wb-mart-prod`
имеет ровно тот же `roles/run.invoker` у своей SA, но вызывает
v2-эндпоинт `.../v2/projects/.../jobs/wb-mart-prod:run` **без overrides**
и отрабатывает штатно (последняя попытка 2026-09-04T09:00Z без ошибки).

**Два возможных исправления:**

1. выдать `sa-ozon-scheduler` роль с `run.jobs.runWithOverrides`
   (`roles/run.developer` на конкретный job) — сохраняет overrides;
2. убрать overrides из заданий и развести сущности иначе
   (три отдельных Cloud Run job либо `ENTITIES` в самом job).

**Ни то, ни другое не применено.** Изменение IAM и конфигурации
планировщиков выходит за периметр Stage 3.4C и требует ACK владельца.
Инцидент вынесен наверх отчёта как есть.

## 19.3 Контракт свежести

Создан `ozon_mart.V_OZON_MART_FRESHNESS`.

Поскольку марты — представления, устареть относительно `ozon_raw` они
не могут: `mart_computed_at` всегда равен моменту чтения. Измерять
поэтому нужно свежесть **самого `ozon_raw` относительно Ozon**.

Допуски выведены из расписаний `OZON_INCREMENTAL_CONTRACT_V1`:

| Сущность | Расписание | Допуск |
|---|---|---:|
| `fbo_postings` | `ozon-fast`, 3×/сутки | 12 ч |
| `finance_accrual` | `ozon-daily` | 30 ч |
| `ads_expense_daily` | `ozon-daily` | 30 ч |
| `ads_sku_daily` | `ozon-daily` | 30 ч |

Детерминированные состояния:

| Состояние | Условие |
|---|---|
| `REFRESH_FAILED` | последняя попытка сущности не `OK`, либо сущность не загружалась никогда |
| `STALE` | все сущности P&L старше своего допуска |
| `PARTIAL_SOURCE_UPDATE` | часть сущностей в допуске, часть — нет |
| `FRESH` | все сущности P&L в допуске |

Отдельное поле `agent_decision_gate` принимает
`DECISIONS_BLOCKED_SOURCE_NOT_FRESH` при любом отклонении и
`DECISIONS_ALLOWED` только при полной свежести. Агент обязан
отказываться от решений в первом случае.

⚠️ **Ограничение, которое нельзя забывать.** Если планировщик вообще
не смог запустить job — ровно сегодняшний случай, `PERMISSION_DENIED` —
строки в `OZON_INGESTION_RUNS` не появляется, и статуса `FAILED` не будет.
Такой отказ ловится **только по возрасту последнего успеха**. Именно
поэтому `STALE` считается по времени, а не по наличию ошибки.

**Фактическое состояние на момент закрытия:**

```
freshness_status     = PARTIAL_SOURCE_UPDATE
agent_decision_gate  = DECISIONS_BLOCKED_SOURCE_NOT_FRESH
fbo_postings         = STALE (23 ч при допуске 12 ч)
finance_accrual      = FRESH (23 ч)
ads_expense_daily    = FRESH (23 ч)
ads_sku_daily        = FRESH (21 ч)
```

Контракт **сработал** и сам показал последствие сломанных планировщиков.

## 19.5 Семантика юнит-экономики: наблюдённое ≠ прогнозное

`V_OZON_SKU_UNIT_ECONOMICS_CURRENT` считает средние за **скользящие
180 дней**. Это **наблюдённая задняя экономика**, и выдавать её
за действующие тарифы нельзя.

Введены явные поля:

```
economics_mode        = 'TRAILING_OBSERVED'
economics_window_days = 180
window_start / window_end
first_observed_month / last_observed_month
forward_pricing_ready = FALSE
forward_pricing_blockers
```

Классификация каждой величины:

| Величина | Класс | Основание |
|---|---|---|
| `trailing_avg_seller_base_price_rub` | **TRAILING_OBSERVED** | средняя цена реализации за окно, не текущий прайс |
| `trailing_avg_commission_unit_rub` | **TRAILING_OBSERVED** | фактические начисления, не действующий тариф |
| `trailing_effective_commission_pct` | **TRAILING_OBSERVED** | наблюдённая эффективная ставка |
| `trailing_avg_variable_mp_cost_unit_rub` | **TRAILING_OBSERVED** | фактическая логистика/последняя миля/эквайринг |
| `trailing_ad_cost_per_realized_unit_rub` | **TRAILING_OBSERVED** | фактически атрибутированный расход |
| `trailing_avg_management_cogs_unit_rub` | **CURRENT_CONTRACTUAL** (величина) | `PROVEN_DOCUMENT` по семи декларациям, взвешена по окну |
| `full_marketplace_break_even_drr_pct` | **NULL, не разносится** | постоянные расходы магазина на SKU не аллоцируются |
| действующая комиссия Ozon | **NOT_PROVEN** | дата вступления ставки 52 % документально не подтверждена |
| действующие тарифы логистики и последней мили | **NOT_PROVEN** | прайс площадки в `ozon_raw` не загружается |

Все расчётные поля переименованы с префиксом `trailing_`, чтобы читатель
или агент не мог принять их за действующие тарифы. Поля целевых цен
названы `trailing_basis_indicative_price_margin_*`: в знаменателе стоит
**наблюдённая** ставка комиссии, поэтому ставить по ним цену нельзя.

`forward_pricing_ready = FALSE` для всех 22 SKU. Значение `TRUE`
появится только тогда, когда действующая комиссия и тарифы будут
подтверждены независимо — **это работа Stage 3.4D**.
Выводить их из средних за 180 дней запрещено.

**Два понятия для Stage 3.4D разведены явно:**

| Понятие | Где живёт сейчас |
|---|---|
| `OBSERVED_TRAILING_UNIT_ECONOMICS` | `V_OZON_SKU_UNIT_ECONOMICS_CURRENT`, опубликовано |
| `FORWARD_UNIT_ECONOMICS` | **не существует**, Stage 3.4D |

Имя объекта содержит `CURRENT` по историческим причинам — оно вошло
в ACK владельца Stage 3.4C. Все поля и описание объекта теперь говорят
`TRAILING_OBSERVED` явно. **Переименование объекта в
`V_OZON_SKU_UNIT_ECONOMICS_TRAILING_180D` предлагается как решение
Stage 3.4D** и без ACK не делается.
