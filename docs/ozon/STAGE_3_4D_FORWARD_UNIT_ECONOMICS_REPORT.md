## 6.1 MODE 2 — на созданный заказ

Без изменений в логике: `E = (1−c)·C − c·0,558·(логистика + return_flow + 15)`,
теперь в двух вариантах (`expected` и `worst`). Вероятность отмены — по
статусам (портфель 12,5 %, 37/296); SKU без заказов в окне получают
`NULL_NO_ORDERS_IN_WINDOW`. Возвраты: `expected_return_cost = NULL`

# 7. FBO ↔ FBS

| Метрика | ПВЗ-отгрузка (база) | СЦ-отгрузка | СЦ + ранняя отгрузка (условно) |
|---|---:|---:|---:|
| `fbs_max_external_ff_to_match_fbo` | **−10 ₽** у всех 20 | **0 ₽** у всех 20 | +0,03 × цена (25…114 ₽) |

По действующим тарифам FBS на уровне заказа **равен FBO при отгрузке в СЦ и
хуже на 10 ₽ при отгрузке в ПВЗ**; лучше FBO он становится только за счёт
условной скидки −3 % за раннюю отгрузку (например, +41 ₽ на `FC-ACNE-50`).
Внешний фулфилмент любой положительной стоимости делает FBS хуже, кроме этого
условного случая. Складская экономика FBO (кросс-докинг по п. 2.2.7, размещение
2,50 ₽/л/день после бесплатного периода) в заказную модель по-прежнему не
разнесена. `comparison_status = PARTIAL`, `preferred_scheme = FBO`,
`fbs_scheme_recommendation = PROVISIONAL`.

## 20. Форвардная экономика: диапазон вместо точки

## 22. FBO ↔ FBS

| Модель отгрузки FBS | Первая миля | `max_external_ff_to_match_fbo` |
|---|---:|---:|
| СЦ (drop-off) | 0 ₽ | **0 ₽** у всех 20 |
| ПВЗ / ППЗ | 10 ₽ | **−10 ₽** у всех 20 |
| курьер | NULL | не считается |

FBS **равен** FBO при отгрузке в сортировочный центр и **хуже на 10 ₽**
при отгрузке в ПВЗ. Любой положительный внешний фулфилмент делает FBS
хуже; при всех сценариях 50–150 ₽ предпочтительная схема — FBO у 20 из 20.

Единственный способ обогнать FBO на уровне заказа — условная скидка
−3 % комиссии за отгрузку в первый рекомендованный слот
(`fbs_early_shipment_discount_max_rub`, 25–114 ₽ по SKU). Это
операционная дисциплина, а не тариф, поэтому в базовую модель не входит.

`fbs_forward_economics_ready = PARTIAL`,
`fbs_scheme_recommendation = PROVISIONAL`. Блокеры: реализованных
FBS-заказов нет за всю историю; FBS-склад не настроен; тариф курьерской
отгрузки устанавливает партнёр и виден только в кабинете.

**Кабинет проверен, доступ есть.** Вход под EVETIS активен, разделы
читаются. Страница FBS показывает ноль заказов и ноль настроенных
складов, поэтому «Управление логистикой» с тарифами партнёров-курьеров
недоступна. Метод `/v1/warehouse/list` отвечает `obsolete method cannot
be used`. То есть тариф курьера не «не найден», а **не существует, пока
не настроен FBS-склад**. Ни одной кнопки не нажато: только навигация и
чтение.

## 27. Premium перестал быть константой

**Дефект, который закрывали.** Статус подписки был доказан API 2026-09-06
и зашит в витрину значением `FALSE`. Если бы Premium возобновили,
форвардный слой не узнал бы об этом никогда: у константы нет возраста.

**Что сделано.** Заведена сущность `seller_info` на двух READ-методах —
`/v1/seller/info` и `/v1/rating/summary`. Таблица
`ozon_raw.RAW_OZON_SELLER_INFO`, зерно `snapshot_date`, один снимок в
сутки, MERGE по дате.

Идентификаторы компании — ИНН, ОГРН, юридическое и торговое название —
**намеренно не сохраняются** ни в колонках, ни в `raw_json`. Для
экономики они не нужны, а хранить их без нужды незачем. Остались
налоговый режим, страна, валюта, флаги подписки и индекс локализации.

Снимок 2026-09-06T11:25:54Z: `is_premium = false`, `type = UNSPECIFIED`,
`premium = false`, `premium_plus = false`, `tax_system = USN`,
локализация 30 % на 2026-08-30.

**Как это теперь работает в витрине.** Поля `premium_active`,
`premium_plus_active`, `premium_status_source_at` приходят из последнего
снимка. `premium_status` принимает пять значений:

| Значение | Когда |
|---|---|
| `ACTIVE` / `PREMIUM_PLUS_ACTIVE` | подписка есть |
| `INACTIVE` | подписки нет, снимок свежий |
| `UNKNOWN_STALE` | снимку больше 30 ч |
| `UNKNOWN_NEVER_INGESTED` | снимка нет вовсе |

Устаревший статус **не превращается в FALSE**. «Подписки нет» — это
утверждение о факте, и делать его на основании отсутствия данных нельзя.

**Чего Premium НЕ делает.** Он не входит и не должен входить в формулу
вклада SKU: это постоянный расход уровня магазина, разносить его на
товар запрещено (`OZON_PNL_POLICY_V1`, запрет 5). Поле
`premium_affects_sku_contribution = FALSE` зафиксировано явно. Поэтому
неизвестный статус подписки **не закрывает аналитику** — он закрывает
только теневую автоматизацию.

## 28. Три уровня готовности вместо одного

| Ворота | Сегодня | Смысл |
|---|---|---|
| `forward_economics_ready` | **TRUE** | считать и смотреть можно |
| `agent_shadow_ready` | **FALSE** | теневой режим закрыт |
| `agent_write_ready` | **FALSE** | право записи, зашито константой |

Разница между первым и вторым принципиальна. Отсутствие второй базы
сравнения тарифа не делает числа неверными — оно означает, что детектор
изменений ещё ни разу не отработал. Смотреть можно, автоматически
действовать нельзя.

`agent_write_ready` не вычисляется ни из чего. Ни одна система не должна
уметь получить право записи как следствие того, что данные оказались
свежими. Снятие требует отдельного ACK и правки кода:
`agent_write_gate = HARDCODED_FALSE_NOT_DERIVABLE_FROM_DATA_REQUIRES_SEPARATE_OWNER_ACK`.

Условия `agent_shadow_ready`: тариф `FRESH`, `seller_info` `FRESH`, ноль
неизвестных компонент, покрытие тарифа 20 из 20, связка идентичности
20 из 20, COGS 20 из 20, база сравнения `BASELINE_OK`,
`forward_economics_ready = TRUE`.

Сегодня выполнены все, кроме последнего по списку:
`agent_shadow_gate = SHADOW_BLOCKED_FIRST_BASELINE_PENDING`.

Исправлено на `CROSS JOIN` и `LEFT JOIN ... ON TRUE`; запрет записан
