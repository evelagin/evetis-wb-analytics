# OZON API — реестр фактической глубины истории

Дата установления: 2026-09-03 (Stage 3.3B).
Проверено вызовами production-креденшелов, не предположениями.

Это **постоянный контракт по глубине истории**. Любое утверждение вида
«у нас нет данных за период X» должно сверяться с этой таблицей: отсутствие
данных может означать либо предел API, либо отсутствие деятельности продавца,
либо непроведённый backfill — это три разные ситуации.

## Разбор по сущностям

### fbo_postings — historical fact
Проверены помесячные окна с 2024-01 по 2026-06. Все двенадцать месяцев 2024 года и
январь–март 2025 вернули HTTP 200 и **ноль отправлений** — это не отказ API, а
отсутствие деятельности: продавца на Ozon тогда не было. Первое отправление — 2025-04-26.

Ограничение: 100 записей на страницу, курсорная пагинация через `has_next`/`cursor`.
Нижнего предела по дате обнаружить не удалось — API принимает произвольно старые окна.

### finance_accrual — historical fact
Помесячная выборка (дни 5/15/25) с 2025-01 показала первый непустой месяц — май 2025.
Посуточная проверка апреля–мая 2025 уточнила границу: **2025-04-22**, одно начисление.
Апрельские начисления единичны (22, 26, 30 апреля по одному) — согласуется с началом продаж.

Ограничения: один день на запрос, пагинация через `last_id`. При частых вызовах
наблюдался HTTP 429 — backoff в runtime его отрабатывает (в backfill 3.3B зафиксировано
7 ретраев на 446 запросов, все успешны).

### ads_expense_daily — historical fact
Помесячные окна с 2025-01: январь–апрель 2025 пусты, первый расход — май 2025
(32 346,56 ₽ за месяц). Первый день с расходом в BigQuery — 2025-05-05.

### ads_sku_daily — historical fact, но добывается асинхронным отчётом
Единственный доказанный источник расхода в разрезе SKU. Отчёт заказывается на батч
кампаний, готовится асинхронно, забирается ZIP-архивом (по CSV на кампанию).

Проверено: окна 2025-05, 2025-09 и 2026-02 отдают реальные SKU-строки — например,
за сентябрь 2025 архив из 10 CSV, 77 SKU-строк на выборке из 4 кампаний.
Историческая глубина ограничена не API, а наличием кампаний с расходом.

**Периметр отчёта** строится из кампаний с расходом в окне, включая архивные:
`state` реестра включает `ARCHIVED`, `FINISHED`, `INACTIVE`, `RUNNING`.

**Ограничение по длине окна — важно для будущих backfill.** Запрос на окно
2026-07-01 … 2026-09-03 (65 дней) вернул **ноль строк при HTTP 200 и статусе
прогона OK** — молча, без ошибки. То же окно, разбитое на части, данные отдаёт:
сентябрь отдельным запросом вернул 26 строк.

Практическое правило: **окна не длиннее двух месяцев**. Все семь окон backfill
Stage 3.3B были двухмесячными и отработали без потерь. Регулярный runtime с
ретроспективой в 7 дней в это ограничение не упирается.

Отсюда же следствие для контроля: нулевой результат `ads_sku_daily` при статусе
`OK` не доказывает отсутствия данных — его нужно перепроверять более узким окном.

### ads_campaigns — SNAPSHOT, не история
`GET /api/client/campaign` отдаёт **текущий** реестр: 92 кампании, `createdAt`
от 2025-04-09 до 2026-08-20, включая архивные и завершённые.

Поле `createdAt` — атрибут кампании, а не наблюдение. Историю состояний кампании
за прошедшие даты API не отдаёт. Псевдоисторические снимки создавать запрещено:
хранятся только фактически полученные наблюдения (`snapshot_date` = дата вызова).

### stocks / prices / catalog / clusters — SNAPSHOT, не история
API отдаёт только состояние на момент вызова. Восстановить прошлые остатки,
цены или состав каталога невозможно.

**STOCK_HISTORY_START = 2026-08-31** — первый реальный снимок. Историю остатков
накапливаем только вперёд. Синтетика запрещена: восстановление остатков из продаж,
вычисление псевдо-stock, интерполяция, fake daily snapshots.

### supply_orders / supplies / bundles — реестр без окна
`/v3/supply-order/list` фильтруется по состояниям, а не по датам, и возвращает
все заказы поставки. Coverage полон по построению: 2025-04-18 → 2026-09-03,
терминальные состояния (`COMPLETED`, `CANCELLED`) присутствуют.
Повторный backfill бессмысленен и не проводился.

Известное ограничение (унаследовано из Stage 3.1): фактические дата и количество
приёмки (`ACTUAL_RECEIPT_TIME`, `ACTUAL_RECEIPT_QUANTITY`) не подтверждены API —
поля `arrival_date` и `quantity_accepted` трактовать как NOT_PROVEN.
