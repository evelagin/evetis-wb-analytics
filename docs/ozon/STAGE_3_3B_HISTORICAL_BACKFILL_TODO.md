# STAGE 3.3B — Historical Ozon Backfill (следующий этап, не выполнен)

Заведено 2026-09-03 по итогам Stage 3.3. **Работы не начинались.**

## Зачем

История продаж и финансов в BigQuery начинается с 2026-06-01/02 — это граница
выбранного окна первичного backfill, а не предел API. Проверено вызовами:
`/v3/posting/fbo/list` отдаёт отправления примерно с апреля 2025,
`/v1/finance/accrual/by-day` — начисления примерно с сентября 2025.

## Объём

- **postings / продажи** — настолько глубоко, насколько API отдаёт стабильно;
- **финансы** — настолько глубоко, насколько API отдаёт стабильно;
- **реклама** — где доступно;
- **синтетическую историю остатков не создавать** ни при каких условиях.

## Чем выполнять

Отдельный код не требуется. `ozon-runtime-ingest` уже принимает окно:

```
ENTITIES=fbo_postings  SINCE=2025-04-01  UNTIL=2026-05-31
ENTITIES=finance_accrual  SINCE=2025-09-01  UNTIL=2026-05-31
```

Загрузка идемпотентна: MERGE по натуральному ключу, повтор дублей не создаёт.

## На что обратить внимание

1. Сначала определить фактическую нижнюю границу по каждой сущности, а не предполагать её.
2. Резать окно на части: `/v3/posting/fbo/list` отдаёт максимум 100 записей на страницу,
   финансы — один день на запрос.
3. Следить за лимитами: у финансов наблюдался HTTP 429 на частых вызовах.
4. Перекрывать границы чанков минимум на сутки — на Stage 3.1B граница чанка
   срезала 31 июля целиком.
5. После загрузки пересчитать канонические итоги и **датировать** их моментом расчёта.
