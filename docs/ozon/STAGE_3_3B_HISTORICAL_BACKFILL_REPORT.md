# Stage 3.3B — Historical Ozon Backfill: отчёт

Дата: 2026-09-03. Базовый коммит: `3feeaa426bc4a47a049fb404c8a763ff31f6bcd8`.
Периметр: только историческая глубина данных. Marts, canonical economics,
прогнозы, bidder, price automation, FBS не затрагивались.

## 1. Что обнаружено

Проверено вызовами, а не предположениями. Полный реестр —
`OZON_API_HISTORY_LIMITS_2026-09-03.md`.

Ключевое: **предела по дате у API нет**. Пустые ответы за 2024 год и январь–март

### 1.2 Два дефекта production runtime Stage 3.3

Backfill вскрыл, что `ads_sku_daily` **никогда не работал** в runtime.

**Дефект 1 — бинарный ответ читался как текст.** `common.py:_request` при
`raw_text=True` делал `body.decode("utf-8")`. Отчёт Performance API приходит
ZIP-архивом (`Content-Type: application/zip`, магия `504b0304`), строгий utf-8
на нём падает с `UnicodeDecodeError: invalid continuation byte`. Исключение
проглатывалось общим `except Exception`, крутилось 5 ретраев и возвращалось
`NET_ERROR`. В `entities.py:ads_sku_daily` это давало `c4 != 200` → `continue`.

Подпись в реестре запусков: `status=OK, rows_received=0, retry_count=5`.
Тихий no-op при зелёном статусе — худший вид отказа.

Загруженные ранее 969 строк `RAW_OZON_ADS_SKU_DAILY` (2026-06 … 2026-08) пришли
из bootstrap-скрипта Stage 3.1B, который читал `r.read()` байтами.

**Дефект 2 — прочерк в числовых колонках.** Обнажился сразу после устранения
первого: `_rub()` падал на `float('-')`. В исторических отчётах колонки
`Заказано на сумму, ₽` и `ДРР (общий), %` приходят как `-`, когда показатель
не определён. Проверочный прогон корректно упал с изоляцией отказа:
`FAILED, rows_received=0`, ни одной строки в BigQuery, порчи нет.

## 2. Почему это проблема

`ads_sku_daily` — **единственный доказанный источник расхода рекламы в разрезе
SKU**. Без него нельзя посчитать ни ДРР по артикулу, ни рекламную составляющую
себестоимости продажи, ни окупаемость отдельной карточки. При этом отказ был
невидим: расписание отрабатывало, статус был `OK`, алертов не возникало.

Второй дефект означает, что даже после устранения первого исторические месяцы
не загрузились бы: прочерк встречается в обычных данных, а не в экзотике.

## 3. Что изменено

Правки внесены по карва-ауту Q09 «runtime code unchanged **unless bugfix
absolutely required**» и согласованы с владельцем отдельно.

`pipelines/ozon/runtime/common.py` — одно слово:

```
- body.decode("utf-8")
+ body.decode("utf-8", "surrogateescape")
```

Round-trip проверен на реальном архиве до правки кода: `raw.decode(...).encode(...)`
даёт **байт в байт** исходные 4753 байта, ZIP открывается, 77 SKU-строк за
сентябрь 2025 парсятся. `entities.py` уже делал встречный
`.encode("utf-8", "surrogateescape")` — правка возвращает код к тому, что он
и предполагал.

`pipelines/ozon/runtime/entities.py` — `_rub()` возвращает `None` вместо падения
на непарсящемся значении; четыре счётчика (`Показы`, `Клики`,
`Добавления в корзину`, `Продано товаров`) получили `or 0`.

Прочерк трактуется как **NULL, а не нуль**: ДРР «не определён» и ДРР «0 %» —
разные утверждения, и подменять первое вторым нельзя.

Схемы таблиц, расписания, cadence, env job не менялись.

### Не изменено намеренно

`ads_expense_daily` использует те же `int(_rub(...))` без защиты. Эта сущность
отработала всю историю с 2025-05 без единой ошибки — прочерк в её колонках не
встречается. Проверенный код не трогался.

Загрузка шла существующим runtime через `SINCE`/`UNTIL`, staging → MERGE,
натуральные ключи и dedupe без изменений. `extracted_at` — реальный момент
извлечения, бизнес-даты исходные исторические.

Окна: postings одним окном 2025-04-01 → 2026-06-30; финансы четырьмя чанками
по ~4 месяца; реклама кампаний четырьмя чанками; реклама по SKU семью
двухмесячными окнами. Границы чанков перекрыты, чтобы не срезать сутки,
как это случилось на Stage 3.1B.

Ретраи: 7 на 446 запросов финансов (HTTP 429), все успешны. Ни одного `FAILED`
среди backfill-прогонов, кроме проверочного `ads_sku`, описанного в §1.2.

### Ограничение длины окна асинхронного отчёта

Запрос `ads_sku_daily` на окно 2026-07-01 … 2026-09-03 (65 дней) вернул **ноль
строк при статусе прогона `OK`** — молча. То же окно по частям данные отдаёт:
сентябрь отдельным запросом дал 26 строк.

Практическое правило зафиксировано в реестре глубины: **окна не длиннее двух
месяцев**. Регулярный runtime с ретроспективой 7 дней в это не упирается.
Следствие для контроля: нулевой `ads_sku_daily` при `OK` не доказывает
отсутствия данных — перепроверять более узким окном.

## 5. Остатки — синтетики нет

**STOCK_HISTORY_START = 2026-08-31**, первый реальный снимок.

Проверка: строк с `snapshot_date < 2026-08-31` — **0**. Ничего не восстанавливалось
из продаж, не интерполировалось, не достраивалось псевдо-снимками. Историю
наличия на складах и кластерах накапливаем только вперёд.

То же относится к `prices`, `catalog`, `clusters` и реестру кампаний: хранятся
только фактически полученные наблюдения, `snapshot_date` = дата вызова.

## 8. Реклама по SKU

После устранения обоих дефектов загружено семью двухмесячными окнами, все семь
прогонов `OK`, дублей 0.

`RAW_OZON_ADS_SKU_DAILY`: 969 → **3 663** строки, 17 месяцев,
**2025-05-05 → 2026-09-03**, непрерывно. 63 кампании, 22 SKU.

Полная помесячная атрибуция — в `OZON_HISTORICAL_COVERAGE_2026-09-03.md`.
Сводно: residual **0,2 – 39,0 %**, медиана около 4 %.

Остаток объясним и требовать нуля нельзя: асинхронный отчёт атрибутирует на SKU
только расход, привязанный к конкретной карточке. Расход кампаний без товарного
трафика в окне, медийные размещения и абонентские списания в SKU-разрез не попадают.

**Два месяца требуют внимания: 2025-11 (residual 39,0 %, 14 044,60 ₽) и
2025-12 (28,6 %, 7 337,54 ₽).** Обе стороны загружены, дублей нет — это не пробел
загрузки. До разбора рекламную составляющую себестоимости за ноябрь–декабрь 2025
нельзя считать полностью разложенной по SKU. Разбор — за пределами Stage 3.3B.

## 9. Наблюдение по финансам, требующее внимания

Помесячная разбивка по типам (`finance_by_type_monthly.csv`) показывает разрыв:
тип **41 CPC_MEDIA** появляется только с сентября 2025, хотя рекламный расход
по данным Performance API есть с мая 2025 (32 346 ₽ за май). За май–август 2025
рекламные списания в финансах проходили иначе — заметная часть под типом
**54 SEARCH_PROMO_CPO**, но суммы не сходятся с расходом кампаний.

Это **не дефект загрузки**: строки загружены как отдано API. Но при построении
canonical economics нельзя считать тип 41 единственным носителем рекламного
расхода на всей истории. Разбор оставлен за пределами Stage 3.3B.

Тип **116 FirstCustomerReview** появляется только с июля 2026 — новый вид
удержания, а не пробел в данных.

## 10. Что осталось

Пробелов в загрузке не осталось: все сущности с исторической глубиной загружены
до фактического начала торговли, покрытие помесячно непрерывно.

Открытые вопросы за периметром Stage 3.3B:

- **Финансовая атрибуция рекламы за май–август 2025** (§9) — тип 41 появляется
  только с сентября 2025; разобрать при проектировании canonical economics.
- **Residual SKU-атрибуции за 2025-11 и 2025-12** (§8) — 39 % и 28,6 %,
  заметно выше медианных 4 %.
- **История остатков** восстановлению не подлежит. Накапливается вперёд
  с 2026-08-31.
- **Проверка регулярного `ads_sku_daily`** — теперь он впервые реально грузит
  данные; стоит убедиться на ближайших плановых прогонах, что ретроспектива
  в 7 дней отрабатывает штатно.
