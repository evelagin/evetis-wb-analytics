## 3. Точные мутации — ровно четыре оператора

Порядок обязателен: витрина Ozon перестраивается раньше своего потребителя.

```
1. CREATE OR REPLACE VIEW ozon_mart.FCT_OZON_SKU_PNL_DAILY     ← sql/current/ozon_mart/FCT_OZON_SKU_PNL_DAILY.sql
2. CREATE OR REPLACE VIEW ozon_mart.FCT_OZON_SKU_PNL_MONTHLY   ← sql/current/ozon_mart/FCT_OZON_SKU_PNL_MONTHLY.sql
3. CREATE OR REPLACE VIEW ozon_mart.FCT_OZON_PNL_MONTHLY       ← sql/current/ozon_mart/FCT_OZON_PNL_MONTHLY.sql
4. CREATE OR REPLACE VIEW wb_mart.V_CT_ACTUAL_DAILY_LIVE       ← sql/control_tower/ct_ubr012_revenue_2026-09-22.sql
```

Ничего сверх этих четырёх. Никаких DML, никаких изменений расписаний, IAM, секретов,
Cloud Run и `CT_CONFIG`.

## 4. Стратегия пересборки CT_ACTUAL_DAILY

Проверка `T10` читает **материализованную** `evetis_ref.CT_ACTUAL_DAILY`, а не живую вью,
поэтому до пересборки она останется красной — это корректный результат, а не провал
развёртывания.

`sp_ct_refresh_daily()` на шаге 0 сравнивает отпечаток источников с последним успешным
прогоном за сегодня. Замена тела вью отпечаток **не меняет**, поэтому немедленный `CALL`
вернёт `guard_skip` — ровно это наблюдалось в UBR-010, и это правильное поведение защиты.

**Выбранный путь — естественная сходимость.** Отпечаток включает `extracted_at`
`RAW_OZON_POSTINGS_FBO`; загрузка Ozon идёт по расписанию, поэтому на ближайшем окне
(07:40 / 09:40 / 12:40 / 16:40 / 19:40 МСК) отпечаток изменится сам и таблица перестроится.
Ожидание — не более одного рабочего дня.

**Путь принудительной пересборки НЕ выбран.** `CT_CONFIG.refresh_force = '1'` — штатное,
самосбрасывающееся переопределение, но это запись в production вне списка §3, и владелец
явно запретил обходить защиту без отдельного разрешения. Если немедленная сходимость нужна,
это отдельный ACK на одну строку DML.

# ⚠️ ИНЦИДЕНТ 2026-09-22: развёртывание сломало плановую пересборку Control Tower

Статус: **production повреждён, откат заблокирован правами агента, требуется решение владельца.**

## И1. Что произошло

Оба окна пересборки после развёртывания упали. Это **не** `guard_skip`, а `ERROR`:

```
16:40 МСК  CT_ACTUAL_DAILY  ERROR
19:40 МСК  CT_ACTUAL_DAILY  ERROR
Access Denied: Table …ozon_mart.FCT_OZON_SKU_PNL_DAILY:
User does not have permission to query table … at [sp_ct_refresh_daily:58:5]
```

Причина — прямое следствие оператора 4. Новое тело `V_CT_ACTUAL_DAILY_LIVE` читает
`ozon_mart.FCT_OZON_SKU_PNL_DAILY`, а у сервисного аккаунта пересборки доступа к этому
датасету нет вовсе:

| датасет | доступ `sa-ct-refresh` |
| --- | --- |
| `wb_mart` | READER |
| `ozon_raw` | READER |
| `evetis_ref` | READER |
| **`ozon_mart`** | **нет на уровне датасета** |

Разница зависимостей старого и нового тела — ровно один объект: добавился
`ozon_mart.FCT_OZON_SKU_PNL_DAILY`.

## И2. Радиус шире выручки

Процедура прерывается на шаге 2, поэтому шаги 3 и 4 **не выполняются** с 12:41 МСК:

- `CT_ACTUAL_DAILY` не перестраивается (несёт состояние 12:41);
- `CT_INVENTORY_SNAPSHOT_DAILY` — партиция за сегодня не заменяется;
- `sp_ct_generate_actions()` — очередь действий владельца не обновляется.

## И3. Почему проверки этого не поймали

Я проверил новую вью под правами владельца — и она корректна: сверка сошлась по всей
цепочке, 12/12 + 11/11 + 10/10 зелёные. Но плановая пересборка исполняется **другой
личностью**, `sa-ct-refresh`, и под ней вью неисполнима.

Дефект манифеста, а не только кода: в §5 не было постпроверки «пересборка успешно
выполняется под собственной учётной записью». Любая будущая миграция, добавляющая
Control Tower зависимость на новый датасет, обязана такую проверку содержать.

## И4. Два средства — выбор за владельцем

**A. Выдать доступ и сохранить исправление.** Дать `sa-ct-refresh` роль READER на
`ozon_mart` (либо точечно на `FCT_OZON_SKU_PNL_DAILY`). Это IAM-мутация вне списка §3,
поэтому без отдельного ACK не выполняется. После гранта — дождаться окна 07:40 МСК.

**B. Откатить оператор 4.** `sql/ozon/ubr012_revenue_2026-09-22/rollback_V_CT_ACTUAL_DAILY_LIVE.sql`
восстанавливает тело, работавшее в 12:41 (читает только `ozon_raw`, ссылок на `ozon_mart`
нет). Пересборка чинится, но дефект выручки +12 788,84 ₽ возвращается.

Три оператора `ozon_mart` (fail-closed) откатывать не нужно ни в одном варианте: они
экономику не меняют, в пересборке не участвуют и остаются корректными.

Попытку выполнить вариант B агент предпринял, но она отклонена классификатором прав
(«Modify Shared Resources»). Обход не предпринимался.

# Инцидент устранён, UBR-012 закрыт — 2026-09-22

## В1. Выбранный грант и почему именно он

**Dataset-level READER на `ozon_mart` для `sa-ct-refresh`** — вариант 2 из решения владельца.

Точечный table-level грант отвергнут по факту, а не по удобству: развёрнутая
`FCT_OZON_SKU_PNL_DAILY` сама читает `ozon_mart.V_OZON_CIS_BUYOUT`, поэтому точечная
модель потребовала бы **двух** записей и ломалась бы при любой новой внутренней
зависимости витрины. Кроме того, в проекте нет ни одного table-level гранта: все
доступы сервисных аккаунтов во всех пяти датасетах — уровня датасета. Точечный вариант
создал бы единственную нестандартную конфигурацию в модели доступа.

Выданная роль совпадает с тем, что у этого же аккаунта уже есть на `wb_mart`,
`ozon_raw` и `evetis_ref`.

## В2. IAM до и после

| | `ozon_mart` |
| --- | --- |
| до | 5 записей: `projectWriters` WRITER, `projectOwners` OWNER, `evelagin@gmail.com` OWNER, `projectReaders` READER, `sa-loaders-prod` READER |
| после | те же 5 + **`sa-ct-refresh` READER** |

Различие: добавлена ровно одна запись, не удалено ничего. `wb_mart`, `ozon_raw`,
`evetis_ref`, `evetis_mart` — побайтно идентичны снимкам «до». Права на запись не
выдавались: `READER` даёт `tables.getData`, но не `tables.updateData`.

Откат гранта подготовлен и применяет сохранённый ACL дословно:
`scratchpad/iam_grant.py rollback` ← `iam/before_ozon_mart.json`.

## В3. Проверка доступа от имени runtime identity

Имперсонация `sa-ct-refresh` недоступна (у владельца нет
`roles/iam.serviceAccountTokenCreator`), и выдавать это право не потребовалось.
Вместо этого использован **штатный путь**: `gcloud scheduler jobs run ct-refresh-prod`
— то же задание, та же identity, тот же механизм, без изменения `CT_CONFIG`, guard
и любых production settings.

Задания BigQuery за окно прогона: **3 под `sa-ct-refresh`, ошибок 0.**

## В6. Две проверки исправлены — это уточнение, а не ослабление

Первый прогон после пересборки дал 2 FAIL в моём же наборе. Обе — дефекты проверок:

- **U01** ловила любую обычную продажу, по которой начисление ещё не пришло. Условие
  `payout_rub = 0` было опущено, а именно оно отличает выкуп от такой продажи и именно
  его использует классификатор витрины. После сужения настоящий незарегистрированный
  выкуп по-прежнему роняет ворота.
- **U08** предполагала, что начисления приходят мгновенно, и ломалась о первую же
  продажу в лаге. Тождество дополнено третьим компонентом, который выводится отдельной
  колонкой, а не прячется.
- Добавлена **U13**: каждая строка, оценённая ценой заказа, обязана быть посчитана в
  `commission_missing_qty`, и ни одна из них не должна иметь сигнатуру выкупа. Цена
  заказа не может примениться молча.

## В7. Дефект процесса развёртывания оформлен

Правило внесено в `docs/architecture/DEFINITION_OF_DONE.md`: миграция, добавляющая
зависимость на новый датасет, обязана до первой мутации доказать доступ от имени
фактической runtime identity; проверка под правами владельца не засчитывается.

Машинная проверка — `tools/check_runtime_access.py` + реестр
`quality/runtime_identities.json`. Только чтение ACL, ненулевой код выхода блокирует
развёртывание. Тест `tools/tests/test_check_runtime_access.py` доказывает, что
инструмент видит именно ту зависимость, которая сломала production, и что откатное
тело её не имеет.
