**Включает ли СПП — проверено на данных, а не по названию поля.** Отношение
buyer/seller монотонно падает с ростом СПП:

| корзина `spp` | строк | по цене продавца | по цене покупателя | доля |
| --- | ---: | ---: | ---: | ---: |
| 0 | 124 | 61 363,84 | 60 944,71 | 99,32 % |
| < 10 | 193 | 104 316,68 | 97 558,08 | 93,52 % |
| 10–20 | 30 | 39 212,00 | 32 949,00 | 84,03 % |
| ≥ 20 | 166 | 158 266,66 | 95 732,50 | 60,49 % |

Формула `price_with_disc × (1 − spp/100)` воспроизводит `finished_price` лишь на
94 строках из 513 — поэтому **производная величина не строилась**: показывается
само поле WB, а не реконструкция.

🔴 **Смешения универсумов нет.** `sales_revenue_buyer_paid_rub` — operational, база
даты «дата продажи». Это **не** «Вайлдберриз реализовал Товар (Пр)» = 287 114,04 ₽:
та величина settlement, база даты «дата финансового отчёта», другой универсум строк.
Близость чисел (delta 70,25) — следствие того, что обе измеряют одно и то же
экономическое явление на разных базах, а не признак их тождественности.

**Решение по показу.** Метрика выведена **дополнительно**, secondary-размером, под
выручкой по цене продавца. Seller-base **не подменена**: комиссия WB, ДРР и обе
рентабельности считаются от неё, и если сделать buyer-paid главным KPI, деление
показанного результата на показанную выручку перестанет давать показанную
рентабельность (−26 183 / 287 184 = −9,12 %, а на экране −7,21 %). Две разные
revenue-семантики носят **разные названия**: «Выручка по цене продавца» и
«Продажи по цене покупателя».

### A2 — формат чисел

Metabase v0.63.15.1 штатно поддерживает `prefix`/`suffix` в `column_settings` для
числовых колонок. Переход с `number_style: currency` (символ слева) на
`number_style: decimal` + `suffix: " ₽"` даёт требуемый вид **без CSS и хаков**.

Проверено не глазами, а собственным форматтером Metabase — экспорт с
`--format-rows` возвращает ровно те строки, что рисует UI:

```
363 159 ₽    287 184 ₽    93 151 ₽    -26 183 ₽    25,65%    -7,21%
```

🔴 **Ограничение.** Metabase печатает обычный дефис-минус `-`, а не типографский
`−` (U+2212). Штатной настройки знака минуса в v0.63 нет; поэтому
`-26 183 ₽`, а не `−26 183 ₽`. Хак ради одного символа не делался.

## 5. Расходы и корректировки — мост вместо смешанного bar chart

Карточка **51**: «Структура затрат за период» → **«Расходы и корректировки периода»**,
display `row` → **`waterfall`**.

**Проблема прежнего вида:** в одном bar chart соседствовали расходы, кредиты
(показанные отрицательными столбцами) и control-only величины. Пользователь
естественно складывал их и получал несуществующую сумму.

**Знаковое правило моста — одно на все статьи:** `шаг = −значение источника`.
Оно не выводится «по смыслу статьи» и не требует ручных исключений — поэтому
кредиты WB поднимают мост вверх автоматически, а не изображаются «отрицательным
расходом». Metabase красит рост и падение разными цветами.

Мост за 27.07–23.08.2026 (накопление проверено в BigQuery):

| шаг | ₽ | накопленное |
| --- | ---: | ---: |
| Выручка | 363 159,18 | 363 159,18 |
| Комиссия WB | −164 683,60 | 198 475,58 |
| Логистика | −37 529,30 | 160 946,28 |
| Реклама | −50 194,07 | **110 752,21** ← доход до себестоимости |
| Хранение | −9 992,46 | 100 759,75 |
| Штрафы | −6 320,00 | 94 439,75 |
| Транзит поставок | −3 258,94 | 91 180,81 |
| Мин. платёж | −1 714,74 | 89 466,07 |
| Утилизация | −38,00 | 89 428,07 |
| Возмещения WB | **+794,79** | 90 222,86 |
| Баллы за отзывы | **+2 928,00** | **93 150,86** ← результат до себестоимости |
| Себестоимость товара | −119 334,00 | **−26 183,14** ← итог |

Мост сходится к копейке, и обе контрольные точки — 110 752,21 и 93 150,86 —
возникают как промежуточные суммы, а не как отдельно посчитанные величины.

Все статьи берутся на сутках своего гейта (`period_result_eligible`,
`after_product_cogs_eligible`), поэтому мост сходится не только на этом окне.
Нулевые статьи периода не выводятся; приёмка, прочее WB, неопознанные и
конфликтные удержания за окно равны нулю и в мосте отсутствуют.
