# UNITKA CALENDAR V2 — динамическая месячная секция и подготовка месяца (Phase 2B)

Статус: **код и офлайн-тесты. В Google Sheets ничего не записано, октябрь НЕ создан, деплоя нет.**
Решения владельца: Phase 2A (дизайн) + Phase 2B (COGS нового блока из канона; слот 24 зарезервирован;
способ тестовой копии — в Phase 2C).

## 1. Что было

Engine знал только сентябрь 2026: `GRID` = строки 735/737..766/767, 30 дней, 24 блока. С 02.10 (LCD = 01.10)
прогон останавливался кодом `MONTH_ROLLOVER_REQUIRED`. BigQuery-слой уже месяце-независим
(`DATE_TRUNC(last_closed_date, MONTH)`) — SQL не менялся.

## 2. Модель месяца

Лист `WB_Юнит_2025` — секции месяцев сверху вниз (январь 2025 … сентябрь 2026). Секция:

| строка | что |
|---|---|
| `topRow` | A: «<Месяц> <год>» (объединение A:K), заголовки блоков «nmID Название» |
| `topRow + 1` | шапка метрик («Дата» в B и в колонке даты каждого блока) |
| `topRow + 2 … + days + 1` | дни месяца (28/29/30/31 — только `daysInMonth`, `Date.UTC`) |
| `lastDailyRow + 1` | MTD («MTD ACTUAL» в колонке даты первого блока) |
| `mtdRow + 1` | разделитель; следующий месяц — сразу за ним (шаг `days + 4`, подтверждён на 21 секции) |

Сентябрь 2026 — просто одна из секций (A735). Октябрь 2026: **769 / 770 / 771..801 / 802 / 803**.

Модуль `cloud/src/loaders/unitka/calendar.ts`: `daysInMonth`, `nextMonth`/`previousMonth`, заголовок,
`geometryAt(key, topRow)`, `MonthLayout` (геометрия + блоки), поиск секции `locateSection`.

## 3. Слоты блоков

Слот `s` = колонки `13 + 24·s … +23`. **Слот 24 (VQ..WN) зарезервирован навсегда**: там унаследованные
расчёты VQ..VZ, подписи WA736/737 и якоря книги WB736..WB739. Блок 25 — **слот 25 = WO..XL (613..636)**,
дальше 26, 27… Выбывший SKU оставляет слот пустым; новые SKU — по возрастанию nm_id в слоты ПОСЛЕ последнего
занятого (освободившийся слот не переиспользуется: ширины и скрытие колонок в Sheets общие для листа).

Уточнение к Phase 2A: колонка WB (600) — это колонка X (реклама) **зарезервированного** слота 24, а не блока 25.
В строках октября она пуста, но через неё проходит сводная полоса `J = SUM(FILTER(X…,MOD(…,24)=0))`.

## 4. Якоря книги

`BOOK_ANCHORS` (`model.ts`): WB736 зеркало LCD, WB737 `REVERSE_LEG_RATE`, WB738/WB739 статус Guard (резерв).
Фиксированы, от месяца не зависят. Ячейка плана — якорь **только по виду** (`lcd`/`reverse`), никогда по
колонке; регрессионный тест: ячейка (771, 600) читается из сетки, а не из зеркала.

## 5. Суточный Engine (`unitka-engine/2.0.0`)

1. LCD (BigQuery, МСК) → месяц → ровно один заголовок в колонке A (`section.ts`):
   нет — `MONTH_SECTION_MISSING`; два — `MONTH_SECTION_AMBIGUOUS`; не помещается в сетку — `MONTH_SECTION_INVALID`.
2. Снимок секции по её геометрии; `preflight` проверяет контракт секции (заголовок, шапка, даты ровно дней месяца,
   «MTD ACTUAL», уникальные nmID, «слот с шапкой, но без nmID») → `MONTH_SECTION_INVALID`; формулы → `STRUCTURE_DRIFT`.
3. Всё — до любой записи. **Месяц Engine не создаёт никогда.** `MONTH_ROLLOVER_REQUIRED` из пути выведен.
4. Предпроверка: если до конца месяца LCD ≤ `UNITKA_MONTH_PREP_WINDOW_DAYS` (5) дней и следующего месяца нет —
   предупреждение `NEXT_MONTH_SECTION_MISSING` (лог + `qa_json.calendar`); прогон не падает.
5. Экономика не менялась: формулы, ставки, QA, Guard — те же; меняются только строки/колонки.

## 6. Подготовка месяца (`unitka-month-prep`)

Отдельный загрузчик (реестр), **не активирован**: нет расписания, нет шага деплоя.

* **ПЛАН по умолчанию.** Запись — только `ENVIRONMENT=prod` **и** `UNITKA_MONTH_PREP_WRITE=1` **и** явный
  `UNITKA_MONTH_PREP_TARGET=YYYY-MM`. `UNITKA_WRITE_ENABLED` права не даёт. В shadow шлюз readonly —
  `structureWrite` отказывает до HTTP.
* Планировщик (`monthprep.ts`, чистый): предыдущий месяц (последняя секция листа) + активные SKU WB
  (`REF_SKU_MASTER`, то же определение, что в `V_UNITKA_DAILY_FACT`) + канон COGS.
* Формулы — явные построители (`formulas.ts`), **не** текст XLSX. Перед созданием планировщик доказывает, что
  построители воспроизводят формулы последнего дня, MTD и сводки предыдущего месяца символ в символ; иначе
  `TEMPLATE_MISMATCH`. Для каждого блока переносятся ровно как были: слагаемое COGS (240 через `$R$45`, нули —
  не исправляются), константа внешней рекламы в Y (10/100), вид проекции остатка/хранения.
* Первый день месяца — без проекции остатка (никаких ссылок на прошлый месяц).
* СПП и блогеры — пустые (ручной ввод); СПП из прошлого месяца не копируется.
* Запрос batchUpdate: `appendDimension` (строки/колонки) → `copyPaste PASTE_FORMAT` (день 1 ← эталон закрытого
  дня, дни 2..N ← последний день, новый блок ← последний блок) → `updateCells` (`formulaValue`) → заметки →
  `mergeCells`. Всё — не выше заголовка нового месяца (предохранитель `assertPlanConfined`).
* Идемпотентность: месяц есть и проходит контракт → `NO_CHANGE`, 0 запросов; неполный → `MONTH_SECTION_PARTIAL`;
  нарушен контракт → `MONTH_SECTION_INVALID`; авто-починки нет.

### COGS нового блока

Только из канона `wb_mart.V_UNITKA_COGS_CANONICAL` (копия `UNITKA_COGS_EFFECTIVE`): последний день копии с
положительным значением. Нет значения → `COGS_MISSING`; копия устарела → `COGS_STALE`; недоступна →
`COGS_UNAVAILABLE` — месяц не готовится, 0 не подставляется. Происхождение (nm_id, значение, дата, время
публикации, run) — в плане, в логе и заметкой на ячейке AI первого дня блока. Для 909951444 на 18.09 канон =
426.735 — значение берётся из данных, особого случая в коде нет.

## 7. Популяция (V1)

Снимок активных SKU на момент подготовки; после принятия раскладка заморожена.

* Новый SKU посреди месяца — блока нет до следующего месяца; Guard: `SKU_WITHOUT_BLOCK`; повторная подготовка
  того же месяца — `NO_CHANGE` с отчётом `unmapped_active`.
* **Ограничение V1:** SKU, выведенный из `REF_SKU_MASTER` посреди месяца, лишается строк в
  `V_UNITKA_DAILY_FACT` → Engine падает `BLOCK_MISSING` (fail-closed). Операционное правило: выводить SKU с
  1-го числа следующего месяца (после подготовки месяца он получит пустой слот). SQL в Phase 2B не менялся.
