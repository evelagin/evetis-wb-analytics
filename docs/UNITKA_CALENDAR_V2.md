## 2. Модель месяца

Лист `WB_Юнит_2025` — секции месяцев сверху вниз (январь 2025 … сентябрь 2026). Секция:

| строка | что |
|---|---|
| `topRow` | A: «<Месяц> <год>» (объединение A:K в прошлых месяцах, A:L в секциях Calendar V2), заголовки блоков «nmID Название» |
| `topRow + 1` | шапка метрик («Дата» в B и в колонке даты каждого блока) |
| `topRow + 2 … + days + 1` | дни месяца (28/29/30/31 — только `daysInMonth`, `Date.UTC`) |
| `lastDailyRow + 1` | MTD («MTD ACTUAL» в колонке даты первого блока) |
| `mtdRow + 1` | разделитель; следующий месяц — сразу за ним (шаг `days + 4`, подтверждён на 21 секции) |

Сентябрь 2026 — просто одна из секций (A735). Октябрь 2026: **769 / 770 / 771..801 / 802 / 803**.

Модуль `cloud/src/loaders/unitka/calendar.ts`: `daysInMonth`, `nextMonth`/`previousMonth`, заголовок,
`geometryAt(key, topRow)`, `MonthLayout` (геометрия + блоки), поиск секции `locateSection`.

## 3. Слоты блоков — сплошная цепочка

Слот `s` = колонки `13 + 24·s … +23`. **Блоки идут сплошной цепочкой, без зарезервированных слотов и дыр**
(решение владельца, visual hardening 2 — заменяет решение Phase 2B «слот 24 зарезервирован»). Новый SKU встаёт
сразу за последним блоком: планировщик вставляет 24 колонки (`insertDimension`) перед «хвостом» книги —
унаследованными расчётами VQ..VZ (скрыты, своя группа колонок), подписями WA и якорями WB736..739. Хвост целиком
сдвигается вправо; в октябре 2026 блок 25 (909951444) = **VQ..WN (589..612)**, хвост = WO..WZ, якоря = **WZ736..739**.
Инвариант: `следующий.start = предыдущий.end + 1`; дыра в цепочке (выбыл SKU из середины) — `BLOCKED CHAIN_GAP`,
решение владельца, авто-сдвига блоков нет.

Побочный эффект вставки, снятый в генераторе: Sheets расширяет диапазоны УФ, кончающиеся ровно на колонке перед
вставкой (в живой книге — правило выходных и «будущий день» блока 24, оба до VP). Их формулы привязаны к первому
диапазону правила, во вставленных колонках ссылаются за край листа (`WEEKDAY(пусто)=6`) — сентябрь получил бы
сплошную полосу на месте нового блока. Планировщик переиздаёт такие правила сразу за вставкой в исходных
диапазонах (`cfInsertTrims`, ссылки формул сдвигаются как у Sheets — `shiftColumnRefs`); формула со ссылкой на
другой лист — `BLOCKED CF_TRIM_UNSAFE`. Остальные правила прошлых месяцев не адресуются.

## 4. Якоря книги

`BOOK_ANCHORS` (`model.ts`) задаёт только СТРОКИ: 736 зеркало LCD, 737 `REVERSE_LEG_RATE`, 738/739 статус Guard
(резерв). **Колонку якорей Engine находит по именованному диапазону `REVERSE_LEG_RATE`** (`resolveAnchorCol`:
одна ячейка в строке 737 листа Unitka, иначе `ANCHOR_UNRESOLVED`) — при вставке колонок Sheets сам сдвигает и
диапазон, и ссылки формул/УФ/`ZZ_QA` (`$WB$736` → `$WZ$736`; проверено на копии: 32 ссылки УФ, 166 строк формул
прошлых месяцев отличаются от предснимка только этим сдвигом). Ячейка плана — якорь **только по виду**
(`lcd`/`reverse`), никогда по колонке. Поиск по активному коду (`600`, `WB`, `MIR`, `REVERSE_LEG_RATE`): в `cloud/src/loaders/unitka` константы колонки нет
— `REVERSE_LEG_RATE` встречается только как ИМЯ диапазона (формулы и `resolveAnchorCol`), остальное — комментарии;
тест `unitka_anchor_contract.test.ts` держит это (скан исходников, якорь 600 → 624 → 648, отказ `ANCHOR_UNRESOLVED`,
запись зеркала LCD в найденную колонку, поиск блоков после вставки). Жёсткая колонка 600 / `$WB$736` осталась только
в спящем наследии Apps Script (`UnitkaS8*.gs`, `UnitkaR75.gs`, `Код.gs` — ручные `s82data`/`s8rates`/`s82lcd` и их
откаты; не запускаются с «UNITKA ENGINE v1 PRODUCTION READY»), в тестах и документах. Контракт выката — §10.

## 5. Суточный Engine (`unitka-engine/2.0.0`)

1. LCD (BigQuery, МСК) → месяц → ровно один заголовок в колонке A (`section.ts`):
   нет — `MONTH_SECTION_MISSING`; два — `MONTH_SECTION_AMBIGUOUS`; не помещается в сетку — `MONTH_SECTION_INVALID`.
2. Снимок секции по её геометрии; `preflight` проверяет контракт секции (заголовок, шапка, даты ровно дней месяца,
   «MTD ACTUAL», уникальные nmID, «слот с шапкой, но без nmID») → `MONTH_SECTION_INVALID`; формулы → `STRUCTURE_DRIFT`.
3. Всё — до любой записи. **Месяц Engine не создаёт никогда.** `MONTH_ROLLOVER_REQUIRED` из пути выведен.
4. Предпроверка: если до конца месяца LCD ≤ `UNITKA_MONTH_PREP_WINDOW_DAYS` (5) дней и следующего месяца нет —
   предупреждение `NEXT_MONTH_SECTION_MISSING` (лог + `qa_json.calendar`); прогон не падает.
5. Экономика не менялась: формулы, ставки, QA, Guard — те же; меняются только строки/колонки.

## 6. Подготовка месяца (`unitka-month-prep`)

Отдельный загрузчик (реестр), **не активирован**: нет расписания, нет шага деплоя.

* **ПЛАН по умолчанию.** Запись — только `ENVIRONMENT=prod` **и** `UNITKA_MONTH_PREP_WRITE=1` **и** явный
  `UNITKA_MONTH_PREP_TARGET=YYYY-MM`. `UNITKA_WRITE_ENABLED` права не даёт. В shadow шлюз readonly —
  `structureWrite` отказывает до HTTP.
* Планировщик (`monthprep.ts`, чистый): предыдущий месяц (последняя секция листа) + активные SKU WB
  (`REF_SKU_MASTER`, то же определение, что в `V_UNITKA_DAILY_FACT`) + канон COGS.
* Формулы — явные построители (`formulas.ts`), **не** текст XLSX. Перед созданием планировщик доказывает, что
  построители воспроизводят формулы последнего дня, MTD и сводки предыдущего месяца символ в символ; иначе
  `TEMPLATE_MISMATCH`. Для каждого блока переносятся ровно как были: слагаемое COGS (240 через `$R$45`, нули —
  не исправляются), константа внешней рекламы в Y (10/100), вид проекции хранения. Проекция остатка — исключение:
  в создаваемом месяце она у КАЖДОГО блока с защитой `LAST_CLOSED_DATE` (см. §8), форма прошлого месяца только
  распознаётся для доказательства шаблона.
* Первый день месяца — без проекции остатка (никаких ссылок на прошлый месяц).
* СПП и блогеры — пустые (ручной ввод); СПП из прошлого месяца не копируется.
* Один `batchUpdate`: `insertDimension` (колонки новых блоков) → переиздание расширенных правил УФ (§3) →
  `appendDimension` (строки) → сброс унаследованных форматов во вставленных колонках → форматы строк-шаблонов +
  контракт границ (`repeatCell`) → значения и формулы в локали книги → заметки COGS → `mergeCells` → УФ из
  визуального контракта → размеры → группы колонок. `copyPaste` не используется. Предохранитель
  `assertPlanConfined`: всё — не выше заголовка нового месяца, кроме вставленных колонок и переизданных правил.
* Идемпотентность: месяц есть и проходит контракт → `NO_CHANGE`, 0 запросов; неполный → `MONTH_SECTION_PARTIAL`;
  нарушен контракт → `MONTH_SECTION_INVALID`; авто-починки нет.

### COGS нового блока

Только из канона `wb_mart.V_UNITKA_COGS_CANONICAL` (копия `UNITKA_COGS_EFFECTIVE`): последний день копии с
положительным значением. Нет значения → `COGS_MISSING`; копия устарела → `COGS_STALE`; недоступна →
`COGS_UNAVAILABLE` — месяц не готовится, 0 не подставляется. Происхождение (nm_id, значение, дата, время
публикации, run) — в плане, в логе и заметкой на ячейке AI первого дня блока. Для 909951444 на 18.09 канон =
426.735 — значение берётся из данных, особого случая в коде нет.

## 7. Популяция (V1)

Снимок активных SKU на момент подготовки; после принятия раскладка заморожена.

* Новый SKU посреди месяца — блока нет до следующего месяца; Guard: `SKU_WITHOUT_BLOCK`; повторная подготовка
  того же месяца — `NO_CHANGE` с отчётом `unmapped_active`.
* **Ограничение V1:** SKU, выведенный из `REF_SKU_MASTER` посреди месяца, лишается строк в
  `V_UNITKA_DAILY_FACT` → Engine падает `BLOCK_MISSING` (fail-closed). Операционное правило: выводить SKU с
  1-го числа следующего месяца (после подготовки месяца он получит пустой слот). SQL в Phase 2B не менялся.

## 8. Визуальный контракт секции месяца (Phase 2C hardening, 19.09.2026)

Источник — живой лист через Sheets API (`userEnteredFormat`, `effectiveFormat`, `conditionalFormats`),
тестовая копия книги (строки 1–768 идентичны оригиналу). Модуль `visual.ts`.

**Семантика колонок блока** (карта UNITKA 2.0): дата (0), день недели (23); ручной ввод — блогеры (1), СПП (15);
факт Engine — показы, переходы, заказы, корзина, отмены, остаток, внутренняя реклама, цена, хранение
(2–7, 11, 14, 20); ставки — комиссия (17), логистика (19); расчёт — остальное. Сводка: A/L день недели,
B дата, C Σ блогеров (окрашена как ручной ввод), D–H и J факт-суммы, I и K расчёт.

**Два вида строки дня.** Пустой будущий день: без заливки у факта, ставок и расчёта (ручной ввод — жёлтая зона
ввода, как всегда), серый текст (УФ). Закрытый день со значением: заливка факта зелёная `#f1f8f4` (цена —
жёлтая `#fffbe8`), ставок — голубая `#f3f8fd`, чёрный текст; пропуск источника (пустая ячейка закрытого дня)
остаётся белым. Заливка закрытого дня — правило УФ «день ≤ LAST_CLOSED_DATE и ячейка не пуста», а не
статический формат: статический формат всех строк дней одинаков (эталон E3 = первый день) — контракт
формата закрытого дня Engine выполняется без перекраски (проверено: 4 прогона Engine на копии, 0 перекрасок,
кроме ячейки, которую сам Engine очистил как GAP и затем заполнил — это штатный E3).

**Выходные.** Суббота и воскресенье по дате строки (`=WEEKDAY($B<r>;2)>5`): заливка `#fcefe3` на ячейке даты и
дня недели сводки (A, B, L) и каждого блока (смещения 0 и 23). Не вся строка. В живом сентябре это работало
только у A, B и дня недели блока 1: формулы `=WEEKDAY(US737;2)>5` записаны относительно первого диапазона
правила (B / AJ), и для остальных диапазонов ссылка уезжает в чужие колонки (пустая → `WEEKDAY(0)=6` →
«выходной» каждый день). Sheets применяет формулу УФ относительно верхней-левой ячейки ПЕРВОГО диапазона
правила — проверено на копии.

**Правило независимости от якоря.** Формулы УФ используют только абсолютные колонки (`$B`, `$WB$736`), строку
первого дня секции (у всех диапазонов правила одинаковые строки) и идиому «эта ячейка»
`INDEX($A<r>:$<last><r>;1;COLUMN())` / «колонка целиком» `INDEX($A$<f>:$<last>$<l>;0;COLUMN())` (COLUMN() и
INDEX вычисляются по каждой ячейке — проверено на копии). Ни одной относительной ссылки на колонку (тест).

**Порядок правил = приоритет** (Sheets применяет первое совпавшее логическое правило; шкала и логическое
правило с цветом текста складываются): уровни доли от максимума колонки (корзина, реклама, заказы; 4 × 3) →
выходные → будущее (серый текст, сводка A..K + весь блок) → шкала доходности (сводка I и каждый блок) →
оборачиваемость (≤15 / 15–30 / 30–60 / >60) → знак доходности на 1 шт → знак доходности → отмены тревожны →
шкалы корзины и доходности на 1 шт → отрицательная доходность, ДРР > 20 %, «показы есть — заказов нет» →
заливка закрытого дня (факт / цена / ставки). 108 правил на 25 блоков; правила предыдущего месяца НЕ копируются.
Наследие сентября, которое не переносится: шкалы на строках заголовка/шапки и парные правила `D<>""`/`D=""`
одного цвета (визуальные no-op).

**Сводка A..L — один блок (hardening 2).** Колонка L (день недели справа) входит в сводку: заголовок месяца
объединён A:L, контур сводки — жирная линия слева от A и справа от L, L берёт вид колонки A (шапка, MTD, план),
правила «выходные» и «будущее» включают L. В сентябре L стояла вне контура A:K — в октябре она выглядела
оторванной лесенкой.

**Контракт границ (`borderSpec`)** — границы не копируются со строки-шаблона: строка первого дня несёт
разделитель шапки (MEDIUM сверху), и его копия на каждый день давала «тяжёлую решётку». Вторая причина тяжести
(final polish): в живом сентябре сетка дня — 1 px чёрным (цвет темы TEXT) на всех четырёх сторонах КАЖДОЙ ячейки,
но под статической заливкой и плотным содержимым; в созданном месяце будущие дни нейтрально белые, и та же чёрная
линия читается сплошной «клеткой». Все тонкие линии октября были созданы генератором, ни одна не обязательна.
Контракт: обычная ячейка дня — волосяная светлая сетка `#d9d9d9` (цвет, близкий к сетке листа); сильные линии —
только смысловые разделители, и больше нигде (тест перечисляет их поимённо): контур сводки A..L (THICK чёрная),
«дата | данные» (MEDIUM чёрная: B|C в сводке, дата | блогеры в блоке), SKU | SKU (MEDIUM `#5f6368`). У общей грани
один владелец: горизонталь между днями — верх НИЖНЕЙ строки, над первым днём — линия шапки (тип строки `dayFirst`,
отдельная полоса форматов), под последним — верх MTD; ни у одного дня нет линии снизу и MEDIUM/THICK сверху.
Шапка (THIN `#9aa0a6`), MTD (рамка MEDIUM `#5f6368`, у сводки снизу THICK) и строка плана — без изменений.
Полоса форматов не может объединять строки разного типа границ (предохранитель в `toStructureRequests`).

**Группы колонок.** У каждого блока группа глубины 1 на смещениях 16..22 (скрытая аналитика); новый блок получает
такую же (`addDimensionGroup` по шаблонному блоку), группа хвоста книги сдвигается вместе с ним.

**Проекция остатка — защита `LAST_CLOSED_DATE` у всех блоков (final polish, решение владельца).** В живой книге
защита есть только у блока 1 (`=IF($M<r>>LAST_CLOSED_DATE;"";T<r-1>−Q<r>+S<r-1>)`), блоки 2..N считают то же без
неё — в свежем месяце «пусто − пусто + пусто» показывало 0 в каждом будущем дне (720 ячеек октября). Создаваемый
месяц ставит защищённую форму каждому блоку (`GENERATED_STOCK_PROJECTION`), первый день — без проекции (нет ссылок
на прошлый месяц). Расчёт закрытого дня тот же; проверено в Sheets на копии: будущий день пуст, фактический 0 и
расчётный 0 закрытого дня остаются числом 0, положительное — числом, граница точная (LCD = дата → число,
LCD + 1 → пусто). Прочая семантика не менялась (проекция хранения — только блок 1, как в сентябре).

**Нули строки MTD — отдельные формулы, не подавляются.** `SUMIF(дата ≤ LCD; …)` блока и `SUM(C..J)` сводки по месяцу
без закрытых дней дают 0 — это законный итог «ничего не закрыто» (283 ячейки в свежем октябре; в сентябре те же
формулы дают те же нули в неиспользуемых колонках). Остаток MTD — `INDEX/MATCH` по LCD, пуст до первого закрытого дня.

**Заголовок, шапка, MTD, строка плана** — из строк-шаблонов предыдущего месяца как есть (шапка окрашена по
семантике колонок: серая дата, жёлтый ручной ввод, зелёный факт, серый расчёт, голубые ставки).
