## 2. Модель месяца

Лист `WB_Юнит_2025` — секции месяцев сверху вниз (январь 2025 … сентябрь 2026). Секция:

| строка | что |
|---|---|
| `topRow` | A: «<Месяц> <год>» (объединение A:K в прошлых месяцах, A:L в секциях Calendar V2), заголовки блоков «nmID Название» |
| `topRow + 1` | шапка метрик («Дата» в B и в колонке даты каждого блока) |
| `topRow + 2 … + days + 1` | дни месяца (28/29/30/31 — только `daysInMonth`, `Date.UTC`) |
| `lastDailyRow + 1` | MTD («MTD ACTUAL» в колонке даты первого блока) |
| `mtdRow + 1` | разделитель; следующий месяц — сразу за ним (шаг `days + 4`, подтверждён на 21 секции) |

Сентябрь 2026 — просто одна из секций (A735). Октябрь 2026: **769 / 770 / 771..801 / 802 / 803**.

Модуль `cloud/src/loaders/unitka/calendar.ts`: `daysInMonth`, `nextMonth`/`previousMonth`, заголовок,
`geometryAt(key, topRow)`, `MonthLayout` (геометрия + блоки), поиск секции `locateSection`.

## 3. Слоты блоков — сплошная цепочка, терминальный блок без разделителя

Слот `s` = колонки `13 + 24·s … +23`. **Блоки идут сплошной цепочкой, без зарезервированных слотов и дыр**
(решение владельца, visual hardening 2). Тело блока — смещения 0..22 (дата … доходность 1 шт). Смещение 23 —
колонка дня недели — существует только **между** блоками: зрительно она начинает следующий SKU. **У последнего
блока месяца её нет** (final polish, F2): цепочка кончается последней метрикой, а не «стартером» несуществующего
блока. Терминальная колонка = `MonthLayout.lastBlockColumn = start(последний) + 22`; колонка за ней раскладке не
принадлежит (`blockOfColumn` → null): ни значений, ни формата, ни границ, ни УФ, ни размеров.

Новый SKU встаёт сразу за последним блоком: планировщик вставляет колонки (`insertDimension`) перед «хвостом» книги
— унаследованными расчётами (10 скрытых колонок, своя группа), подписями и колонкой якорей. Хвост — последние 12
колонок листа, его начало = якорь − 11 (`tailStartOf`). Геометрия вставки (`insertGeometry`) — ровно до последней
метрики нового последнего блока, чтобы **хвост вставал сразу за цепочкой**:

* книга до Calendar V2 (у последнего блока колонка дня недели физически есть, как VP в сентябре): `24·n − 1` колонок
  за ней; бывшая «своя» колонка дня недели становится разделителем;
* книга после Calendar V2 (хвост сразу за последней метрикой): `24·n` колонок — «разделитель + тело» на каждый блок;
* хвост не там, где его ждёт цепочка, — `BLOCKED TAIL_GEOMETRY_UNKNOWN`.

Октябрь 2026: вставка 23 колонок за VP; блок 25 (909951444) = **VQ..WM (589..611)**, хвост = WN..WY, якоря =
**WY736..739**. Месяц без нового SKU на книге с физической VP: колонки не вставляются, VP в новых строках пуста.
Инвариант: `следующий.start = предыдущий.end + 1`; дыра в цепочке — `BLOCKED CHAIN_GAP`, авто-сдвига блоков нет.

Побочные эффекты вставки, снятые в генераторе (все пойманы чтением копии книги):

* **УФ.** Sheets расширяет диапазоны УФ, кончающиеся ровно на колонке перед вставкой (правило выходных и «будущий
  день» блока 24 — до VP); их формулы привязаны к первому диапазону, во вставленных колонках ссылаются за край листа
  (`WEEKDAY(пусто)=6`) — сентябрь получил бы сплошную полосу. Такие правила переиздаются сразу за вставкой в исходных
  диапазонах (`cfInsertTrims`, `shiftColumnRefs`); ссылка на другой лист — `BLOCKED CF_TRIM_UNSAFE`.
* **Группы колонок.** (1) Sheets сливает стоящие вплотную группы одной глубины: у последнего блока нет разделителя, и
  его группа аналитики (16..22) встала бы вплотную к группе хвоста — первая колонка хвоста выводится из группы хвоста
  (`tailGroupDetach`; она остаётся скрытой; откат возвращает её, группы сливаются в исходную). (2) Sheets расширяет
  группу, кончающуюся ровно на точке вставки: вставленные колонки выводятся из неё (`groupInsertTrims`), затем новый
  блок получает свою группу.

диапазон, и ссылки формул/УФ/`ZZ_QA` (`$WB$736` → `$WY$736`; проверено на копии: 32 ссылки УФ, 166 строк формул
прошлых месяцев отличаются от предснимка только этим сдвигом). Ячейка плана — якорь **только по виду**
(`lcd`/`reverse`), никогда по колонке. Поиск по активному коду (`600`, `WB`, `MIR`, `REVERSE_LEG_RATE`): в `cloud/src/loaders/unitka` константы колонки нет
— `REVERSE_LEG_RATE` встречается только как ИМЯ диапазона (формулы и `resolveAnchorCol`), остальное — комментарии;
тест `unitka_anchor_contract.test.ts` держит это (скан исходников, якорь 600 → 624 → 648 (в книге — 600 → 623), отказ `ANCHOR_UNRESOLVED`,
запись зеркала LCD в найденную колонку, поиск блоков после вставки). Жёсткая колонка 600 / `$WB$736` осталась только
в спящем наследии Apps Script (`UnitkaS8*.gs`, `UnitkaR75.gs`, `Код.gs` — ручные `s82data`/`s8rates`/`s82lcd` и их
откаты; не запускаются с «UNITKA ENGINE v1 PRODUCTION READY»), в тестах и документах. Контракт выката — §10.

## 5. Суточный Engine (`unitka-engine/2.0.0`)

1. LCD (BigQuery, МСК) → месяц → ровно один заголовок в колонке A (`section.ts`):
   нет — `MONTH_SECTION_MISSING`; два — `MONTH_SECTION_AMBIGUOUS`; не помещается в сетку — `MONTH_SECTION_INVALID`.
2. Снимок секции по её геометрии; `preflight` проверяет контракт секции (заголовок, шапка, даты ровно дней месяца,
   «MTD ACTUAL», уникальные nmID, «слот с шапкой, но без nmID») → `MONTH_SECTION_INVALID`; формулы → `STRUCTURE_DRIFT`.
3. Всё — до любой записи. **Месяц Engine не создаёт никогда.** `MONTH_ROLLOVER_REQUIRED` из пути выведен.
4. Предпроверка: если до конца месяца LCD ≤ `UNITKA_MONTH_PREP_WINDOW_DAYS` (5) дней и следующего месяца нет —
   предупреждение `NEXT_MONTH_SECTION_MISSING` (лог + `qa_json.calendar`); прогон не падает.
5. Экономика не менялась: формулы, ставки, QA, Guard — те же; меняются только строки/колонки.

## 6. Подготовка месяца (`unitka-month-prep`)

Отдельный загрузчик (реестр), **не активирован**: нет расписания, нет шага деплоя.

* **ПЛАН по умолчанию.** Запись — только `ENVIRONMENT=prod` **и** `UNITKA_MONTH_PREP_WRITE=1` **и** явный
  `UNITKA_MONTH_PREP_TARGET=YYYY-MM`. `UNITKA_WRITE_ENABLED` права не даёт. В shadow шлюз readonly —
  `structureWrite` отказывает до HTTP.
* Планировщик (`monthprep.ts`, чистый): предыдущий месяц (последняя секция листа) + активные SKU WB
  (`REF_SKU_MASTER`, то же определение, что в `V_UNITKA_DAILY_FACT`) + канон COGS.
* Формулы — явные построители (`formulas.ts`), **не** текст XLSX. Перед созданием планировщик доказывает, что
  построители воспроизводят формулы последнего дня, MTD и сводки предыдущего месяца символ в символ; иначе
  `TEMPLATE_MISMATCH`. Для каждого блока переносятся ровно как были: слагаемое COGS (240 через `$R$45`, нули —
  не исправляются), константа внешней рекламы в Y (10/100), вид проекции хранения. Проекция остатка — исключение:
  в создаваемом месяце она у КАЖДОГО блока с защитой `LAST_CLOSED_DATE` (см. §8), форма прошлого месяца только
  распознаётся для доказательства шаблона.
* Первый день месяца — без проекции остатка (никаких ссылок на прошлый месяц).
* СПП и блогеры — пустые (ручной ввод); СПП из прошлого месяца не копируется.
* Один `batchUpdate`: `insertDimension` (колонки новых блоков) → переиздание расширенных правил УФ (§3) →
  `appendDimension` (строки) → сброс унаследованных форматов во вставленных колонках → форматы строк-шаблонов +
  контракт границ (`repeatCell`) → значения и формулы в локали книги → заметки COGS → `mergeCells` → УФ из
  визуального контракта → размеры по контракту §8 → группы колонок. `copyPaste` не используется. Предохранитель
  `assertPlanConfined`: всё — не выше заголовка нового месяца, кроме вставленных колонок и переизданных правил.
* Идемпотентность: месяц есть и проходит контракт → `NO_CHANGE`, 0 запросов; неполный → `MONTH_SECTION_PARTIAL`;
  нарушен контракт → `MONTH_SECTION_INVALID`; авто-починки нет.

### COGS нового блока

Только из канона `wb_mart.V_UNITKA_COGS_CANONICAL` (копия `UNITKA_COGS_EFFECTIVE`): последний день копии с
положительным значением. Нет значения → `COGS_MISSING`; копия устарела → `COGS_STALE`; недоступна →
`COGS_UNAVAILABLE` — месяц не готовится, 0 не подставляется. Происхождение (nm_id, значение, дата, время
публикации, run) — в плане, в логе и заметкой на ячейке AI первого дня блока. Для 909951444 на 18.09 канон =
426.735 — значение берётся из данных, особого случая в коде нет.

## 7. Популяция (V1)

Снимок активных SKU на момент подготовки; после принятия раскладка заморожена.

* Новый SKU посреди месяца — блока нет до следующего месяца; Guard: `SKU_WITHOUT_BLOCK`; повторная подготовка
  того же месяца — `NO_CHANGE` с отчётом `unmapped_active`.
* **Ограничение V1:** SKU, выведенный из `REF_SKU_MASTER` посреди месяца, лишается строк в
  `V_UNITKA_DAILY_FACT` → Engine падает `BLOCK_MISSING` (fail-closed). Операционное правило: выводить SKU с
  1-го числа следующего месяца (после подготовки месяца он получит пустой слот). SQL в Phase 2B не менялся.

## 8. Визуальный контракт секции месяца (Phase 2C hardening, 19.09.2026)

Источник — живой лист через Sheets API (`userEnteredFormat`, `effectiveFormat`, `conditionalFormats`),
тестовая копия книги (строки 1–768 идентичны оригиналу). Модуль `visual.ts`.

**Семантика колонок блока** (карта UNITKA 2.0): дата (0), день недели (23); ручной ввод — блогеры (1), СПП (15);
факт Engine — показы, переходы, заказы, корзина, отмены, остаток, внутренняя реклама, цена, хранение
(2–7, 11, 14, 20); ставки — комиссия (17), логистика (19); расчёт — остальное. Сводка: A/L день недели,
B дата, C Σ блогеров (окрашена как ручной ввод), D–H и J факт-суммы, I и K расчёт.

**Два вида строки дня.** Пустой будущий день: без заливки у факта, ставок и расчёта (ручной ввод — жёлтая зона
ввода, как всегда), серый текст (УФ). Закрытый день со значением: заливка факта зелёная `#f1f8f4` (цена —
жёлтая `#fffbe8`), ставок — голубая `#f3f8fd`, чёрный текст; пропуск источника (пустая ячейка закрытого дня)
остаётся белым. Заливка закрытого дня — правило УФ «день ≤ LAST_CLOSED_DATE и ячейка не пуста», а не
статический формат: статический формат всех строк дней одинаков (эталон E3 = первый день) — контракт
формата закрытого дня Engine выполняется без перекраски (проверено: 4 прогона Engine на копии, 0 перекрасок,
кроме ячейки, которую сам Engine очистил как GAP и затем заполнил — это штатный E3).

**Выходные.** Суббота и воскресенье по дате строки (`=WEEKDAY($B<r>;2)>5`): заливка `#fcefe3` на ячейке даты и
дня недели сводки (A, B, L) и каждого блока (смещения 0 и 23). Не вся строка. В живом сентябре это работало
только у A, B и дня недели блока 1: формулы `=WEEKDAY(US737;2)>5` записаны относительно первого диапазона
правила (B / AJ), и для остальных диапазонов ссылка уезжает в чужие колонки (пустая → `WEEKDAY(0)=6` →
«выходной» каждый день). Sheets применяет формулу УФ относительно верхней-левой ячейки ПЕРВОГО диапазона
правила — проверено на копии.

**Правило независимости от якоря.** Формулы УФ используют только абсолютные колонки (`$B`, `$WB$736`), строку
первого дня секции (у всех диапазонов правила одинаковые строки) и идиому «эта ячейка»
`INDEX($A<r>:$<last><r>;1;COLUMN())` / «колонка целиком» `INDEX($A$<f>:$<last>$<l>;0;COLUMN())` (COLUMN() и
INDEX вычисляются по каждой ячейке — проверено на копии). Ни одной относительной ссылки на колонку (тест).

**Порядок правил = приоритет** (Sheets применяет первое совпавшее логическое правило; шкала и логическое
правило с цветом текста складываются): уровни доли от максимума колонки (корзина, реклама, заказы; 4 × 3) →
выходные → будущее (серый текст, сводка A..K + весь блок) → шкала доходности (сводка I и каждый блок) →
оборачиваемость (≤15 / 15–30 / 30–60 / >60) → знак доходности на 1 шт → знак доходности → отмены тревожны →
шкалы корзины и доходности на 1 шт → отрицательная доходность, ДРР > 20 %, «показы есть — заказов нет» →
заливка закрытого дня (факт / цена / ставки). 108 правил на 25 блоков; правила предыдущего месяца НЕ копируются.
Наследие сентября, которое не переносится: шкалы на строках заголовка/шапки и парные правила `D<>""`/`D=""`
одного цвета (визуальные no-op).

**Сводка A..L — один блок (hardening 2).** Колонка L (день недели справа) входит в сводку: заголовок месяца
объединён A:L, контур сводки — жирная линия слева от A и справа от L, L берёт вид колонки A (шапка, MTD, план),
правила «выходные» и «будущее» включают L. В сентябре L стояла вне контура A:K — в октябре она выглядела
оторванной лесенкой.

**Контракт границ (`borderSpec`)** — границы не копируются со строки-шаблона: строка первого дня несёт
разделитель шапки (MEDIUM сверху), и его копия на каждый день давала «тяжёлую решётку». Вторая причина тяжести
(final polish): в живом сентябре сетка дня — 1 px чёрным (цвет темы TEXT) на всех четырёх сторонах КАЖДОЙ ячейки,
но под статической заливкой и плотным содержимым; в созданном месяце будущие дни нейтрально белые, и та же чёрная
линия читается сплошной «клеткой». Все тонкие линии октября были созданы генератором, ни одна не обязательна.
Контракт: обычная ячейка дня — волосяная светлая сетка `#d9d9d9` (цвет, близкий к сетке листа); сильные линии —
только смысловые разделители, и больше нигде (тест перечисляет их поимённо): контур сводки A..L (THICK чёрная),
«дата | данные» (MEDIUM чёрная: B|C в сводке, дата | блогеры в блоке), SKU | SKU (MEDIUM `#5f6368`). У общей грани
один владелец: горизонталь между днями — верх НИЖНЕЙ строки, над первым днём — линия шапки (тип строки `dayFirst`,
отдельная полоса форматов), под последним — верх MTD; ни у одного дня нет линии снизу и MEDIUM/THICK сверху.
Шапка (THIN `#9aa0a6`), MTD (рамка MEDIUM `#5f6368`, у сводки снизу THICK) и строка плана — без изменений.
Полоса форматов не может объединять строки разного типа границ (предохранитель в `toStructureRequests`).

**Граница сводка → SKU (final polish, F1).** K — ДРР (последняя метрика сводки), L — день недели сводки (её формула
читает дату блока 1, как колонки-разделители между блоками), M — дата блока 1. Сводка — A..L одним контуром; граница
сводка | SKU — **правая грань L** (THICK чёрная; в строке плана — MEDIUM `#5f6368`). Раньше ту же грань задавал и блок 1
(левая грань M, MEDIUM серая) — единственное исключение из правила «у грани один владелец»: Sheets хранит обе и рисует
серую линию поверх контура. Теперь блок 1 свою левую грань не задаёт; исключений в контракте нет (тест).

**Конец цепочки (F2).** Блок закрывает колонка-разделитель (правая грань MEDIUM `#5f6368`); у последнего блока её
нет — цепочку закрывает правая грань его последней метрики, во всех типах строк.

**Контракт размеров (F3, `planDimensions`).** Размеры не копируются с сентября: там заголовки месяца (кегль 20) и
строки MTD (кегль 16) стоят в строках 18 px — текст срезан; шапке не хватает высоты на 5 строк переноса; шестизначная
сумма в рублях кеглем 16 не помещается в 84 px («####»). Контракт — по смыслу, без координат месяца:

* высота строки: заголовок и MTD — не ниже `heightForFont(кегль)` (20 пт → 40 px, 16 пт → 33 px; кегль — из
  строки-шаблона), шапка — не ниже шаблона и вмещает перенос своих подписей (оценка по словам, ≤ 120 px; живая
  книга: 108), дни и план — как в прошлом месяце (18);
* ширина колонки: по смыслу смещения — всё 84, разделитель 56, итоговые денежные колонки шире: «доходность
  (общая)» 104 (как I сводки), «реклама внутренняя» 100 (как J сводки); сводка — как в живой книге;
* вставленные колонки получают ширину контракта и скрытие блока-шаблона; **существующие колонки раскладки — только
  расширение до контракта** (поле `pixelSize`, скрытие не трогается). Ширина колонки общая для всех месяцев, поэтому
  расширения перечислены в плане (`width_upgrades`) и возвращаются откатом (`restoreWidths`). Живая книга: 48 колонок
  (смещения 10 и 11 блоков 1..24): 84 → 104/100. Строки прошлых месяцев генератор не трогает: заголовок
  «Сентябрь 2026» остаётся в строке 18 px — разовое решение владельца.

**Группы колонок.** У каждого блока группа глубины 1 на смещениях 16..22 (скрытая аналитика); новый блок получает
такую же (`addDimensionGroup` по шаблонному блоку), группа хвоста книги сдвигается вместе с ним.

**Проекция остатка — защита `LAST_CLOSED_DATE` у всех блоков (final polish, решение владельца).** В живой книге
защита есть только у блока 1 (`=IF($M<r>>LAST_CLOSED_DATE;"";T<r-1>−Q<r>+S<r-1>)`), блоки 2..N считают то же без
неё — в свежем месяце «пусто − пусто + пусто» показывало 0 в каждом будущем дне (720 ячеек октября). Создаваемый
месяц ставит защищённую форму каждому блоку (`GENERATED_STOCK_PROJECTION`), первый день — без проекции (нет ссылок
на прошлый месяц). Расчёт закрытого дня тот же; проверено в Sheets на копии: будущий день пуст, фактический 0 и
расчётный 0 закрытого дня остаются числом 0, положительное — числом, граница точная (LCD = дата → число,
LCD + 1 → пусто). Прочая семантика не менялась (проекция хранения — только блок 1, как в сентябре).

**Нули строки MTD — отдельные формулы, не подавляются.** `SUMIF(дата ≤ LCD; …)` блока и `SUM(C..J)` сводки по месяцу
без закрытых дней дают 0 — это законный итог «ничего не закрыто» (283 ячейки в свежем октябре; в сентябре те же
формулы дают те же нули в неиспользуемых колонках). Остаток MTD — `INDEX/MATCH` по LCD, пуст до первого закрытого дня.

**Заголовок, шапка, MTD, строка плана** — из строк-шаблонов предыдущего месяца как есть (шапка окрашена по
семантике колонок: серая дата, жёлтый ручной ввод, зелёный факт, серый расчёт, голубые ставки).

## 10a. Остаток MTD: семантический контракт ячейки и семейство формулы (production rollout patch, 19.09.2026)

Ячейка остатка MTD (смещение 7, строка MTD) значит одно: **остаток на `LAST_CLOSED_DATE` в диапазонах дней своего блока
и своего месяца; даты нет — пусто.** В живых книгах встречаются два семейства записи:

| семейство | где | форма (локаль ru_RU) |
|---|---|---|
| `native` | production-книга: 24 блока из 24, обёрток на листе нет | `=IFERROR(INDEX(T737:T766;MATCH(LAST_CLOSED_DATE;$M$737:$M$766;0));"")` |
| `wrapped` | копия книги (Drive) | `=ARRAY_CONSTRAIN(ARRAYFORMULA(<та же формула>); 1; 1)` |

`formulas.recogniseMtdStock` принимает ТОЛЬКО эти два семейства и только если ядро указывает ровно на диапазон остатка
и диапазон дат ЭТОГО блока в днях ЭТОГО месяца, имя `LAST_CLOSED_DATE`, точный поиск `0` и подстановку `""`. Это не
регулярное выражение «на всё похожее» и не отключение проверки шаблона: остальные 20 формул строки MTD по-прежнему
сверяются с построителем символ в символ. Отказ (`TEMPLATE_MISMATCH` с адресом ячейки и кодом):

`MTD_STOCK_NOT_FORMULA` · `MTD_STOCK_UNKNOWN_WRAPPER` (любая обёртка, кроме доказанной) · `MTD_STOCK_MULTI_CELL_OUTPUT`
(`ARRAY_CONSTRAIN` не 1×1) · `MTD_STOCK_MALFORMED` (лишние аргументы, другой лист, битая ссылка, двойная обёртка) ·
`MTD_STOCK_WRONG_STOCK_RANGE` (другая колонка, другой блок SKU, другой интервал строк/месяц, иная абсолютность) ·
`MTD_STOCK_WRONG_NAMED_RANGE` · `MTD_STOCK_WRONG_DATE_RANGE` · `MTD_STOCK_WRONG_MATCH_TYPE` · `MTD_STOCK_WRONG_FALLBACK`
(в т.ч. `" "` вместо `""`).

**Источник истины для генератора — месяц-источник самой книги.** Перенесённый блок сохраняет СВОЁ семейство
(`BlockFormulaParams.mtdStockFamily`), новый блок берёт семейство блока-шаблона (последнего перенесённого), дописанный
посреди месяца — семейство самого месяца. Production получает `native` со сдвинутыми ссылками и не зависит от
артефакта копии; копия остаётся `wrapped`. В журнале плана — `mtd_stock_family` (`{"native": 25}`).

## 10b. Исполняемый откат создания месяца (`unitka-month-rollback`, `monthrollback.ts`)

Откат — не восстановление книги, а ровно обратные действия к мутациям подготовки месяца, одним атомарным `batchUpdate`:
правила УФ новой секции → вставленные колонки (хвост, якоря и `REVERSE_LEG_RATE` возвращаются сами) → строки секции →
ширины расширенных колонок (`width_upgrades`) → первая колонка хвоста обратно в группу хвоста. Объединения, заметки,
форматы, высоты строк и группы новых блоков лежат внутри удаляемых строк/колонок; проверок данных подготовка не создаёт.

**Манифест** (`unitka-calendar-v2/month-create`, v1) строится из плана и состояния листа ДО записи и пишется в журнал и
в режиме плана, и перед записью (`unitka_month_prep_rollback_manifest`: `digest`, `manifest`, `manifest_b64`):
книга/лист/месяц; «до» — сетка, колонка якорей, число правил УФ и объединений, группы колонок и строк с флагом
«свёрнуто», отпечатки УФ / объединений / ширин / высот / скрытых колонок и строк; «создано» — геометрия секции, блоки,
вставленные колонки, сетка и якорь после, число созданных правил УФ и переизданных правил прошлых месяцев, объединений,
заметок, проверок данных (0), расширенные ширины, высоты строк, выведенная из группы колонка хвоста, добавленные и
урезанные группы, число запросов, число и отпечаток записываемых ячеек, семейства остатка MTD. `digest` = sha256
канонического JSON без служебных полей (время, сборка).

**Запись месяца привязана к манифесту:** `UNITKA_MONTH_PREP_MANIFEST_DIGEST` обязателен и должен совпасть с манифестом
этой записи — иначе `MONTH_PREP_MANIFEST_DIGEST_REQUIRED` / `_MISMATCH` до любой записи. Пишется ровно просмотренный
план (структура и содержимое), а манифест отката гарантированно существует до записи. Изменилась книга (в т.ч. владелец
свернул/развернул группу) или канон COGS нового блока — повторить план.

**Откат fail-closed.** Мутации строятся, только если живая книга — та, что описана в манифесте как «после создания»:

| код отказа | когда |
|---|---|
| `ROLLBACK_MANIFEST_INVALID` | манифест не передан, не разбирается, чужой вид/версия, отпечаток не сходится, внутренне несогласован |
| `ROLLBACK_TARGET_REQUIRED` | `UNITKA_MONTH_PREP_TARGET` не задан или не равен месяцу манифеста |
| `ROLLBACK_MANIFEST_FOREIGN` | другая книга / лист |
| `ROLLBACK_SECTION_MISSING` / `_AMBIGUOUS` / `_MISMATCH` | заголовка месяца нет (откат уже выполнен) / он не один / секция не на своём месте или блоки заголовка не те |
| `ROLLBACK_LATER_MONTH_EXISTS` | есть следующий месяц или строки после секции |
| `ROLLBACK_APPEND_DETECTED` | после создания дописан SKU — сначала откат дописывания |
| `ROLLBACK_GEOMETRY_CHANGED` / `ROLLBACK_ANCHOR_MOVED` | сетка или колонка якорей не как после создания |
| `ROLLBACK_CF_AMBIGUOUS` | правил УФ в секции / всего не столько, сколько создано |
| `ROLLBACK_INSERTED_COLUMNS_NOT_EMPTY` | во вставленных колонках выше секции есть значения или формулы |
| `ROLLBACK_MANUAL_DATA_PRESENT` | в секции введены СПП / блогеры (в т.ч. 0): откат стёр бы ручной ввод |
| `ROLLBACK_EVIDENCE_UNAVAILABLE` | секция или вставленные колонки не прочитаны |

Факты Engine в секции откату не мешают (восстановимы из BigQuery). Ширину, которую после создания меняли вручную, откат
не трогает (отчёт `skipped_widths`). После исполнения загрузчик перечитывает структуру и сверяет с «до»:
структурное расхождение → `ROLLBACK_VERIFY_FAILED`; расхождение только вида (скрытые колонки, флаг «свёрнуто») —
в отчёте `view_state`, не ошибка. Полная сверка значений, формул и форматов — внешним снимком (read-only учётка).

Режимы: по умолчанию ПЛАН (шлюз readonly); исполнение — `ENVIRONMENT=prod` И `UNITKA_MONTH_ROLLBACK_WRITE=1` И
манифест И явный месяц. **`DRY_RUN=1` запрещает структурную запись Calendar V2 (создание, дописывание, откат)
независимо от прочих флагов.** BigQuery откат не читает и не пишет. Расписания и шага деплоя нет.

Репетиция на копии (19.09.2026, три формы): семейство `wrapped`, семейство `native` (24 ячейки сентября копии
приведены к production-форме), `native` + все 24 группы колонок свёрнуты (вид production). В каждой: план → создание с
отпечатком → приёмка (25 блоков, 909951444 = VQ..WM, семейство источника 25/25, 0 ошибок формул, 0 межмесячных ссылок,
проекция остатка пуста в будущих днях) → повтор `NO_CHANGE` / 0 POST → план отката → откат по манифесту → копия
снимок в снимок (значения, формулы, форматы, заметки, проверки данных, высоты, ширины, скрытие, группы колонок и
строк с флагами, объединения, УФ, именованные диапазоны, сетка — все 11 листов). Повторный откат —
`ROLLBACK_SECTION_MISSING`, 0 POST.

## 11. Дописывание нового SKU в текущий месяц (final polish, F4; `monthappend.ts`) — НЕ активировано

**Что было.** Месяц создан → `unitka-month-prep` отвечал `NO_CHANGE` и лишь перечислял активные SKU без блока
(`unmapped_active`); Engine обходит блоки секции, поэтому SKU без блока не попадал ни в блок, ни в итоги магазина до
следующего месяца (пример: 909951444 активен в сентябре, блока нет).

**MID_MONTH_SKU_QUALIFICATION.** SKU дописывается, если он (1) активный SKU WB в популяции Unitka
(`REF_SKU_MASTER`: WB, active), (2) не представлен блоком секции и (3) в `V_UNITKA_DAILY_FACT` за ЭТОТ месяц на дату
≤ `LAST_CLOSED_DATE` есть **остаток > 0 ИЛИ заказы > 0**. Только справочник, показы, корзины, цена — не основание
(SKU «ждёт», попадает в `waiting`). Слой тот же, что читает Engine; он плотный (активный SKU × день), поэтому у
дописанного блока есть строка на каждый закрытый день — дни до появления остаются нулевыми/пустыми по фактам.

| случай | итог |
|---|---|
| SKU только в справочнике, нет остатка, заказов, активности | не дописывается (`waiting`) |
| появился остаток | дописывается (основание STOCK, дата) |
| первый заказ при отсутствии снимка остатков | дописывается (основание ORDERS) |
| SKU уже представлен / реактивирован | `NO_CHANGE`, блок тот же |
| SKU выбыл из справочника, блок в месяце есть | блок остаётся на месте; порядок не меняется, ничего не удаляется |
| два новых SKU в один прогон | оба, по возрастанию `nm_id` |

**Только добавление в конец.** Порядок блоков месяца неизменен. Вставляются колонки «разделитель + тело» перед хвостом
(§3), новый блок получает все даты месяца, формулы, MTD, COGS из канона (заметка), группу; прежний последний блок —
свою колонку-разделитель. Значения пишутся **сериями** только в новые колонки и в формулы сводки, чей диапазон
действительно расширился (C..K каждого дня, ДРР MTD) + подписи «N SKU»; форматы — только правее прежней последней
метрики (у неё самой — только границы); правила УФ секции заменяются целиком (идиомы зависят от последней колонки и
якоря). Факты, формулы и ручной ввод (СПП, блогеры) существующих блоков не адресуются — предохранитель
`assertAppendConfined`. **СПП остаётся ручным:** новый блок стартует с пустым СПП; пустой СПП при заказах закрытого
дня — `MANUAL_REQUIRED`, 0 — допустимое ручное значение; автоматизация СПП вне рамок.

**Fail-closed** (0 запросов): `MONTH_SECTION_INVALID`, `CHAIN_GAP`, `DUPLICATE_SKU`, `TAIL_GEOMETRY_UNKNOWN`,
`TEMPLATE_MISMATCH` (построители не воспроизводят формулы секции — расширение сводки «не понято»),
`CF_SECTION_DRIFT` (правила УФ секции не те, что строит генератор; месяцы, созданные до Calendar V2, поэтому не
дописываются), `LATER_SECTION_EXISTS` (следующий месяц уже создан), `COGS_*`, `STRUCTURE_UNAVAILABLE`,
`TEMPLATE_FORMATS_UNAVAILABLE`, `CF_TRIM_UNSAFE`; не текущий месяц LCD или слой фактов не прочитан — `NO_CHANGE`.
Неизвестную раскладку генератор не чинит.

**Гейты.** План пишется в журнал (`unitka_month_append_plan`) при любом прогоне `unitka-month-prep` на существующем
месяце. Запись — `ENVIRONMENT=prod` + `UNITKA_MONTH_PREP_WRITE=1` + цель + **отдельно `UNITKA_MONTH_PREP_APPEND=1`**;
после записи — повторное чтение: контракт секции, список блоков, колонка якорей (`MONTH_PREP_VERIFY_FAILED`).
Откат — `planAppendRollback` (колонки и SKU — из журнала плана): удаляет правила УФ секции и вставленные колонки,
возвращает сводке диапазоны и подписи, границу прежней последней метрики и правила УФ прежней раскладки; отказывает
при любом расхождении (`APPEND_ROLLBACK_MISMATCH`, `APPEND_ROLLBACK_UNSAFE`, `CF_SECTION_DRIFT`).
