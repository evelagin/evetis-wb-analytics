## 1. Инструмент и порядок запуска

Один-разовый bound Apps Script `UnitkaE6.gs` в книге (как `r75run` в R7.5; основной проект
`evetis-wb-analytics` не используется). Функции, по одной на шаг, с чекпойнтами в `ZZ_CONFIG`
(лимит 6 минут): `e6backup` → `e6snapshot` → `e6cf` (E6.1) → `e6freeze` (E6.2/E6.3) →
`e6fix` (E6.5) → `e6trim` (E6.4) → `e6qa` → при FAIL `e6rollback`. Между шагами — чтения только
после записей (урок R7.5: чтение после записи пересчитывает книгу целиком).
Порядок E6.5 раньше E6.4 намеренно: удалять колонки только после того, как все ссылки проверены.
После `e6qa` — Engine в SHADOW (`scheduler-control: unitka-engine, shadow, run-now`): ожидание
`SHADOW_MATCH`/`SHADOW_DIFF` только по новому дню, `STRUCTURE_DRIFT` нет, `FORMULA_ERRORS 0`.

## 7. Rollback

1. **Полная копия книги** до запуска (`DriveApp.makeCopy`, ID → `ZZ_AUDIT_LOG` и CHANGELOG) — откат «всё сразу»: заменить книгу копией (ID книги меняется → `UNITKA_SPREADSHEET_ID` Engine) либо скопировать листы обратно.
2. Пошаговый откат внутри книги (`e6rollback <шаг>`), данные для него пишет `e6snapshot` в Drive-папку `UNITKA_E6_<дата>`:
   * E6.1 — JSON всех правил УФ (`Sheets.Spreadsheets.get` → `conditionalFormats`) + матрицы фонов → удалить новые правила, вернуть старые, очистить статические фоны там, где их не было;
   * E6.2/E6.3 — JSON формул листов → вернуть формулы, снять скрытие;
   * E6.4 — вставить удалённые пустые колонки/строки (данных в них не было — восстановление структурное);
   * E6.5 — таблица «ячейка → старое значение/формула» (§5) → вернуть.
3. Engine на время run'а: Scheduler `unitka-engine-prod` **pause** (окна 10:00/12:30 МСК), после `e6qa` + SHADOW — resume. Окно запуска — после 12:30 МСК, чтобы не пересечься с прогонами.

## 8. E6-B — COGS и ДРР через BigQuery (дизайн, после E6-A)

**COGS (п. 1).** Источник — `evetis_ref.REF_SKU_COGS_HISTORY` с effective dating. Вью
`wb_mart.V_UNITKA_COGS_EFFECTIVE(nm_id, month_start, cogs, valid_from, batch)` — COGS, действующий
на 1-е число месяца; для активного WB-SKU без строки или с `cogs <= 0` → строка `COGS_MISSING`.
Engine v1.2: новый факт `cogs` на блок и месяц — **ячейка в строке шапки блока** (строка 735,
смещение 22, сейчас пустая) → формулы `доходность 1 шт` и `блогеры ₽` ссылаются на неё
(`AI = AE − AF − AH − <шапка>$…$735`), литералы уходят; гейт **`COGS_MISSING`** = fail-closed
(план не строится, алерт). Гранулярность — месяц (партия на 1-е число); смена партии внутри месяца
видна как `MODEL_PARAMETER_REFRESH` с датой в журнале. Надбавка самовыкупа (`+10`/`+100`) → имя
`SELF_BUYOUT_FEE` в `ZZ_CONFIG`. Строка 45 — display-only (Engine её не пишет, формулы на неё не ссылаются).
Историческим месяцам COGS по партиям пишет BACKFILL тем же механизмом (эффективная дата = 1-е число).

**ДРР backend (п. 2–3).** Вью `wb_mart.V_UNITKA_DRR_DAILY` (nm × дата, только закрытые дни):
`orders, self_buyouts, revenue_ac, ads, cogs, commission_rub, logistics_rub, storage_rub, cancels_cost`,
`contribution_before_ads = orders·AI − storage − cancels`, `contribution_after_ads = … − ads`,
`profit_per_order`, **`be_drr_full = contribution_before_ads / revenue_ac`**, `drr = ads / revenue_ac`,
`target_drr = be_drr_full − buffer_pp` (параметр `unitka_scale_buffer_pp = 5` в `evetis_ref.CT_CONFIG`,
не в коде), статус `STOP` (drr > be_drr_full), `HOLD` (target < drr ≤ be), `SCALE` (drr ≤ target);
`V_UNITKA_DRR_MTD` — то же за месяц накопительно (взвешенно). В книгу Engine пишет **служебный лист
`ДРР`** (первая вкладка, 24 строки × 10 колонок: SKU, ДРР MTD, BE-ДРР, цель, вклад до/после рекламы,
прибыль/заказ, статус, обновлено) — без формул, мобильный формат; Master не меняет геометрию.
Гейт `DRR_STATUS_CONSISTENT` (лист = вью). Как и COGS — сначала SHADOW, потом controlled write.
