## C. PRICE CONTRACT

### Что означают ценовые поля WB (доказано на данных)

| Поле | Смысл | Доказательство |
| --- | --- | --- |
| `total_price` | цена до скидки продавца («зачёркнутая») | — |
| `price_with_disc` | **цена продавца**: после скидки продавца, **до СПП** | `= total_price × (1 − discount_percent/100)` в 4 394 из 4 419 продаж (±1 ₽); в финотчёте это `retail_price_withdisc_rub`: **928/928** совпадений по `srid` до копейки (20.07–13.09) |
| `finished_price` / `retailAmount` | **сумма, фактически оплаченная покупателем** | `FACT_SALES.finished_price` = финотчёт `retailAmount` в **924/928** строк; при этом `finished_price ≠ price_with_disc × (1 − spp/100)` в 91 % строк (в среднем на 2–3 п.п. ниже): процент `spp` **не описывает** цену покупателя полностью |
| финотчёт `for_pay` | **начисление продавцу за товар** | тождество цепочки `seller − for_pay = СПП + vw + vwNds + acquiringFee + ppvzReward` с остатком ≤ 0,01 ₽/строку; Statistics API `for_pay` с финотчётом **не совпадает ни в одной** из 928 строк — использовать только финотчёт |
| наблюдатель цен `RAW_WB_PRICES.seller_effective_price` | **установленная** цена продавца (снимки каждые ~20 мин) | с 07.09.2026, 25 SKU; совпадает с ценой в заказах (Крем Руки 640 ₽ с 07.09) |

Все три потока — 1 строка = 1 единица: `FACT_ORDERS.quantity = 1` (4 744/4 744), финотчёт `quantity = 1` (4 940/4 940),
продажи — одна строка на выкуп. Поэтому средневзвешенная по единицам цена = `SUM(цена) / COUNT(строк)`, это и есть
`SUM(price × units)/SUM(units)`; AVG дневных средних не используется.

## E. Предлагаемый контракт экономики SKU

**Наименование.** Показатель — **не «Прибыль»**: в нём нет тарифной опции, штрафов, утилизации, прочих удержаний, OPEX,
фулфилмента и налога. Предлагаю «**Вклад SKU**» по уровням («маржинальный вклад»):

| Уровень | Формула (все слагаемые DIRECT) | Название |
| --- | --- | --- |
| 0 | Σ цена продавца по выкупам | Выручка по цене продавца |
| 1 | − СПП − вознаграждение WB − НДС − эквайринг − ПВЗ | **Начисление за товар** (= for_pay) |
| 2 | − логистика SKU − хранение SKU (с 01.09) | **Вклад после расходов WB** |
| 3 | − реклама (атрибуция) | **Вклад после рекламы** |
| 4 | − себестоимость (COGS, по дате выкупа — как Executive; ⚠️ исправлено в Phase B) | **Вклад SKU после себестоимости** |

Маржа = уровень 4 / выручка по цене продавца (та же база, что маржа Executive). Вклад на выкуп = уровень 4 / выкупы.

**Ответы:**
1. **Можем ли сегодня корректно показать результат каждого SKU после COGS?** Да, как «вклад после себестоимости»: все
   компоненты уровней 1–4 доказаны на грейне SKU. Хранение по SKU есть только с 01.09.2026; для окон раньше уровень 2
   PARTIAL (без хранения) — нужно показывать это явно.
2. **Что входит:** начисление за товар (цена − СПП − вознаграждение − НДС − эквайринг − ПВЗ), логистика SKU, хранение SKU,
   атрибутированная реклама, себестоимость.
3. **Что не входит:** тарифная опция/минимальный платёж, штрафы, утилизация, прочие удержания, приёмка, компенсации,
   разница «атрибуция − биллинг», хранение до 01.09, OPEX, ФФ, налог.
4. **Сходимость с Executive:** сумма по SKU **не должна** совпадать с Executive; разница сводится **точным мостом**
   (проверен на двух окнах, 0,00 ₽):

   `Σ SKU доход до себестоимости − уровень счёта (хранение + тарифная опция + прочее) + (атрибуция − биллинг) = результат Executive до себестоимости`

   | Окно | Σ SKU | − уровень счёта | + (атрибуция − биллинг) | = Executive | Δ |
   | --- | --- | --- | --- | --- | --- |
   | 31.08–13.09 | 41 658,72 | 4 237,13 | 20 862,25 − 20 748 | **37 535,84** | 0,00 |
   | 01.09–14.09 | 44 198,52 | 4 218,47 | 20 699,52 − 20 581 | **40 098,57** | 0,00 |

   Выручка, логистика и себестоимость совпадают один к одному. Для нового уровня 2 (с хранением по SKU) мост
   упрощается: из уровня счёта остаются тарифная опция и прочее; хранение по API расходится с финотчётом на копейки
   (01.09–14.09: 1 798,54 против 1 798,47).
5. **Ожидаемые расхождения:** атрибуция выше биллинга (+0,55 … 1,8 %); SHARED-расходы уровня счёта; даты (реклама —
   активность, финотчёт — операция); копейки округления цены продавца между Statistics API и финотчётом (0,10 ₽ на 202 шт).

(2–4 заказа за 2 недели) процент статистически неустойчив — нужен минимальный объём для показа (GAP-07).

## G. Сравнение с предыдущим периодом

Текущая реализация (карточки 67/68): предыдущее окно той же длины непосредственно перед текущим (границы из плотного
календаря `V_DASH_KPI_DAILY`); сравнение только при равном числе покрытых суток по метрике; ratio — разность в п.п.;
Δ% — от `ABS(prev)`. Недостатки: покрытие глобальное, нет логики отсутствующего SKU, отдельная таблица на 24×11.

Предлагаемый алгоритм для V2 (сравнение рядом с KPI, `650 ₽ ↓ 8,5 %`):
- окна: `[d1, d2]` и `[d1 − len, d1 − 1]`, `len` — число суток текущего окна;
- **сопоставимость**: по каждой метрике число покрытых суток в окнах равно (как сейчас) **и** оба окна не содержат
  неполных суток этой метрики; иначе вместо Δ — «н/с»; окно с текущими сутками сравнивается только по уже закрытым
  суткам или помечается 🟡;
- **SKU нет в прошлом окне** (0 заказов и 0 выкупов, но покрытие есть) → «новый», Δ% не выводится;
- **деление на ноль** → Δ% NULL, выводится абсолютная Δ;
- **единицы**: шт и ₽ — Δ% и Δ абсолютная; доли (% выкупа, доля отмен, ДРР, маржа) — **только п.п.**;
- **цена**: Δ% средней цены только если в обоих окнах ≥ N единиц (порог N — решение, GAP-07); цена считается как
  средневзвешенная в каждом окне отдельно, не как среднее дневных;
- % выкупа по когорте сравнивается только по зрелым когортам (оба окна старше ~21 дня), иначе 🟡.

## Ответы на 7 вопросов

1. **Средняя цена продавца по SKU** — да, достоверно: `price_with_disc` (1 строка = 1 шт) в заказах с 13.04.2026 и в
   выкупах с 30.03; в выкупах совпадает с финотчётом до копейки (928/928 по `srid`).
2. **Цена по заказам и по выкупам отдельно** — да. Цена покупателя — только по выкупам (в заказах не загружается, GAP-01).
3. **Полная экономика SKU после прямых расходов и COGS** — да, как «Вклад SKU после себестоимости»: все прямые компоненты
   доказаны на SKU; разложение удержаний — с 13.07, хранение по SKU — с 01.09.
4. **Нельзя честно отнести к SKU:** тарифная опция / минимальный платёж, штрафы, утилизация, прочие удержания,
   компенсации, приёмка, хранение до 01.09 и разница «атрибуция − биллинг».
5. **Сверка с Executive** — да, точным мостом (0,00 ₽ на двух окнах): Σ SKU − уровень счёта + (атрибуция − биллинг) =
   Executive. Различия ожидаемы: SHARED-расходы и два рекламных контракта.
6. **Что добавить в backend:** суммы цены продавца в заказах; когорту по SKU; цену покупателя и цепочку финотчёта по
   SKU × день; начисление; ноги логистики и хранение по SKU; себестоимость в SKU-слое; лояльность; статус данных.
7. **Рекомендуемая архитектура:** материализованный `SKU_PERFORMANCE_V2_DAILY` (day × nm_id, только суммы) по шаблону
   Executive C2; Level 1 Portfolio (таблица с Δ рядом со значением) и Level 2 SKU Detail (цепочка цены, вклад по уровням,
   динамика цена ↔ спрос) — оба поверх одного view; средние и Δ — ratio-of-sums в SQL, не в Metabase.
