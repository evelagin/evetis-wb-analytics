# PR-Mart3b-4 — controlled enablement Cloud Scheduler `wb-mart-prod`

**Дата:** 2026-08-11
**Предшественники:** #88 (Scheduler+IAM, PAUSED), #89 (fix Terraform prod-job drift)
**Тип:** операционный шаг + один read-only SQL. Инфраструктура НЕ меняется.

## Состояние на входе

`wb-mart-prod` создан Terraform'ом, расписание `0 7,9,12,16 * * *` Europe/Moscow, состояние
**PAUSED**. Приёмка PR3b-3 закрыта: `run-now` → `MART_RUNS` COMPLETE, target 2026-08-10,
`mart_rows = 7036`; повторный запуск → `guard_skip` / `reason=COMPLETE` / `exit(0)`, **новой строки
в журналах не появилось**. Provenance цела (`git_sha`, `image_digest` — реальные).

## Что делает этот шаг

Один клик: `Actions → scheduler-control → Run workflow`
→ `environment = prod`, `loader = wb-mart`, `action = resume`.

После этого витрина строится сама, без человека. Дальше — окно наблюдения.

## ⚠️ Осознанный риск окна наблюдения

Алертов (PR-Mart3b-5) ещё нет. Значит **три ERROR подряд за день никто не заметит автоматически**.
На время окна роль алерта выполняет человек: ежедневный прогон Q1 из
`sql/mart3/pr_mart3b4_rollout_check.sql`. Решение принято сознательно — 3b-5 идёт сразу за окном,
чтобы слепое пятно закрылось раньше, чем прекратится ручное наблюдение.

Отдельно помнить: **ads делает одну попытку в сутки (~05:07, ретраев нет)**. Если падает ads,
ни одно из четырёх окон витрину не спасёт — это лечится в PR-Mart3b-6, а не расписанием.

## Ежедневная проверка (окно 3–5 дней)

Каждое утро после 07:30 МСК гонять **Q1** из `sql/mart3/pr_mart3b4_rollout_check.sql`.
Ожидаемая строка за вчерашний `target_date`:

| Поле | Норма |
|---|---|
| `verdict` | 🟢 OK |
| `built_at_msk` | **07:0x** — сработало основное окно |
| `attempts` | 1 (happy path) |
| `errors` | 0 |
| `mart_rows` | > 0, дельта ко вчера в разумных пределах (наблюдалось +24/день) |
| `dur_s` | ~180 (наблюдалось 177–194) |

При 🟡/🔴 — Q2 (детализация: `freshness_json` покажет виноватый источник, `steps_json` — шаг),
затем Q4a/Q4b из `sql/mart3/pr_mart3b3_freshness_readiness.sql` (состояние слота sales 10:2x).
Q3 — независимая проверка свежести самой витрины: `days_behind` обязан быть 0,
`distinct_builds` = 1.

### Что означают вердикты

- **🟢 OK** — витрина построена без зафиксированных ERROR.
  `built_at_msk` показывает, какое окно фактически выполнило построение;
  норма для основного окна — `07:0x`.
- **🟡 OK ПОСЛЕ РЕТРАЯ** — первое окно упало, следующее починило. Система отработала как задумано,
  но `error_trail` разобрать: если это `FRESHNESS_GATE` из-за sales — проверить Q4a (PR#87).
- **🔴 FAILED** — за день витрина не построена ни одним окном. Разбираться в тот же день.
- **⚫ НЕТ ЖУРНАЛЬНОЙ ПОПЫТКИ** — за этот `target_date` в журналах нет ни одной строки. Само по себе
  это НЕ означает, что Scheduler не сработал: окна, вышедшие по `guard_skip`, строк не пишут.
  Различать по Cloud Scheduler / Cloud Run Executions — сработали ли окна вообще, и по
  `built_at_msk` соседних дней.

## Критерии успеха окна

Rollout считается принятым, если за 3–5 подряд суток:

1. каждый день имеет 🟢 или 🟡 (ни одного 🔴 и ни одного ⚫);
2. минимум 3 дня из них — 🟢 с `built_at_msk = 07:0x` (основное окно рабочее, а не фолбэки);
3. `distinct_builds = 1` и `days_behind = 0` в Q3 на каждое утро;
4. ни одного `lease_only_no_mart = TRUE`;
5. в `MART_RUNS` **ровно одна** строка COMPLETE на каждый `target_date` — дубликатов построения нет.

## Откат

Если пошло не так: `Actions → scheduler-control` → `action = pause`, `loader = wb-mart`,
`environment = prod`. Расписание останется в Terraform (`ignore_changes = [paused]` гарантирует,
что следующий `terraform apply` состояние паузы не тронет), витрину можно строить `run-now`,
как раньше. Данные при этом не страдают: `sp_build_mart_sku_daily` полностью пересобирает
`MART_SKU_DAILY` от global_start, поэтому пропущенный день = устаревшая витрина, а НЕ дыра в
истории (проверено 11.08: один `build_as_of_date` на всю таблицу, 705 дней данных, 7036 строк).
