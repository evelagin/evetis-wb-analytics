## 1. Forensic: фактическая форма `raw_json`

Схема WB из документации не принималась. Разобраны все 22 291 строк production.

**18 путей присутствуют в 100 % строк** — форма стабильна на всей истории:

```json
{ "id": 23732891, "bid_type": "unified", "currency": "RUB", "status": 7,
  "settings": { "name": "…", "payment_type": "cpm",
                "placements": { "search": true, "recommendations": true } },
  "restrictions": { "can_change_nms": true },
  "timestamps": { "created": "…", "started": "…", "updated": "…", "deleted": "…" },
  "nm_settings": [ { "nm_id": 305101272,
                     "bids_kopecks": { "search": 40000, "recommendations": 40000 },
                     "subject": { "id": 372, "name": "сыворотки" } } ] }
```

| Путь | Тип | Домен / наблюдения |
|---|---|---|
| `$.id` | number | никогда NULL; **0 расхождений** с плоской колонкой `advertId` |
| `$.status` | number | `{7, 9, 11}` |
| `$.bid_type` | string | `{manual, unified}` |
| `$.settings.payment_type` | string | `{cpc, cpm}` |
| `$.settings.name` | string | никогда NULL |
| `$.settings.placements.search` / `.recommendations` | bool | `{true, false}` |
| `$.currency` | string | только `RUB` |
| `$.restrictions.can_change_nms` | bool | |
| `$.timestamps.{created,started,updated,deleted}` | string | 100 % парсятся `%Y-%m-%dT%H:%M:%E*S%Ez` |
| `$.nm_settings` | 🔴 **array \| null** | null у **11 752 (52,7 %)**, массив у 10 539 |
| `$.nm_settings[].nm_id` | number | 10 539 / 10 539, NULL нет |
| `$.nm_settings[].bids_kopecks.search` | number | всегда присутствует, 0…150 000 |
| `$.nm_settings[].bids_kopecks.recommendations` | number | всегда присутствует, 0…150 000 |
| `$.nm_settings[].subject.{id,name}` | number/string | NULL нет, 5 названий |

🔴 **`campaign_type` в `raw_json` ОТСУТСТВУЕТ.** Единственный источник — плоская колонка
`type`, единственное наблюдаемое значение `'9'`.

🔴 **Плоские колонки `payment_type`, `name`, `campName`, `nm_ids` пусты во всех 22 291
строке** — использовать их нельзя, всё берётся из JSON.

Альтернативных форм `bids_kopecks` не обнаружено: объект либо есть целиком с обоими
ключами, либо отсутствует вместе со всем `nm_settings`.

## 2. Грейн — гипотеза ADS-0 отвергнута данными

| Кандидат | Уникальных ключей | Вердикт |
|---|---:|---|
| `snapshot_ts × advert_id` | **22 291** = число строк | ✅ уникален |
| `snapshot_ts × advert_id × nm_id` | 22 291 | эквивалентен (nm ≤ 1) |
| `snapshot_date × advert_id` | **21 011** | 🔴 теряет **1 280 строк** |

- 290 различных `load_ts`, 52 `run_id`, 49 суток, 430 кампаний
- **1 280** пар «сутки × кампания» имеют 2 снимка за день
- 🔴 **22** пары имеют **разную конфигурацию внутри одних суток** — реальные
  внутридневные состояния (преимущественно смена `status` 9↔11)
- точных дублей на одном `load_ts` — **0**

**Решение: `snapshot_ts × advert_id × nm_index`.** Суточная свёртка сделана
отдельной вью `V_ADV_CAMPAIGN_CONFIG_DAILY` с явным правилом: **последний снимок
суток** по `snapshot_ts`, при равенстве — больший `run_id`. Детерминизм обеспечен
уникальностью `(snapshot_ts, advert_id)`. В шапке вью прямо сказано, что
внутридневные состояния там теряются по построению.

`nm_index` оставлен в ключе намеренно: сегодня `nm_settings` — массив ровно длины 1
(`min_len = max_len = 1`) либо JSON null, поэтому фактически грейн равен
`snapshot_ts × advert_id`. Если WB начнёт присылать несколько настроек, вью честно
вырастет в строках вместо молчаливой потери, и это будет видно по `nm_settings_count`.

## 4. NULL-семантика

Различаются три разных состояния, zero-fill не применяется нигде:

| Состояние | Как выражено | Строк |
|---|---|---:|
| Пономенклатурной настройки НЕТ | `nm_settings_count = 0`, ставки и `nm_id` = **NULL** | 11 752 |
| Настройка есть, WB вернул ноль | ставка = **0** | search 208, reco 2 520 |
| Настройка есть, ставка задана | ставка > 0 | остальные |

`NULL` и `0` означают разное и никогда не смешиваются. Случая «поле отсутствует в
историческом payload» не обнаружено: где `nm_settings` есть, обе ставки присутствуют
всегда.

## 5. Enum

Расшифровки числовых кодов не выдумывались. `status_raw` остаётся строкой `{7,9,11}` —
**семантика UNPROVEN**. `campaign_type_raw` = `'9'` — **UNPROVEN**. `payment_type_raw`
и `bid_type_raw` приходят от WB строками и самоописательны, но суффикс `_raw` сохранён:
нормализация — задача следующего этапа. `appType` в этом слое не участвует вовсе.

## 6. Кампанийные ставки ≠ ставки по запросам

| | Этот слой | `RAW_WB_ADV_QUERY_BIDS` |
|---|---|---|
| Источник | `RAW_WB_ADV_CAMPAIGNS.raw_json` | `normquery/get-bids` |
| Грейн | snapshot_ts × advert × nm_index | snapshot_date × advert × nm × norm_query |
| Что за ставка | на **размещение** (search / recommendations) | на **поисковый запрос** |
| Единицы | копейки | рубли + копейки |
| История | 11.07–06.09.2026, 49 суток | с 14.08.2026 |
| Покрытие | 430 кампаний | 17 кампаний, только `manual`+`cpm` |

Слои не пересекаются и не должны объединяться: разные сущности, разные грейны,
разная история. Никаких join'ов между ними в ADS-2 нет.

## 9. Качество данных — все проверки пройдены

| Проверка | Ожидание | Факт |
|---|---|---|
| Строк вью = строк RAW | 22 291 | **22 291** — потерь и fan-out нет |
| Уникальность грейна | = числу строк | **22 291**, дублей **0** |
| `advert_id IS NULL` | 0 | **0** |
| `snapshot_ts IS NULL` | 0 | **0** |
| Отрицательные ставки | 0 | **0** |
| `nm_settings_count>0`, но `nm_id` NULL | 0 | **0** |
| `nm_settings_count=0`, но ставка не NULL | 0 | **0** |
| `search_bid_rub = kopecks/100` | точно | **0** расхождений |
| `recommendations_bid_rub = kopecks/100` | точно | **0** расхождений |
| Строк с `nm_settings_count > 1` | 0 | **0**, максимум = 1 |
| `settings_updated_at` не распарсился | 0 | **0** |
| Детерминизм повторного запуска | хеши равны | ✅ snapshot и daily |

Fan-out невозможен по построению: `LEFT JOIN UNNEST` по массиву длины ≤ 1.
`LEFT` обязателен — иначе 11 752 снимка кампаний без пономенклатурной настройки
исчезли бы из истории.
