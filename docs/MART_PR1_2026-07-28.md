# PR-Mart1 — FACT-слой MART (реализация)

**Дата:** 2026-07-28 (rev2 после аудита)
**Дизайн:** `docs/MART_DESIGN_2026-07-23_rev2.md` (аудит APPROVE WITH CHANGES; виза владельца дана 28.07)
**Файлы:** `sql/mart/pr_mart1_facts.sql` (создаёт объекты), `sql/mart/pr_mart1_validation.sql` (read-only проверки), `sql/mart/pr_mart1_negative_tests.sql` (негативные тесты каждого класса каста)
**Статус:** аудиты #1 (5) + #2 (4) + #3 (fail-closed guards + 2 синхр + lock-idempotency) = REQUEST CHANGES → **все замечания закрыты** → на APPROVE. `wb_mart` до APPROVE НЕ создаётся.

## Правки аудита #1 (REQUEST CHANGES → закрыто)

1. **Потеря partition/cluster на publish.** `CTAS SELECT *` НЕ наследует физику →
   PARTITION BY / CLUSTER BY **повторены на всех 6 финальных таблицах**; добавлена
   ASSERT-валидация физики через `wb_mart.INFORMATION_SCHEMA.COLUMNS`
   (`is_partitioning_column`=1, число `clustering_ordinal_position` как задумано: 2/2/2/3/2/1).
2. **Неполный parse-QC.** ORDERS: добавлен ASSERT `quantity`. ADS_SKU: ASSERT на
   `date, advertId, nmId, views, clicks, orders, sum`. ADS_COSTS: `updDate, advertId, updSum`.
   Добавлены ASSERT «все grain-ключи и partition-даты в BUILD NOT NULL» на каждый факт.
3. **Небезопасный `'%s'`.** Убрана строковая интерполяция; `run_id`/`built_at` передаются
   **query-параметрами** `EXECUTE IMMEDIATE ... USING @run_id, @built_at`.
4. **«Атомарность всего набора» отозвана.** Процедура переименована в
   `sp_bootstrap_facts`, помечена **BOOTSTRAP / MANUAL-ONLY**: advisory-lock
   `_MART_BOOTSTRAP_LOCK` (конкурентный запуск запрещён), потребителей не подключать
   до PR-Mart3; единую публикацию всего набора (staging-набор → один переключатель) даёт PR-Mart3 (Cloud Run + execution-guard).
   Комментарии и отчёт обновлены.
5. **Дата ADS_SKU.** `DATE(SAFE_CAST(... AS TIMESTAMP))` → **`SAFE.PARSE_DATE('%Y-%m-%d', SUBSTR(date,1,10))`**
   (календарная дата без TZ-каста) + parse-QC даты.

**Пост-фикс проверки (read-only, 28.07):** повторные пробы — NULL grain/partition = 0,
все касты/парсы = 0 (вкл. новый ADS_SKU date=0 null, quantity/views/clicks/orders/advertId = 0 сбоев);
негативные тесты — `all_guards_fire = TRUE` (money 3, int64 3, date 2, grain-null 1, dedup TRUE).
Физику final FACT (partition/cluster) проверяет ASSERT после publish + `pr_mart1_validation.sql`.

## Правки аудита #2 (REQUEST CHANGES → закрыто)

1. **Shadowing переменных/колонок в lock.** `DECLARE run_id` совпадал с колонкой `run_id`
   (`UPDATE ... SET run_id = run_id` неоднозначен). Переменные → **`v_run_id` / `v_built_at`**;
   во всех `EXECUTE IMMEDIATE` — `USING v_run_id AS run_id, v_built_at AS built_at`; при acquire
   пишем `run_id = v_run_id`. Release решён явно: `is_running=FALSE, run_id=NULL, last_run_id=v_run_id`
   (добавлена колонка `last_run_id` для аудита) — и при успехе, и в EXCEPTION.
2. **Finance-ключ маскировал NULL.** `CONCAT(IFNULL(report_id,''),'#',IFNULL(rrd_id,''))` прятал
   отсутствие части, а `finance_row_key IS NULL` её не ловил. Добавлен **ASSERT по источнику**
   (`report_id`/`rrd_id` NOT NULL и NOT empty), ключ строится `CONCAT(report_id,'#',rrd_id)` без IFNULL.
   Строковые грейны ORDERS/SALES усилены — ловим **NULL И empty** (`order_srid`, `sale_id`).
   (Проверено live 28.07: report_id/rrd_id/srid/sale_id пустых/NULL = 0.)
3. **Validation использовал старый код даты ADS.** `DATE(SAFE_CAST(date AS TIMESTAMP))` →
   `SAFE.PARSE_DATE('%Y-%m-%d', SUBSTR(date,1,10))` (как в процедуре); в validation выведен полный
   parse-QC `date/advertId/nmId/views/clicks/orders/sum`.
4. **Документация.** `sp_build_facts` → `sp_bootstrap_facts` везде; формулировка «атомарный publish
   всего набора» убрана → «последовательный publish каждой FACT» (единая публикация набора — PR-Mart3).

До ФИНАЛЬНОГО APPROVE `wb_mart` НЕ создаётся.

## Правки аудита #3 (REQUEST CHANGES → закрыто)

1. **Fail-closed: пустой источник мог стереть FACT.** Перед publish на каждый из 6 FACT добавлены
   volume-guards: (а) `ASSERT COUNT(*) > 0` (непустой BUILD) и (б) соответствие объёму —
   ORDERS/SALES/FINANCE `BUILD rows = source rows`; ADS_SKU/ADS_COSTS/STOCKS
   `BUILD rows = source distinct grain` (для STOCKS — по ВЫБРАННЫМ последним COMPLETE-снапшотам).
   Проверено live 28.07: ORD 3804, SALE 3563, FIN 202471, ADS_SKU 4962, ADS_COSTS 1558, STOCKS 1509 —
   BUILD совпадает. (Источник читается в рантайме: редкий дозаписанный ряд во время прогона может
   вызвать несоответствие → прогон fail-SAFE прерывается до publish, prod не тронут, нужен повтор.)
2. **Синхронизация validation (finance-ключ).** `CONCAT(IFNULL(...))` заменён на `CONCAT(report_id,'#',rrd_id)`;
   добавлен вывод `key_parts_fail = COUNTIF(report_id/rrd_id NULL или empty)`.
3. **Синхронизация числа денежных колонок.** «12» → **13** (включая `other_amount`) — в отчёте; процедура и
   validation и так проверяли 13.
4. **Идемпотентность lock-схемы.** После `CREATE TABLE IF NOT EXISTS _MART_BOOTSTRAP_LOCK` добавлен
   `ALTER TABLE ... ADD COLUMN IF NOT EXISTS last_run_id STRING` (на случай старой версии таблицы без колонки).

До ФИНАЛЬНОГО APPROVE `wb_mart` НЕ создаётся.

## Что / зачем / риск

**Что:** датасет `wb_mart` (EU) + хранимая процедура `wb_mart.sp_bootstrap_facts(run_id)` (BOOTSTRAP/MANUAL-ONLY),
которая строит 6 таблиц FACT из живых вью `wb_raw` по паттерну
**BUILD → ASSERT (parse-QC + not-null/not-empty grain + дедуп) → последовательный publish каждой FACT**.

**Зачем:** первый слой MART (rev2, §2.1–2.6, §11). На нём затем строятся витрины
`MART_SKU_DAILY` / `MART_ACCOUNT_DAILY` (PR-Mart2) и оркестратор + freshness-gate + run-log + триггер (PR-Mart3).

**Движок (решение владельца 28.07):** MART собираем **engine-agnostic BigQuery** (хранимая процедура),
т.к. проект уходит с Apps Script на Cloud Run — новый Apps Script под MART не пишем. Оркестратором
позже станет Cloud Run Job (`node dist/cli.js mart` → `CALL wb_mart.sp_bootstrap_facts('')`), консистентно
с миграцией остатков. Логика трансформаций в SQL переносима между движками.

**Риск и как снят:**
- Смешение типов (деньги-строки с запятой) → `SAFE_CAST(REPLACE(x,',','.') AS NUMERIC)` + ASSERT parse-QC=0.
- Разные типы nm_id (STRING в orders/finance/ads, INT64 в sales/stocks/REF) → единый каст к INT64 + ASSERT=0.
- Неатомарность (Блокер 4) → BUILD-таблицы + ASSERT'ы до publish; **последовательный publish каждой FACT**
  (`CREATE OR REPLACE TABLE ... AS SELECT`, НЕ атомарно по всему набору). Единая публикация набора и run-log — PR-Mart3.
- Несколько COMPLETE-снапшотов остатков в день (правка 7) → берём последний по `started_at`, затем сумма складов.
- Реклама смешивала грейны (Блокер 1) → два раздельных факта (SKU-директивный vs costs-истина).

## Приёмка (§8) для этого PR
1. Дедуп: rows(FACT_*) == distinct(ключ) — все 6 ✓ (см. выше, ASSERT в процедуре).
2. Parse-QC (§6) = 0 — ✓ (ASSERT в процедуре).
3. Реклама-инвариант Σcosts ≥ Σstats — ✓.
4. Покрытие: операционка с ~2026-04-13, финансы с 2024-09-05 — ✓.
Полнота денег (§8.4, `Σ SKU + ACCOUNT == Σ FINANCE`) и раздельные возвраты — проверяются на PR-Mart2 (витрины).

## Как запускать (после ПОВТОРНОГО аудита, владелец, БЕЗ параллельных запусков)
```sql
-- 1) датасет + lock + процедура:
--    выполнить sql/mart/pr_mart1_facts.sql
-- 2) bootstrap фактов (manual-only):
CALL `wb_mart.sp_bootstrap_facts`('');   -- '' → авто-UUID run_id; вернёт mart_run_id + FACTS_BOOTSTRAPPED
-- 3) сверить: выполнить sql/mart/pr_mart1_validation.sql (вкл. проверку физики через INFORMATION_SCHEMA)
```
Негативные тесты: `sql/mart/pr_mart1_negative_tests.sql` (предикаты guard'ов, read-only) +
сквозной тест в песочнице (описан в шапке файла): битое money → ASSERT прерывает bootstrap,
финальные FACT НЕ перезаписываются, lock освобождается. Потребителей до PR-Mart3 не подключать.

## Не входит в PR-Mart1 (следующие шаги)
- **PR-Mart2:** `MART_SKU_DAILY` (day×nm) + `MART_ACCOUNT_DAILY` (day×cost_category), джойны, «не сопоставлено»,
  раздельные возвраты, `unattributed_spend = Σcosts − Σstats`, контрольные §8.4. Блокеры-решения владельца:
  список `cost_category` (идёт анализ), поведение freshness-gate при OK_NO_NEW (готовятся варианты).
- **PR-Mart3:** `runWbMartDaily` (Cloud Run Job) + freshness-gate + `MART_LOADER_RUNS` + full-set staging + триггер ~09:00 МСК.
- **MART v2:** прибыль/маржа — после COGS в BQ (REF Sync PR2) и recon базы выручки for_pay.
