## Почему это не подтверждённое исправление

**1. Сумма групп 2+3 одинакова в обоих вариантах — 255 611,51 ₽.**
Обе версии замыкают тождество на один и тот же итог 9 660 106,53 ₽. Денег
не теряется ни там, ни там; различается только граница между двумя группами
(248,98 ₽ и 96 строк переходят из группы 3 в группу 2).

**2. Цифра из stash противоречит перечню компонент, стоящему строкой ниже.**
Перечень в обеих версиях одинаков и не менялся:

```
acquiring 449 142,73 + loyalty 87,40 + penalty(SKU) 1 322,00
        + reimbursement_logistics(SKU) −209 900,62 = 240 651,51
```

Точная сумма — **240 651,51**, то есть значение из **main**. Значение из
stash (240 900,49) этим компонентам не соответствует. Похоже, при
перезамере обновили итог и число строк, но забыли перечень компонент.
Применение правки как есть сделало бы документ внутренне противоречивым.

**3. Проверить по BigQuery сегодня нельзя.**
Замер делался 20.08.2026. Сегодня `wb_mart.V_WB_FINANCE_AMOUNTS_LONG_MAPPED`
даёт `SUM(cost_amount_positive) = 7 198 114,42` при 245 581 строке и
`max(finance_date) = 2026-09-05`. Это не рост данных, а другая величина:
итог **меньше** задокументированных 9 660 106,53 — значит вью или его
источник с тех пор переопределяли. Ни цифру main, ни цифру stash сегодняшним
замером воспроизвести нельзя.

## Что сделано

Ничего не применено. `sql/dash/dashboard_contract_v2.sql` в main не тронут —
и это важно: с 26.08 он получил 67 строк жёсткого правила Stage 1.10B о двух
несовместимых базах дат выкупа. Механическая замена файла из stash стёрла бы
