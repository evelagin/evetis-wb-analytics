# UNITKA 2.0 — аудит обратной логистики WB (отмены и возвраты)

Источник: `wb_raw.V_WB_FINANCE_CANONICAL` (канонический финансовый отчёт WB).
Окна: 01.06–09.09.2026 (для устойчивости выводов) и 11.08–09.09.2026 (rolling-30, рабочее окно модели).
Сверка привязки: `wb_mart.FACT_ORDERS.is_cancel`.
Агент claude-opus-5, 11.09.2026. **Формула сводки по итогам аудита НЕ менялась.**

## 1. Есть ли отдельная фактическая операция обратной логистики

**Отдельной строки с именем операции «обратная логистика» — нет.** Проверено по всем
значениям `supplier_oper_name` за три месяца:

| операция | строк | что это |
|---|---|---|
| Возмещение издержек по перевозке / складским операциям | 5 829 | WB возвращает продавцу, а не удерживает |
| Продажа | 2 228 | выкупы |
| **Логистика** | **2 531** | **вся логистика, 147 638,6 ₽ — и прямая, и обратная** |
| Возмещение издержек по перемещению и обработке | 213 | возврат продавцу |
| Доставка | 144 | 8 621,5 ₽ |
| Хранение / Коррекция хранения | 101 | |
| Возмещение за выдачу и возврат товаров на ПВЗ | 97 | 0 ₽ |
| **Возврат** | **1** | за три месяца — одна строка, не является механикой отмен |
| Удержание, Штраф, баллы за отзывы | 78 | |

`operation_type_normalized` пустой у всех строк, `doc_type_name` у «Логистики» пустой —
ни одно поле не размечает прямое/обратное плечо.

**Обратное плечо в данных есть, но выражено формой записи, а не именем операции:**
у заказа, от которого покупатель отказался, появляется **вторая строка «Логистика» с тем же `srid`**.

## 2. Доказательство: две строки «Логистика» = отказ

Окно 01.06–09.09, группировка по `srid`:

| строк логистики на srid | srid'ов | есть строка «Продажа» | нет «Продажи» | подтверждено `is_cancel` | средняя логистика на srid |
|---|---|---|---|---|---|
| 1 | 2 107 | 2 105 | 2 | 0 | **60,31 ₽** |
| 2 | 212 | 1 | **211** | **172** | **96,96 ₽** |

То есть: один `srid` с одной строкой логистики = выкуп; с двумя — почти всегда нет выкупа
и в 81 % случаев заказ помечен `is_cancel = TRUE` в `FACT_ORDERS`. Оставшиеся 18 % — заказы
старше горизонта `FACT_ORDERS`, противоречащих случаев один из 212.

Разложение двух плеч (01.06–09.09): меньшее плечо **33,48 ₽**, большее **63,48 ₽**.

## 3. Атрибуция к nmID — есть

`wb_nm_id` заполнен у **100 %** строк «Логистика», `srid` — у 100 %. Отказ однозначно
привязывается к SKU. Проблема не в атрибуции, а в объёме наблюдений (см. §5).

Нет. За rolling-30 по всем 24 блокам набралось **44 отказа на 17 SKU**:

## 6. Подтверждается ли допущение «50 ₽ × отмены»

**Нет.** 50 ₽ не совпадает ни с одним из двух осмысленных определений:

| определение | факт rolling-30 | 50 ₽ отклоняется на |
|---|---|---|
| только обратное плечо (доп. расход отказа) | 32,02 ₽ | +56 % |
| полная логистика отказанной единицы | 92,63 ₽ | −46 % |

Константа 50 ₽ находится между ними и не воспроизводится из данных ни при каком
разумном определении. Как окончательный тариф её использовать нельзя.

## 7. Двойной счёт — главная находка

Ставка логистики SKU в модели считается как **вся логистика окна / выкупы**:
38 715,60 ₽ / 553 = 70,0101 ₽/ед. Числитель уже включает 4 075,70 ₽ (10,5 %) логистики,
уплаченной **за отказанные единицы**, — они размазаны по выкупам.

Значит, отказы **уже оплачены внутри ставки логистики**. Дополнительное вычитание
`отмены × 50 ₽` в `I767` списывает те же деньги второй раз.

Владельцу нужно выбрать соглашение учёта — оба корректны, но смешивать их нельзя:

**Вариант A — «ставка по выкупам» (то, как считается сейчас).**
Логистика = вся логистика / выкупы. Отказы уже внутри. Тогда отдельный член за отмены
должен быть **0**, а не 50 ₽. Плюс: одна ставка, ничего не забудешь. Минус: отказ не виден
как отдельная статья, дорогие по возвратам SKU маскируются.

**Вариант B — «событийный».**
Логистика = только прямые плечи выкупов / выкупы = **60,37 ₽/ед**, а каждый отказ
списывается отдельно по факту: **92,63 ₽** (полная логистика отказа) или **32,02 ₽**
(только обратное плечо, если прямое считать понесённым в любом случае).
Плюс: отказы видно и ими можно управлять. Минус: два источника вместо одного.

Масштаб на сентябре 01–09: отмен 6. Разница между 50 ₽ и фактом — сотни рублей,
но принцип влияет на все будущие периоды и на Engine.

## 8. Что предлагается для Engine

1. **Не константа.** Ставка обратной логистики считается из финотчёта тем же механизмом,
   что комиссия и логистика: окно D-30..D-1 от `LAST_CLOSED_DATE`, пересчёт каждый прогон.
2. **Уровень — магазин, не SKU.** `n = 44` за 30 дней по магазину — MEDIUM;
   по SKU (0–13) — LOW. Собственную ставку SKU включать только при `n ≥ 10`
   (сейчас проходит один SKU) — тем же правилом, что уже принято для прямой логистики.
3. **Пер-день по сентябрю фактом закрыть нельзя.** Удержание за обратное плечо приходит
   в финотчёт через 2–6 недель после заказа: отказы, попавшие в окно 11.08–09.09, имеют
   даты заказа 25.07–25.08. За 01–09.09 фактов ещё нет. Поэтому дневная строка сентября
   может быть закрыта только модельной ставкой, а фактом — задним числом, при пересчёте.
4. **Fallback (rolling/model).** Пока факта по дню нет:
   `обратная_логистика_день = отмены_день × ставка_обратного_плеча_rolling30`,
   ставка = Σ(обратные плечи) / число отказов за окно, сегодня 32,02 ₽.
   При появлении факта строка пересчитывается и расхождение уходит в сверку.
5. **Соглашение учёта фиксирует владелец** (вариант A или B из §7). До этого решения
   формулу сводки не трогаем.

## Как это проверить повторно

```sql
WITH lg AS (
  SELECT srid, SAFE_CAST(wb_nm_id AS INT64) nm_id,
         SAFE_CAST(logistics_amount AS NUMERIC) amt,
         ROW_NUMBER() OVER (PARTITION BY srid ORDER BY SAFE_CAST(logistics_amount AS NUMERIC)) rn,
         COUNT(*)     OVER (PARTITION BY srid) legs
  FROM `project-fa311fc0-4d87-4781-986.wb_raw.V_WB_FINANCE_CANONICAL`
  WHERE supplier_oper_name = 'Логистика'
    AND _rr_date BETWEEN DATE '2026-08-11' AND DATE '2026-09-09'
)
SELECT legs, COUNT(DISTINCT srid) srids,
       ROUND(SUM(amt) / COUNT(DISTINCT srid), 2) rub_per_srid,
       ROUND(SUM(IF(rn = 1, amt, 0)) / NULLIF(COUNTIF(rn = 1 AND legs = 2), 0), 2) reverse_leg
FROM lg GROUP BY legs ORDER BY legs;
```
