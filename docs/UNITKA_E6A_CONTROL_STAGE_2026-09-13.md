## 3. Что пришлось исправить в `UnitkaE6.gs` (инфраструктура, не бизнес-логика)

Первый живой прогон выявил три дефекта подготовленной версии `9a7daef`; все исправления — в этом
коммите, каждое проверено повторным запуском. Логика печи/удаления/добавления УФ, заморозки, правок
F1–F6 и гейтов QA не менялась.

1. **`SpreadsheetApp.getActive()` = null.** Проект «Проект без названия» — standalone, а не bound
   (в нём и прежние скрипты открывают книгу через `openById`). `ss_()` теперь
   `getActive() || openById(E6.SSID)`. Первый `e6backup` упал на строке 82 до каких-либо действий.
2. **`Out of memory` в `e6snapshot`.** Снимок значений/формул/визуала/УФ (≈37 МБ JSON) плюс
   статические фоны через Sheets API в одном запуске не помещаются в память. Снимок разделён:
   `e6snapshot` (часть 1, освобождает большие объекты после записи каждого файла) и
   `e6snapshotStatic` (часть 2; чанки по 50 строк). Часть 2 сделана возобновляемой по листам, потому
   что один главный лист (`includeGridData`, 767×600) занимает ≈330 с из лимита 360 с: первый запуск
   успел только главный лист (`Exceeded maximum execution time`), второй — 2024 и OZON. Файлы теперь
   по листам: `snap_static_bg__<лист>.json`; `e6rollback` читает их так же.
3. **Ключ группировки формульных правил.** Sheets API отдаёт цвета с произвольным порядком ключей
   (`red/green/blue` в разном порядке у одинаковых форматов), из-за чего `JSON.stringify(format)`
   давал 301 группу вместо 30 и первый dry-run показал 4 671 → 403 правила (фрагментов всё равно 895).
   Введён `canon_()` — сериализация с сортировкой ключей — для ключей и формульных, и градиентных
   правил. После исправления dry-run совпал с репетицией.

Дополнительно: `apps-script/UnitkaE6Run.gs` — диспетчер `e6()` (выпадающий список функций в
редакторе не переключается автоматизацией: клик по `e6snapshot` привёл к повторному `e6backup`).
