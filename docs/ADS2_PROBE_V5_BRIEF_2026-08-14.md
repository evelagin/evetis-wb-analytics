# Ads-2 · Probe v5 — бриф

Дата: 2026-08-14 · файл: `apps-script/WbAdsProbeV5.gs` · точка входа: `probeV5_runAll()`
Режим: **read-only**. Ничего не пишет — ни в листы, ни в BigQuery, ни в Script Properties.
Ни одного write-вызова WB: ставки не трогаются, кампании не меняются.
Длительность ~2 минуты, 11 HTTP-вызовов, собственный тайм-бюджет 5 минут.

## Зачем

Дизайн Ads-2 (query-level stats + backfill) упирается в четыре вопроса, ответы на которые
есть только у API, и один — про полноту нашей схемы.

| блок | вопрос | почему нельзя ответить из хранилища |
|---|---|---|
| **A** | принимает ли `normquery/stats` окно `from = to` (одни сутки) и отдаёт ли данные | у нас лежит ровно один недельный срез, суточных запросов мы не делали никогда |
| **B** | воспроизводится ли прошлое: тот же запрос за 04–10.07 даёт те же 44 строки и 297 ₽ | если выдача за прошлое «плывёт», backfill надо проектировать с переснятием |
| **AB** | **аддитивны ли сутки** — сходится ли сумма семи суточных запросов с одним недельным | это и есть решение о грейне; из данных не выводится |
| **C** | сколько пар реально принимает один запрос: 10 / 50 / 100 | в документации 100, на нашем контуре не проверено ни разу |
| **D** | есть ли потолок числа кластеров на пару (обрезка выдачи) | наблюдали максимум 19 на пару у ставок, потолок неизвестен |
| **E** | полный инвентарь полей ответа | схема RAW уже теряет `spend`, `shks`, `currency` — надо знать, что ещё |

## Позитивный контроль (блок B)

Probe считает ту же неделю, что уже лежит в `RAW_WB_ADV_SEARCH_CLUSTERS` с 11.07.2026:

```
пара 36047250 / 438775437 · период 2026-07-04 … 2026-07-10
ожидается: 44 строки · spend 297,00 ₽ · clicks 27 · atbs 3 · orders 2 · shks 2
```

Эти же 297 ₽ — ровно сумма списаний с баланса за те дни (21+60+36+108+72 по `V_ADV_COSTS`).
То есть query-level расход уже один раз сошёлся с деньгами до рубля. Если блок B
воспроизводит цифры — эндпоинт стабилен и пригоден как источник расхода по запросам.
Если НЕ воспроизводит — это важнее всех остальных блоков, и дизайн меняется целиком.

## Что probe НЕ делает

* не меняет ставки и вообще ничего не пишет в WB;
* не пишет в наши таблицы и листы — только Execution log;
* не трогает `runWbAdsDaily`, триггеры и рекламный BQ-sink;
* не пытается сам решить вопрос о грейне: он измеряет, вывод делаем после лога.

## Как запустить

1. Вставить `WbAdsProbeV5.gs` в проект Apps Script новым файлом.
2. Выбрать функцию `probeV5_runAll` → Run.
3. Дождаться завершения (~2 минуты) и прислать **весь Execution log целиком**.

Токен берётся из Script Properties тем же способом, что и остальные загрузчики
(`getWbAdsToken_`), и в лог не попадает — печатается только имя ключа.

## Как читать результат (заранее, чтобы не толковать задним числом)

* **A: `HTTP 200`, но 0 строк во все семь дней** — это ещё не «суточное окно не работает».
  Возможно, у пары в те дни не было показов. Решает блок AB: если недельный запрос по той
  же паре данные вернул, а суточные — нет, значит суточная нарезка режет данные.
* **AB: счётчики (`spend/clicks/views/atbs/orders/shks`) обязаны совпасть.** Это одни и те
  же события, порезанные иначе. Расхождение = суточный грейн брать нельзя.
* **AB: наборы `norm_query` совпадать НЕ обязаны.** У суток порог показа может отсечь
  редкий запрос, который за неделю набрал вес. Это ожидаемое поведение, а не дефект.
* **C: «пакетов вернулось меньше, чем пар запрошено» — не дефект сам по себе.** У пары без
  показов в этот день данных нет. Дефект — если доля вернувшихся пакетов **падает с ростом
  размера пачки**: тогда API режет выдачу, и пачку надо уменьшать.
* **D: круглое число (20/25/30/50/60/100/200) — подозрение на обрезку**, а не на реальный
  максимум. Если максимум оказался круглым, до backfill нужен отдельный замер.
* **E: красным помечены поля, которые API отдаёт, а наша схема теряет.** Сегодня это
  `spend`, `shks`, `currency` — они попадают только в `raw_json`.

## Что дальше по плану Ads-2

После разбора лога: контракт данных → дизайн с явными инвариантами → ACK владельца →
код → внешний аудитор → PR. Backfill — только после того, как замерены пачка и потолок:
упереться в лимит на середине истории дороже, чем потратить три пробных запроса.
