## 1. C1 — журнал ранов `wb_raw.RAW_WB_ADV_COSTS_RUNS`

**Грейн:** `(run_id, window_index)` — по строке на КАЖДЫЙ HTTP-запрос к `adv/v1/upd`,
включая `http_success` с нулём строк и включая failed-попытки.

**Связь с RAW:** `run_id` + `(period_from, period_to)`. По F1 это однозначно: дата не может
прийти в одном ране из двух окон, поэтому «строки RAW этого окна» — определённое множество.
`window_index` фиксирует порядок окон внутри рана и нужен для воспроизводимости, а не для join.

**Схема** (все STRING — конвенция RAW-слоя проекта, как в `RAW_WB_ADV_QUERY_STATS_RUNS`):

```
load_ts             -- момент записи строки журнала
run_id              -- тот же id, что в RAW_WB_ADV_COSTS
source_method       -- 'adv/v1/upd'
window_index        -- 0,1,2… порядковый номер окна внутри рана
period_from         -- ЧТО МЫ ПРОСИЛИ (YYYY-MM-DD)
period_to
requested_days      -- DATE_DIFF(period_to, period_from) + 1
http_status         -- код ответа
http_success        -- 'true' / 'false'
returned_rows       -- сколько строк вернул WB (0 — легитимное наблюдение, ради него всё и делается)
returned_days       -- сколько различных updDate в ответе
returned_min_date   -- ЧТО НАМ ОТВЕТИЛИ: границы фактического диапазона
returned_max_date
rows_out_of_window  -- строк с updDate вне [period_from, period_to] (см. F4)
duration_ms
status              -- 'OK' | 'ERROR'
error_message
```

**Правка:** `apps-script/WbAdsRawLoader.gs`, функция загрузки costs (около строки 456, где уже
формируется цикл по окнам). Запись журнала — рядом с существующей записью для query stats.
Порядок записи внутри окна: сначала данные, затем строка журнала. Строка журнала — **commit-marker**
этого окна, как header в поставках: окно без строки журнала считается незавершённым и в снапшоты
не попадает. Ран, упавший на середине, оставит окна без маркеров, и они будут проигнорированы,
а не приняты за пустой ответ.

## 2. C2 — окна чтения, определённые данными

| Контур | Окно | Частота | run_id prefix |
|---|---|---|---|
| Operational reread | `D−14 … D−1` | ежедневно, как сейчас | `ADSRAW_` |
| Low-frequency audit | `D−45 … D−8` | еженедельно | `ADSAUDIT_` |
| Recheck queue | конкретные даты | ежедневно, пока не стабилизируются | `ADSRECHECK_` |

**Почему 14, а не 7.** Наблюдавшаяся ревизия — на D+7, ровно на границе текущего окна D−7…D−1.
Наблюдение обрывалось там же, где данные ещё менялись, поэтому «стабильность» была артефактом
прекращения чтения. 14 суток — стартовый кандидат: вдвое дальше наблюдавшейся ревизии.
Константа пересматривается по журналу (запрос в §8, инвариант I7), а не по памяти.

**Почему нужен audit до D−45.** Operational-окно закрывается на D+14. Без второго контура
поздняя коррекция после D+14 не была бы обнаружима **в принципе** — не потому, что её нет,
а потому что мы перестали спрашивать. Еженедельный audit на D−45…D−8 даёт каждой дате
ещё ~4–5 независимых наблюдений после выхода из operational-окна.

**Формулировка SLA.** `billed_complete` — это **operational settlement state по нашему SLA**,
а не утверждение о финальности данных WB. Мы не знаем и не заявляем, что WB больше не изменит
день. Мы заявляем ровно следующее: день был явно запрошен, ответ получен и наблюдаем,
день старше `SETTLE_DAYS`, и последние `N_STABLE` независимых чтений совпали. Любое последующее
расхождение снимает это состояние (§4).

## 3. C3 — snapshot-based canonical layer

### 3.1 Точный грейн снапшота

**Снапшот = `(run_id, window_index)`.** Одно окно одного рана = один полный ответ WB на один
явный запрос. Снапшот **покрывает** дату `D`, если:

```
journal.http_success = 'true'  AND  journal.status = 'OK'
AND  period_from <= D <= period_to
```

Доказательство отсутствия смешения: F1 — на 344 парах `(run_id, date)` ни одна дата не пришла
из двух окон одного рана. Значит «строки даты D из снапшота S» определены однозначно.

### 3.2 Механизм выбора снапшота для даты

```sql
-- для каждой даты — РОВНО ОДИН снапшот: последний успешный, покрывший её
chosen AS (
  SELECT d, run_id, window_index
  FROM (
    SELECT d, j.run_id, j.window_index,
           ROW_NUMBER() OVER (PARTITION BY d
                              ORDER BY j.load_ts DESC, j.run_id DESC, j.window_index DESC) rn
    FROM day_spine
    JOIN journal j
      ON  day_spine.d BETWEEN j.period_from AND j.period_to
     AND  j.http_success = 'true' AND j.status = 'OK'
  ) WHERE rn = 1
)
```

Канонические строки даты `D` = строки `RAW_WB_ADV_COSTS`, у которых
`run_id = chosen.run_id`, `(period_from, period_to)` = окно выбранного снапшота
и `updDate BETWEEN period_from AND period_to`.

Последнее условие отсекает out-of-window строки (F4): их снапшот не запрашивал, полным ответом
за ту дату они не являются, и именно они дали 65,00 ₽ из 334,00 ₽.

**Ключевое следствие.** Если запись исчезла в новом полном ответе — она исчезает из canonical,
потому что canonical **не объединяет** ответы, а берёт один. Отзыв (10.07, 77 ₽) и разовый
выброс (05.08, 192 ₽) лечатся тем же механизмом, без специальных правил.

### 3.3 Идентичность записи внутри снапшота

`(advertId, updTime)` — уникален внутри `(run_id, updDate)` на всех 344 парах (F2).
`updSum` — **атрибут**, не часть ключа. Это и есть исправление корневой ошибки текущего слоя:
в ключе `(advertId, updTime, updSum)` исправленная сумма выглядит новой записью, и старая
не умирает никогда.

Ключ нужен **не для суммирования** (снапшот берётся целиком), а для диффа снапшотов:
`keys_added` / `keys_removed` / `keys_amount_changed` в §4 и §8.

`updNum` для идентификации не использовать (F3).

### 3.4 Что происходит со старым `V_ADV_COSTS`

`V_ADV_COSTS` переопределяется на snapshot-based. Старое union-тело сохраняется как
`wb_raw.V_ADV_COSTS_UNION_LEGACY` на один релиз — для сверки и отката.
🔴 Это ломающее изменение семантики RAW-слоя: producer contract downstream
(`FACT_ADS_COSTS_DAILY`) меняет значения. Отдельный PR, отдельная приёмка, changelog.

## 4. C4 — completeness formula и поведение при поздней ревизии

### 4.1 Формула

```
requested_ok   = ∃ снапшот, покрывающий D, с http_success='true', status='OK'
                 и DATE(load_ts,'Europe/Moscow') >= D + 1
                 ⚠️ считается ПО ЖУРНАЛУ, поэтому успешный ответ с 0 строк — полноценное
                    наблюдение: «успешные сутки с 0 ₽» отличимы от «день не загружен»

age_ok         = DATE_DIFF(CURRENT_DATE('Europe/Moscow'), D, DAY) >= SETTLE_DAYS   -- 15

stable_reads   = число ПОСЛЕДНИХ ПОДРЯД успешных снапшотов D, у которых набор
                 (advertId, updTime, updSum) совпадает со снапшотом-победителем
stable_ok      = stable_reads >= N_STABLE                                          -- 3

billed_complete = requested_ok AND age_ok AND stable_ok
zero_spend_day  = billed_complete AND answer_rows = 0
not_loaded      = NOT requested_ok
```

`SETTLE_DAYS = 15` — на сутки дальше operational-окна (D+14), то есть день объявляется
settled только после того, как все 14 ежедневных чтений уже состоялись.
`N_STABLE = 3` — три независимых чтения подряд. Обе константы живут в одном месте
и пересматриваются по журналу инвариантом I7.

🔴 `stable_reads >= 2` отвергнуто сознательно: два совпавших чтения наблюдались и перед
ревизией 02.08 (там совпало семь). Само по себе число совпадений финальности не доказывает —
поэтому оно и не называется доказательством, а только одним из условий operational SLA.

### 4.2 Поздняя ревизия дня, который уже `billed_complete = TRUE`

Специального правила не требуется — формула делает это по построению:

1. Audit-ран (или recheck) даёт новый снапшот с другим набором ключей.
2. Он становится победителем → **сумма дня немедленно исправляется** (C3).
3. `stable_reads` обнуляется до 1 → `stable_ok = FALSE` → **`billed_complete` снимается**.
4. Дата попадает в **recheck queue** и читается ежедневно, а не раз в неделю; через
   `N_STABLE` суток совпадающих чтений состояние возвращается.

Наблюдаемость ревизии сохраняется отдельно и не затирается:

```
settled_first_at          -- когда день впервые стал settled (не сбрасывается никогда)
revised_after_settled_at  -- когда была замечена ревизия ПОСЛЕ settled
revision_count            -- сколько раз это случалось
revision_delta_rub        -- сумма последнего изменения (со знаком)
```

**Цена решения, названная явно.** На время ре-стабилизации (до 3 суток) billed-KPI этого дня
становятся NULL — исторический отчёт «моргнёт». Альтернатива — оставлять `TRUE` и молча
менять сумму — хуже: она означала бы, что флаг перестал что-либо гарантировать.
`settled_first_at` позволяет consumer'у отличить «никогда не был закрыт» от «временно снят».

## 5. Исторический bootstrap 13.04.2026 — сегодня

Старый загрузчик не журналировал пустые успешные раны, поэтому ретроспективно объявить
старые сутки полными нельзя: доказательства не существует, а не «оно где-то есть».
Единственный честный путь — **перечитать период заново уже журналируемым загрузчиком**.

### 5.1 Какие даты и какими окнами

* Диапазон: **13.04.2026 … CURRENT_DATE − 1** (на 20.08 это 129 суток).
* Лимит WB на `adv/v1/upd` — 31 день на запрос. Берём окна по **30 суток** с запасом:
  `13.04–12.05 · 13.05–11.06 · 12.06–11.07 · 12.07–10.08 · 11.08–19.08` → **5 окон на проход**.
* Каждое окно — отдельная строка журнала. Пустой ответ по окну — тоже строка журнала.

### 5.2 Сколько повторных чтений

**3 прохода** (`N_STABLE`), по одному в сутки, три дня подряд. Разнос по суткам обязателен:
проходы в один день не независимы — WB публикует списания в течение дня, и три чтения подряд
измерили бы один и тот же момент.

Результат: у каждой исторической даты появляется 3 снапшота нового контракта.
`age_ok` для них выполняется тривиально (все старше 15 суток), `requested_ok` — по журналу,
`stable_ok` — по трём проходам.

### 5.3 Как не повредить текущий RAW

* Bootstrap **только append**: новые строки в `RAW_WB_ADV_COSTS` с префиксом `ADSBACKFILL_`
  и строки в `RAW_WB_ADV_COSTS_RUNS`. Ни `DELETE`, ни `UPDATE`, ни `TRUNCATE`.
* Старые строки остаются на месте навсегда — они нужны для аудита расхождений.
* Snapshot-canonical перестаёт их выбирать сам, потому что bootstrap-снапшоты новее.
  Ничего удалять не нужно и нельзя.
* 🔴 Порядок обязателен: **сначала C3 (snapshot-canonical), потом bootstrap.**
  В обратном порядке bootstrap-строки попадут в union и изменят текущие числа
  непредсказуемым образом ещё до того, как появится механизм выбора снапшота.

### 5.4 Как получить canonical baseline и сравнить

После третьего прохода:

```sql
-- Дневная сверка нового canonical против текущего FACT
WITH new_canon AS (   -- V_ADV_COSTS (snapshot) → та же агрегация, что в FACT_ADS_COSTS_DAILY
  SELECT `date`, SUM(actual_spend_rub) new_rub FROM <snapshot canonical> GROUP BY `date`),
old_fact AS (
  SELECT `date`, SUM(actual_spend_rub) old_rub
  FROM `wb_mart.FACT_ADS_COSTS_DAILY` GROUP BY `date`)
SELECT `date`, old_rub, new_rub, new_rub - old_rub delta,
       CASE WHEN new_rub IS NULL THEN 'DAY_LOST'
            WHEN old_rub IS NULL THEN 'DAY_NEW'
            WHEN new_rub <> old_rub THEN 'CHANGED' ELSE 'SAME' END verdict
FROM new_canon FULL OUTER JOIN old_fact USING (`date`)
WHERE new_rub IS DISTINCT FROM old_rub
ORDER BY `date`;
```

🔴 Заранее известными считаются только 4 даты и 334,00 ₽. Сверка нужна именно для того,
чтобы увидеть остальное; ожидание «изменятся только эти четыре» **не является гейтом**
и не должно им становиться. Любая дата со статусом `DAY_LOST` — стоп: снапшот не покрыл сутки,
которые раньше были в FACT.

### 5.5 Исправление уже найденных 334,00 ₽

| Дата | FACT сейчас | Ожидаемый canonical | Δ | Механизм, который это чинит |
|---|---|---|---|---|
| 10.07 | 3 676 | 3 599 | −77 | снапшот вместо union: отозванный ключ `(advertId, updTime)` исчезает |
| 02.08 | 2 544 | 2 483 | −61 | out-of-window строка не входит в снапшот |
| 04.08 | 1 463 | 1 459 | −4 | то же |
| 05.08 | 1 309 | 1 117 | −192 | берётся один снапшот, промежуточный выброс не накапливается |
| **Итого** | **514 064,00** | **513 730,00** | **−334,00** | |

Это **ожидание, а не обещание**: bootstrap читает WB заново, и WB вправе ответить иначе.
Фактическая дельта фиксируется запросом §5.4 и приёмкой I5.

```

3.  C2: окно operational 7 → 14; отдельная функция audit-прогона D−45…D−8
4.  Наблюдение ≥ 3 суток: журнал наполняется, проверяются инварианты I1–I3
5.  C3: V_ADV_COSTS_UNION_LEGACY (копия текущего тела) → затем V_ADV_COSTS = snapshot-based
        🔴 ломающее изменение producer contract; отдельный PR + ревью аудитора
6.  Historical bootstrap: 3 прохода × 5 окон, по одному проходу в сутки (§5)
7.  Сверка §5.4; при чистом результате — пере-bootstrap FACT
8.  C4: CREATE VIEW wb_raw.V_ADV_COSTS_DAY_COVERAGE
9.  Приёмка I1–I9
10. scheduler-control.yml → resume wb-mart-prod
11. Только после этого разблокируется Stage 3B (change-set уже ссылается на V_ADV_COSTS_DAY_COVERAGE)
```

Шаги 5 и 6 нельзя переставлять (§5.3). Шаг 4 нельзя пропускать: без наполненного журнала
снапшотов не существует, и C3 выберет пустое множество.

## 7. Validation invariants

| # | Инвариант | Ожидание |
|---|---|---|
| I1 | Каждая строка `RAW_WB_ADV_COSTS` нового рана имеет строку журнала с тем же `(run_id, period_from, period_to)` | 0 сирот |
| I2 | Внутри `(run_id, date)` — ровно одно окно | 0 нарушений (F1 держится и после C2) |
| I3 | `(advertId, updTime)` уникален внутри `(run_id, updDate)` | 0 нарушений (F2) |
| I4 | Каждая дата canonical-слоя происходит ровно из ОДНОГО `(run_id, window_index)` | 0 дат с двумя снапшотами |
| I5 | Сверка нового canonical против `FACT_ADS_COSTS_DAILY` (§5.4) | ни одной даты `DAY_LOST` |
| I6 | `billed_complete = TRUE` ⇒ существует ≥ `N_STABLE` совпадающих снапшотов и день старше `SETTLE_DAYS` | 0 нарушений |
| I7 | Максимальный наблюдённый лаг ревизии по журналу < `SETTLE_DAYS` | если ≥ — константу поднять, а не проигнорировать |
| I8 | `zero_spend_day` подтверждён строкой журнала с `http_success='true'` и `returned_rows='0'` | 0 дней «нулевых по умолчанию» |
| I9 | K9 по `V_ADV_COSTS`, `V_ADV_COSTS_DAY_COVERAGE`, `V_ADV_COSTS_UNION_LEGACY` | repo == production |

I7 — не разовая проверка, а регулярная: константы `SETTLE_DAYS` и `N_STABLE` обязаны
пересматриваться по журналу. Иначе они превратятся в цифры, выбранные один раз в августе.

## 8. Влияние на `FACT_ADS_COSTS_DAILY`

* Значения меняются: ожидаемо −334,00 ₽ (514 064,00 → 513 730,00) на 4 датах, фактическое —
