## 🔴 1. Найдена причина провала «Формирования набора» 29.07.2026

Раздел **4.1.2.4. Формирование набора** задаёт условия. Ключевое:

> **при формировании набора из вложений в статусе «INTRODUCED» (В обороте):**
> у формируемого набора должен быть статус «APPLIED» (Нанесён) и **тип эмиссии
> «LOCAL» (Произведён в РФ) или «REMAINS» (Маркировка остатков)**. При этом:
> - если тип эмиссии набора «LOCAL», то у вложений может быть любой тип эмиссии;
> - если «REMAINS», то у вложений может быть только «REMAINS».

**Что было у нас.** Наборы эмитированы со способом ввода **«Ввезён в РФ»
(`FOREIGN`)**, а компоненты лежали в статусе «В обороте» (`INTRODUCED`).
Правило требует у набора `LOCAL` либо `REMAINS`. `FOREIGN` в этом сценарии
не допускается — документ и падал.

**Отсюда следует:**

1. Исправление, которое сделала поддержка по обращению (**«Ввезён в РФ» →
   «Произведён в РФ»**, то есть `FOREIGN → LOCAL`), было **ровно тем, что нужно**.
   Мы тогда считали его косметическим — оно было обязательным условием.
2. Битый код энзимной пудры (`)Oup)` вместо `)OUp)`) — **вторая, независимая
   причина**. Обе нужно было устранить, и обе устранены.
3. Проверить перед следующей попыткой: у всех 91 набора тип эмиссии должен
   быть `LOCAL`. Выгрузка по типу упаковки «Набор» это покажет.

### Второе важное следствие

> **в результате успешного формирования статус набора изменится на «INTRODUCED»
> (В обороте) — набор автоматически вводится в оборот.**

То есть **отдельный документ «Ввод в оборот» для набора не нужен** — набор
вводится в оборот самим фактом успешного формирования. Именно поэтому ЛК
отказывался вводить наборы в оборот и требовал сначала сформировать набор.

### Остальные условия формирования набора

- отправитель документа должен быть **собственником кодов**; после успешной
  обработки вложения сменят владельца на отправителя;
- до формирования **все вложения должны быть в одинаковом статусе** —
  `APPLIED` либо `INTRODUCED`; особое состояние отсутствует или равно
  `WAIT_TRANSFER_TO_OWNER` (снимается после обработки);
- КИ/КИК не должны быть **вложены в другой агрегат**;
- при формировании из вложений в статусе `APPLIED`: одинаковый тип эмиссии
  у вложений и набора, тип не может быть `REMARK` или `REAPPLY`, у набора
  статус `APPLIED`;
- товарная группа «Косметика, бытовая химия и товары личной гигиены» —
  **в списке поддерживаемых**, подача только в формате `*.json`.

### Тип документа и тело

| Тип | Описание |
|---|---|
| `SETS_AGGREGATION` | Формирование набора. JSON (MANUAL) |
| `SETS_AGGREGATION_XML` | Формирование набора. XML |

```json
{
  "participantId": "7777777777",
  "aggregationUnits": [
    {
      "unitSerialNumber": "010461111111111121LLLLLLLLLLLLL",
      "sntins": ["010462111111111121NNNNNNNNNNNN"]
    }
  ]
}
```

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `participantId` | string | + | ИНН участника оборота товаров |
| `aggregationUnits` | array | + | Список формируемых наборов |
| `unitSerialNumber` | string | + | Код идентификации набора |
| `sntins` | array | + | Коды вложений |

**КИН набора:** от 18 до 74 символов — цифры, латиница и спецсимволы
`A-Z a-z 0-9 % & ' " ( ) * + , - _ . / : ; < = > ? !`.

🔴 Обрати внимание: в перечень входят `&`, `'`, `"`, `<`, `>` — те самые
символы, на которых мы дважды обожглись при разборе XML. При подаче
документов их нужно экранировать по отдельному документу ЦРПТ
**«Рекомендуемый алгоритм экранирования специальных символов в составе
кода идентификации»**.

## 2. Авторизация

Только через УКЭП, три шага:

1. `GET /api/v3/true-api/auth/key` → возвращает `uuid` и `data`
2. Значение `data` подписать **присоединённой** УКЭП, привести к Base64
   в одну строку (удалить `\r\n`)
3. `POST /api/v3/true-api/auth/simpleSignIn` с телом `{"uuid": "...", "data": "<подпись>"}`
   → возвращает `token`

**Токен действителен 10 часов.** Долгоживущего ключа не предусмотрено.

Для ИП с машиночитаемыми доверенностями от разных организаций в тело
добавляется `"inn"` — ИНН организации, под которой нужна авторизация.

Приватные методы: заголовок `Authorization: Bearer <token>`.

## 3. Получение сведений о кодах

**`POST /api/v3/true-api/cises/info?pg=<товарная группа>`**

- до **1000 КИ** в одном запросе;
- КИ указывать **без крипто-хвоста** — обрезать начиная с ``;
- статус кода возвращается в поле `status`.

Наша таблица `RAW_WB_KIZ_SUPPLY` уже хранит КИ ровно в этом виде (24 символа,
без крипто-части) — то есть готова к подаче в этот метод как есть.

Смежные методы раздела 5: история движения КИ (5.2), список агрегированных КИ
(5.3), история агрегирования (5.4), баланс на складе (5.10), операции на
складе (5.11).

## 4. 🔑 Выгрузки данных — то, что заменит ручной экспорт из ЛК

Раздел **8** описывает полноценный асинхронный конвейер:

| Метод | Назначение |
|---|---|
| 8.3 | Создание нового задания на выгрузку |
| 8.5 | Получение статуса задания |
| 8.6 | Получение результирующих ID выгрузок |
| 8.7 | **Получение ZIP-файла выгрузки** |
| 8.8 / 8.9 | Число доступных выгрузок по типу задания / по отчёту |
| 8.10 | Удаление файлов выгрузки |

Плюс 8.1 и 8.2 — доступность выгрузок по товарным группам и типам отчёта.

**Что это даёт нам.** Те четыре ZIP-архива, что ты выгружал руками, можно
получать программно: создать задание → дождаться готовности → скачать ZIP →
разобрать в BigQuery. Это закрывает сторону ЧЗ в КИЗ-контуре и снимает
ручную работу с 17 GTIN и четырёх статусов.

Ограничение прежнее: **токен живёт 10 часов и требует подписи УКЭП**, поэтому
полностью автономный ночной загрузчик потребует узла подписи с сертификатом.
Для периодической сверки (раз в неделю, по запуску владельцем) — работает
без оговорок.

## 5. Подача документов

**`POST /api/v3/true-api/lk/documents/create?pg=<товарная группа>`**

- документ закодировать в Base64 → параметр `product_document`;
- подписать **откреплённой** УКЭП → параметр `signature` в Base64;
- в ответе — `uuid` документа;
- статус проверять методом получения списка загруженных документов;
- содержимое — методом получения информации о списке КИ по фильтрам.

⚠️ Параметр `pg` для нашей товарной группы нужно уточнить: в выгрузках ЧЗ
группа обозначена как `CHEMISTRY`, но в URL используются короткие коды
(в примерах документации `lp`, `milk`, `beer`). Подтвердить по справочнику
«Список поддерживаемых товарных групп» перед первым вызовом.

## 6. Что делать дальше

1. **Выгрузить наборы из ЧЗ** (тип упаковки «Набор», 4 статуса) и проверить,
   что у 91 набора тип эмиссии стал `LOCAL`. Если да — формирование должно
   пройти; если остался `FOREIGN` — это и есть оставшийся блокер.
2. **Не подавать отдельный «Ввод в оборот» для наборов** — он не нужен,
   набор вводится в оборот автоматически при успешном формировании.
3. Скачать из ЛК ГИС МТ PDF **«Описание True API»** и **«Рекомендуемый
   алгоритм экранирования специальных символов»** — детальные схемы
   публикуются только в PDF, онлайн-версия их не содержит целиком.
4. Для КИЗ-контура заложить раздел 8 (выгрузки) как источник стороны ЧЗ
   вместо ручных экспортов.
