## 1. Рецепт C-RATIO probe (контрольные значения от 21.08.2026)

### Подготовка

1. Looker Studio → **Создать → Источник данных** → **BigQuery**.
2. Проект `project-fa311fc0-4d87-4781-986` → набор `wb_mart` → таблица **`V_DASH_KPI_DAILY`**.
3. Поле даты по умолчанию: **`day`**.

### Шаг 1 — самый различающий тест: средняя цена заказа

Создать **вычисляемое поле** (тип: метрика, агрегация — `Auto`):

```
_probe_avg_price  =  SUM(orders_revenue_rub) / SUM(orders_qty)
```

Положить на страницу **Scorecard** с этим полем, Date Range = **01.08.2026 – 07.08.2026**.

| что покажет | вывод |
|---|---|
| **594,73** | ✅ считается **после** агрегации диапазона — контракт работает |
| **785,75** | ❌ считается построчно, затем усредняется — это `AVG(row_ratio)`, запрещено |

Разрыв **191 ₽** — ошибиться при считывании невозможно.

### Шаг 2 — контроль на ДРР

```
_probe_drr  =  SUM(ad_spend_attributed_rub) / SUM(sales_revenue_seller_base_rub)
```

Тот же диапазон 01–07.08.2026:

| что покажет | вывод |
|---|---|
| **16,77 %** (0,167744) | ✅ ratio-of-sums |
| **20,75 %** (0,207488) | ❌ AVG(row_ratio) |

Опорные суммы для самопроверки: `SUM(ad_spend_attributed_rub)` = **13 485,07 ₽**,
`SUM(sales_revenue_seller_base_rub)` = **80 390,63 ₽**.

### Шаг 3 — сравнение с предыдущим периодом

На том же Scorecard включить **Comparison date range → Previous period**.
Looker возьмёт **25.07 – 31.07.2026**. Ожидается:

| метрика | текущий период | предыдущий период |
|---|---|---|
| `_probe_avg_price` | **594,73** | **1 009,09** |
| `_probe_drr` | **16,77 %** | **25,72 %** |
| `SUM(ad_spend_attributed_rub)` | 13 485,07 ₽ | 23 221,83 ₽ |
| `SUM(sales_revenue_seller_base_rub)` | 80 390,63 ₽ | 90 288,43 ₽ |

Если сравнение показывает эти числа — предыдущий период тоже считается ratio-of-sums,
и весь §12 контракта можно строить без оговорок.

### Шаг 4 — контроль CTR (проверка на малой разнице)

```

```
01–07.08.2026 → **2,4807 %** (ratio-of-sums) против **2,4495 %** (AVG).
Разница мала намеренно: она подтверждает, что шаги 1–2 не совпали случайно.

## 4. Двойная семантика свежести — визуальное решение

Две величины стоят **рядом в шапке**, всегда обе, никогда одна вместо другой:

```
┌────────────────────────────────────────────┬──────────────────────────────────────┐
│ ДАННЫЕ ЭКРАНА                              │ СИСТЕМА                              │
│ 19.08.2026 · OK                            │ 17.08.2026 · STALE                   │
│ mart_sku_daily · finance · orders ·        │ 2 слоя не в норме:                   │
│ sales · fact_ads_sku_daily                 │ ads_costs, fact_ads_costs_daily      │
│ ● зелёная точка                            │ ● жёлтая точка                       │
└────────────────────────────────────────────┴──────────────────────────────────────┘
```

**Правила отображения:**

1. **Левый блок — крупный, правый — мелкий.** Владелец каждый день смотрит на левый:
   он отвечает «насколько свежи числа НА ЭТОМ экране».
2. **Правый блок — всегда виден, никогда не скрывается**, даже когда зелёный.
   Он отвечает «что происходит во всём контуре», в том числе со слоями, которых на экране нет.
3. **Цвет — независимо у каждого.** Сегодня: левый зелёный (OK), правый жёлтый (STALE).
   Жёлтый справа при зелёном слева — **нормальная и информативная картина**,
   а не противоречие: стареет рекламный биллинг, который экран не использует.
4. **Подпись причины обязательна** в правом блоке: `ads_costs, fact_ads_costs_daily`.
   Число без причины заставляет гадать.
5. **Никакого «худшего из двух».** Свести их в одну плашку — значит потерять именно то
   различие, ради которого вводилась `V_DASH_FRESHNESS_BY_CONTRACT`.
6. Слои без даты (`ref_sku_master`) в дату не входят, но подписаны строкой
   «справочник — без отметки даты» из `layers_used_without_date_list`.
7. Часы слоёв с `success_age_is_sla = FALSE` (`ads_query_stats`, `sku_orphans`) —
   **серым**, не зелёным: это измерение, а не обещание.

Тексты берутся из полей: `header_text_used` (левый) и `header_text` + `header_warning` (правый).

## 7. Индикаторы покрытия, provisional и предупреждения

Три бейджа в шапке. Все три — из аддитивных счётчиков PR1, никакой логики в Looker.

| бейдж | условие | текст |
|---|---|---|
| **Покрытие** | `SUM(ads_uncovered_days) + SUM(orders_uncovered_days) + SUM(sales_uncovered_days) > 0` | ⚠️ «В выбранном периоде N суток без данных: реклама N₁, заказы N₂, продажи N₃. Эти сутки не считаются нулевыми — они исключены из расчёта.» |
| **Вклад неполон** | `SUM(contribution_uncovered_days) > 0` | ⚠️ «Вклад посчитан по N суткам из M: за остальные нет одного из компонентов (выкупы, реклама или финансы).» |
| **Provisional** | `SUM(contribution_provisional_days) > 0` | ⚠️ «Период содержит N суток с предварительными финансовыми данными. Числа могут измениться после закрытия недели WB.» |

**Дополнительное предупреждение при выходе за границу покрытия** (появляется, когда
начало диапазона < 13.04.2026):

> 🔴 «Выбранный период начинается раньше 13.04.2026. Заказы, продажи и реклама
> за более ранние сутки в BigQuery отсутствуют — WB хранит статистику 90 суток,
> и восстановить их невозможно. Финансовые показатели за этот период есть
> и считаются корректно.»

**Предупреждение на карточках сравнения:**

> «Сравнение недостоверно: в предыдущем периоде N суток без покрытия.»
> Дельта при этом серая, без стрелки и без процента.

## 8. Правила NULL / «нет данных» вместо 0

Слой данных уже отдаёт `NULL` вне покрытия — это гарантировано гейтами D7/D8
(протечек ноль). Задача интерфейса — **не превратить `NULL` обратно в ноль**.

```
N1  В настройках каждого поля Looker: «Missing data» → показывать «—» / «нет данных»,
    НЕ «0». Это отдельная настройка на каждое поле; по умолчанию Looker рисует 0.
N2  На графиках: разрывы линии в сутках без покрытия. Не соединять точки через дыру
    и не подставлять ноль. Тип линии — с пропусками, не «zero-fill».
N3  Ни одного calculated field вида IFNULL(x, 0) / COALESCE(x, 0) / NARY_MAX(x, 0).
    Запрет буквальный: такие поля восстанавливают ровно тот дефект, ради устранения
    которого построен весь слой.
N4  Ratio с нулевым знаменателем показывает «—», а не 0 и не «∞».
N5  Карточка вклада при SUM(contribution_uncovered_days) = период целиком —
    показывает «нет данных за период», а не 0 ₽.
N6  Сравнение с предыдущим периодом, где метрика NULL, показывает «—», а не −100 %.
```

🔴 Почему это критично именно в Looker: `SUM()` молча пропускает `NULL`, поэтому
сумма за диапазон, наполовину выходящий за покрытие, **выглядит законченной**.
Ловят это только бейджи §7 — они и есть механизм, а не украшение.

**Группы колонок** (в Looker — порядок и разделители-заголовки):

|---|---|

## 14. 🔴 Что меняется, если C-RATIO probe провалится

Если Looker покажет **785,75** вместо 594,73, значит поле считается построчно.
Тогда — по убыванию предпочтительности:

1. **Проверить тип поля.** В Looker Studio `SUM(a)/SUM(b)` обязано быть создано как
   поле с **агрегацией `Auto`**; если ему выставлена `Average` или `Sum`, оно
   превращается в построчное. Это настройка, а не свойство платформы —
   в 9 случаях из 10 причина здесь.
2. **Проверить, что поле создано в отчёте, а не в источнике** с типом «Число».
3. Если и это не помогает — вынести ratio в BigQuery **нельзя**: посуточное отношение
   не агрегируется. Пришлось бы делать параметризованную вью с датами из Looker-параметров,
   что ломает требование «произвольный Date Range без изменения SQL».
   В этом случае возвращаюсь к вам с развилкой, а не выбираю сам.

Пункт 3 — реальный риск архитектуры, поэтому проба и стоит **до** сборки, а не после.
