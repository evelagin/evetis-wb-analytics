# PR-PROMO-4 — Inventory & Sell-Through Context

**Дата:** 2026-09-24 · **Ветка:** `feat/promo-4-inventory-context` · **База:** `main dc7fda4`
(PR-PROMO-1/2/3 закрыты, `PR_PROMO_3_GATE = GO`).

Слой отвечает на вопросы: сколько запаса на самом деле, с какой скоростью он продаётся, на
сколько дней его хватит, есть ли у запаса предел по сроку годности, какая скорость нужна, чтобы к
дате с происхождением остался заданный остаток, и насколько она отличается от текущей. **Решений
слой не принимает**: ни ENTER/STAY/EXIT, ни баллов, ни ранжирования, ни ослабления порога маржи.

Что НЕ сделано намеренно: историческая эффективность акций, оптимизация производства и закупок,
прогноз P&L, рекомендации. Второй системы запасов нет — слой читает Control Tower.

### 3. Понятия запаса

| Понятие | Колонка | Определение |
|---|---|---|
| Доступно покупателю сейчас | `marketplace_available_units` | WB FBO + Ozon FBO + FBS |
| Склад (общий пул) | `warehouse_ff_units` | ФФ = срез владельца − отгрузки после среза |
| В пути | `in_transit_units` | WB + Ozon, уже списано с ФФ |
| **Позиция запаса** (физический запас в известных местах, плановая величина) | `inventory_position_units` | = ФФ + площадки + в пути = CT `sellable_units` |
| Резерв (у покупателя) | `reserved_in_delivery_units` | только WB; резерв Ozon в API не наблюдается |
| Недоступно | `unavailable_claimed_units` | WB, претензия/утрата |
| Не получено | `inbound_not_received_units`, `inbound_eta` | партия в пути от производителя |

«Физический» и «плановая позиция» совпадают: Control Tower других физических мест не знает.
Отдельной меры «физический запас» не вводится, чтобы не создать вторую величину без источника.

### 4. Свежесть

Каждый факт несёт время: `inventory_as_of` (момент среза CT), `ff_anchor_date`, `wb_stock_as_of`,
`ozon_stock_as_of`, `sales_as_of`, `ct_actuals_refreshed_at`. Статус свежести — по контракту
Control Tower: сроки `wb_mart.V_CT_FRESHNESS` (остатки WB и Ozon — 1 день, срез ФФ — 7 дней) и
`CT_CONFIG.refresh_sla_hours = 26` для самого среза. `FRESH` — все четыре в OK.

Само `V_CT_FRESHNESS` слой **не читает**: оно тяжёлое (сканирует `V_DASH_SKU_DAILY`, финансы) и
раскрывается при каждом обращении — составные запросы упирались в предел планировщика BigQuery.
Сроки применяются к датам внутри среза; паритет со статусами `V_CT_FRESHNESS` доказывает DQ I05
(расхождение порога — провал проверки, а не тихий дрейф).

**На 24.09:** срез ФФ от 09.09 — 15 дней при SLA 7 → `FF_STOCK=STALE`, запас всех SKU `STALE`.
Это собственный контракт платформы, а не порог PR-PROMO-4. Следствие — §12.

### 5. Идентичность SKU

Грейн запаса — физический SKU `REF_PRODUCT_MASTER` (11 шт.). Каналы — `REF_SKU_CHANNEL_MAP`
(`is_current`): `wb_nm_ids`, `wb_vendor_codes`, `ozon_skus`, `ozon_offer_ids`, `listed_on_*`.
`mapping_status`: `CANONICAL_SKU` / `NOT_IN_PRODUCT_MASTER` / `BUNDLE_IN_COMPONENT_GRAIN`.
Остатки площадок без канонического SKU Control Tower отбрасывает на входе — поэтому они
поверхностно проверяются по RAW в DQ I06 (на 24.09: 0 строк WB, 0 строк Ozon). Новой карты нет.

### 6. Событие продаж

Канон Control Tower: **заказанные единицы без отмен, по дате заказа, в физических единицах по
BOM, WB + Ozon** (`V_CT_PHYSICAL_DAILY.units_ordered`). Обоснование платформы: «заказ — ведущий
показатель, сигнал спроса сегодня» (CT Phase 1 §1); заказ списывает единицу с полки площадки, и
план сезона записан в тех же единицах (карточки без отмен). Выкупы — справочно (`units_sold_30d`).
Это **наблюдаемая скорость продаж**, не спрос. Известное ограничение канона: `V_CT_ACTUAL_DAILY_LIVE`
раскладывает всю историю по текущему BOM.

### 7. Окна скорости

7 / 14 / 30 / 60 / 90 суток, буквально N дней, окно кончается последним **полным** днём обоих
каналов: `sales_as_of = LEAST(последний день WB, последний день Ozon в CT_ACTUAL_DAILY, дата
пересборки − 1)`; скорость = единицы / N. Ни одно окно не объявлено «плановой скоростью»:
существующая плановая скорость Control Tower — это план (`plan_units_per_day_next_45d`), а не
факт. Опорное окно для покрытия и целей — 30 дней (как `days_of_stock_total_at_30d_rate` CT).
Для ускорения и обвала — отношения `velocity_ratio_7d_to_90d`, `velocity_ratio_30d_to_90d`, окна
не усредняются.

Отличие от CT: окно CT = `(дата среза − 30; дата среза]` включает неполный сегодняшний день
(WB — ноль, Ozon — частично). Поэтому 30-дневные скорости расходятся (крем для рук 5,87 против
5,50); тождество `30 × (слой − CT) = Σ дней только слоя − Σ дней только CT` проверяет DQ I36 точно.

### 8. Искажение наличием

История наличия — сам срез CT (с 10.09.2026). День окна «с нулём на полке», если у SKU есть
текущая карточка канала и в срезе этого дня на полке канала 0. Качество окна (порядок):
`UNKNOWN` (фактов продаж нет) → `INSUFFICIENT_HISTORY` (первый заказ позже начала окна) →
`STOCKOUT_CONSTRAINED` → `AVAILABILITY_NOT_FULLY_OBSERVED` (наличие видно не за все дни окна) →
`NO_SALES_WITH_STOCK` → `NORMAL`. Спрос статистически не восстанавливается. На 24.09 окна 7 и 14
дней наблюдены полностью; 30/60/90 — `AVAILABILITY_NOT_FULLY_OBSERVED`, пока история не накопится
(90 дней — к 08.12.2026).

### 9. Покрытие

`cover_days_N = позиция / скорость окна N`, для каждого окна; дополнительно покрытие полок площадок
за 30 дней. Статусы: `COMPUTED`; `ZERO_INVENTORY` (позиция 0, скорость > 0 → 0 дней);
`NO_VELOCITY` (позиция > 0, скорость 0 → NULL, не 0); `NO_INVENTORY_NO_VELOCITY`;
`VELOCITY_UNAVAILABLE`. Замен нуля на 0,001 нет.

### 12. Требуемая распродажа

```
required_units_to_sell        = MAX(позиция − целевой остаток, 0)
required_units_per_day        = required_units_to_sell / (target_date − inventory_as_of_date)
required_inventory_uplift_pct = (required_units_per_day / скорость 30 дн − 1) × 100
```
Горизонт — дни `[inventory_as_of_date; target_date − 1]`. Это **другая ось**, чем
`required_sales_uplift_pct` PR-PROMO-3 (экономический break-even); они не складываются и не
взвешиваются. Статусы: `SKU_NOT_IN_INVENTORY` · `NO_TARGET` · `INVALID_TARGET` ·
`EXPIRY_LOT_ALLOCATION_UNKNOWN` (партий на руках > 1 или ждём партию) ·
`TARGET_DATE_NOT_IN_FUTURE` · `INVENTORY_STALE` · `NO_ACCELERATION_REQUIRED` (uplift 0) ·
`VELOCITY_UNAVAILABLE` · `CURRENT_VELOCITY_ZERO` (единицы в день есть, процента нет) · `COMPUTED`.
Отрицательный uplift не обнуляется. Для справки — `RUN_RATE_PROJECTION` остатка к цели при текущей
скорости (не прогноз).

**Устаревший запас не считается как текущий:** при `STALE` требуемые числа NULL, статус
`INVENTORY_STALE`, факты (позиция, скорость, покрытие, дни до срока) видны. На 24.09 это все SKU
(срез ФФ 15 дней). Обновление `CT_STOCK_SNAPSHOT` владельцем включит расчёт без изменения кода.

### 14. Месячный план продаж

**Второго хранилища плана нет.** План живёт в Control Tower: `CT_PLAN_VERSION` (версия, статус
DRAFT/ACTIVE/SUPERSEDED, источник, автор, горизонт) + `CT_SEASON_PLAN_MONTHLY` (версия × месяц ×
канал × карточка, `target_cards`, физические единицы). Требования §23 спецификации (SKU, месяц,
количество, канал, версия, источник, статус, заметки) выполнены им полностью, кроме одного —
**утверждения владельцем**.

Активная версия `SET_2026-09-09` — модельный сценарий SEASON_EXECUTION_TARGET (`ct.py`,
«рекомендуемый сценарий»); слово «утверждённый» есть только в тексте загрузчика и аналитических
записках, записи решения владельца нет. Поэтому добавлен один справочник
`evetis_ref.REF_SALES_PLAN_APPROVAL` (append-only, пишет только владелец): строка `APPROVED`
превращает версию CT в бизнес-план. Без неё `V_SALES_PLAN_MONTHLY_CURRENT` показывает структуру,
факт и календарь, а плановые числа, исполнение и прогноз — NULL со статусом
`PLAN_APPROVAL_NOT_RECORDED`. Автоматическая цель не выдаётся за план.

Метрики при утверждении: план месяца (карточки и физ. единицы), факт с начала планового периода,
остаток плана, оставшиеся календарные дни, требуемый темп на остаток, % исполнения,
`RUN_RATE_PROJECTION` = факт + скорость 30 дн × оставшиеся дни (с качеством скорости).

### 15. Календарная раскладка

Плановый период месяца = `[max(1-е число, начало горизонта); min(последний день, конец
горизонта)]`, дни — датами (`LAST_DAY`, `GENERATE_DATE_ARRAY`): 28/29/30/31, неполные месяцы
помечены. «Месяц × 30» и 30,44 не используются (Control Tower использует 30,44 в
`required_units_per_month_to_expiry` — это не наследуется). Раскладка требуемой распродажи по
месяцам — нейтральный ровный темп (`NEUTRAL_REQUIRED_RUN_RATE_NOT_APPROVED_PLAN`).

### 16. Основа прямой траектории запаса

`V_SKU_INVENTORY_TRAJECTORY_MONTHLY_CURRENT`: остаток на начало − продажи периода + пополнение =
остаток на конец, по календарным месяцам, две основы (не смешиваются): нейтральный требуемый темп
цели и **утверждённый** план CT в физических единицах (текущий месяц — остаток плана после факта).
Пополнение не моделируется (`REPLENISHMENT_NOT_MODELLED`, `replenishment_units = NULL`): производство
и закупки не выдумываются; колонка готова принять план пополнения. `closing_units_unconstrained`
ниже нуля — нехватка позиции под план (`projected_shortfall_units`).

### 17. Мост к будущей прибыли

Формулы экономики в слое нет. Будущий слой посчитает `плановые единицы × вклад на единицу`
соединением `V_SALES_PLAN_MONTHLY_CURRENT` (marketplace, internal_sku, month, `planned_cards`) с
`V_PROMO_ECONOMICS_SCENARIO_CURRENT` (marketplace, internal_sku; BASELINE — цена продавца, PROMO — цена
акции). Ключи совпадают: `marketplace` WB/OZON в верхнем регистре, `internal_sku` карточки (наборы —
своими SKU, у них своя экономика). Месяц — `DATE` первого числа.

`REF_PRODUCT_MASTER` имеют BOM; набор без BOM получает `BUNDLE_BOM_UNAVAILABLE` без мощности.

### 19. Мощность наборов

`component_capacity_units = FLOOR(ФФ компонента / qty)`, `technical_assembly_capacity_units = MIN`.
Числитель — ФФ: сборка идёт на ФФ, единицы на полках уже в карточках. Число совпадает с
`V_CT_BUNDLE_STATUS.assemblable_now_ff` (14/14 наборов, 33/33 строки). Добавлено то, чего у CT нет:
детерминированный ограничивающий компонент (все с минимумом, по алфавиту; у CT — произвольный при
равенстве), мощность каждого компонента, общие компоненты, одиночные продажи, самый ранний срок
годности среди компонентов. `evetis_ops.V_CT_BUNDLE_CAPACITY` считает то же из журнала ФФ, но
журнал заморожен на посеве — не используется.

### 20. Общие компоненты

Мощность **не распределена**: компонент входит в несколько наборов и продаётся поодиночке.
`shares_components_with`, `bundles_using_component`, `component_also_sold_standalone`,
`capacity_is_independent`, `capacity_semantics = TECHNICAL_ASSEMBLY_CAPACITY_FROM_FF_UNITS_NOT_ALLOCATED`.
Мощности наборов не складываются, резерв под наборы не вычитается — системы распределения нет.

### 22. Время акции и запаса

Контекст: `promo_observed_at` (время снимка акций, `V_PROMO_OBSERVATION_HISTORY`),
`economics_basis_as_of` (снимок базиса PR-PROMO-3), `inventory_as_of` (срез CT),
`inventory_temporal_gap_minutes`. Правило — существующее в платформе: `ALIGNED`, если
`|разрыв| ≤ CT_CONFIG.refresh_sla_hours` (26 ч, «без успешной пересборки дольше этого витрина
STALE»). Иначе значения запаса NULL, `INVENTORY_CONTEXT_STALE`, сценарий остаётся. Контекст —
текущий: история контекста по слотам не строится (срез CT текущего дня переписывается до пяти
раз в день; неизменная история потребовала бы собственных снимков — не нужна до этапа
исторической эффективности).
