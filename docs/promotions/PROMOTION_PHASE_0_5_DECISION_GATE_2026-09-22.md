## 1. EXECUTIVE SUMMARY

**Канонические экономики WB и Ozon сверены с Git побайтово и совпадают.** SHA-256 тел
четырёх ключевых вью, снятые из `INFORMATION_SCHEMA.VIEWS` сегодня, равны хешам в

**Хранение уже исключено из обеих канонических экономик — решение владельца им
соответствует.** WB: «НЕ ВХОДЯТ намеренно: налог, хранение, приёмка, штрафы, удержания
уровня кабинета, фулфилмент, OPEX». Ozon: поле
`storage_applicability = 'EXCLUDED_FROM_ORDER_ECONOMICS_INVENTORY_HOLDING'`. Никаких
изменений в витринах не нужно.

**Пол 20 % по каноническому свидетелю сегодня не выдержан у 9 из 22 считаемых SKU WB.**
Записка от 21.09 объявляла пол «вклад ≥ 20 %», но считала по собственной упрощённой
формуле с хранением. По `V_WB_SKU_FORWARD_ECONOMICS_CURRENT` при ценах, установленных
21.09: 13 SKU `PASS_EXPECTED`, **9 `FAIL_EXPECTED`**, 3 `ECONOMICS_UNAVAILABLE`.

**Три из этих девяти — не ценовая ошибка, а давление запасов.** Крем для рук:
`status_code = EXPIRY_HARD`, 2927 годных единиц, 5,83 шт/день, 501 день покрытия при
**100 днях до истечения срока**. Кремы Амбра и Вишня: `OVERSTOCK`, 4570 и 4501 единиц,
4155 и 4823 дня покрытия. Это ровно тот случай, ради которого запасы должны быть
**модификатором решения**, а не переопределением вклада.

**WORST у WB и Ozon — семантически разные величины, и одинаковый порог к ним неприменим.**
Ozon worst меняет только логистику на `fbo_direct_flow_trans_max` (верхняя граница
тарифного коридора, детерминированная). WB stress меняет эквайринг на p90 эмпирического
распределения за 45 суток и логистику на отношение p90/среднее за 90 суток. Первое —
граница тарифа, второе — статистический хвост. Сводить их к одному числу нельзя.

**Сегодня катастрофического случая нет ни у одного SKU WB:** минимальный вклад в stress —
7,0 % (набор руки+амбра), отрицательных нет.

**СПП: расхождение 32 % против ≈15,65 % полностью объяснено и закрыто.** Это не два
разных показателя и не ошибка допущения — это **одна метрика на двух разных популяциях**.
15,74 % — среднее по всей таблице с 2024-09, включая ~24 тыс. строк LEGACY-слоя, где
`spp_percent ≈ 0,24` (фактически ноль). На окне 2026-07-01+ медиана `spp_percent` = 30,06 %,
и независимый источник (Sales API) даёт медиану наблюдаемой скидки покупателя 32,28 %.
**Допущение 32 % в записке от 21.09 подтверждено данными.** Но фиксировать его константой
нельзя: за пять месяцев СПП прошла 39 → 42 → 42 → **7** → 30 %.

**Ключевая находка по WB-акциям: участие в автоакциях не снижало нашу цену.** В 186 заказах
за 07.09–22.09 цена продавца в момент заказа совпала с наблюдаемой установленной ценой во
**всех** случаях после учёта задержки распространения (≤ 1 ч). Скидка продавца держалась
ровно 60 % во всех 1087 наблюдениях. Значит участие в автоакции WB — это, по всей
видимости, **квалификация по уровню цены, а не применяемая скидка**; экономического ущерба
в наблюдаемом окне оно не нанесло.

**Требуемый рост продаж в процентах не требует истории.** Это чистая функция цен и
издержек: `C_base/C_promo − 1`. Истории требует только пересчёт в штуки в день. Поэтому
режим `ECONOMICS_ONLY` доступен с первого дня, и `INSUFFICIENT_DATA` больше **не может**
скрыть детерминированный отказ экономики.

Вердикт гейта — в §15.

### 2.2 Точные формулы `CONFIRMED_EXISTING_CODE`

**Wildberries — модель `WB_FE_V1`, `tax_model_status = 'PRE_TAX'`**
(`sql/pricing/pr2_wb_forward_economics.sql:137-140`):

```
take_base          = (effective_commission_pct + acquiring_p50_pct) / 100
take_conservative  = (effective_commission_pct + acquiring_p75_pct) / 100
take_stress        = (effective_commission_pct + acquiring_p90_pct) / 100

logistics_base         = logistics_burden_per_sale_rub            -- Σ логистики / Σ продаж, 90 сут
logistics_conservative = logistics_base × (p75 / mean построчного распределения)
logistics_stress       = logistics_base × (p90 / mean)

contribution_before_ads_pre_tax = P − P×take_base − logistics_base − COGS
break_even_base         = (logistics_base         + COGS) / (1 − take_base)
break_even_conservative = (logistics_conservative + COGS) / (1 − take_conservative)
break_even_stress       = (logistics_stress       + COGS) / (1 − take_stress)
```

Сегодня по всем 25 SKU: `effective_commission_pct = 42,25`, `acquiring_p50 = 3,4584`,
`acquiring_p90 = 3,9957` → `1 − take_base = 0,542916`.

**Ozon — `FORWARD_MODELLED`, `PRE_TAX`**
(`sql/current/ozon_mart/V_OZON_SKU_FORWARD_ECONOMICS_CURRENT.sql:28-35,83`):

```
c_frac = commission_fbo_pct / 100          a_frac = acquiring_pct / 100
fixed_ex_logistics = COGS + last_mile_rub

contribution_best     = P − COGS − commission_rub − acquiring_max_rub − fbo_logistics_min      − last_mile
contribution_expected = P − COGS − commission_rub − acquiring_max_rub − fbo_logistics_expected − last_mile
contribution_worst    = P − COGS − commission_rub − acquiring_max_rub − fbo_logistics_max      − last_mile
break_even_price_expected = (fixed_ex_logistics + fbo_logistics_expected) / (1 − c_frac − a_frac)
```

`fbo_logistics_expected = LEAST(GREATEST(медиана наблюдений при n≥2, иначе min×1,20), max)`.

Алгебра одна: `contribution(P) = P·(1 − take) − fixed − COGS`. Движок акций подставляет
акционную цену в **эти** компоненты и ничего не переопределяет.

## 3. ТОЛКОВАНИЕ ПОЛА 20 %

### 3.1 Решение владельца, зафиксированное

> Жёсткий пол 20 %. Хранение **не** входит в канонический пол вклада, поскольку оно
> исключено из авторитетных вью WB и Ozon.

Это решение **совпадает** с фактическим устройством витрин (§2.3), поэтому не требует
изменения ни одной формулы. Противоречие, зафиксированное в фазе 0, закрыто в пользу
канонических вью.

### 3.2 Полная семантика

| Параметр | Значение | Класс |
|---|---|---|
| Метрика | `contribution_before_ads_pre_tax_rub` (WB) / `contribution_expected` (Ozon) | решение владельца + `CONFIRMED_EXISTING_CODE` |
| База доли | **цена продавца** (`seller_effective_price_rub` / `seller_base_price`) | `CONFIRMED_EXISTING_CODE` |
| До/после рекламы | **до** рекламы | решение владельца |
| До/после налога | **до** налога, `PRE_TAX` | `CONFIRMED_EXISTING_CODE` |
| Хранение | **не входит** | решение владельца |
| Случай | **EXPECTED** (см. §4) | решение владельца |
| Жёсткость | **жёсткий** для допуска в акцию | решение владельца |
| Площадки | обе | решение владельца |

Формально: `PASS_EXPECTED ⟺ contribution_expected_rub / seller_price × 100 ≥ 20`.

### 3.3 Записка 21.09 против канона — почему числа разошлись

Записка считала:
`вклад = цена × 0,5415 − логистика − хранение − COGS` (комиссия 42,25 %, эквайринг 3,6 %).

| Отличие | Записка | Канон | Направление |
|---|---|---|---|
| Эквайринг | 3,6 % | 3,4584 % (p50 за 45 сут) | записка строже на 0,14 п. п. |
| Множитель цены | 0,5415 | 0,542916 | записка строже |
| Хранение | вычитается | **не вычитается** | записка строже |
| Логистика | величина в записке не приведена | `logistics_burden_per_sale_rub` — **нагрузка на проданную единицу**, включает невыкупы (1,19–1,68 события на продажу) | **канон строже, и заметно** |

Итог: записка строже по трём мелким статьям и мягче по одной крупной. Именно логистика с
невыкупами разводит числа. Это не ошибка записки и не ошибка витрины — это разные
определения логистики. **Канон авторитетен.**

## 4. EXPECTED И WORST: РАЗДЕЛЕНИЕ НАЗНАЧЕНИЙ

### 4.1 EXPECTED — основной коммерческий допуск

`expected_contribution_margin_pct ≥ 20 %`. Применяется к `EXPECTED`-случаю обеих площадок.

### 4.2 WORST — что это на самом деле

| | WB `stress` | Ozon `worst_case` |
|---|---|---|
| Что меняется | эквайринг → p90 эмпирического распределения (45 сут); логистика → `база × (p90/mean)` построчного распределения (90 сут) | **только** логистика → `fbo_direct_flow_trans_max` |
| Что НЕ меняется | комиссия, COGS | комиссия, COGS, эквайринг (уже max в expected), last mile |
| Природа | **статистический хвост наблюдений** | **верхняя граница тарифного коридора API** |
| Ограниченность сверху | нет — зависит от выборки | **да** — тариф не может превысить свой max |
| Публикуется ли как вклад | **нет**: есть только `break_even_before_ads_pre_tax_stress`, колонки `contribution_stress` не существует | **да**: `contribution_worst_case`, `margin_worst_case_pct`, `safety_class_worst_case` |
| Возвраты/отмены | уже внутри базовой логистики | отдельно, в `expected_contribution_per_created_order_worst_rub` |
| Существующий порог в коде | нет | `safety_class_worst_case`: ≥25 `SCALE_SAFE`, ≥20 `HEALTHY_SAFE`, ≥10 `WATCH`, <0 `LOSS_RISK_WORST_CASE` |

**Семантически сопоставимы? Нет.** Три независимые причины: разная природа возмущения
(хвост против границы тарифа), разный периметр возмущаемых компонентов, разное место
возвратов. Одинаковый числовой порог к ним неприменим.

### 4.3 Следствие для реализации

WB не публикует вклад в stress. Его придётся вычислять в слое акций **из уже
опубликованных компонентов** той же вью:

```
contribution_stress_wb(P) = P × (1 − (effective_commission_pct + acquiring_p90_pct)/100)
                            − logistics_p90_rub − cogs_rub
```

Все четыре входа — существующие колонки `V_WB_SKU_FORWARD_ECONOMICS_CURRENT`. Это **не
новая формула**: это та же алгебра §2.2 с уже опубликованными stress-компонентами.
Проверка тождества: при подстановке `P = break_even_before_ads_pre_tax_stress` результат
обязан быть 0 ± 0,01 ₽ — это станет `ASSERT` в PR-PROMO-3.

### 4.4 Катастрофический порог — предложение без числа

Предлагаемый показатель — **не процент, а знак и запас**:

```
CATASTROPHIC_BLOCK ⟺ contribution_worst(P_promo) < 0
```

То есть: в худшем случае площадки акционная цена делает единицу убыточной **до рекламы**.
Этот критерий не требует выбора числа, одинаково осмыслен на обеих площадках несмотря на
разную конструкцию WORST, и уже используется на Ozon (`loss_risk_worst_case`).

Второй, более мягкий уровень — `DOWNSIDE_WARNING` — предлагается как
`contribution_worst(P_promo) / P_promo < X %`. **Число X не выбирается в этой фазе.**
Доказательная база на сегодня:

| Величина | WB, 22 считаемых SKU | Ozon, 20 SKU |
|---|---|---|
| Минимальный вклад в WORST | **7,0 %** (набор руки+амбра) | **−0,29 %** (−4,15 ₽) — тот же товар, `LOSS_RISK_WORST_CASE` |
| Отрицательных в WORST | **0** | **1** из 20 (930334396, набор руки+амбра) |
| Существующий порог в коде | отсутствует | 10 % → `WATCH`, 20 % → `HEALTHY_SAFE` |

Любое X в диапазоне 0–7 % сегодня на WB не сработает ни разу; X = 10 % отсечёт 3 SKU
(руки+амбра 7,0 %, руки+вишня 7,14 %, крем для рук 8,71 %) — ровно те три, что находятся
под давлением запасов. **Это решение владельца, а не вывод из данных.**

### 4.5 Состояния экономики — не булево

| Состояние | Условие |
|---|---|
| `PASS_EXPECTED` | `contribution_expected_pct ≥ expected_contribution_floor_pct` |
| `FAIL_EXPECTED` | `contribution_expected_pct < floor`, но `contribution_worst ≥ 0` |
| `DOWNSIDE_WARNING` | `contribution_worst_pct < catastrophic_warning_pct` (порог не задан) |
| `CATASTROPHIC_BLOCK` | `contribution_worst < 0` |
| `ECONOMICS_UNAVAILABLE` | любой обязательный вход отсутствует (`blocked_reason`) |

`DOWNSIDE_WARNING` и `CATASTROPHIC_BLOCK` **ортогональны** `PASS/FAIL_EXPECTED` и
выставляются независимо: SKU может быть `PASS_EXPECTED` и одновременно
`DOWNSIDE_WARNING`. В строке решения это **две колонки**, а не одна.

**Правила использования.**
1. Append-only. Правка «на месте» запрещена: аудит решения требует знать, какая политика
   действовала в момент рекомендации.
2. Разрешение конфликтов — по специфичности: `INTERNAL_SKU` > `PRODUCT_TYPE` > `ALL`,
   при равной специфичности побеждает более поздняя `effective_from`.
3. Пустая таблица или отсутствие действующей строки → `policy_status = 'NOT_SET'`:
   движок считает и показывает **все числа**, но не выдаёт `ENTER`/`EXIT`.
4. Пороги не дублируются в коде. В SQL допустима единственная константа — имя политики
   по умолчанию.

**Формально — по всем 25 SKU:** записка не моделировала участие в автоакциях WB, потому что
это состояние тогда не наблюдалось (календарь WB не вызывался ни разу до фазы 0).

**Фактически ущерб в наблюдаемом окне нулевой** (§7.3): цена заказа ни разу не была ниже
установленной.

**Непроверенный риск направлен в обратную сторону.** 21.09 цены выросли у 11 SKU (до +16,7 %).
Если участие в автоакции — квалификация по уровню цены (гипотеза `STRONGLY_INFERRED`), то

не ошибка записки, а слепая зона, которую закрывает PR-PROMO-1 с первого же дня.

по всей истории вместе с LEGACY-слоем, где поле практически не заполнено. Правильная
величина для сравнения — помесячная на окне WEEKLY-слоя.

1. `buyer_price_wb` остаётся **ненаблюдаемой до заказа** величиной; в формулу вклада не
   входит и не войдёт — база выручки везде цена продавца.
2. Где нужна «полка» (сравнение с Ozon, оценка спроса), берётся **наблюдаемая помесячная
   медиана за последние 30 суток**, с явным `spp_basis = 'OBSERVED_TRAILING_30D_MEDIAN'`
   и `spp_observation_lag_days`.
3. Фиксированное число допускается только как сценарий с меткой `ASSUMED`, и его значение
   приходит из `REF_PROMO_POLICY`, а не из кода.

### 9.5 Отдельная находка: августовский провал СПП

С 42 % (июль) до 7 % (август) и обратно до 30 % (сентябрь), подтверждено двумя независимыми
источниками. Это **не артефакт данных**. Причина — `UNPROVEN`; по времени совпадает с
отменой выбора склада FBW 15.08.2026, но связь не доказана. Величина существенная: при
цене 700 ₽ разница между СПП 42 % и 7 % — это полка 406 ₽ против 651 ₽, то есть совершенно
разный спрос при неизменной выручке продавца. Заслуживает отдельного разбора вне движка
акций.

## 10. ПЕРЕСМОТРЕННАЯ АРХИТЕКТУРА СОСТОЯНИЙ РЕШЕНИЯ

Фаза 0 допускала, что `INSUFFICIENT_DATA` может поглотить детерминированный отказ
экономики. Это исправлено: **две независимые оси**.

### 10.1 Ось 1 — `economics_status` (доступна с первого дня)

| Значение | Условие |
|---|---|
| `PASS_EXPECTED` | `contribution_expected_pct ≥ expected_contribution_floor_pct` |
| `FAIL_EXPECTED` | ниже пола, но `contribution_worst ≥ 0` |
| `ECONOMICS_UNAVAILABLE` | отсутствует обязательный вход (`blocked_reason`) |

### 10.2 Ось 2 — `downside_status` (доступна с первого дня)

| Значение | Условие |
|---|---|
| `DOWNSIDE_OK` | `contribution_worst ≥ 0` и выше порога предупреждения |
| `DOWNSIDE_WARNING` | `contribution_worst_pct < catastrophic_contribution_floor_pct` (порог не задан) |
| `CATASTROPHIC_BLOCK` | `contribution_worst < 0` |
| `DOWNSIDE_UNAVAILABLE` | нет stress-компонентов |

### 10.3 Ось 3 — `evidence_status` (наполняется со временем)

| Значение | Условие |
|---|---|
| `HIGH_EVIDENCE` / `MEDIUM_EVIDENCE` / `LOW_EVIDENCE` | по §5.4 `PROMOTION_ECONOMICS_SPEC_2026-09-22.md` |
| `INSUFFICIENT_HISTORY` | нет завершённых акций с полными окнами |

### 10.4 Ось 4 — `inventory_status` (модификатор)

`INVENTORY_SAFE` · `STOCK_CONSTRAINED` · `OVERSTOCK_PRESSURE` · `EXPIRY_PRESSURE` ·
`INVENTORY_UNAVAILABLE`.

### 10.5 Свод в рекомендацию

```
recommendation = f(economics_status, downside_status, evidence_status,
                   inventory_status, lifecycle_stage, policy)
```

Жёсткие правила, не подлежащие смягчению:

1. `ECONOMICS_UNAVAILABLE` → `BLOCKED_ECONOMICS`. Всегда, независимо от остальных осей.
2. `CATASTROPHIC_BLOCK` → никогда не `ENTER` и не `STAY`. Ни доказательная база, ни
   запасы этого не отменяют.
3. `FAIL_EXPECTED` **никогда** не маскируется значением `INSUFFICIENT_HISTORY`. Обе оси
   всегда печатаются рядом.
4. `OVERSTOCK_PRESSURE` / `EXPIRY_PRESSURE` могут ослабить пол **только** если
   `REF_PROMO_POLICY.overstock_relaxes_floor = TRUE`, и только до
   `overstock_floor_override_pct`, и только при `downside_status != CATASTROPHIC_BLOCK`.
5. Обилие запасов **никогда** не делает отрицательную юнит-экономику приемлемой.

Пример вывода, который обязан быть возможен сегодня:

```
SKU = EVT-HC-HAND-300, акция = <гипотетическая, цена −15 %>
economics_status   = FAIL_EXPECTED        (вклад 10,93 % при поле 20 %)
downside_status    = DOWNSIDE_OK          (вклад в WORST 8,71 %, положительный)
evidence_status    = INSUFFICIENT_HISTORY
inventory_status   = EXPIRY_PRESSURE      (100 дней до срока при 501 дне покрытия)
recommendation     = WATCH
reason_codes       = [PROMO_BELOW_CONTRIBUTION_FLOOR, PROMO_EXPIRY_PRESSURE,
                      PROMO_EVIDENCE_INSUFFICIENT]
```

Четыре независимых факта, ни один не скрыт другим.

## 11. РЕЖИМ `ECONOMICS_ONLY`

### 11.1 Почему он вообще возможен

Ключевое наблюдение, пропущенное в фазе 0:

```
required_sales_uplift_pct = C_base / C_promo − 1
```

**не зависит от объёма продаж.** Это чистая функция цены и издержек. Сокращается:

```
baseline_contribution_per_day = U × C_base
required_units_per_day        = U × C_base / C_promo
required_uplift               = (U × C_base / C_promo) / U − 1 = C_base / C_promo − 1
```

Поэтому процент требуемого роста доступен **немедленно**, а история нужна только для двух
вещей: перевода процента в штуки в день и оценки правдоподобия.

### 11.2 Что доступно в режиме `ECONOMICS_ONLY`, с первого дня

| Показатель | Требует истории акций? |
|---|---|
| вклад на единицу при акционной цене | нет |
| маржа вклада, % | нет |
| точка безубыточности по цене | нет |
| **максимально допустимое снижение цены** = `(P − break_even)/P` | нет |
| максимальная акционная цена, удовлетворяющая полу 20 % | нет |
| **требуемый рост продаж, %** | **нет** |
| предельный ДРР при акционной цене | нет |
| вклад в WORST и его знак | нет |
| базовый вклад в день | нужна скорость продаж (есть с 2024-09), **не** история акций |
| требуемые штуки в день | то же |
| правдоподобие требуемого роста | **да** |
| наблюдённая разница до/во время/после | **да** |

Максимально допустимое снижение цены до безубыточности, посчитанное сегодня по WB
(`(P − break_even_base)/P`): от **19,89 %** (набор руки+амбра) до **63,09 %** (крем УВЛ).
До пола 20 % запас нулевой или отрицательный у девяти SKU (§8.2). Ни одно из этих чисел
не потребовало ни одного дня истории акций.

### 11.3 Правило включения

`REF_PROMO_POLICY.economics_only_mode_enabled = TRUE` и
`minimum_evidence_class = 'INSUFFICIENT_DATA'` → `ENTER` разрешён при
`PASS_EXPECTED` + `DOWNSIDE_OK` + приемлемых запасах, **даже без истории**, но строка
обязана нести `evidence_status = 'INSUFFICIENT_HISTORY'` и
`uplift_plausibility = 'UNKNOWN'`, а `decision_confidence` понижается на ступень.

Обоснование: акция, требующая +1592 % роста продаж, информативна и без причинной модели.
Симметрично — акция по текущей цене (`action_price = price`, как у 18 товаров Ozon в
«Эластичном бустинге») не требует роста вовсе, и отказывать ей из-за отсутствия истории
было бы прямой потерей бустинга.

## 12. ТРЕБУЕМЫЙ РОСТ: АУДИТ ЗНАМЕНАТЕЛЯ И КРАЕВЫЕ СЛУЧАИ

### 12.1 Разделение на две метрики

| Метрика | Формула | Требует |
|---|---|---|
| `required_sales_uplift_pct` | `C_base / C_promo − 1` | только экономику |
| `required_units_per_day` | `U_base × C_base / C_promo` | ещё и `units_per_day_30d` |

Смешивать их в одной колонке нельзя: первая существует всегда, вторая — нет.

### 12.2 Детерминированные состояния `uplift_status`

| # | Условие | `required_sales_uplift_pct` | `uplift_status` | Что показывается вместо |
|---|---|---|---|---|
| 1 | `C_promo > 0`, `C_base > 0`, `C_promo < C_base` | значение | `UPLIFT_REQUIRED` | — |
| 2 | `C_promo ≥ C_base > 0` | ≤ 0 | `NO_UPLIFT_REQUIRED` | прирост вклада, ₽ |
| 3 | `C_promo ≤ 0` | **NULL** | `PROMO_CONTRIBUTION_NON_POSITIVE` | `max_admissible_price` = цена безубыточности; **процент не печатается** |
| 4 | `0 < C_promo < 0,01 × P_promo` | значение + флаг | `PROMO_CONTRIBUTION_NEGLIGIBLE` | результат неустойчив: ±1 ₽ издержек меняет его в разы |
| 5 | `C_base ≤ 0`, `C_promo > 0` | **NULL** | `BASELINE_NON_POSITIVE_PROMO_IMPROVES` | абсолютный прирост вклада, ₽ |
| 6 | `C_base ≤ 0`, `C_promo ≤ 0` | **NULL** | `BOTH_NON_POSITIVE` | — |
| 7 | нет обязательного входа | **NULL** | `ECONOMICS_UNAVAILABLE` | `blocked_reason` |
| 8 | `U_base` NULL или 0 | процент печатается | `NO_BASELINE_SALES` | `required_units_per_day` = NULL |
| 9 | `required_units_per_day > available_units / promo_days_remaining` | значение | `UPLIFT_NOT_SERVICEABLE_BY_STOCK` | дата исчерпания |
| 10 | базисы цен различаются | **NULL** | `PRICE_BASIS_MISMATCH` | — |

Правило №3 закрывает требование «никогда не выдавать огромный положительный процент при
нулевом или отрицательном вкладе в акции»: при `C_promo ≤ 0` процент не печатается вовсе.

Правило №4 прямо адресует наблюдённый случай: `930334396` при автоцене 1130 ₽ даёт
`C_promo = 9 ₽` (0,8 % цены) и формально «+1592 %». Число верное, но неустойчивое, и должно
подаваться как «вклад практически обнулён», а не как точная оценка.

### 12.3 Инварианты, проверяемые `ASSERT` в PR-PROMO-3

| # | Инвариант | Зачем |
|---|---|---|
| I-1 | обе стороны используют **цену продавца** | На Ozon `action_price` — цена продавца; на WB цена покупателя вообще не наблюдаема. Смешение базисов исказит и вклад, и рост |
| I-2 | `fixed_rub` (логистика, last mile) **не зависит** от цены | Формула верна только при фиксированной логистике. Проверяется тождеством: `C(P) − C(P′) = (P − P′)·(1 − take)` |
| I-3 | `take_frac` одинаков в обоих сценариях | Комиссия могла бы измениться при смене схемы продажи — тогда сравнение недействительно |
| I-4 | `C(break_even) = 0 ± 0,01 ₽` | замыкает формулу на опубликованную точку безубыточности |
| I-5 | `C(P_now)` совпадает с колонкой вью до копейки | доказывает отсутствие второй формулы |
| I-6 | при `uplift_status ∈ {PROMO_CONTRIBUTION_NON_POSITIVE, BASELINE_NON_POSITIVE_*, BOTH_NON_POSITIVE, ECONOMICS_UNAVAILABLE, PRICE_BASIS_MISMATCH}` поле процента **строго NULL** | защита от вводящих в заблуждение чисел |

## 13. ПРИВАТНОСТЬ: «ХОЧУ СКИДКУ» НЕ ЗАГРУЖАЕТСЯ

**Решение владельца принято и зафиксировано.**

```
Источник: POST /v1/actions/discounts-task/list (Ozon Seller API)
Статус:   DEFERRED_PRIVACY_SENSITIVE_SOURCE
Версия:   Promotion Engine V1 — НЕ загружается
```

Основание: метод возвращает персональные данные покупателей —
`customer_name`, `first_name`, `last_name`, `patronymic`, `email`, `user_comment`
(`CONFIRMED_API`, наблюдено в схеме ответа сегодня). Для текущей задачи — решения о входе
в акции маркетплейса — эти поля не нужны.

Что это означает практически:

1. В PR-PROMO-1 вызов этого пути **отсутствует физически**. Он входит в deny-list, который
   проверяется тестом по исходному тексту загрузчика.
2. Таблица `RAW_OZON_PROMO_DISCOUNT_TASK` **не проектируется и не создаётся**.
3. Ни имя, ни фамилия, ни отчество, ни e-mail, ни свободный комментарий покупателя
   **не попадают** в аналитическую модель акций ни в каком виде — ни в строке, ни в
   хеше, ни в сыром payload.
4. Если в будущем анализ покажет предсказательную ценность источника, проектируется
   **отдельная** приватная загрузка: поля личности отбрасываются **в загрузчике до
   формирования строки**, а не маскируются вью и не «удаляются потом». Сохраняемый
   периметр — только `sku`, `offer_id`, `status`, `requested_price`, `approved_price`,
   `approved_discount_percent`, `min_auto_price`, `base_price`, `approved_quantity_min/max`,
   `edited_till`, `end_at`, `is_auto_moderated`, `created_at`, `moderated_at`.
   Это отдельный PR с отдельным решением владельца.

| B-2 | **`overstock_relaxes_floor`: да или нет.** Семь из девяти сегодняшних отказов по полу — один кластер под давлением запасов (кремы для рук/тела и наборы с ними). Если ослабление запрещено, движок будет постоянно говорить `FAIL_EXPECTED` по товарам, которые владелец сознательно держит ниже пола ради оборачиваемости | — | до PR-PROMO-5 |
| B-3 | **Наполнение `REF_PROMO_POLICY`** (`owner_approved_by`, `effective_from`) | — | до PR-PROMO-5 |
| B-4 | **Девять SKU ниже пола 20 % сегодня.** Это ценовое решение, а не решение об акциях, и оно вне периметра движка | — | отдельно от этого гейта |

Вопросы, закрытые в этой фазе и **более не являющиеся** блокерами:

| Было | Стало |
|---|---|
| Хранение в поле 20 %: включать или нет | **Не включать.** Совпадает с обеими каноническими вью; изменений в витринах не требуется |
| База случая для пола: EXPECTED или WORST | **EXPECTED** для допуска; WORST — отдельная ось защиты от падения |
| Загружать ли «Хочу скидку» | **Нет.** `DEFERRED_PRIVACY_SENSITIVE_SOURCE` |

| Может ли `INSUFFICIENT_DATA` скрыть отказ экономики | **Нет.** Четыре независимые оси, §10 |

Дополнительно подтверждено в этой фазе, сверх списка:

- `PROMOTION_WRITE_ALLOWED = FALSE` соблюдено: ни одной мутации, ни одного `terraform apply`,

- токен WB `WB_PRICES_READ_TOKEN` имеет бит 30 (read-only), срок до 2027-03-08 — запись на

- `wb_mart.V_CT_INVENTORY_TRUTH` **не содержит строк для SKU-наборов** (`EVT-SET-*`):

- задержка распространения цены в конвейер заказов WB — до ~1 часа (§7.3): требование

`UNKNOWN` из §7.4 без единого действия на площадке.
