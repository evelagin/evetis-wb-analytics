# CONTROL TOWER DASHBOARD — спецификация v1 (Metabase)

Назначение: не «показать данные», а каждый день выдавать владельцу список действий с количествами. Шесть страниц, три цвета алертов, четыре фазы внедрения. Всё ниже — спецификация и предложенный SQL-слой; **ничего не деплоится** без отдельного разрешения (READ-ONLY-режим проекта). Семантика денег — правила проекта: WB по `V_WB_FINANCE_CANONICAL` / `V_ADS_SKU_ECONOMIC_LIMITS` (с обходом маппинга через `REF_SKU_CHANNEL_MAP` по `wb_nm_id`), Ozon — полная цена = выручка + баллы + программы партнёров, реклама Ozon — отчёт кабинета, а не только атрибуция по SKU. Заменяет `DASHBOARD_SPEC.md` v1 (8 страниц) — там страницы описывали данные, здесь — решения.

## Принципы

1. Одна строка = одно действие с количеством (ship 214, pull 281, stop ads, raise 1 367), а не метрика.
2. Наборы считаются в двух единицах: карточки (спрос) и флаконы (запас); BOM разворачивается всегда.
3. План = `SEASON_EXECUTION_TARGET` (seed из `SET_DETAIL.csv`, `SET_MONTHLY_PLAN.csv`); факт = заказы без отмен (WB `FACT_ORDERS`, Ozon постинги без cancelled); деньги — выкупы и выплаты.
4. Цвет — из правил (раздел «Алерты»), а не из ручной раскраски.
5. Владелец видит только страницы 1 и 6 ежедневно; 2–5 — по дням недели (раздел «Ритм»).

## PAGE 1 — OWNER HOME

Вопрос: *что делать сегодня и что ждёт моего решения?*

Блоки сверху вниз: (1) статус дня — пять светофоров: продажи vs план MTD, наличие (SKU в нуле на WB/Ozon), реклама (ДРР дня и объекты выше потолка), крем для рук (фл./день против программы), деньги (seller cash MTD против плана); (2) **ACTION QUEUE** — до 10 строк из `OWNER_ACTION_QUEUE` с приоритетом, дедлайном, количеством и кнопкой «сделано» (статус хранится в seed-таблице, обновляется владельцем); (3) **DECISIONS PENDING** — строки со статусом «НУЖНО РЕШЕНИЕ ВЛАДЕЛЬЦА» и ценой ошибки; (4) plan-vs-actual MTD: карточки, флаконы, GMV, реклама, ДРР, вклад — план / факт / % / прогноз на конец месяца; (5) следующие 7 дней: отгрузки WB (лоты), Ozon (поставки), сборка наборов, перекладка с паллет.

Источники: `V_CT_OWNER_ACTION_QUEUE` (seed + правила), `V_CT_PLAN_VS_ACTUAL_DAILY`, `V_CT_ALERTS_CURRENT`.

## PAGE 2 — INVENTORY COMMAND CENTER

Вопрос: *где товар, сколько дней он проживёт и что с каждым SKU делать?*

Таблица `SKU_CONTROL` по базовым SKU: роль (HERO / CASH GENERATOR / BUNDLE DRIVER / BUNDLE RELEASE / SLOW STOCK / LIQUIDATION / REPLENISH), приоритет P0–P3 и score 0–100, остаток по точкам (полка ФФ / паллеты / WB живой / Ozon / в пути / FBS), срок годности и месяцы до него, дни запаса на площадке и всего, темп 30 дн против цели SET на месяц, маржа до рекламы WB/Ozon, ДРР 28 дн, реализованная цена, остаток на март по плану, алерты и действие с количеством (ship WB / ship Ozon / pull). Переключатель «наборы как позиции» показывает `PHYSICAL_SETS`. Второй блок — **EXPIRY CONTROL**: партия, срок, флаконов, требуемый темп/мес до срока, текущий темп, план SET, gap-фактор, остаток к марту, приоритет; красным — крем для рук (31.12.2026) и партии 5–6 (окт–ноя 2027). Третий блок — **LOST_CLAIMED** отдельно (3 973 фл., 0,65 млн, претензия к РВБ) — никогда не смешивается с продаваемым.

Формула score (0–100): срок годности ≤ 4 мес +40 / ≤ 9 мес +20 / ≤ 14 мес +10; покрытие > 365 дн +20 / > 180 +10; вклад после рекламы < 0 +15; ДРР выше потолка +10; SKU в нуле на площадке при запасе на ФФ +10; лимитирующий компонент наборов −10 (защищаем, а не ускоряем). P0 ≥ 60, P1 35–59, P2 25–34, P3 < 25.

Источники: `V_WB_STOCKS_T5_CURRENT` (живой агрегат), `RAW_OZON_STOCKS` (последний снимок), `RAW_OZON_SUPPLY_*` (в пути), seed `CT_FF_STOCK` (полка/паллеты — до появления `usend_raw`), `REF_COST_BATCH` + правило expiry, `V_ADS_SKU_ECONOMIC_LIMITS`.

## PAGE 3 — SALES PLAN

Вопрос: *идём ли по плану сезона и где отстаём?*

Верх — сезон целиком: план SET по месяцам (карточки / флаконы / GMV / реклама / деньги / вклад / OPEX / операционный результат / остаток) против факта нарастающим; линия «исторический сезон 2024/25 и 2025/26» для сравнения формы. Середина — месяц по SKU × канал: план / факт / % / прогноз EOM (факт MTD × дни месяца / прошедшие дни с поправкой на день недели); цвет по правилу plan-vs-actual. Низ — **BUNDLE-FIRST**: соло / 2-предметные / 3-предметные / 4-предметные единицы, доля наборов (план 32–38 %), топ-наборы по вкладу. Фильтр сценария: SET / BALANCED / MARGIN_PROTECTION / AGGRESSIVE (seed `SCENARIOS_V2`).

Источники: `FACT_ORDERS`, `RAW_OZON_POSTINGS_FBO`, `V_WB_FINANCE_CANONICAL`, seed `CT_SEASON_PLAN` (из `SET_DETAIL.csv`), `HISTORICAL_SEASONS`.

## PAGE 4 — BUNDLE FACTORY

Вопрос: *сколько и каких наборов собрать на этой неделе и что их ограничивает?*

Таблица по наборам: BOM, продажи 14 дн WB/Ozon, остаток набора на площадках, целевой сбор на две недели (2-недельный спрос × 1,2), лимитирующий компонент и его остаток на полке ФФ, статус (собрать / достаточно / стоп — компонент в дефиците), экономика набора против компонентов поштучно. План `BUNDLE_PRODUCTION_PLAN` на 8 недель, факт сборки — seed от Usend (пока вручную). Алерт: лимитирующий компонент < 60 дней → REPLENISH (сейчас крем для лица АКНЕ).

## PAGE 5 — MARKETPLACE CONTROL

Вопрос: *что сделать в кабинетах WB и Ozon сегодня?*

Три вкладки. **Реклама** — по объекту (SKU × канал): класс (ADVERTISED / ORGANIC_HALO / BUNDLE_SUPPORTED / LIQUIDATION_ADS), ДРР 7/28 дн, потолок, рабочая цель, статус (SCALE / KEEP / REDUCE / ORGANIC ONLY / LIQUIDATION ADS / STOP), бюджет месяца по плану; сверху — «объекты выше потолка» и «ADVERTISED-объекты с ДРР < 5 %» (недокрутка). **Цены** — прайс, реализованная 7/28 дн, отношение (алерт < 90 %), рекомендуемая полка, промо-диапазон, пол, действие (HOLD / RAISE / LOWER / PROMO ONLY / LIQUIDATION / TEST), текущие акции (`RAW_WB_PROMOTIONS`/Ozon actions если появятся). **Поставки** — WB: лоты по 25 кг, статус приёмки, дни запаса после приёмки, черновики без склада; Ozon: поставки по кластерам, `ACTUAL_RECEIPT_TIME`, дни наличия по кластеру (когда накопятся снимки).

Источники: `V_ADS_SKU_ECONOMIC_LIMITS`, `MART_SKU_DAILY`, `RAW_OZON_ADS_SKU_DAILY` + отчёт кабинета (seed), `RAW_OZON_PRICES`, `V_WB_PRICES_*`, `RAW_WB_SUPPLIES`, `RAW_OZON_SUPPLY_ORDERS`.

## PAGE 6 — MONEY / CASH CONVERSION

Вопрос: *сколько денег реально пришло и сколько запаса превратилось в деньги?*

Плитки: GMV / расходы площадок / реклама / **деньги продавца** / COGS проданного / **вклад (до OPEX)** / OPEX / **операционный результат** — за неделю, MTD, сезон (план SET рядом). Никогда не подписывать вклад как «чистая прибыль». Водопад запаса: открытие 34 514 фл. (5,75 млн) + партия 8 + дозаказ − продано = остаток; конверсия запаса в деньги % (план сезона 49,6 %). Крем для рук отдельной строкой: деньги / вклад / остаток / «стоимость ликвидации против списания». Выплаты WB (недельные) и Ozon — фактические поступления против модели денег продавца (расхождение > 10 % → алерт «проверить удержания»).

Источники: `V_WB_FINANCE_CANONICAL`, `V_WB_DEDUCTIONS_CLASSIFIED`, Ozon финансовые отчёты (пока seed), `V_PRODUCT_COGS_EFFECTIVE`, seed `CT_OPEX` (77 000 / 65 000).

## Алерты (правила, цвет считается автоматически)

| Правило | RED | YELLOW | GREEN |
|---|---|---|---|
| Продажи vs план MTD (карточки) | < 70 % | 70–90 % | ≥ 90 % |
| SKU в нуле на WB при запасе на ФФ | ≥ 3 SKU | 1–2 | 0 |
| Дни запаса на площадке при спросе > 1/день | < 10 | 10–20 | > 20 |
| Дни запаса всего | > 365 (SLOW) | 180–365 | 30–180 (< 30 → BLUE replenish) |
| Срок годности | < 4 мес, или требуемый темп > 2× текущего | 4–9 мес | > 9 мес |
| ДРР объекта vs потолок класса | выше потолка 7 дн подряд | выше 3 дня | в цели |
| ДРР ADVERTISED-объекта | — | < 5 % при наличии (недокрутка) | 8–12 % |
| Реализованная цена / прайс | < 85 % | 85–92 % | ≥ 92 % |
| Вклад после рекламы SKU (7 дн) | < 0 | 0–5 % | > 5 % |
| Крем для рук фл./день vs программа | < 60 % программы | 60–90 % | ≥ 90 % |
| Лимитирующий компонент наборов | < 30 дн | 30–60 дн | > 60 |
| Приёмка WB | нет принятых поставок 5 рабочих дней | лоты в пути > 7 дн | принято |
| Партия 8 | не отпущена к 15.09 | в пути дольше 45 дн | принята на ФФ |
| Расхождение выплат площадки vs модель денег | > 10 % | 5–10 % | < 5 % |

## Правила решений владельца (что делать, когда загорелось)

| Сигнал | Правило |
|---|---|
| SKU в нуле на площадке, на ФФ ≥ 100 фл. | отгрузить 45-дневную цель немедленно (лот ≤ 25 кг); если приёмки нет — FBS |
| ДРР объекта > потолка класса 7 дней | REDUCE ставку на 30 %; повторно через 7 дней → STOP; ADVERTISED-объект не выключать полностью, пока маржа до рекламы > 20 % |
| ADVERTISED-объект с ДРР < 5 % при наличии | SCALE на +30 % бюджета до цели 8–12 % |
| Реализованная цена < 90 % прайса 3 дня подряд | выйти из автоакции; если не выходит — поднять прайс так, чтобы реализованная = целевая полка |
| Крем для рук < 60 % темпа программы две недели подряд | перейти на следующую программу (HC-B → HC-A): цена −50 ₽, ДРР +3 п.п. |
| Лимитирующий компонент < 60 дней | дозаказ / остановить масштабирование наборов с этим компонентом |
| Срок годности < 4 мес, темп < требуемого | программа ликвидации: цена по полу, наборы, внешний канал; списание считать явно |
| Продажи < 70 % плана при полном наличии 2 недели | пересмотреть месяц (не сезон): −20 % к цели месяца, реклама по классам без изменений |
| Продажи > 120 % плана 2 недели | поднять цель FBO до 60 дней, ускорить сборку наборов, проверить вклад после рекламы |
| Расхождение выплат > 10 % | сверка удержаний (`V_WB_DEDUCTIONS_CLASSIFIED`) до любых решений по ставкам |

## Модель обновления

| Частота | Что | Источник / механика |
|---|---|---|
| Интрадей (каждые 2–4 ч) | заказы WB/Ozon, остатки WB/Ozon, статусы поставок | `RAW_WB_ORDERS` → `FACT_ORDERS`, `RAW_OZON_POSTINGS_FBO`, `V_WB_STOCKS_T5_CURRENT`, `RAW_OZON_STOCKS` (уже по расписанию загрузчиков) |
| Ежедневно (утро) | реклама (billing WB, отчёт Ozon), реализованные цены, алерты, `DAILY_OWNER_BRIEF` | `V_WB_DEDUCTIONS_CLASSIFIED`, `V_ADS_SKU_ECONOMIC_LIMITS` 7 дн, `RAW_OZON_ADS_SKU_DAILY` + seed отчёта, правила алертов |
| Еженедельно (понедельник) | остатки ФФ (срез Usend → seed `CT_FF_STOCK`), план сборки, план лотов, `PLAN_VS_ACTUAL` недели, выплаты WB | ручной срез ФФ до `usend_raw`; пересчёт `ct2.py` |
| Ежемесячно (1-е число) | перерасчёт сценариев (`ct.py`), сезонные множители по факту, OPEX, программы крема для рук и партии 5, `EXPIRY_CONTROL` | `ct.py` + `ct2.py`; обновление seed-таблиц плана |

## План внедрения в Metabase (фазы)

| Фаза | Срок | Что появляется | Что нужно |

| **2 — Inventory & Alerts** | неделя 3–4 | `V_CT_INVENTORY_TRUTH_DAILY` (WB живой + Ozon + в пути + ФФ seed, наборы разложены по `REF_BUNDLE_COMPONENTS`), `V_CT_SKU_CONTROL` (score, роль, алерты по правилам), `V_CT_EXPIRY_CONTROL`, `V_CT_ALERTS_CURRENT`; страница 2 | снимки Ozon ≥ 30 дней для дней наличия по кластерам |

| **4 — Money & Automation** | неделя 7–8 | `V_CT_CASH_CONVERSION` (деньги / вклад / OPEX / операционный результат / водопад запаса / выплаты vs модель), `V_CT_DAILY_BRIEF` (текст сводки из правил), почтовая рассылка Metabase в 08:00; страница 6 | финансовые отчёты Ozon в BQ (`ozon_raw.RAW_OZON_FINANCE_*` — предложение), `usend_raw` (API Usend) |

Все `V_CT_*` — предложение имён; grain: `V_CT_PLAN_VS_ACTUAL_DAILY` — день × SKU × канал; `V_CT_INVENTORY_TRUTH_DAILY` — день × базовый SKU × точка хранения; `V_CT_SKU_CONTROL` — базовый SKU (текущее); `V_CT_ADS_ACTIONS` / `V_CT_PRICE_ACTIONS` — SKU × канал (текущее, окна 7/28); `V_CT_CASH_CONVERSION` — месяц × сценарий. Ничего из этого не создаётся в production без отдельного разрешения.

## Ритм владельца

Понедельник: страницы 2 и 4 — перекладка, лоты, сборка (20 мин). Ежедневно: страница 1 + `DAILY_OWNER_BRIEF` (10 мин). Среда: страница 5 (реклама) и 3 (план-факт) (20 мин). Пятница: страница 5 (цены) и 6 (деньги, выплаты) (20 мин). Выходные: только RED-алерты из рассылки. Первое число месяца: пересчёт сценариев и решения (60 мин).
