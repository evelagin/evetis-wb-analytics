# UNITKA ENGINE v1 — Stage E3: post-write аудит первого controlled PROD write (11.09.2026)

Прогон: `prod:unitka:2026-09-12T13:863c728c…:unitka-engine-prod-5npcz`, 10:12:56–10:13:26 UTC,
`mode=WRITE`, `cells_planned = cells_written = 1477`, `qa_status = PASS`, LCD 10.09 → 11.09.
Книга после записи выгружена в xlsx (Drive API, 10:30 UTC) — значения, формулы и **статические
форматы** всех 24 блоков; сверено с живыми вью BigQuery того же момента. В книгу ничего не
записывалось; prod-Job не запускался; Scheduler'ы Engine на паузе.

## 1. Root cause — три разных причины

### COMMISSION и LOGISTICS — статическая «граница будущего», которую никто не двигал

Бледный вид ставок на 10–11.09 — не условное форматирование и не «старые значения». Это
**статический цвет шрифта `#b7b7b7`** на колонках `logistics` и `commission` в строках **746–766**
(даты ≥ 10.09) во всех 24 блоках — ни одно правило УФ на эти колонки не ссылается (проверены
все 4 671 правило листа). Граница «746» — это первый день после `LAST_CLOSED_DATE = 09.09` на
момент вёрстки Master (Stage 8, 11.09): закрытые дни 737–745 получили чёрный шрифт, будущие —
серый, статически. Ни `s82lcd` (Apps Script, 10.09), ни Engine при `LCD_ADVANCE` (11.09) эту
границу не переносили: **у Engine v1.0 вообще не было понятия формата** — он писал только
значения. Значения при этом верны (§2).

Та же статическая граница у колонки `storage`: строки 746–766 без заливки (`#f1f8f4` только в
737–745). Плюс наблюдение: две ячейки, в которые Engine записал пустую строку (`AG746`, `AG747`),
в выгрузке имеют числовой формат `General` — контракт формата это тоже закрывает, когда в них
появится значение.

### STORAGE — upstream: платное хранение никто не грузит после 09.09

`wb_raw.RAW_WB_PAID_STORAGE`: **одна** сессия загрузки — 10.09 20:19 UTC, 3 352 строки за
01–09.09. Загрузчик — `apps-script/UnitkaR3Ingest.gs::r3StorageToBq()` с **жёстко прошитым окном**
`R3_FROM = '2026-09-01', R3_TO = '2026-09-09'`, без триггера, без записи в `LOADER_RUNS`; в
Terraform нет Job'а хранения; в `LOADER_RUNS` нет loader'а `storage`. То есть production
storage pipeline **не существует** — был разовый ручной backfill R3. Ожидание D-1 для хранения
никем не обеспечивается. Engine повёл себя правильно: 10–11.09 = GAP (пусто, не ноль), источник
честно показан как `storage = 09.09` в `source_freshness_json`; при появлении данных окно
«весь месяц ≤ LCD» подхватит их автоматически (`LATE_SOURCE_CORRECTION`, тест
«хранение 10.09 появилось в источнике»). Протягивать 09.09 на 10–11.09 нельзя и не делается.

## 3. Канонический контракт формата закрытого дня (код: `model.ts`, `plan.ts::formatContract`)

Для каждой колонки, которую пишет Engine (9 факт + `logistics` + `commission`), **статический
формат ячейки закрытого дня (дата ≤ LCD) = формат эталонной строки 737 того же блока и той же
колонки** — первый день месяца всегда закрыт и свёрстан. Сравниваются и восстанавливаются три
свойства `userEnteredFormat`: заливка, цвет шрифта, числовой формат. УФ не трогается.

Исключения по построению: будущие дни (> LCD) не рассматриваются — сохраняют «будущий» вид до
закрытия; **GAP-ячейки** (факт, которого нет в источнике, `want = null`) вне контракта — у Master
своя разметка пропусков (оранжевый фон остатков 03.09 остаётся), формат следует за значением и
ставится в том же прогоне, когда источник даёт факт.

Механика: `spreadsheets.get(includeGridData)` читает форматы строк 737–766 вместе со снимком;
план получает `formatCells` (`FORMAT_CHANGE`); в PROD после `values.batchUpdate` идёт один
`spreadsheets.batchUpdate` из `repeatCell` (смежные строки одной колонки — один запрос);
reconciliation получает проверку **`CLOSED_FORMAT_CONTRACT`** (закрытые ячейки со значением
≠ эталону → FAIL, код `FORMAT_CONTRACT`). В SHADOW — informational, как mismatch. Повтор при
совпадении — 0 запросов. `engine_version = unitka-engine/1.1.0`.

## 6. Upstream: нужен ли `wb-storage`

**Да, требуется — и это не Engine.** Пока платное хранение грузится только ручным R3-скриптом с
прошитым окном 01–09.09, все дни после 09.09 навсегда GAP. Предлагаемый Stage E3-storage:
загрузчик `storage` на общем образе Cloud Run (как `funnel`): контракт WB
`GET /api/v1/paid_storage?dateFrom&dateTo` → task → download (проверен R3), токен
`WB_TOKEN_ANALYTICS` (уже у `sa-loaders-prod`), окно D-8…D-1 МСК с перекрытием (WB досчитывает),
идемпотентная замена окна в `RAW_WB_PAID_STORAGE`, `LOADER_RUNS`, Scheduler ~08:30 МСК (до
Engine 10:00). Свежесть уже отслеживается (`V_UNITKA_SOURCE_FRESHNESS.storage`), Engine
подхватит данные без изменений. До появления загрузчика допустим разовый ручной R3 с окном
10–11.09 — только как backfill, не как production-механика.
